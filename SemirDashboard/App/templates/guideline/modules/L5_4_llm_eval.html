Level 5 · LLM Systems · ~30 phút

  • Build eval set cho V20 investor thesis skill
💡 LLM Eval bằng ngôn ngữ đời thường

Đánh giá đầu bếp:

  1. Reference-based: Yêu cầu nấu 1 món chuẩn (trứng ốp la) → so sánh với ảnh mẫu. Đúng recipe = pass. Dùng khi có "đúng/sai" rõ ràng (dịch, tóm tắt).
  2. Pairwise (A/B): 2 đầu bếp nấu cùng món → khách chọn ngon hơn. Dễ hơn chấm điểm tuyệt đối.
  3. Human rating: Khách chấm 1-5 sao. Chuẩn vàng nhưng đắt, chậm, dễ bias.
  4. LLM-as-judge: Đầu bếp khác (Claude/GPT-4) chấm điểm. Rẻ, scale được, nhưng có bias (thích câu dài, position bias).

Bench (MMLU, HumanEval) = kỳ thi tiêu chuẩn hoá — so sánh model. Nhưng không thay thế eval trên use case cụ thể của bạn.

2. Auto-metrics

n-gram là gì? (nền tảng của BLEU/ROUGE)

n-gram = cụm N từ liên tiếp trong câu. Câu "VN-Index tăng mạnh hôm nay" có các 2-gram (bigram): "VN-Index tăng", "tăng mạnh", "mạnh hôm", "hôm nay". BLEU/ROUGE hoạt động bằng cách đếm bao nhiêu n-gram của câu model sinh ra TRÙNG với câu reference (đáp án mẫu) — không hiểu nghĩa, chỉ đếm trùng chữ.

Ví dụ tính BLEU thô (n=2): Reference: "Cổ phiếu tăng mạnh hôm nay". Model output: "Cổ phiếu tăng rất mạnh hôm nay". Bigram của reference: {Cổ-phiếu, phiếu-tăng, tăng-mạnh, mạnh-hôm, hôm-nay} = 5 bigram. Bigram của output trùng với reference: {Cổ-phiếu, phiếu-tăng, mạnh-hôm, hôm-nay} = 4/6 bigram của output khớp → precision ~0.67. Model chỉ chêm thêm 1 từ "rất" nhưng đã làm giảm điểm — đây chính là lý do BLEU "phạt oan" câu diễn đạt khác nhưng đúng nghĩa.

  • BLEU: đo precision n-gram (bao nhiêu % n-gram của output có xuất hiện trong reference). Translation, summarization. Weak for creative gen — 2 câu đúng nghĩa nhưng khác chữ vẫn bị điểm thấp.
  • ROUGE: đo recall n-gram (bao nhiêu % n-gram của reference có xuất hiện trong output) — ngược hướng với BLEU. Summarization. Same weakness as BLEU.
  • Perplexity: exp(loss) — loss ở đây là cross-entropy loss, đo model "bất ngờ" bao nhiêu khi thấy token thực tế tiếp theo (loss cao = model không đoán được, loss thấp = model đoán đúng hướng). Perplexity là loss được "đổi thang" dễ đọc hơn: perplexity=1 nghĩa là model đoán đúng 100% chắc chắn, perplexity=100 nghĩa là model bối rối như đang đoán ngẫu nhiên giữa 100 lựa chọn. Language modeling. Lower = model tin token thực tế hơn.
  • Exact match / F1: for closed QA (SQuAD).

3. LLM-as-judge (Zheng 2023, MT-Bench)

Prompt to judge (Claude/GPT-4):

Rate response quality 1-10 based on:
- Correctness (facts accurate)
- Helpfulness (addresses user request)
- Clarity (well-structured)

User: {original_prompt}
Response: {model_output}
Reference (optional): {ground_truth}

Explain reasoning briefly, then rate.

Pitfalls

Biases
  • Verbosity bias: judge prefer longer answers → gaming.
  • Position bias: A/B compare, prefer first / second position → randomize order.
  • Self-enhancement bias: judge model prefer own family (Claude judge prefers Claude output).
  • Formatting bias: markdown better than plain text.

Fix: multi-judge (average), randomize positions, control prompt format.

Elo ranking là gì? Hệ thống chấm điểm bắt nguồn từ cờ vua: mỗi model có 1 điểm số; sau mỗi trận đấu (human chọn A hay B thắng), model thắng LẤY điểm từ model thua — thắng model điểm cao được cộng nhiều hơn thắng model điểm thấp (giống thắng kèo dưới không đáng bao nhiêu). Điểm hội tụ dần về đúng "sức mạnh tương đối" sau hàng chục nghìn trận — đây là lý do Chatbot Arena cần traffic sống liên tục thay vì chấm 1 lần rồi thôi.

Benchmark limitations

Contamination

Test set may leak vào pretrain data (crawl public benchmarks). Model có thể "memorize" not "reason". → New benchmark saturate quickly. Solution: private eval set, held-out data post model release.

Saturation

MMLU 88%+ tất cả top models — không distinguish. Cần harder benchmark (GPQA, Frontier Math).

=== Perplexity ===
Đo trên test corpus → không capture "hữu ích", "friendly"

=== LLM-as-judge (Claude judge GPT vs Gemini) ===
Prompt: "Which response is more helpful?"
Response A: 85% wins → A better
Nhưng có position bias — swap A/B thì kết quả có thể đổi.
Fix: random order + kappa >0.6 with human sample.
  (kappa = Cohen's κ, thước đo mức đồng thuận giữa 2 người/hệ thống chấm —
   0 nghĩa là đồng thuận không hơn gì may rủi, 1 là đồng thuận tuyệt đối;
   thang điểm đầy đủ giải thích ở §4.8 bên dưới)

=== Human eval (100 pairs, 3 raters) ===
Kappa 0.72 → reliable.
A wins 65% → A better. Confidence interval ±9% (SE=√(0.65×0.35/100)≈0.048, 95% margin=1.96×0.048≈9.4pp — rộng hơn case n=200 ở trên vì mẫu nhỏ hơn, đúng chiều thống kê).
Cost: $500-1000 nhưng đáng tin cậy.

4.7 — Rubric-based eval: định nghĩa rõ mới đo được

Từ "response có tốt không" → rubric checklist
# Rubric cho investor thesis (V20 style)
{
  "criteria": [
    {"name": "price_accuracy",
     "check": "All numbers within ±2% of current_price",
     "weight": 0.30, "score": [0, 1]},
    {"name": "rule_compliance_R2",
     "check": "entry ≤ current × 1.05 AND stop < entry < target",
     "weight": 0.20, "score": [0, 1]},
    {"name": "reasoning_quality",
     "check": "Multi-timeframe context + catalyst + risk section",
     "weight": 0.25, "score": [1, 2, 3]},
    {"name": "actionability",
     "check": "Clear entry/stop/target, no vague 'monitor'",
     "weight": 0.15, "score": [1, 2, 3]},
    {"name": "format_compliance",
     "check": "JSON schema valid + word count ≤ 200",
     "weight": 0.10, "score": [0, 1]},
  ]
}

Vì sao rubric > free-form judge? Free-form judge trả 1-10 → 2 judges khác nhau 3 điểm. Rubric buộc judge answer từng câu binary/small-scale → κ jumps từ 0.4 → 0.75.

4.8 — Offline vs Online eval + Statistical Significance

Đừng ship khi p-value chưa đủ

Offline: eval set cố định, LLM-as-judge / rubric. Fast iteration nhưng không capture user behavior thật.

Online: A/B test production, đo real metrics (satisfaction, retry rate, conversion). Slow nhưng ground truth.

Wilson CI là gì? Wilson score interval — 1 công thức tính khoảng tin cậy (confidence interval) cho tỷ lệ %, chính xác hơn công thức thông thường (normal approximation) khi mẫu nhỏ hoặc tỷ lệ gần 0%/100% — dùng thay vì công thức CI đơn giản chính vì lý do đó.

# Win rate + Wilson CI cho A/B pairwise
n = 200 comparisons; A wins 118, B wins 82; ties 0
p_A = 118/200 = 0.59
95% Wilson CI = [0.52, 0.66]   → LOWER bound > 0.5 → A significantly better

Sample size cần cho win rate 55% vs 50% (power 0.8):
  n ≈ (1.96+0.84)² × 2×0.25 / 0.05²

  # Giải thích từng phần:
  # 1.96 = z-score ứng với 95% confidence (mức tin cậy chuẩn ngành)
  # 0.84 = z-score ứng với 80% power (xác suất phát hiện được khác biệt thật nếu nó tồn tại)
  # 2×0.25 = 2 × p×(1-p) với p=0.5 (trường hợp "khó phân biệt nhất", variance
  #          lớn nhất của tỷ lệ nhị phân — dùng làm ước lượng AN TOÀN, chưa
  #          biết win rate thật nên giả định xấu nhất)
  # 0.05² = bình phương của "khác biệt nhỏ nhất muốn phát hiện" (55%-50%=5%=0.05,
  #          gọi là MDE — Minimum Detectable Effect). Muốn phát hiện khác biệt
  #          CÀNG NHỎ → mẫu số càng nhỏ → n càng LỚN (khó phát hiện hơn cần nhiều data hơn)
  # Càng muốn chắc chắn (confidence cao) + càng muốn chắc phát hiện được (power cao)
  #   + càng muốn phát hiện khác biệt nhỏ (MDE nhỏ) → n càng lớn

  n ≈ (1.96+0.84)² × 2×0.25 / 0.05² = 1568 comparisons

Bootstrap CI (khi score continuous):
  Resample 1000× → 95% CI of mean difference
  Reject null nếu 0 ∉ CI

Multiple comparison correction:
  Test 10 rubric criteria → Bonferroni α=0.05/10=0.005
  Không correct → false positive rate 40%

Kappa (Cohen's κ) interpretation: <0.2 poor · 0.2-0.4 fair · 0.4-0.6 moderate · 0.6-0.8 substantial · >0.8 near-perfect. Sub-0.6 = eval unreliable, đừng deploy based on it.

4.9 — Calibration: model có BIẾT khi nào nó có thể sai không?

💡 Analogy

Mọi phương pháp eval ở mục 1-4 đo "model trả lời ĐÚNG hay SAI bao nhiêu %" — nhưng có 1 câu hỏi KHÁC hoàn toàn: khi model NÓI "tôi chắc 95%", nó có thực sự đúng ~95% số lần không? Giống 1 học sinh làm bài thi: điểm số (accuracy) đo học sinh giỏi cỡ nào, nhưng CALIBRATION đo học sinh có "tự biết mình" không — 1 học sinh nói "chắc chắn 100%" cho MỌI câu trả lời (kể cả câu sai) là học sinh KHÔNG được calibrate, dù điểm thi có thể vẫn cao.

Vấn đề cụ thể: rất nhiều ứng dụng thực tế (investor thesis, medical advice, code generation) cần model biết "câu này tôi không chắc, nên double-check" — không chỉ cần accuracy cao mà cần confidence score PHẢN ÁNH ĐÚNG xác suất đúng thật. Nghiên cứu gần đây (Xiong et al. 2023 và nhiều paper 2024-2026 tiếp theo) phát hiện: LLM hệ thống OVERCONFIDENT — khi hỏi model tự đánh giá confidence bằng lời ("verbalized confidence"), con số trả về gần như luôn rơi vào khoảng 80-100% (thường là bội số của 5: 85%, 90%, 95%) BẤT KỂ accuracy thật của câu trả lời đó cao hay thấp.

# Expected Calibration Error (ECE) — đo độ lệch giữa confidence model TỰ NÓI
# và accuracy THẬT ĐO ĐƯỢC, chia theo từng "bin" (khoảng confidence):

ECE = Σ_bin (|bin| / N) × |accuracy(bin) − confidence_trung_bình(bin)|

# Giải thích: chia mọi câu trả lời thành các bin theo confidence model tự báo
# (VD bin 90-100%, bin 80-90%, ...). Với MỖI bin, so sánh:
#   - confidence_trung_bình(bin) = model tự nói trung bình bao nhiêu % trong bin đó
#   - accuracy(bin) = THỰC TẾ đo được bao nhiêu % câu trong bin đó đúng
# Bin càng LỆCH giữa 2 con số này càng góp nhiều vào ECE tổng (weighted theo |bin|/N
# = số câu trong bin đó chia tổng số câu — bin nhiều câu hơn ảnh hưởng ECE nhiều hơn)

Ví dụ số cụ thể: eval 100 câu hỏi investor thesis, model tự báo confidence cho mỗi câu, chia thành 2 bin:

Bin "90-100%" (model tự nói tin 90-100%): 70 câu, confidence trung bình tự báo = 95%
  Đo thực tế: chỉ 60/70 câu ĐÚNG → accuracy(bin) = 60/70 ≈ 85.7%
  |85.7% − 95%| = 9.3 điểm phần trăm lệch — model OVERCONFIDENT ở bin này

Bin "50-70%" (model tự nói tin 50-70%): 30 câu, confidence trung bình tự báo = 60%
  Đo thực tế: 20/30 câu ĐÚNG → accuracy(bin) = 20/30 ≈ 66.7%
  |66.7% − 60%| = 6.7 điểm phần trăm lệch — model hơi UNDERCONFIDENT ở bin này

ECE = (70/100)×9.3 + (30/100)×6.7 = 6.51 + 2.01 = 8.52 điểm phần trăm
→ ECE càng gần 0 càng "biết mình" tốt; ECE=8.52 nghĩa là trung bình, khi model
  tự báo 1 con số confidence, con số THẬT lệch khoảng 8.5 điểm phần trăm

⚠️ Chỗ dễ nhầm nhất: accuracy cao KHÔNG đồng nghĩa calibration tốt — 1 model có thể đúng 90% câu hỏi (accuracy tốt) nhưng LUÔN tự báo "100% chắc chắn" cho mọi câu kể cả 10% câu sai (calibration tệ, ECE cao). Ngược lại, 1 model yếu hơn (đúng 70%) nhưng biết chính xác lúc nào nên nói "tôi không chắc" lại CALIBRATE TỐT HƠN — hữu ích hơn trong production vì downstream system biết khi nào cần double-check/escalate human review.

Insight: đây là lý do "confidence" mà LLM tự in ra trong output (VD field confidence: 0.85 trong JSON structured output) KHÔNG NÊN được tin tưởng mù quáng như 1 xác suất thống kê thật — nó chỉ là 1 con số model "cảm thấy" hợp lý để viết ra (thường thiên về 80-100%, xem nghiên cứu Xiong 2023), không tự động = xác suất đúng thực đo. Muốn dùng confidence cho quyết định thật (VD "chỉ auto-approve nếu confidence > 90%"), phải tự đo ECE trên eval set CỦA CHÍNH BẠN trước, không giả định con số model tự báo đã calibrated sẵn.

📖 Mở rộng — cách cải thiện calibration thực tế: (1) Temperature scaling — hậu xử lý đơn giản, chia logit (điểm số thô model gán cho mỗi lựa chọn/token TRƯỚC KHI qua softmax, chưa phải xác suất) cho 1 hằng số học được trên validation set trước softmax, không cần train lại model; (2) Self-consistency (đã học ở L5_1_prompt.html) — sample N lần, tỷ lệ đồng thuận giữa N lần TỰ NHIÊN là 1 tín hiệu confidence tốt hơn con số model tự nói ra 1 lần; (3) Ensemble nhiều model/judge (đã học ở mục 3 trên) — mức độ đồng thuận giữa nhiều judge độc lập cũng là proxy calibration tốt hơn 1 con số tự báo.

Common failure modes
  1. Eval set overlaps với training data → benchmark cheating.
  2. Judge model = candidate model → self-preference bias.
  3. Không randomize A/B order → position bias overwhelm signal.
  4. Sample <100 → CI quá rộng, "improvement" thực ra noise.
  5. Không có κ với human sample → không biết judge có reliable không.
  6. Đánh giá offline chỉ, không A/B production → optimize sai metric.

✅ QA Gate

1. BLEU vs LLM-as-judge — nào tốt cho creative writing eval?

LLM-as-judge. BLEU chỉ đo n-gram overlap — creative task có nhiều valid answers. Judge có thể grade coherence, style, novelty.

2. Judge bias verbosity — fix?

(1) Explicit prompt "length not quality". (2) Length-normalize scores. (3) Multiple judges + average. (4) Pair with reference answer để anchor.

3. MMLU 88% — model tốt hay benchmark saturate?

Benchmark saturate. Top models tất cả 85-89% → không distinguish real capability. Cần benchmark harder (GPQA, ARC-Challenge, private held-out set).

4. Contamination detect thế nào?

(1) Check n-gram overlap benchmark ↔ pretrain data. (2) Perplexity of benchmark data (nếu extremely low → seen). (3) Behavior test: rephrase question → accuracy drop = memorized. (4) Post-release private eval sets.

5. Build eval cho stock LLM. 3 metric?

(1) Price consistency (all numbers in thesis match current ± tolerance). (2) Rule compliance (no BUY on broken pattern etc). (3) Forward return correlation (BUY thesis → actual return positive over N days, live production only).

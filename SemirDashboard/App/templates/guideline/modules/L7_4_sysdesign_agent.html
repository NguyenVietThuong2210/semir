7.4 · System Design Mock 2 — Multi-Agent Code Assistant

Design AI Orchestrator-like system. 11 agents, LangGraph, HITL, checkpointing. Best cho senior AI engineer roles.

Level 7 · Interview · ~45 phút

Prompt

Interviewer

"Design a multi-agent system that takes user requirement, plans, implements code, tests, deploys, and provides retrospective. Similar to GitHub Copilot Workspace or Devin."

💡 Agent System Design bằng ngôn ngữ đời thường

Client bảo "làm chatbot cho tôi" — chatbot gì?

  • Support khách hàng (RAG trên FAQ, tone thân thiện)?
  • Bán hàng (product recommendation, upsell)?
  • Nội bộ (code review, HR question)?
  • Multi-agent SDLC (như AI Orchestrator — 11 agents cooperate)?

Mỗi loại có architecture khác: số agents, tools cần, level HITL, cost profile. Clarify trước = tránh design 10 agents khi client chỉ cần 1 chatbot đơn giản.

HITL (Human-In-The-Loop) = điểm dừng bắt buộc trong pipeline chờ người duyệt trước khi AI đi tiếp — như thợ xây phải chờ chủ nhà duyệt bản vẽ trước khi đổ móng, không tự ý xây theo ý mình. Ngược lại là "full autonomous" — AI tự quyết hết, nhanh hơn nhưng rủi ro cao hơn (sai bước đầu → sai cả chuỗi).

LangGraph = thư viện xây agent dạng "đồ thị trạng thái" (state graph): mỗi agent là 1 node, cạnh (edge) nối node quy định "xong node này thì đi đâu tiếp". Khác chatbot đơn giản (1 LLM trả lời 1 câu), LangGraph cho phép loop lại (QA fail → quay lại Engineer), rẽ nhánh có điều kiện, và lưu trạng thái (checkpoint) giữa các bước để resume nếu crash.

2.5 Concrete walkthrough — 1 user request end-to-end (nói cái này để chứng minh hiểu data flow, không chỉ liệt kê box)

📦 Ví dụ cụ thể

User request: "Thêm dark mode toggle vào trang settings."

t=0s     User gửi request qua Web UI → API Gateway xác thực (auth) → tạo
         job_id, khởi tạo ProjectContext{initial_request: "...dark mode..."}
         → LangGraph bắt đầu chạy từ node "PM".

t=5s     PM node: LLM đọc initial_request, hỏi lại nếu thiếu info
         (ở đây đủ rõ, không cần hỏi) → ghi pm_report{
             scope: "Add toggle UI + persist preference + apply theme CSS",
             out_of_scope: "không đổi color palette hiện có"
         }
         → route sang "Analyser".

t=15s    Analyser node: đọc pm_report + quét codebase (RAG-retrieved:
         settings.tsx, theme.ts, user_prefs table) → spec_analysis{
             affected_files: ["Settings.tsx", "ThemeProvider.tsx", "user_prefs schema"],
             risk: "low — additive feature, không đổi API contract cũ"
         }
         → needs_clarification = false → route "SpecAnalyze" → "TaskDecompose".

t=25s    TaskDecompose: chia thành kanban_board = [
             {id:1, task:"Add dark_mode column to user_prefs"},
             {id:2, task:"Build ThemeProvider dark variant"},
             {id:3, task:"Add toggle component in Settings.tsx"},
             {id:4, task:"Wire toggle → persist → apply on load"}
         ]
         → HITL GATE: hiện spec + task list cho user duyệt (đây là điểm
         dừng bắt buộc — xem HITL ở callout trên). User approve.

t=40s    Engineer node chạy task 1-4 tuần tự (hoặc song song nếu độc lập).
         Mỗi task: Read code liên quan → Edit/Write → chạy test cục bộ.
         engineer_reports = [{task:1, success:true, files:["migrations/xxx.sql"]},
                              ...]

t=3m     Reviewer node: đọc diff toàn bộ 4 task → reviewer_report{
             verdict: "minor issue — toggle thiếu aria-label (a11y)"
         }
         → route "engineer_retry" cho task 3 only (không chạy lại cả 4).

t=3m30s  Engineer sửa task 3 → Reviewer pass → Security node scan
         (không có secret/injection risk) → route "QA".

t=4m     QA node: chạy full test suite + Playwright screenshot toggle
         hoạt động → qa_report{verdict:"pass"} → route_qa() trả về "deploy"
         (xem code route_qa ở mục 5 — Python quyết định, không phải LLM).

t=4m30s  Deploy node: merge branch, chạy CI, deploy staging → smoke test
         → deploy_report{success:true, url:"staging.app/settings"}.

t=5m     Retrospective node: tổng hợp toàn bộ agent_events → ghi log
         "4 task, 1 review-fix cycle, $0.35 total cost, 5 min wall-clock"
         → trả kết quả cuối cho user qua Web UI.

Điều cần nói to trong phỏng vấn: (1) Mỗi node ghi report riêng vào state — audit trail đầy đủ, biết chính xác bước nào fail. (2) HITL gate ở đầu (duyệt spec) chứ không phải cuối (duyệt code) — rẻ hơn: sai ở spec catch sớm, không phí compute Engineer làm sai hướng. (3) Reviewer fail chỉ retry task cụ thể (task 3), không restart toàn bộ pipeline — tiết kiệm cost + thời gian.

4. Deep dive — Engineer agent (5 min)

Input: task from kanban, spec, codebase summary
Prompt: system role + tools available + task description
       + relevant code context (RAG-retrieved)

Tools: Read, Write, Edit, Bash, Grep

Output: files_changed[], report{
    success: bool,
    changes_summary: str,
    tests_added: list[str],
    concerns: list[str],
}

Failure handling:
- Timeout (5 min per task) → mark task failed
- Tool error → retry với error message
- Parse error → escalate to Analyser

5. Deep dive — routing (5 min)

def route_qa(state: ProjectContext) -> str:
    qa = state.get("qa_report", {})
    if qa.get("verdict") == "pass":
        return "deploy"

    iters = state.get("qa_iterations", 0)
    if iters >= MAX_QA_ITERATIONS:  # 2, matches real orchestrator/graph.py default
        return "retrospective_failed"

    if qa.get("severity") == "major":
        return "analyser_qa_fail"   # back Analyser redesign

    return "engineer_retry"

# Python function, testable, deterministic
# No LLM decides — audit clear

5.5 Tool registry + budget guard (must mention)

# Tool registry — declarative, versioned, permission-scoped
TOOL_REGISTRY = {
    "read_file":  {"handler": read_fs,  "scope": "repo",  "cost_est": 0.001,
                   "schema": {"path": "str"}},
    "run_bash":   {"handler": docker_exec, "scope": "sandbox", "cost_est": 0.05,
                   "requires_approval": True},   # HITL for destructive
    "web_search": {"handler": tavily,   "scope": "public", "cost_est": 0.02},
}

def dispatch_tool(name, args, ctx):
    tool = TOOL_REGISTRY[name]
    # Permission check
    if tool.get("requires_approval") and not ctx.approved_tools.get(name):
        raise ApprovalRequired(name)
    # Budget guard — pre-check
    if ctx.spent_usd + tool["cost_est"] > ctx.budget_usd:
        raise BudgetExceeded(f"would exceed ${ctx.budget_usd}")
    result = tool["handler"](**args)
    ctx.spent_usd += tool["cost_est"]
    return result

# Session persistence — LangGraph PostgresSaver
# thread_id = f"{user_id}:{project_id}:{job_uuid}"
# Every node commit → checkpoint row. Resume = load latest by thread_id.

3 things senior interviewer looks for: (1) Tool registry not hardcoded if/else — pluggable + versioned. (2) Budget cap enforced at dispatch, not "check after". (3) HITL flag per-tool (destructive tools = approval required).

6. Scale considerations (5 min)

10 concurrent jobs

  • API: 1 instance handle async I/O (LangGraph task queue)
  • Backend: multiple worker containers, distributed via Redis queue
  • Postgres: connection pool, index thread_id
  • LLM API: rate limit awareness, backoff, batching

100 concurrent → 1000

  • Horizontal scale workers
  • Sharding by user_id
  • Cost concern: LLM API cost dominant — batch + cache aggressive

6.5 Fair scheduling — 1 team "noisy neighbor" chiếm hết queue thì sao?

💡 Analogy

Nhắc lại bài toán ở mục 6 — "100 dev teams concurrent, ~10 jobs peak", tất cả job đẩy vào 1 Redis queue chung. Nếu 1 team gửi CÙNG LÚC 50 job "feature" (mỗi job 30 phút-2 giờ), job của 99 team còn lại phải XẾP HÀNG PHÍA SAU 50 job đó — dù mỗi team chỉ gửi 1 job nhỏ. Đây gọi là "noisy neighbor" (hàng xóm ồn ào) — 1 tenant (khách thuê) chiếm dụng tài nguyên chung khiến MỌI tenant khác bị ảnh hưởng, dù họ dùng đúng mức bình thường. Giống 1 khu chung cư có nước dùng chung: 1 căn hộ mở vòi xối cả ngày → mọi căn hộ khác mất áp lực nước, dù họ chỉ dùng bình thường.

Vấn đề cụ thể: hàng đợi (queue) đơn giản kiểu FIFO (First-In-First-Out, vào trước ra trước — đã ngầm dùng ở kiến trúc "Redis queue" mục 6) coi MỌI job như nhau, xử lý đúng thứ tự gửi lên. Vấn đề: FIFO không phân biệt "job đến từ 1 team gửi dồn dập" hay "job đến từ 99 team khác nhau" — 1 team gửi nhiều job LIÊN TỤC sẽ chiếm phần lớn "lượt" trong hàng đợi một cách hợp pháp (không vi phạm gì), khiến team khác phải chờ lâu bất thường dù họ chỉ gửi 1 job.

# Fair scheduling — chia hàng đợi THEO TENANT, không phải 1 hàng đợi chung:

# KHÔNG fair (1 queue FIFO chung):
queue = ["team_A_job1", "team_A_job2", ..., "team_A_job50", "team_B_job1"]
# team_B phải đợi hết 50 job của team_A dù chỉ gửi 1 job

# Fair scheduling — round-robin giữa các tenant, không phải theo thứ tự gửi:
per_tenant_queues = {
    "team_A": ["job1", "job2", ..., "job50"],
    "team_B": ["job1"],
    # ... 98 team khác
}

def get_next_job():
    # Round-robin: lần lượt lấy 1 job từ MỖI tenant đang có job chờ,
    # không lấy liên tiếp nhiều job từ CÙNG 1 tenant
    for tenant in round_robin_order(per_tenant_queues):
        if per_tenant_queues[tenant]:
            return per_tenant_queues[tenant].pop(0)

# → team_B's job1 được xử lý ngay ở lượt thứ 2 (không phải lượt 51),
#   dù team_A gửi TRƯỚC và gửi NHIỀU HƠN

⚠️ Chỗ dễ nhầm nhất: fair scheduling KHÔNG PHẢI rate limit (đã học ở L7_3_sysdesign_predict.html §5.5) — rate limit GIỚI HẠN tổng số request/job 1 tenant được GỬI trong 1 khoảng thời gian (chặn TỪ ĐẦU VÀO); fair scheduling không chặn ai gửi bao nhiêu, chỉ đảm bảo THỨ TỰ XỬ LÝ công bằng giữa các tenant ĐÃ gửi (công bằng ở ĐẦU RA/xử lý). 1 hệ thống có thể cần CẢ HAI: rate limit để team_A không gửi 10,000 job/giây (bảo vệ hệ thống khỏi quá tải tổng), fair scheduling để 50 job hợp lệ của team_A không "chèn" job của 99 team khác (bảo vệ CÔNG BẰNG giữa các tenant hợp lệ).

8. Failure modes (10 min)

  1. Infinite loop: QA fail, Engineer retry same bug, loop. Fix: max_iterations + progress detection (compare Engineer output diff).
  2. Cost runaway: user submit vague request, Analyser loop clarify. Fix: budget cap per job, alert user, cost estimate before start.
  3. Malicious code injection: Engineer generate rm -rf/. Fix: sandboxed Docker exec + code scan (bandit) + human review before deploy.
  4. Prompt injection: user request contains "ignore instructions". Fix: role tag data, guard model check.
  5. LLM API outage: Anthropic down. Fix: multi-provider fallback (Claude → GPT-4 → Llama-3). Circuit breaker.
  6. Compliance: generated code contains license issue. Fix: license scan pre-deploy, DCO signoff, user liability.
  7. Data leak: user's codebase leaked into LLM training. Fix: contract terms (no train on customer data — thường gọi BYOK, Bring Your Own Key, cho phép enterprise dùng API key riêng với điều khoản zero-retention), local Llama fine-tune option for sensitive.
💡 Circuit breaker — vì sao không chỉ retry

Circuit breaker hoạt động như cầu dao điện nhà bạn: dòng điện quá tải → cầu dao TỰ NGẮT để bảo vệ hệ thống, không đợi cháy nhà mới ngắt. Áp dụng cho gọi LLM API:

  • Closed (bình thường): request gọi thẳng Anthropic API như thường lệ.
  • Open (ngắt): sau N lần lỗi liên tiếp (ví dụ 5 lần trong 30s) → circuit "mở", ngừng gọi Anthropic hoàn toàn trong X giây, route thẳng sang GPT-4 fallback hoặc trả lỗi nhanh cho user — không tiếp tục retry vào 1 service đang chết (retry mù quáng chỉ làm outage tệ hơn, tốn thêm queue).
  • Half-open (thử lại): sau X giây, cho 1 request "dò đường" — nếu thành công thì đóng lại circuit (trở về closed), nếu vẫn lỗi thì mở lại, đợi thêm.

Khác retry đơn thuần (cứ lỗi là thử lại ngay) — circuit breaker biết khi nào nên "ngừng cố gắng tạm thời" để không làm quá tải hệ thống đang gặp sự cố.

9. Trade-offs discussion

Q: "Fewer LLM calls (1 mega prompt) vs many specialized agents?"
A: Specialized:
   + Better quality per role (focused prompt)
   + Easier debug (know which agent failed)
   + Reusable roles across projects
   - Higher cost + latency

   Start monolith, split when observe specific weakness.

Q: "Support arbitrary languages / frameworks?"
A: Start Python (highest LLM training data).
   Extend: same graph, different toolset per language.
   Test coverage grows: don't promise Rust support if not verified.

10. Anti-patterns (mention 2-3 để show maturity)

  1. LLM as router: "let the LLM decide next agent" → non-deterministic, cannot unit test. Use Python router.
  2. Unbounded loop: no max_iter → runaway cost + user timeout. Always max_qa_iter=2 + progress detection.
  3. No sandbox on Bash tool: LLM generates rm -rf / → catastrophic. Docker isolation + read-only mount + syscall filter.
  4. Silent tool failure fallback: tool returns "" on error → LLM proceeds as if success (V19.5 lesson). Fail loud with typed exception.
  5. Storing raw customer code in LLM provider logs: compliance violation. Enterprise: BYOK + zero-retention API endpoint.

4.1 · Tokenization + Embeddings

Cách LLM "đọc" text: word-level → BPE → SentencePiece. Vocab size, token cost, Vietnamese quirks. Embeddings — nền tảng semantic.

Level 4 · LLM · ~30 phút

💡 Tokenization bằng ngôn ngữ đời thường

Học tiếng Việt qua từ điển đầy đủ: Từ điển có "phở, phở bò, phở gà, phở đặc biệt, phở tái, phở nạm..." — vocab bung to 500k từ, gặp "phở-siêu-cay-mới-ra" chưa có → chịu.

BPE (Byte Pair Encoding): Học các mảnh nhỏ "ph", "ở", "bò", "gà" — chỉ 50k mảnh nhưng ghép thành mọi từ có thể. "phở-siêu-cay" = "ph" + "ở" + "-" + "siêu" + "-" + "cay" → OK.

Trade-off: Tokenizer chọn cỡ nhỏ (byte-level) → xử lý được mọi text nhưng câu dài (mỗi ký tự = 1 token). Cỡ lớn (word-level) → câu ngắn nhưng OOV (out-of-vocab). BPE ở giữa — sweet spot của GPT/Llama.

1. Vì sao không dùng word-level?

  • Vocab huge (English 500k+ words) → giant embedding table
  • OOV (out-of-vocabulary): từ mới, typo, code → UNK token → info loss
  • Morphology: "running", "runs", "ran" → 3 separate embeddings, not sharing "run" root

2. Character-level — extreme opposite

  • Vocab tiny (~100 characters)
  • No OOV
  • Nhưng: sequence 5-10× dài hơn → O(L²) attention explode
  • Semantic weak (mỗi char không có meaning riêng)

3. Byte-Pair Encoding (BPE)

Original Gage 1994 for data compression, adopted for NLP bởi Sennrich 2016.

ALGORITHM (training):
1. Start vocab = all characters + special tokens (BOS, EOS, PAD)
2. Compute frequency of adjacent character pairs in corpus
3. Merge most frequent pair → new token in vocab
4. Repeat until vocab size = target (e.g., 50k)

Example (English):
Corpus: "low", "lowest", "newest", "widest"
Chars: l, o, w, e, s, t, n, i, d
Pair freq: ('e','s') = 3, ('e','w') = 2, ('l','o') = 2, ...
Merge 'e'+'s' → 'es': "low", "lowest" → "low", "low+est"
Continue: merge 'est', 'ow', ...

Result vocab: chars + merged subwords + full words

Tokenize new text

Input: "widened"
Greedy longest match: 'wide' (if in vocab), 'ned' → ['wide', 'ned']
Or fallback to chars: ['w', 'i', 'd', 'e', 'n', 'e', 'd']
🎯 Deep-dive — BPE từng bước tay (worked example) + SentencePiece Unigram math

Ví dụ tiếng Việt: tokenize "học sinh giỏi" từng bước (giả sử vocab đã trained trên corpus giáo dục VN).

  1. Khởi tạo vocab chỉ có characters + byte fallback: V₀ = {h, ọ, c, _, s, i, n, g, ỏ, ...} (~200 chars UTF-8 VN).
  2. Đếm frequency các cặp adjacent trong corpus. Giả sử corpus có "học sinh học giỏi học tập": pairs = {(h,ọ): 3, (ọ,c): 3, (s,i): 1, (i,n): 1, (n,h): 1, (g,ỏ): 1, ...}. Cặp thắng: (h,ọ) tần 3 → merge thành token mới họ. V₁ = V₀ ∪ {họ}.
  3. Đếm lại sau khi merge (corpus giờ có "họ c sinh họ c giỏi họ c tập"): (họ, c): 3 → merge → V₂ ∪ {học}.
  4. Lặp cho đến khi |V| = target (VD 32k). Sau nhiều iteration: V_final ⊃ {học, sinh, giỏi, học_sinh, học_giỏi, ...}.
  5. Encode câu mới "học sinh giỏi" bằng greedy longest match — vocab càng lớn, càng ít token:
    • Vocab có compound: ["học_sinh", "▁giỏi"] = 2 tokens.
    • Vocab chỉ có unigram: ["học", "▁sinh", "▁giỏi"] = 3 tokens.
    • Chỉ character-level: 11 tokens.

SentencePiece Unigram (Kudo 2018) — khác BPE thế nào

Ý tưởng ngược: BPE bottom-up (bắt đầu char, merge lên). Unigram top-down (bắt đầu vocab HUGE, prune xuống).

💡 2 thuật ngữ lạ trước khi đọc tiếp: Viterbi + EM là gì?

Viterbi = "tìm đường đi rẻ nhất qua mê cung":

  • Câu "họcsinh" có thể cắt nhiều cách: "học"+"sinh", "họ"+"c"+"sinh", "h"+"ọ"+"c"+"s"+"i"+"n"+"h"...
  • Mỗi cách cắt có 1 "chi phí" = tổng −log p(mỗi mảnh).
  • Thử HẾT mọi cách cắt là exponential — Viterbi tránh việc đó bằng dynamic programming.
Lattice cắt chữ "họcsinh" — mỗi mũi tên là 1 token khả dĩ, mỗi path đầu-cuối là 1 cách cắt:

  0 →[h]→ 1 →[ọ]→ 2 →[c]→ 3 →[s]→ 4 →[i]→ 5 →[n]→ 6 →[h]→ 7    (path toàn ký tự — dài, chi phí cao)
  0 ------[họ]----→ 2 →[c]→ 3 → ...                              (dùng token "họ")
  0 ---------------[học]-------→ 3 →[s]→[i]→[n]→[h]→ 7           (dùng token "học")
  0 ---------------[học]-------→ 3 -------[sinh]-------→ 7       (2 token: "học" + "sinh")

Viterbi KHÔNG liệt kê hết các path trên. Đi trái→phải, tại mỗi vị trí i chỉ giữ 1 con số:
  best_cost[i] = chi phí RẺ NHẤT để đến vị trí i (từ mọi token kết thúc tại i)
  best_cost[0] = 0
  best_cost[i] = min qua mọi token w kết thúc ở i của ( best_cost[i − len(w)] + (−log p(w)) )
→ Tuyến tính theo độ dài câu, không cần nhớ lại toàn bộ lịch sử mỗi path — giống GPS chỉ cần
  biết "tới ngã tư này rẻ nhất là bao nhiêu", không cần nhớ lại mọi lộ trình đã thử.

EM (Expectation-Maximization) = "đoán rồi chỉnh, lặp lại tới khi ổn định" — giải bài toán con gà quả trứng: muốn biết xác suất p(w) của mỗi token thì cần biết câu bị cắt (segment) thế nào; nhưng muốn cắt tối ưu thì lại cần biết p(w) trước.

  ┌──────────────────────┐
  │    p(w) hiện tại       │
  └───────────┬────────────┘
              │  E-step: cố định p(w), dùng Viterbi tìm cách cắt TỐT NHẤT cho mọi câu trong corpus
              ▼
  ┌──────────────────────┐
  │  cách cắt tốt nhất     │
  │  cho từng câu          │
  └───────────┬────────────┘
              │  M-step: cố định cách cắt vừa tìm, đếm lại tần suất mỗi token → p(w) MỚI
              ▼
  ┌──────────────────────┐
  │     p(w) mới           │──── lặp lại vài chục vòng cho tới khi p(w) hội tụ ──→ (quay về E-step)
  └──────────────────────┘

Analogy: 2 người bạn đoán giá 1 món hàng lạ — người 1 đoán giá dựa trên "loại hàng"; người 2 phân loại hàng dựa trên "giá vừa đoán"; lặp qua lại vài lần thì cả 2 hội tụ về ước lượng hợp lý.

  1. Sinh vocab lớn ban đầu (500k subwords, mọi substring xuất hiện ≥ 2 lần).
  2. Gán probability p(w) cho mỗi token. Loss = − Σ log p(sentence) với sentence được segment tối ưu bằng Viterbi.
  3. Chạy EM (xem sơ đồ ở trên) — tính p(w) → segment optimal → update p(w). Lặp.
  4. Prune 10% tokens ít contribute nhất (theo Δ log-likelihood). Về target size.
  5. Ở inference, mỗi câu có NHIỀU segmentation valid → sample theo probability (BPE-dropout tương tự) → data augmentation trong training.

Δ log-likelihood pruning bằng số cụ thể (Bước 4): thuật toán tính Δ (log-likelihood corpus giảm bao nhiêu nếu bỏ token này) cho toàn bộ vocab, sort, cắt 10% có Δ nhỏ nhất:

  • Bỏ token "họ_sinh" → câu chứa nó phải segment lại thành "học" + "sinh" (2 token thay 1). Log-likelihood corpus giảm từ −1000.0 xuống −1000.3 (Δ = 0.3 — giảm nhẹ, không quá quan trọng) → nằm trong nhóm 10% bị prune trước.
  • Bỏ token "▁và" (từ nối cực phổ biến) → Δ = 45.0 (giảm rất mạnh) → giữ lại.

Vì sao Unigram tốt cho VN: dấu diacritic (á, ắ, ế) tạo nhiều ambiguity segment. Unigram probabilistic — chọn segmentation thống kê tốt nhất, không greedy đơn thuần.

Gotchas tokenization thường gặp:

  • Leading space matter: "hello" ≠ " hello" trong BPE. Token ▁hello (có space) khác hello (không). Debug: tokenizer.encode("hello")[0] có thể là hello; tokenizer.encode(" hello")[0] là ▁hello.
  • Pad token ≠ EOS token: Llama không có PAD gốc. Nếu set pad_token = eos_token → khi tính loss trên batch, model học "predict EOS everywhere" → generation dừng sớm. Fix: dùng pad_token = "<unk>" và mask trong loss.
  • Padding side: decoder-only LLM cần padding_side="left" khi generate (right-pad → model attend vào pad tokens → garbage). Encoder (BERT): right-pad OK.
  • BOS auto-inject: Llama tokenizer tự thêm <s> ở đầu. Nếu bạn concat 2 conversation → có 2 BOS ở giữa → confuse model. Kiểm: tokenizer.encode(x, add_special_tokens=False).

4. WordPiece (BERT)

Similar BPE nhưng merge criterion: maximize likelihood of training data (không chỉ frequency).

💡 "Maximize likelihood" khác "frequency" thế nào? — ví dụ số

BPE chọn cặp ghép xuất hiện nhiều nhất, bất kể ghép đó có "đáng" hay không. WordPiece chọn cặp làm likelihood của corpus tăng nhiều nhất nếu ghép — tức là so sánh "ghép 2 mảnh lại" với "để riêng 2 mảnh" xem cách nào predict corpus tốt hơn.

Ví dụ cụ thể: giả sử corpus có cặp ("t","h") xuất hiện 1000 lần VÀ cặp ("q","u") xuất hiện 500 lần.

  • BPE: chọn ("t","h") vì tần suất cao hơn (1000 > 500) — không quan tâm gì khác.
  • WordPiece tính: score = count(pair) / (count(token1) × count(token2)). "t" và "h" đều rất phổ biến riêng lẻ (xuất hiện trong hàng ngàn từ khác) → score("t","h") = 1000/(50000×40000) = rất nhỏ. "q" gần như LUÔN đi kèm "u" trong tiếng Anh (q hiếm khi đứng 1 mình) → count("q")≈520 → score("q","u") = 500/(520×600) = lớn hơn nhiều dù tần suất tuyệt đối thấp hơn.
  • → WordPiece chọn ghép ("q","u") trước, vì ghép này "giải thích" dữ liệu tốt hơn (giảm surprise/entropy nhiều hơn), dù ít gặp hơn về số lần tuyệt đối.
# Prefix subwords với ##:
"unhappy" → ["un", "##happy"]
"##" indicates continuation, not word start

5. SentencePiece (LLaMA, T5)

  • Language-agnostic: treat text as raw byte stream, không assume whitespace = word boundary (crucial cho VN/CN/JP)
  • Trained bằng BPE hoặc Unigram (Kudo 2018)
  • Reversible: text → tokens → text exact
  • Byte fallback (xem callout dưới)
💡 "Byte fallback" nghĩa là gì?

Vocab dù 32k-256k cũng KHÔNG thể chứa mọi ký tự Unicode có thể (emoji hiếm, chữ Hán cổ, ký hiệu toán học lạ...). Nếu gặp ký tự chưa từng thấy trong vocab, tokenizer cần 1 "lưới an toàn" (safety net) để không bị crash / mất thông tin.

Cơ chế: mọi text đều encode được thành chuỗi byte UTF-8 (256 giá trị byte có thể: 0x00-0xFF). Tokenizer luôn có sẵn 256 token đặc biệt đại diện "byte thô". Ký tự lạ (VD 1 emoji hiếm 🫠) → decompose thành 3-4 byte UTF-8 → mỗi byte trở thành 1 token riêng ("<0xF0>", "<0x9F>", ...) thay vì bị thay bằng UNK (mất thông tin hoàn toàn).

Lợi ích: tokenizer KHÔNG BAO GIỜ mất thông tin (100% reversible, kể cả input rác/binary). Đây là lý do LLaMA, GPT-4 xử lý được bất kỳ input nào (kể cả tiếng hiếm, code, base64) mà không lỗi UNK.

6. Vietnamese quirks

VN token cost cao

English "Hello world" = 2 tokens (GPT-4). VN "Xin chào thế giới" = 6-9 tokens (BPE trained mostly on English). VN diacritics (á, ắ, ế) + tone marks → often split into multiple tokens.

Ảnh hưởng: API cost cao 2-3× cho VN text, context window effective size nhỏ hơn.

import tiktoken
enc = tiktoken.encoding_for_model("gpt-4")
print(len(enc.encode("Hello world")))          # 2
print(len(enc.encode("Xin chào thế giới")))    # 8
print(len(enc.encode("VN30 tăng 1.5% phiên hôm nay")))  # ~15

8. Number tokenization — vì sao LLM yếu toán KHÔNG chỉ vì "chưa học đủ"

💡 Analogy

Tưởng tượng bạn cộng 2 số nhưng ai đó cắt ngẫu nhiên chữ số của chúng thành từng cụm 1-3 chữ số KHÔNG THEO HÀNG (không theo hàng đơn vị/chục/trăm) trước khi đưa cho bạn — VD số "1234" bị cắt thành "12"+"34" nhưng số "123" (chỉ ít hơn 1 chữ số) lại bị cắt thành "1"+"23" (ranh giới cắt hoàn toàn khác, không phải "giữ nguyên 3 chữ số cuối"). Bạn vẫn có thể cộng được số nhỏ (nhìn quen mắt), nhưng số càng dài, cách cắt càng "lộn xộn" không nhất quán giữa các số khác nhau → rất khó giữ đúng hàng đơn vị/chục/trăm khi cộng. Đây CHÍNH XÁC là những gì tokenizer BPE làm với số, không phải ẩn dụ.

Vấn đề cụ thể: BPE/tiktoken không có khái niệm "đây là 1 con số, phải giữ nguyên cấu trúc hàng chục/hàng trăm" — nó coi digit-run (chuỗi chữ số liên tiếp) y hệt như coi 1 từ tiếng Anh: cắt theo tần suất xuất hiện trong corpus, không theo ý nghĩa toán học. Kết quả: cách cắt 1 số PHỤ THUỘC vào TỔNG ĐỘ DÀI của số đó, không phụ thuộc vị trí hàng (đơn vị/chục/trăm) của từng chữ số bên trong.

# Ví dụ từ tokenizer họ tiktoken (GPT-4/4o, greedy left-to-right, tối đa 3 chữ số/token):
"2", "20", "200", "201" đều được gộp thành ĐÚNG 1 token (không cắt thành "2"+"01"
hay "20"+"1") — mỗi digit-run ngắn (≤3 chữ số) thường lọt vừa 1 token duy nhất.

# Nhưng với số DÀI HƠN, ranh giới cắt (chunk boundary) nhảy lung tung:
"1234" → có thể cắt "123" + "4"      (3 chữ số đầu + 1 chữ số cuối)
"2345" → có thể cắt "234" + "5"      (giống pattern trên — ổn)
"12345"→ có thể cắt "123" + "45"     (3+2 — khác hẳn pattern của số 4-chữ-số ở trên)

→ Model KHÔNG thấy "hàng nghìn/hàng trăm/hàng chục/hàng đơn vị" như con người — nó thấy
  các "cụm số" (chunk) mà ranh giới thay đổi tuỳ độ dài tổng thể, không theo vị trí hàng.

⚠️ Chỗ dễ nhầm nhất: đây KHÔNG phải "model chưa học đủ toán trong lúc pretrain" (dù data toán ít cũng là 1 phần vấn đề) — đây là 1 giới hạn CẤU TRÚC ở tầng tokenizer, xảy ra TRƯỚC KHI model nhìn thấy bất kỳ token nào. Cho dù train thêm 100× data toán, nếu tokenizer vẫn cắt "1234" và "2345" theo 2 pattern khác nhau, model vẫn phải học "bù" sự bất nhất quán này thay vì học phép cộng thật sự theo hàng — nghiên cứu thực nghiệm (arXiv:2402+ nhiều paper) cho thấy accuracy cộng số giảm về gần 0% khi số có ≥5 chữ số, chính xác ở vùng ranh giới chunk trở nên phức tạp nhất.

Fix thực tế:

  • Chèn dấu phẩy/space giữa mỗi 3 chữ số khi viết số lớn trong prompt (VD "1,234,567" thay vì "1234567") — ép tokenizer cắt theo ranh giới CỐ ĐỊNH và ổn định hơn, cải thiện accuracy cộng/trừ đáng kể trong thực nghiệm.
  • Single-digit tokenization: 1 số kiến trúc/tokenizer chuyên biệt (không phải BPE thường) ép MỖI CHỮ SỐ = 1 token riêng biệt (VD Llama một số phiên bản tokenize digit-by-digit) — tốn nhiều token hơn nhưng giữ đúng cấu trúc hàng, giúp arithmetic tốt hơn hẳn.
  • Không dựa vào LLM để tính toán chính xác số lớn — dùng tool-calling gọi ra calculator/code execution thay vì để model tự cộng nhẩm bằng token, đặc biệt với số >4-5 chữ số.

Insight: đây là ví dụ cụ thể cho nguyên lý chung của cả trang này — cách tokenizer cắt text KHÔNG TRUNG LẬP, nó áp đặt 1 cấu trúc lên input mà model buộc phải "học sống chung" thay vì học bản chất vấn đề. VN token cost cao (§6) là 1 biểu hiện của cùng nguyên lý (tokenizer bias theo ngôn ngữ training), số bị cắt sai hàng là 1 biểu hiện khác (tokenizer bias theo cấu trúc số học).

9. Embeddings — lookup + math

💡 "d_model" là gì? (thuật ngữ sẽ dùng suốt phần LLM còn lại)

d_model = số chiều (dimension) của vector đại diện cho MỖI token bên trong model — "độ rộng" của model. Mỗi token, sau khi tra bảng embedding, không còn là 1 con số (token id) mà biến thành 1 vector d_model số thực, VD d_model=768 (GPT-2 small), 4096 (Llama-7B), 12288 (GPT-3). Vector này mang thông tin ngữ nghĩa — 2 từ gần nghĩa thì vector gần nhau trong không gian d_model chiều. d_model càng lớn → model càng "biểu diễn giàu" nhưng càng tốn compute/memory (embedding table = vocab_size × d_model số).

class Embedding(nn.Module):
    def __init__(self, vocab_size, d_model):
        super().__init__()
        self.weight = nn.Parameter(torch.randn(vocab_size, d_model) * 0.02)
        # × 0.02: khởi tạo nhỏ (std ≈ 0.02) — nếu embedding init to (VD std=1),
        # dot-product Q·K ở layer attention đầu tiên sẽ có variance lớn ngay từ bước 0
        # → softmax saturate sớm (xem L4.2 vì sao chia √d). Init nhỏ giữ activation
        # ổn định cho vài layer đầu trước khi LayerNorm "tiếp quản". Đây là convention
        # GPT-2 (std=0.02), không phải con số ma thuật — chỉ cần đủ nhỏ.

    def forward(self, token_ids):
        # token_ids: (batch, seq_len) integer indices
        return self.weight[token_ids]   # (batch, seq_len, d_model)

Tied weights (weight sharing)

# Output layer LM = embedding^T
# Save params + regularize
logits = hidden @ embedding.weight.T   # (batch, seq_len, vocab_size)

LLaMA, GPT-2 tied. Saves 50M+ params, comparable quality.

10. Glitch tokens — khi 1 token trong vocab chưa bao giờ được "học" thật sự

💡 Analogy

Tưởng tượng 1 cuốn từ điển 100.000 từ, nhưng có 500 từ trong đó CHỈ xuất hiện đúng 0-1 lần trong toàn bộ sách giáo khoa bạn dùng để học (dù từ điển liệt kê chúng vì chúng có trong 1 nguồn khác lúc BIÊN SOẠN từ điển). Bạn "biết" từ đó tồn tại (có trong từ điển) nhưng KHÔNG BAO GIỜ học được nghĩa thật của nó — nếu ai đó ép bạn dùng từ đó trong câu, bạn sẽ đoán bừa hoặc phản ứng kỳ lạ. Đây chính xác là "glitch token": tồn tại trong vocab (vì tokenizer train trên corpus A) nhưng gần như vắng mặt trong dữ liệu model thực sự HỌC (corpus B, thường khác corpus A) → embedding của nó gần như chưa từng được cập nhật gradient.

Vấn đề cụ thể (case nổi tiếng — "SolidGoldMagikarp", GPT-2/GPT-3): tokenizer BPE được train trên 1 tập dữ liệu (VD chứa dump Reddit, có username hiếm gặp như "SolidGoldMagikarp" lặp lại đủ nhiều để BPE gộp nó thành 1 TOKEN DUY NHẤT trong vocab) — nhưng model chính lại được PRETRAIN trên 1 corpus khác (đã lọc/khác nguồn), trong đó chuỗi "SolidGoldMagikarp" gần như KHÔNG xuất hiện. Kết quả: token này có 1 slot trong embedding table (vì nằm trong vocab) nhưng vector embedding của nó gần như giữ nguyên giá trị KHỞI TẠO NGẪU NHIÊN (chưa bao giờ nhận đủ gradient update để mang ý nghĩa).

# Cơ chế cụ thể (2 bước tách biệt, dễ nhầm là 1):
Bước 1 — Tokenizer training: corpus A (VD Reddit dump) → BPE đếm tần suất → "SolidGoldMagikarp"
          (1 username Reddit lặp lại nhiều) đủ tần suất → được gộp thành 1 TOKEN trong vocab.

Bước 2 — Model pretraining: corpus B (đã filter/khác nguồn, KHÔNG chứa nhiều "SolidGoldMagikarp")
          → token này CÓ trong vocab (nên CÓ 1 dòng trong embedding table) nhưng gradient đi
          qua dòng đó gần như = 0 suốt cả pretraining (vì token gần như không bao giờ xuất hiện
          làm input để model cần "học" biểu diễn nó).

→ Embedding vector của token này vẫn ~= giá trị random init ban đầu, "trôi nổi" ở 1 vùng
  KHÔNG GIAN không liên quan gì tới các embedding "đã học" xung quanh nó.

⚠️ Chỗ dễ nhầm nhất: đây KHÔNG phải bug trong code hay lỗi kiến trúc model — bản thân cơ chế (tokenizer train trên corpus khác corpus pretrain model) là chuyện BÌNH THƯỜNG và phổ biến ở nhiều pipeline LLM. Vấn đề chỉ lộ ra khi 2 corpus lệch nhau ĐỦ NHIỀU để một số token "lọt lưới" — có mặt ở vocab nhưng vắng mặt ở dữ liệu train model. Hậu quả quan sát được: khi prompt chứa 1 glitch token, model phản ứng như đang được hỏi về 1 khái niệm NGẪU NHIÊN, không liên quan (VD yêu cầu lặp lại "SolidGoldMagikarp" khiến GPT-3 trả lời như thể được hỏi về từ "distribute") — vì vị trí embedding của nó trong không gian vector không mang thông tin gì hữu ích để model "neo" vào.

Insight: đây là hệ quả trực tiếp của 1 nguyên lý đơn giản — embedding chỉ học được ý nghĩa qua gradient update LẶP LẠI NHIỀU LẦN; mỗi token cần XUẤT HIỆN ĐỦ NHIỀU trong training để embedding của nó "hội tụ" về 1 vị trí có ý nghĩa trong không gian d_model chiều (xem §9 "d_model là gì?" ở trên về khái niệm không gian embedding). Token xuất hiện 0 hoặc gần 0 lần = embedding gần như vẫn là nhiễu ngẫu nhiên ban đầu — không phải model "không biết" theo nghĩa thiếu kiến thức, mà là vùng không gian đó CHƯA BAO GIỜ được "định hình" bởi training signal nào.

📖 Mở rộng — cách fix trong thực tế: GPT-4 xử lý vấn đề này đơn giản bằng cách ĐỔI tokenizer — "SolidGoldMagikarp" giờ bị cắt thành 5 token bình thường (Solid, Gold, Mag, ik, arp), mỗi token này XUẤT HIỆN THƯỜNG XUYÊN ở nơi khác trong corpus nên có embedding đã học tốt — loại bỏ hoàn toàn "slot chết" trong vocab. Bài học cho pipeline thực tế: LUÔN train tokenizer trên đúng (hoặc đại diện sát) corpus sẽ dùng để pretrain model — không dùng tokenizer train sẵn từ 1 nguồn dữ liệu khác hẳn mà không kiểm tra token-frequency overlap.

11. Position + Token embedding combined

x_input = embed_token(token_ids) + embed_position(positions)

# Alternative modern: RoPE (rotary) — apply to Q, K in attention, not add

Ghi chú: RoPE chỉ mới nhắc tên ở đây — công thức xoay đầy đủ + tại sao nó "extrapolate" tốt hơn được giải thích chi tiết bằng số ở L4.2 (Attention + Transformer), phần "Deep-dive RoPE".

✅ QA Gate

1. BPE algorithm — 4 bước.

(1) Init vocab với characters. (2) Find most frequent adjacent pair. (3) Merge pair → new token. (4) Repeat until target vocab size.

2. Vì sao SentencePiece thay BPE cho Asian languages?

BPE assume whitespace = word boundary. VN/CN/JP không có whitespace (CN, JP) hoặc phức tạp (VN với dấu). SentencePiece raw byte, ignore whitespace → language-agnostic.

3. VN text 2× tokens của EN cùng meaning → API cost impact?

2-3× cost per API call. Cần optimize: (1) Use Claude/GPT-4o với 128k vocab (VN token/char tốt hơn). (2) Cache repeated content. (3) Prompt compression (shorter format). (4) Fine-tune VN model với VN-specific tokenizer.

4. Tied weights — save gì?

Output projection layer = embedding.T. Save vocab_size × d_model params. GPT-2 medium 50k × 1024 = 50M params saved. Also mild regularization effect.

5. RoPE khác absolute position embed?

Absolute: add position embedding to token embedding. RoPE: rotate Q, K trong attention theo position. Ưu RoPE: relative position aware, extrapolate longer context tốt hơn. LLaMA, GPT-J, Falcon dùng.

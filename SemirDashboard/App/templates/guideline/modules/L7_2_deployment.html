7.2 · Model Deployment (Batch / Real-time / Streaming)

3 serving patterns. FastAPI + XGBoost, vLLM + LLM, event-driven. Cost + latency + SLA trade-offs.

Level 7 · Production · ~30 phút

🎯 Learning objectives

  • 3 deployment patterns + when
  • Model serving stack (FastAPI, TorchServe, vLLM)
  • Auto-scaling for GPU
  • Blue-green vs canary vs shadow deployment
💡 Deployment patterns bằng ngôn ngữ đời thường

Bán phở:

  • Batch: Cửa hàng nấu sẵn 100 bát sáng sớm → bán cả ngày. Rẻ per bát nhưng phở nguội. Áp dụng: dự đoán churn hàng ngày cho 1M user — không cần realtime.
  • Real-time: Khách gọi, làm từng bát tươi. Đắt per bát, phải chờ 5 phút, nhưng tươi ngon. Áp dụng: fraud detection khi user swipe thẻ.
  • Streaming: Phở take-away liên tục theo dòng khách qua cửa sổ drive-thru. Áp dụng: click-through prediction cho ads bidding — inference trên stream events Kafka.

Chọn pattern nào dựa vào SLA latency (chấp nhận phở nguội 1 tiếng hay phải nóng?) + volume (100 bát/ngày hay 100 bát/phút?) + freshness signal (khách hôm nay đến có khác hôm qua không?).

SLA (Service Level Agreement) = cam kết chất lượng dịch vụ bằng số cụ thể — ví dụ "p95 latency < 200ms" nghĩa là 95% request phải trả lời dưới 200ms. Không có SLA rõ ràng = không biết pattern nào "đủ nhanh".

1. 3 patterns

1.1 Batch inference

Nightly Airflow DAG:
1. Fetch all users needing prediction (~1M)
2. Run model in batches of 10k (parallel)
3. Store predictions in DB (Postgres/Redis)
4. UI reads pre-computed predictions

# Cost: cheap (batch efficient, spot instances OK)
# Latency: N hours behind live
# Use: recommendation, monthly report

# Cost: higher (24/7 warm instance)

Event bus (Kafka) → consumer → model → sink

2. V18 serving stack

Request → FastAPI (routers/predict.py)
             ↓
          Check tier-3 skip (fast reject)
             ↓
          TTLCache lookup (in-memory)
             ↓
          Postgres cache (prediction_log)
             ↓
          engine.predict() [XGBoost inference]
             ↓
          Composite confidence
             ↓
          Response JSON

# Latency budget: ~20ms p95
# 86 tickers concurrent OK
💡 2 thuật ngữ trong flow trên

Tier-3 skip: trước khi chạy model tốn kém, check nhanh các điều kiện rẻ tiền để từ chối sớm (ví dụ ticker không đủ lịch sử data, hoặc ngoài giờ giao dịch) — "tier-3" vì đây là lớp check rẻ nhất/nhanh nhất trong chuỗi validate. Giống bảo vệ hỏi "anh có hẹn không" trước khi cho vào — khỏi tốn công dẫn khách lên tận phòng họp.

TTLCache (Time-To-Live Cache): cache lưu trong RAM của chính process, mỗi entry tự hết hạn sau N giây (TTL). Nhanh nhất (không qua network) nhưng chỉ tồn tại trong 1 process — nếu chạy nhiều instance, mỗi instance có cache riêng (không chia sẻ như Redis).

3. LLM serving stack

Request → API gateway → Rate limit → Request batcher
                                          ↓
                                      vLLM engine (PagedAttention + Continuous batching)
                                          ↓
                                      GPU worker (A100/H100)
                                          ↓
                                      Streaming SSE back to client

# vLLM: up to 24× throughput of HuggingFace Transformers, up to 3.5× của TGI (vllm.ai blog 2023)
# Multi-LoRA: serve 100+ fine-tuned variants trên 1 base
💡 Vì sao vLLM nhanh hơn nhiều lần — 2 kỹ thuật cốt lõi

PagedAttention: Bình thường, mỗi request cần cấp phát 1 khối bộ nhớ GPU liền mạch (contiguous) cho KV cache (xem L7.5 Q17) — như đặt cả bàn dài cho 1 khách dù họ chỉ ăn ít. Nếu output ngắn hơn dự kiến → phí bộ nhớ (fragmentation). PagedAttention chia bộ nhớ thành "trang" (page) nhỏ như hệ điều hành quản lý RAM — cấp phát đúng nhu cầu, không phí, phục vụ nhiều request đồng thời hơn trên cùng GPU.

Continuous batching: Batching kiểu cũ (static) phải đợi đủ N request rồi mới chạy cùng lúc, request xong sớm vẫn phải chờ cả batch — như xe bus chỉ chạy khi đủ khách, ai lên sớm vẫn ngồi chờ. Continuous batching: request nào xong thì rời "bus" ngay, request mới join ngay lập tức vào slot trống — không ai phải chờ vô ích. Kết quả: GPU luôn bận, throughput cao hơn nhiều.

LoRA (Low-Rank Adaptation) — nhắc trước khi đọc "Multi-LoRA": thay vì fine-tune lại toàn bộ model (hàng tỷ tham số) cho mỗi use-case, LoRA chỉ train 1 cặp ma trận nhỏ (rank thấp) "gắn thêm" vào model gốc đã đóng băng (frozen). Nhẹ (~50MB thay vì 10GB+), swap nhanh. Multi-LoRA = 1 GPU giữ 1 bản model gốc dùng chung, nạp nhiều "miếng dán" LoRA khác nhau theo request — xem code implementation ở L7.5 Q16.

4. Auto-scaling GPU

GPU is expensive

1 × A100 = $2-3/h. Idle GPU = wasted money. Must scale.

# Kubernetes HPA (Horizontal Pod Autoscaler):
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  minReplicas: 1
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: nvidia.com/gpu
      target:
        type: Utilization
        averageUtilization: 70
  - type: Pods
    pods:
      metric:
        name: llm_queue_depth
      target:
        type: AverageValue
        averageValue: "5"

# Scale up when queue depth > 5 or GPU util > 70%
# Scale down after 5 min idle (avoid thrashing)

Cold start problem

New GPU instance startup: 60-180s (pull image + load model 30GB)
User request during scale-up: timeout

Solutions:
1. Keep min 1 replica warm (24/7 cost)
2. Predictive scaling (traffic pattern learned)
3. Provisioned concurrency (AWS Lambda-style)
4. Serverless spot mixed (spot cheaper, fallback on-demand)

5. Deployment strategies

5.1 Blue-Green

Blue = current prod
Green = new version, warm & ready

Switch: LB point to Green (instant)
Rollback: LB back to Blue (instant)

# Cost: 2× while both running
# Best cho monolith apps

5.2 Canary

Route 1% → 5% → 25% → 100% traffic to new version
Monitor at each stage, rollback if degradation

# Slower rollout, safer
# Better cho ML models (real-world verification)

5.3 Shadow (dark launch)

All requests go to old model (user sees result)
Duplicate request to new model (compare offline, no user impact)

# Zero user risk
# Compare predictions apples-to-apples
# Best cho major architecture change

7. Cost anatomy real-time serving

App: 1M requests/day, 50ms model + 20ms other

Baseline throughput per instance:
  50ms/req → 20 req/s per instance
  1M/86400 sec ≈ 12 req/s average
  Peak 3× ≈ 35 req/s → need 2 instances

Instance cost:
  Small (2 vCPU, 4GB): $50/month × 2 = $100/month
  Plus Redis: $30/month
  Plus DB (Postgres t3.medium): $50/month
  Total: ~$180/month for 1M req/day predictor

Deployment anti-patterns

Đừng làm
  1. Big-bang deploy 100% traffic: bug → toàn bộ user affected + rollback stress. Canary 1% → 10% → 100% với auto-rollback trên metric drop.
  2. Autoscale trên CPU only: LLM/ML workload thường I/O-bound waiting API → CPU thấp nhưng queue depth cao. Scale trigger: queue depth, p95 latency, GPU util (nếu có).
  3. Không có warm-up: new pod nhận full traffic ngay → cold cache + JIT compile → p99 spike. Warm-up: replay 100 canary requests trước khi mark ready.
  4. Shared model file mutable: 2 pods đọc cùng file khi 1 pod đang overwrite → corruption. Immutable versioned dirs + atomic symlink swap.
  5. GPU idle vì batch=1: online serving 1 request/1 GPU forward pass → utilization 5%. Dynamic batching (Triton) gộp 8-32 requests trong 20ms window.

✅ QA Gate

1. Batch vs Real-time vs Streaming — 3 examples.

Batch: nightly recommendation refresh, monthly credit score. Real-time: search ranking, chat response, fraud detection. Streaming: clickstream anomaly, real-time ad bidding.

2. Blue-green vs Canary — khi nào chọn nào?

Blue-green: instant cut-over, stateless apps, monoliths. Canary: gradual, ML models (verify production behavior), microservices. Shadow: zero risk major changes.

3. GPU auto-scale — cold start problem?

New instance startup 60-180s (image + model load). User request timeout during. Fix: (1) Keep min 1 warm. (2) Predictive scaling. (3) Provisioned concurrency (pre-warm N instances). (4) Small standby model for fallback.

4. Serve 100 fine-tuned LoRA variants — architecture?

Base model shared trong GPU memory (single copy). LoRA weights (~50MB each) loaded on-demand. vLLM Multi-LoRA support: request specifies adapter_id, forward pass với base + LoRA. Save 100× memory vs separate deployments.

5. Shadow deployment 1 tuần cho V20 vs V18. Compare gì?

(1) Prediction agreement rate (V20 says UP when V18 says UP?). (2) Confidence calibration. (3) Latency p50/p95. (4) Downstream: PnL simulation nếu trader follow V20 predictions vs V18. (5) Sanity: outputs valid schema, no NaN.

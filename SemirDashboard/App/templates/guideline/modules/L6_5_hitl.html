6.5 · Human-in-the-Loop (HITL)

Interrupt gates, approval flows, edit/reject patterns. Cân bằng automation với human oversight cho high-stakes agent actions.

Level 6 · Agents · ~25 phút

🎯 Learning objectives

  • 3 HITL patterns: approve, edit, redirect
  • Implement interrupt_before + Command(resume=...)
  • UI design cho approval flow
  • Timeout + auto-approve fallback
💡 Human-in-the-Loop bằng ngôn ngữ đời thường

Xe tự lái Tesla: Tự chạy 99% tình huống ngon lành. 1% cần người can thiệp: đèn đỏ hư, tai nạn phía trước, biển báo mờ. Xe dừng, alert tài xế → tài xế quyết định.

AI agent: LLM đề xuất "chuyển 500tr từ tài khoản A sang B" → không nên tự thực hiện. Pause, hỏi human "confirm chuyển tiền?" → human duyệt → thực thi. HITL cho quyết định rủi ro cao/không đảo được.

3 patterns HITL:

  • Approve/reject: user Y/N.
  • Edit: user chỉnh sửa output LLM trước khi thực thi.
  • Interactive: LLM hỏi làm rõ khi câu hỏi mơ hồ (Cursor "which file did you mean?").

1. Vì sao HITL?

  • High-stakes actions: deploy prod, send money, delete data
  • Compliance: regulated industries require human sign-off
  • Quality: agent 90% correct, need human catch 10% edge cases
  • Learning: human feedback improves system over time
  • Trust: user comfort with automation gradually

2. 3 HITL patterns

2.1 Approve / Reject

# Simplest: binary decision
Agent produce spec → pause → user click "Approve" / "Reject"

# Reject → back to agent với reason, retry
# Approve → continue pipeline

2.2 Edit

# User modify agent output before continue
Agent generate code → user edit → user confirm → deploy

# UI shows diff, user makes changes, save

2.3 Redirect

# User change direction mid-pipeline
Agent implementing feature X → user say "actually do Y instead"
System back to analyser với new requirement
⚠️ Common confusion — Redirect vs Interactive Q&A

Bảng so sánh ngay dưới đây dùng tên "Interactive Q&A" thay vì "Redirect" — dễ tưởng đây là pattern thứ 4. Thực ra chúng là 2 biến thể của cùng ý tưởng "đổi hướng", khác nhau ở ai chủ động bấm nút dừng:

  • Redirect = user chủ động ngắt ngang khi agent đang chạy bình thường (không ai hỏi gì cả) — "Agent implementing feature X → user tự nói 'thôi làm Y đi'". Agent không ngờ trước việc này.
  • Interactive Q&A = agent chủ động dừng lại và hỏi vì nó phát hiện mơ hồ ("which file did you mean?") — agent biết trước nó cần hỏi, user chỉ trả lời câu hỏi cụ thể.

Cả 2 đều dùng chung cơ chế kỹ thuật (interrupt() + graph quay lại node trước), nên bảng dưới gộp chung 1 cột để so sánh gọn — nhưng khi thiết kế UI, nhớ tách rõ: Redirect cần nút "Change direction" luôn hiển thị; Interactive Q&A chỉ xuất hiện khi agent tự yêu cầu.

Ví dụ concrete — AI code assistant deploy 3 patterns

=== Approve/Reject ===
Agent: "I'm about to force-push to main. Confirm?" [Y/N]
User: Y → execute
Simple, fast, but limited flexibility.

=== Edit before execute ===
Agent: "Here's the PR description [3 paragraphs]. Edit or approve."
User: chỉnh 1 câu → approve
Better content quality but more effort.

=== Interactive Q&A ===
Agent: "You said 'fix the bug' — which file?
       Option 1: auth.py:42 (last edited)
       Option 2: test_auth.py:15 (test file)"
User: "Option 1"
Agent: continues
Best cho ambiguous tasks but slower.

3. LangGraph implementation

interrupt_before vs interrupt() — 2 thứ khác nhau, dùng CÙNG NHAU

Code dưới đây dùng cả 2 — dễ tưởng bị trùng lặp. Thực ra chúng làm 2 việc khác nhau, bổ sung cho nhau:

  • interrupt_before=["human_gate"] khai báo LÚC COMPILE graph — nói với LangGraph "trước khi chạy node tên human_gate, luôn dừng lại". Đây là cấu hình tĩnh, áp dụng cho mọi lần chạy graph này.
  • interrupt(payload) gọi LÚC RUNTIME, bên TRONG thân hàm node — nó không chỉ dừng, mà còn đóng gói dữ liệu (payload) gửi ra ngoài cho UI hiển thị, và khi resume, giá trị user trả về (qua Command(resume=...)) chính là return value của lời gọi interrupt() đó.

Nói cách khác: interrupt_before trả lời câu hỏi "graph dừng Ở ĐÂU", còn interrupt() trả lời câu hỏi "dừng thì GỬI GÌ cho user và NHẬN GÌ khi tiếp tục". Chỉ dùng interrupt_before mà không có interrupt() trong node vẫn dừng được, nhưng UI sẽ không có payload rõ ràng để hiển thị.

from langgraph.types import interrupt, Command

def human_gate(state: ProjectContext) -> dict:
    """Pause for spec approval."""
    # interrupt() pauses graph, returns None to caller
    result = interrupt({
        "reason": "spec_review",
        "spec": state["spec_analysis_report"],
        "prompt": "Approve this spec? (yes/no + optional comments)",
    })
    return {
        "spec_approved": result["approved"],
        "user_feedback": result.get("feedback", ""),
    }

# Compile with interrupt_before
app = graph.compile(
    checkpointer=saver,
    interrupt_before=["human_gate"],
)

# Runtime: graph runs until pauses at human_gate
config = {"configurable": {"thread_id": job_id}}
result = await app.ainvoke(initial_input, config=config)
# result contains __interrupt__ signal

# Later, after user approves via UI:
await app.ainvoke(
    Command(resume={"approved": True, "feedback": "LGTM"}),
    config=config,
)

5. Auto-approve fallback

Timeout strategy

User đi vacation 3 ngày không approve → agent waste checkpointed state. Options:

  1. Timeout auto-reject: sau N hours, treat as reject, fail job
  2. Timeout auto-approve: risky, chỉ cho low-stakes decisions
  3. Escalate: notify secondary approver
  4. Preserve: pause indefinitely (default), notify user via email

AI Orchestrator: preserve + email notification. Cost checkpoint storage → cleanup 30 days.

6. Notification patterns

  • Push notification (mobile app)
  • Email digest (batch multiple approvals)
  • Slack/Teams webhook (team collaboration)
  • In-app dashboard (persistent list)

7. Multi-approver

# N-of-M approval: require k approvals from set of M reviewers
def multi_approve_gate(state):
    approvals = interrupt({
        "type": "multi_approval",
        "required_k": 2,
        "eligible_approvers": ["u1", "u2", "u3", "u4"],
    })
    if len(approvals["approved_by"]) >= 2:
        return {"approved": True}
    return {"approved": False, "reason": "insufficient approvals"}

9. HITL pain points

  1. Approval fatigue: user click "approve" without reading → defeat purpose. Fix: batch reviews, quality assurance sampling.
  2. Latency killer: user response = hours. Total pipeline days. Fix: async notification, prioritize by risk.
  3. Dropout: user không complete approval. Fix: reminders, escalation, timeout policy.
  4. Race condition: 2 users approve simultaneously → conflict. Fix: version state, optimistic locking.

Optimistic locking là gì? Thay vì khoá database khi user A mở màn hình approval (pessimistic — chặn user B luôn), hệ thống gắn 1 số version vào state. Khi user A bấm Approve, request gửi kèm version=5 (bản họ đang xem). Server chỉ chấp nhận nếu version hiện tại trong DB vẫn = 5; nếu user B đã approve trước đó và version đã tăng lên 6, request của A bị từ chối với lỗi "state đã thay đổi, tải lại". "Optimistic" vì hệ thống giả định ít khi xung đột nên không khoá trước — chỉ kiểm tra và từ chối nếu phát hiện xung đột lúc ghi, rẻ hơn khoá pessimistic nhưng cần code xử lý "reload + báo lỗi" cho user.

✅ QA Gate

1. 3 HITL patterns describe briefly.

(1) Approve/Reject binary. (2) Edit — user modify then continue. (3) Redirect — change pipeline direction.

2. LangGraph interrupt_before vs interrupt() inside node — khác biệt?

interrupt_before: pause BEFORE node executes. interrupt() called inside node: pause DURING node with data package. interrupt() flexible, allows agent produce data first then wait for user to inspect.

3. User đi vacation 3 ngày, không approve. System should?

Preserve checkpoint + email reminders. High-stakes: escalate to secondary approver after 24h. Low-stakes: consider auto-approve with timeout. Cleanup abandoned threads after 30 days.

4. Multi-approver 2-of-4 flow — implement outline?

interrupt() returns list of approvals. Track approver IDs. Continue when count >= k. Handle timeouts per approver. Audit each decision.

5. Approval fatigue — fix?

(1) Reduce gate count — only high-stakes. (2) Batch similar reviews (approve 10 SFT samples at once). (3) Sampling QA (auto-approve 90%, human check 10%). (4) Delegate to trusted sub-agent for routine. (5) Track approval time — if too fast (<2s), warn user.

7.3 · System Design Mock 1 — Stock Prediction System

45-min interview walkthrough using PredictStock as base. Requirements → high-level → components → deep-dive. Answer template + evaluator scoring rubric.

Level 7 · Interview · ~45 phút

🎯 Learning objectives

  • Structure 45-min system design answer
  • Communicate trade-offs explicitly
  • Handle follow-up questions
  • Score yourself với rubric

Prompt

Interviewer

"Design a stock prediction system cho VN market. 86 tickers, provide UP/DOWN/FLAT predictions với confidence. Users query API real-time cho trading decisions."

💡 System Design ML bằng ngôn ngữ đời thường

Xây nhà cho khách: Nếu bắt tay vào xây ngay không hỏi khách — sẽ ra căn nhà 5 phòng ngủ trong khi khách chỉ cần 2. Hỏi trước: bao nhiêu người ở? ngân sách? khi nào cần dọn vào? có yêu cầu đặc biệt (thang máy, sân vườn)?

ML system design: 5 phút đầu KHÔNG code, chỉ hỏi:

  • SLA: latency p95 < bao nhiêu? throughput QPS?
  • Accuracy: target bao nhiêu? có bias/fairness constraint?
  • Cost budget: $10/ngày hay $10k/ngày?
  • Data: bao nhiêu, có label, refresh rate?
  • User: retail hay B2B? Vietnam only hay global?

Skip step này = design chuông vàng nhưng khách cần chuông giấy.

1. Requirements gathering (5 min)

Ask clarifying questions before diving into design.

Q: How many users / QPS?
A: 1000 daily active, peak 50 QPS.

Q: Prediction horizon?
A: T+1, T+3, T+5 days.

Q: Latency SLA?
A: p95 < 500ms.

Q: Update frequency?
A: Predictions refresh daily post-market-close.

Q: What data available?
A: OHLCV history 5+ years, foreign flow, news headlines.

Q: Real money involved?
A: Advisory only, not auto-execute. Regulatory: disclaimer required.

Q: Existing infrastructure?
A: Postgres, some Redis, no GPU cluster yet.

3. Data flow (10 min)

Nightly (training + prediction)

1. 15:35 VN (post-close): fetch new day OHLCV from VCI API
2. Compute features (RSI, MACD, MA, foreign flow) → feature store
3. Predict for all 86 tickers with current model
4. Store predictions + explanations in Postgres (prediction_log)
5. Weekly: retrain on last 5 years, validate, register if better

Real-time (user query)

1. User → GET /api/predict/FPT
2. API → Redis cache lookup (TTL 5min)
3. Cache miss → Postgres prediction_log latest
4. Compose response: signal, confidence, features, disclaimer
5. Return + populate cache

Latency: ~20ms if cache hit, ~50ms if Postgres read (prediction đã precompute), ~200ms nếu phải compute model trực tiếp (fallback hiếm gặp — prediction thường đã có sẵn từ batch đêm trước)

4. Component deep-dive (15 min)

Model architecture (V18-inspired)

  • 2-stage XGBoost, cả 2 stage đều binary: Direction gate (DIR vs FLAT) → UP vs DOWN. Output 3-way UP/DOWN/FLAT là kết quả ghép của 2 stage binary, không có classifier 3-class nào
  • Per-ticker training (86 individual models)
  • Sample weights: class balance + recency decay + label clarity
  • Calibration: Platt (stage 1) + Isotonic (stage 2) — calibration = chỉnh model output score cho khớp xác suất thực tế (model nói "70% tin UP" thì thực tế phải đúng ~70% số lần). Platt = fit 1 đường sigmoid đơn giản (ít data cũng ổn). Isotonic = fit đường bậc thang tự do hơn, chính xác hơn nhưng cần nhiều data hơn để không overfit.
  • Composite confidence: weighted sum of 4 signals

Feature engineering

  • ~80 features: technical, flow, cross-asset, calendar
  • Compute in features_v18.py::build_v18_features() shared train + inference (no skew)
  • Test: hash input → hash features stable across runs

Serving

  • FastAPI + async Postgres
  • TTLCache in-memory (fast) → Redis (shared) → Postgres (source)
  • Docker container, 2 instances behind load balancer

Training pipeline

  • Airflow DAG: fetch → features → train per ticker (parallel workers) → validate → register
  • Time-series CV với gap (avoid label leak)
  • Optuna hyperparameter search (50 trials)
  • ECE calibration check (target < 0.02) — ECE (Expected Calibration Error): chia prediction thành bins theo confidence (0-10%, 10-20%...), so % thực tế đúng trong mỗi bin với confidence trung bình bin đó, lấy trung bình chênh lệch (weighted theo số sample). ECE thấp = "model nói bao nhiêu % tin thì đúng bấy nhiêu %" (well-calibrated), không phải chỉ accuracy cao.

Monitoring

  • Prediction accuracy vs actual outcome (label after T+5)
  • PSI on top-10 features (drift alert)
  • 7-day rolling hit rate per ticker (V20 Slice 5 pattern)
  • Latency, error rate, cost

5. Scaling considerations (5 min)

If 10× traffic

  • API: add instances behind LB, stateless scale horizontal
  • DB: read replicas + connection pooling
  • Cache: Redis cluster for larger dataset
  • Feature compute: batch offline, cache heavy features

If 10× tickers (860)

  • Train pipeline: parallelize across ticker workers
  • Consider group models (sector-level)
  • Storage: partition prediction_log by ticker + date

5.5 Capacity planning + rate limit (senior detail)

Capacity math — 50 QPS peak, p95 < 500ms

Assumption:
  - Cache hit rate 80% (predictions refresh daily, hot tickers repeat)
  - Cache-hit path: 20ms (Redis + serialize)
  - Cache-miss path: 50ms (Postgres query + compose — prediction đã precompute,
    không phải tính lại model; case hiếm phải compute trực tiếp ~200ms không tính vào average này)

Effective per-request latency = 0.8×20 + 0.2×50 = 26ms average

Concurrency requirement (Little's Law):
  N = throughput × latency = 50 req/s × 0.026s = 1.3 concurrent

→ 1 FastAPI worker (async) đủ handle. Chạy 2 replicas cho HA/rolling deploy.
💡 Little's Law bằng ngôn ngữ đời thường

Quán cafe có khách đến 50 người/giờ (throughput), mỗi người ngồi trung bình 30 phút (latency) → số khách ĐANG NGỒI trong quán cùng lúc (concurrency) = 50 × 0.5h = 25 người. Đó là công thức N = throughput × latency — dùng để tính cần bao nhiêu "chỗ ngồi" (worker/thread/connection) để phục vụ hết khách mà không ai phải đứng chờ ngoài cửa.

Postgres load:
  Cache miss rate 20% × 50 QPS = 10 QPS on Postgres
  Query: SELECT ... WHERE ticker=? AND date=today LIMIT 1 → 5ms indexed
  → 10 × 5ms = 50ms/s DB time = 5% of 1 core. Massive headroom.

Redis load:
  50 QPS × 2 ops (GET + SETNX) = 100 ops/s. Redis handles 100k+ ops/s. Non-issue.

Rate limit — token bucket per user

💡 Token bucket bằng ngôn ngữ đời thường

Mỗi user có 1 "xô" chứa tối đa burst token (ví dụ 20). Xô tự động rót thêm token vào với tốc độ rate token/giây (ví dụ 10/s), không vượt quá miệng xô. Mỗi request tiêu 1 token. Xô hết token → request bị từ chối (429) cho tới khi rót thêm. Ưu điểm so với đếm request đơn giản: cho phép burst ngắn hạn (xô đầy sẵn) nhưng vẫn giới hạn tốc độ trung bình dài hạn.

from redis import Redis

def rate_limit(user_id, rate=10, burst=20):
    # 10 req/s sustained, 20 burst
    key = f"rl:{user_id}"
    now = time.time()
    # Lua script atomic: current tokens = min(burst, tokens + rate*elapsed)
    tokens = redis.eval(TOKEN_BUCKET_LUA, keys=[key],
                        args=[rate, burst, now, 1])
    if tokens < 0:
        raise HTTPException(429, "rate limit exceeded")

5.7 Load shedding — khác Rate Limit (mục 5.5) thế nào khi CẢ HỆ THỐNG quá tải?

💡 Analogy

Rate limit (mục 5.5, token bucket) giới hạn TỪNG USER — công bằng, ngăn 1 user spam. Nhưng nếu TẤT CẢ user đều gửi request hợp lệ, đúng giới hạn, mà TỔNG LƯỢNG vẫn vượt quá khả năng phục vụ của CẢ HỆ THỐNG (VD 15:00 giờ đóng cửa, mọi trader cùng lúc check giá) — rate limit không giúp được gì (không ai vi phạm giới hạn cá nhân). Load shedding giải quyết bài toán KHÁC: khi hệ thống THẬT SỰ quá tải, chủ động TỪ CHỐI bớt request ÍT QUAN TRỌNG HƠN để cứu request QUAN TRỌNG — giống phòng cấp cứu bệnh viện quá tải: không từ chối HẾT bệnh nhân, mà ưu tiên ca nặng, hoãn ca nhẹ (tái khám định kỳ) lại.

Vấn đề cụ thể: hệ thống có sức chứa GIỚI HẠN (VD Postgres §5.5 tính được "massive headroom" ở tải bình thường, nhưng có mức tải NÀO ĐÓ sẽ vượt ngưỡng) — nếu không có cơ chế bảo vệ, hệ thống quá tải KHÔNG chỉ chậm đi TỪ TỪ mà thường SỤP HOÀN TOÀN (queue tràn, connection pool cạn, mọi request đều timeout — kể cả request đơn giản) — tệ hơn nhiều so với việc từ chối MỘT PHẦN request để phần còn lại vẫn chạy tốt.

# Load shedding — phân loại request theo ĐỘ QUAN TRỌNG, bỏ bớt loại ít quan
# trọng khi hệ thống báo hiệu "tôi đang quá tải":

PRIORITY = {
    "get_prediction":        1,   # CRITICAL — lý do chính user dùng app
    "get_price_realtime":    1,   # CRITICAL
    "get_historical_chart":  2,   # EXPECTED — quan trọng nhưng chịu được delay nhẹ
    "log_analytics_event":   3,   # BACKGROUND — không ảnh hưởng trải nghiệm chính
}

def handle_request(req):
    current_load = get_system_load()   # VD % connection pool đang dùng, queue depth
    if current_load > 0.9 and PRIORITY[req.type] >= 3:
        return Response(503, "Service busy, try again later")   # shed BACKGROUND trước
    if current_load > 0.97 and PRIORITY[req.type] >= 2:
        return Response(503, "Service busy")                     # shed cả EXPECTED
    # CRITICAL (priority 1) luôn được cố gắng phục vụ tới giới hạn cao nhất
    return process(req)

⚠️ Chỗ dễ nhầm nhất: Load shedding KHÔNG PHẢI rate limit "phiên bản mạnh hơn" — rate limit (mục 5.5) là PHÒNG NGỪA, áp dụng ĐỀU cho mọi user bất kể hệ thống có tải hay không (giới hạn cố định 10 req/s/user). Load shedding là PHẢN ỨNG, chỉ kích hoạt khi hệ thống THẬT SỰ đang quá tải (đo bằng tín hiệu thực: queue depth, connection pool usage, CPU) và áp dụng KHÔNG ĐỀU (ưu tiên request quan trọng, bỏ request ít quan trọng) — 2 cơ chế bổ sung cho nhau, không thay thế nhau: rate limit ngăn LẠM DỤNG, load shedding xử lý QUÁ TẢI HỢP LỆ (mọi user đều dùng đúng, chỉ là tổng cầu vượt cung).

Insight: nguyên tắc cốt lõi của load shedding là "degrade có kiểm soát tốt hơn sụp đổ hoàn toàn" — 1 hệ thống từ chối 10% request ÍT QUAN TRỌNG khi quá tải vẫn phục vụ TỐT 90% request còn lại; 1 hệ thống cố phục vụ 100% request khi quá tải thường kết thúc bằng việc KHÔNG phục vụ được request nào (queue timeout dây chuyền, connection pool cạn kiệt). Đây chính là lý do "graceful degrade" đã nhắc ở mục 6 Anti-patterns bên dưới (3-tier fallback: cache → heuristic → "NO SIGNAL") — về bản chất là 1 hình thức load shedding: khi model serving quá tải/lỗi, "shed" xuống mức phục vụ RẺ HƠN (heuristic) thay vì trả lỗi 500 hoàn toàn.

6. Failure modes

5 concerns interviewer expect
  1. Silent failure: model swap serves wrong version. Mitigation: version stamp + smoke test + consistency cron (V19.5 lesson)
  2. Data quality: VCI API return partial data → bad features. Mitigation: schema validation + freshness check
  3. Retrain drift: new model worse than old. Mitigation: A/B canary + rollback
  4. Compliance: prediction perceived as investment advice. Mitigation: disclaimer + advisory-only role
  5. Regulatory: VN SBV data restrictions. Mitigation: source VCI (licensed provider), audit trail

V18 architecture decision retrospective

V18 chọn: Hybrid batch + real-time + Postgres + In-process serving. Vì:

  1. Universe 86 tickers small → in-process serving đủ.
  2. Trading hours daily → hybrid batch precompute + real-time refresh work well.
  3. Business data + ML data cùng Postgres → operational simplicity.
  4. XGBoost model load rất nhanh (~200ms) → không cần persistent serving.

Khi cần scale lên: 10k tickers → TimescaleDB. Multi-language clients → gRPC service. GPU-based NN → KServe/Triton.

Insight quan trọng: System design không phải "chọn best tech". Là "chọn tech phù hợp với constraints hiện tại + roadmap 12 tháng". Enterprise architect chọn Kubernetes cho 5 dev + 100 users = over-engineer.

6.5 Anti-patterns (say aloud để score senior)

  1. Feature skew train vs serve: compute RSI khác nhau ở train pipeline vs API → prediction drift. Rule: shared features_v18.py::build_v18_features(), hash-checked cả 2 side.
  2. Model version implicit: "latest.pkl" symlink → không rollback được. Rule: immutable versioned dirs models/v20_20260701/.
  3. No calibration monitor: model confidence 0.9 nhưng actual accuracy 0.6 → user tin nhầm. Track ECE weekly.
  4. Cache invalidate on write not on model swap: swap model xong cache vẫn serve prediction cũ → mismatch signal vs displayed features (V19.5 lesson).
  5. No graceful degrade: DB down → 500 error. Rule: 3-tier fallback (cache → heuristic → "NO SIGNAL").

7. Follow-up questions

Q: "Model accuracy 60% - deploy or not?"
A: Depends on baseline (3-class random = 42%) + business ROI.
   Skill score = (0.60-0.42)/(1-0.42) = 0.31 → có edge.
   If PnL simulation positive after cost → yes.

Q: "How measure success post-deploy?"
A: (1) Prediction hit rate (rolling 30d) vs baseline.
   (2) BUY signal PnL simulation (paper trade).
   (3) Calibration ECE monitoring.
   (4) User engagement (view rate, session length).

Q: "V18 fails, degrade gracefully?"
A: 3 fallback tiers: (1) Cached prediction (up to 24h old with WARN),
   (2) Baseline heuristic (RSI + MA rule), (3) Return "NO SIGNAL" — user knows model unavailable.

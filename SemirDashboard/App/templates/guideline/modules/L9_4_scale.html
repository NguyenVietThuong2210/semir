ZeRO stages (DeepSpeed)

  • ZeRO-1: shard optimizer states (Adam m,v). Cuts 4× vs DDP.
  • ZeRO-2: + shard gradients. Cuts 8×.
  • ZeRO-3: + shard params. Cuts N× (# GPUs). Equivalent to FSDP.

Tensor Parallel — chi tiết Megatron split

# Attention layer: split heads across GPUs (col-parallel)
#   W_q, W_k, W_v shape [d_model, d_model]
#   Split col: GPU_0 gets d_model/N cols → attention heads 0..H/N
#   Sau attention: AllReduce concat outputs
#
# MLP layer: 2-stage split
#   Layer 1 (up-projection): col-parallel (split output dim)
#   Layer 2 (down-projection): row-parallel (split input dim)
#   → chỉ 1 AllReduce per MLP block (không 2)
#
# Communication cost: O(batch × seq × d_model) per layer
# Chỉ efficient khi high-bandwidth (NVLink 900GB/s), không PCIe (32GB/s)

Pipeline Parallel — bubble problem

# Naive PP: GPU_0 layers 0-8, GPU_1 layers 9-16, ...
# Timeline (T = forward+backward per micro-batch):
#   GPU_0: [====F====] idle    idle    [====B====]
#   GPU_1: idle      [====F====][====B====]
# Bubble = idle time = (N-1) × T
# Utilization (M=1 micro-batch, naive) = 1/N → giảm khi N tăng
# (khớp công thức bubble tổng quát (N-1)/(M+N-1) dưới đây khi M=1: bubble=(N-1)/N, utilization=1/N)
#
# Fix: 1F1B (one-forward-one-backward) hoặc interleaved schedule
# Bubble 1F1B: (N-1)/(M+N-1) với M = # micro-batches
# → M >> N để bubble small

Expert Parallelism (MoE — Mixture of Experts)

# DeepSeek-V3, Mixtral, GPT-4 rumored MoE
# Model có E experts (VD 8 experts × 7B params = 56B total)
# Nhưng chỉ 2 experts active per token (top-2 routing) → 14B FLOPS
#
# Expert Parallel: 8 experts distribute across 8 GPUs
# Router (small NN) decides token → expert
# Token dispatch: AllToAll communication (expensive!)
#
# Trade-off:
#   ✓ Sparse compute (bigger model, same FLOPS as dense)
#   ✗ AllToAll bottleneck (need high-bandwidth interconnect)
#   ✗ Load balance issue (some experts hot, others cold)
#
# Auxiliary loss: encourage uniform expert usage

3D parallelism (Megatron-Turing NLG 530B)

# Combine TP + PP + DP
# TP=8 (within node, NVLink)
# PP=8 (across nodes)
# DP=32 (replicate whole 3D setup)
# Total: 8 * 8 * 32 = 2048 GPUs

# Llama-70B, mixed precision (fp16 weights, fp32 master + optim)
params = 70e9

# Per-param memory:

# Total: 16 bytes/param → 70B * 16 = 1.12 TB

# Plus activations (batch, seq_len, hidden):
# batch=4, seq=4096, hidden=8192, layers=80
# activation ≈ 4 * 4096 * 8192 * 80 * 2 = ~21 GB (with checkpointing)

# → cần 15+ A100 80GB just for weights, without ZeRO
🎯 Deep-dive — Distributed training: vì sao 8 GPU chỉ = 5× throughput, không phải 8× (chi tiết dễ hiểu)

Điều gây shock: Bạn thuê 8 GPU H100. Naive expectation: training nhanh 8×. Thực tế: 5-6× (best case), thường 3-4×. 30-50% GPU idle. Đây là communication overhead — hầu hết ML engineer không hiểu, kết quả là scale không hiệu quả và tốn tiền vô ích.

Bước 1 — Naive Data Parallel hoạt động thế nào

  1. Model 70B params copy vào 8 GPU (mỗi GPU đầy đủ model).
  2. Batch 32 chia thành 4/GPU. Mỗi GPU compute forward + backward → gradient local.
  3. AllReduce: 8 GPU chia sẻ gradient để consistent. Mỗi GPU nhận gradient trung bình của tất cả 8.
  4. Mỗi GPU update model với gradient chung.

Bước 2 — AllReduce là bottleneck

Ring-AllReduce (thuật toán chuẩn, NCCL dùng) có chi phí ≈ O(P / bandwidth) — gần như KHÔNG phụ thuộc N (số GPU) với N đủ lớn, vì thuật toán ring chia nhỏ dữ liệu và pipeline việc truyền giữa các GPU thay vì mỗi GPU gửi riêng cho N-1 GPU khác:

  • P = param size (70B params × 2 bytes = 140GB gradients)
  • bandwidth = tốc độ interconnect

Với 8 GPU + NVLink 600 GB/s: mỗi AllReduce ≈ 140GB / 600GB/s = ~0.23s. Nếu forward+backward chỉ 2s → AllReduce chiếm 0.23/(2+0.23) ≈ 10% mỗi step.

Nhưng cross-node (không NVLink, chỉ InfiniBand 25 GB/s): AllReduce = 140GB / 25GB/s = 5.6s. Nếu compute 2s → overhead 74%. GPU idle 74% thời gian.

Bước 3 — Đây là why interconnect matter HƠN GPU compute

Con số biết nói: Cluster A với 64 A100 + NVLink + InfiniBand: train Llama-70B trong 21 ngày. Cluster B với 64 A100 + PCIe (không NVLink): 3 tháng. Cùng GPUs, cùng model — chỉ khác interconnect = 4.3× thời gian.

Analogy đời thực — dây chuyền lắp ráp:

  • GPU = công nhân (làm nhanh).
  • Interconnect = băng chuyền (vận chuyển bộ phận giữa công nhân).

Nếu băng chuyền chậm → công nhân đứng chờ → dây chuyền không tăng tốc dù thuê thêm công nhân. Đây là why cluster design PHẢI ưu tiên interconnect + GPU balance.

Vì sao Model > 100B cần 3D Parallelism?

Vấn đề: GPT-3 175B, mỗi param FP16 = 2 bytes → 350GB. A100 80GB không fit. Data Parallel (full model per GPU) không dùng được.

Solution — chia model theo 3 axes:

1. Tensor Parallel (TP): chia 1 layer thành 2 GPU. Ví dụ ma trận W (4096×4096) chia đôi cột thành W_left (4096×2048) và W_right. Compute matmul song song. Communication cần every layer → phải intra-node NVLink. TP typical = 2-8 (trong 1 node).

2. Pipeline Parallel (PP): chia layers thành các stage. Layer 1-10 trên GPU 1, layer 11-20 trên GPU 2, etc. Communication ít (chỉ activations qua stage boundaries) → dùng inter-node InfiniBand OK.

Vấn đề PP: "bubble" — GPU 2 idle chờ GPU 1 finish stage. Fix bằng micro-batching (GPipe): chia batch 32 thành 8 micro-batch. GPU 1 xong micro 1 → sang micro 2 → GPU 2 làm micro 1. Overlap → bubble giảm 8×.

3. Data Parallel (DP): replicate the whole 2D setup (TP × PP). Chia batch across replicas.

Combine — Megatron-Turing NLG 530B:

  • TP = 8 (trong node, NVLink)
  • PP = 35 (across nodes)
  • DP = 32 (replicate)
  • Total: 8 × 35 × 32 = ~9000 GPUs

Train được nhờ pattern này. Không có 3D parallel = train được cùng lắm 30B model.

ZeRO / FSDP — đơn giản hơn 3D nhưng chậm 20-30%

Insight ZeRO: Với Data Parallel, mỗi GPU giữ full copy của params + gradients + optimizer states. 70B model:

  • Params FP16: 140GB
  • Gradients FP16: 140GB
  • Optimizer states (Adam m, v FP32): 560GB
  • Total: 840GB per GPU. Không GPU nào fit.

Nhưng nếu 8 GPU shard: mỗi GPU chỉ giữ 1/8 params + grads + optim = 105GB. Fit A100 80GB nếu bỏ activations.

3 stages ZeRO:

  • ZeRO-1: shard optimizer states only. Đơn giản, tiết kiệm 4×.
  • ZeRO-2: + shard gradients. Tiết kiệm 8×.
  • ZeRO-3 (= FSDP): + shard params. Tiết kiệm N× (# GPU).

Trade-off: ZeRO-3 phải AllGather params từ shards trước mỗi forward pass. Communication overhead 20-30% cao hơn pure DP. Nhưng đơn giản hơn 3D parallel (không phải reshape model).

Cheat sheet chọn strategy:

PagedAttention — vì sao inference breakthrough

Vấn đề serving: Khác training (fixed batch), serving requests đến/đi ngẫu nhiên, sequence length khác nhau. Naive allocation KV cache contiguous → fragmentation:

  • Request A dài 2000 tokens, cấp block 4000 (dự phòng)
  • Request A finish → free block 4000
  • Request B cần 5000 tokens → không dùng được block 4000 (chỉ có 4000)
  • Fragmentation 60-80% memory GPU.

PagedAttention insight: Quản KV cache như OS quản virtual memory. Chia thành pages nhỏ (16 tokens/page). Non-contiguous allocation. Request có thể "wire" cache từ scattered pages.

Kết quả: Fragmentation 60-80% → 4%. Cùng GPU serve 4× throughput. Cùng revenue infrastructure = 4× profit margin. Đây là why vLLM/SGLang thắng HuggingFace vanilla transformers cho production LLM serving.

Khi cơ chế vỡ — communication dominates ở batch nhỏ

Small batch (32) → compute nhanh (0.2s) → AllReduce overhead 0.5s (2.5× compute). GPU idle 71%. Fix: Gradient accumulation — chạy N micro-batches trước 1 AllReduce. Effective batch = 32 × N. Communication phân bổ trên N steps → overhead 1/N.

Nhưng tăng effective batch → cần scale LR. Rule: linear scaling (Goyal 2017) — batch × 2 → LR × 2. Hoặc √-scaling (Krizhevsky 2014). Không scale → converge tệ.

Đây là why hyperparams recipe từ paper nhỏ (batch 32) KHÔNG dùng được trực tiếp cho cluster (batch 32k). Phải scale LR + warmup + học rate schedule.

Take-away tổng hợp:

  1. Distributed training = communication problem, không phải compute. 8 GPU ≠ 8× throughput.
  2. Interconnect (NVLink 600GB/s vs InfiniBand 25GB/s) quyết định efficiency hơn GPU speed.
  3. Model >100B cần 3D parallel (TP + PP + DP). ZeRO-3 chậm hơn 20-30% nhưng đơn giản hơn.
  4. Serving khác training — PagedAttention giải quyết fragmentation 60-80% → 4× throughput.
  5. Batch scaling cần LR scaling — không copy recipe từ paper batch 32 cho cluster batch 32k.

3. vLLM — PagedAttention + Continuous Batching

Problem

  • KV cache dominates memory at inference
  • Static batching wastes GPU khi sequences kết thúc lệch nhau
  • Traditional attention allocates contiguous KV — fragmentation waste 60-80%

PagedAttention (Kwon 2023)

  • KV cache = pages (like OS virtual memory), 16 tokens/page
  • Non-contiguous storage, block table maps logical → physical
  • Zero fragmentation, sharing between beams (copy-on-write)

Continuous batching

# Static batching:
# batch = [req1, req2, req3, req4]
# Wait until all finish → next batch. Waste GPU idle.

# Continuous (iteration-level):
# Every step, new requests can join, finished ones leave.
# Throughput 5-20× higher (Yu et al 2022, Orca).

4. Speculative decoding + variants

Standard speculative (Leviathan 2023)

  • Small draft model generates K tokens
  • Large target model verifies in parallel (1 forward pass, KV cache trick)
  • Accept longest prefix matching target's argmax
  • 2-3× speedup with equivalent output distribution

Medusa

  • Multiple decoding heads on same model predict N tokens ahead
  • No separate draft model needed
  • Trained via head fine-tuning

EAGLE-2

  • SOTA cuối 2024, dynamic tree drafting
  • 3-5× speedup, no quality loss

7. Interview design — "serve Llama-70B at 1000 QPS, p95 < 500ms"

Full answer template
  1. Model choice: Llama-70B AWQ 4-bit → fits 2× A100 80GB with room for KV cache
  2. Serving: vLLM cluster, tensor parallel=2, continuous batching, PagedAttention
  3. Speculative: EAGLE-2 → 3× throughput. Draft = same model with medusa heads.
  4. Scaling: Assume avg 200 in + 100 out tokens/req. Single vLLM instance ~30 QPS at p95 500ms → need ~40 instances. Route via NGINX + least-loaded.
  5. Cache: SGLang-style radix cache cho system prompt (10× hit rate cho agent workloads)
  6. Fallback: 5% traffic to smaller model (Llama-8B) via router when queue depth > threshold. Graceful degrade.
  7. Monitoring: prom + grafana. Track: TTFT (time to first token), TPOT (time per output token), queue depth, KV cache utilization, GPU SM utilization.
  8. Cost: 40 A100 80GB × $2/hr ≈ $58k/mo. Compare to API cost: 1000 QPS × 100 out tokens × 86400s × 30 = 259B tok/mo × $15/1M = $3.9M/mo. Self-host wins ≈67× ($3.888M / $57.6k).

8. Case study — PredictStock ML training scale

Không cần distributed nhưng vẫn có principle

V18 unified train: 86 tickers × 3 horizons × 30 min = ~129 GPU-hour serial.

Parallelization applied:

  • Tickers train independently → embarrassingly parallel across CPU workers (docker exec ProcessPool 8)
  • 3 horizons per ticker chạy async
  • Total real time: 129h / 8 workers ≈ 16.1h

Lesson: 1st optimization là data parallel embarrassingly parallel dimension trước khi think TP/PP. Applies to ML backtest, hyperparam sweep, RAG index build.

🎯 Deep-dive — Request routing, GPU scheduling, cost/token vs utilization (VN scenario)

Analogy VN — cảng Cát Lái phân xe container

Cảng có N cửa (GPU), xe container (request) tới liên tục. Có 3 chiến lược:

  • Round-robin = phân đều theo thứ tự → cửa nhanh vẫn phải chờ xe cồng kềnh ở cửa chậm. Utilization ~50%.
  • Least-loaded = chọn cửa ít xe nhất → tốt hơn nhưng bỏ qua "xe này chở gì" (short vs long context).
  • Prefix-aware (SGLang RadixAttention) = xe cùng bill of lading (shared prompt prefix) gom về cùng cửa → tận dụng KV cache hit. Utilization ~85%+.

Anti-pattern VN

  • Chạy 1 request/GPU: sm_util ~5%, cost/token cao 20×. Fix: continuous batching (vLLM default).
  • TP cross PCIe: 8 GPU trên 2 host qua PCIe → AllReduce nghẹt. Fix: TP intra-node, PP inter-node.
  • Đo latency thay throughput: benchmark 1 req/lần → không biết throughput dưới load. Đo p50/p95/p99 dưới concurrency 32/64/128.
  • Không tách prefill vs decode: prefill compute-bound, decode memory-bound. Mixing → utilization thấp cả 2. Fix: disaggregated serving (DeepSeek 2024).

Interview Q&A

  1. Q: Serve Llama-70B 1000 QPS, budget $X — bạn thiết kế thế nào? A: (1) Quantize INT4/FP8 (fit 1×H100 80GB). (2) vLLM với continuous batching + PagedAttention. (3) TP=2 nếu context dài. (4) Speculative decoding EAGLE-2 (2-3× throughput). (5) Router prefix-aware để hit KV cache. (6) Autoscale GPU pool theo p95 latency SLO.
  2. Q: Prefill vs decode phase khác gì? A: Prefill = xử lý input prompt 1 lần (compute-bound, parallel token). Decode = generate 1 token/lần (memory-bound vì đọc full KV cache mỗi step). Ratio prefill:decode quyết định optimization strategy.
  3. Q: Cost/token vs GPU utilization — quan hệ? A: Không tuyến tính. Utilization 100% có thể vẫn cost cao nếu throughput thấp (memory-bound). Metric đúng: $ / 1M output tokens, không phải $ / GPU-hour.
  4. Q: KV cache size cho Llama-70B, batch=32, seq=8k? A: 2 (K+V) × 80 layers × 8k tokens × 8192 hidden × 2 bytes (fp16) × 32 batch = ~670GB. Vượt xa 1 GPU → paged + tiered (HBM → CPU RAM offload).
  5. Q: Dead-letter queue trong distributed inference? A: Request timeout/OOM → không retry vô hạn (loop hại). Push vào DLQ với metadata (input, error, retry_count). Alert nếu DLQ growth > threshold. Root cause thường: input quá dài, model degrade, GPU straggler.

✅ QA Gate

1. DDP vs FSDP — khi nào chuyển?

DDP khi model fit 1 GPU (replicate). FSDP (ZeRO-3) khi model > GPU memory, muốn giữ DP semantics. Trade-off: FSDP có AllGather param overhead mỗi forward → chậm 20-30% so DDP nhưng fit model to hơn.

2. PagedAttention giải quyết gì?

KV cache fragmentation. Naive: contiguous alloc waste 60-80% memory khi sequences varying length. Paged: OS-style pages 16 tokens, non-contiguous. Cho phép batch to hơn 2-4× → throughput tăng.

3. Continuous batching benefit?

Static batch wait cho slowest req finish. Continuous (iteration-level) cho req mới join giữa batch. 5-20× throughput (Orca 2022). Standard trong vLLM/TGI/SGLang.

4. Speculative decoding — mất quality?

Với sampling-based verification (Leviathan 2023), distribution equivalent với greedy. Nghĩa là output identical statistically. 2-3× speedup free. EAGLE-2 hiện SOTA 3-5×.

5. Chọn INT4 quantization — GPTQ vs AWQ?

AWQ (activation-aware weight quant) tốt hơn GPTQ khi model có activation outliers (large models). GPTQ ổn định general. Cả 2 <2% quality drop trên MMLU. Combined with FP8 activations = tương lai H100/B100.

Bước 2 — Duck typing là gì? (khái niệm dễ trước)

Python không ép bạn khai báo kiểu dữ liệu trước khi dùng. Một hàm nhận tham số x có thể hoạt động với bất kỳ object nào có method/thuộc tính đúng tên mà hàm cần — không quan tâm object đó "là gì".

def total_volume(ticker_list):
    return sum(t.volume for t in ticker_list)
# Hàm này chạy được với list Ticker, list Stock, hay bất kỳ object nào
# có thuộc tính .volume — Python không kiểm tra "kiểu" trước khi chạy.

Câu nói kinh điển: "nếu nó đi như vịt, kêu như vịt, thì nó là vịt" — Python không hỏi "bạn có phải class Duck không?", chỉ hỏi "bạn có .quack() không?".

Cái giá phải trả: lỗi type chỉ lộ ra khi code chạy tới dòng đó, không phải lúc viết code. Đây là lý do dự án vẫn chạy mypy — một static type-checker riêng — để bắt trước một phần lớp lỗi này (xem mục 8).

Bước 3 — GIL (Global Interpreter Lock) — điểm học thuật quan trọng nhất

Đây là phần khó nhất của module này. Đọc chậm.

Định nghĩa: CPython (bản Python phổ biến nhất, dự án này dùng) chỉ cho phép 1 thread thực thi bytecode Python tại 1 thời điểm trong 1 process — dù máy có 16 core, dù code tạo ra 100 thread.

BướcĐiều gì xảy ra
1Tạo 2 thread A và B trong cùng 1 Python process.
2Cả 2 thread đều muốn chạy Python bytecode (VD 1 vòng lặp tính toán).
3GIL chỉ cấp "quyền chạy" cho 1 thread tại 1 thời điểm — thread kia phải đợi, dù có core rảnh.
4Kết quả: 2 thread CPU-bound trên Python không nhanh hơn 1 thread — đôi khi còn chậm hơn vì tốn overhead chuyển đổi.

Điểm mấu chốt hay bị hiểu sai: GIL không khoá CPython suốt 100% thời gian — nó chỉ khoá trong lúc thread đang chạy bytecode Python. Khi 1 thread gọi 1 hàm I/O cấp thấp (socket recv, đọc file, time.sleep) — tức là đang chờ hệ điều hành, không chạy bytecode gì cả — CPython chủ động nhả GIL ra trong lúc chờ, để thread khác được chạy. Đây là lý do threading VẪN hoạt động thật cho I/O-bound work — không phải nó "không dùng được", chỉ là nó không phải lựa chọn tối ưu nhất trong dự án này (xem bảng so sánh đầy đủ ở mục 📊 bên dưới).

  • I/O-bound (chờ mạng, chờ DB trả kết quả) → cả threading lẫn asyncio đều chạy được nhờ cơ chế nhả GIL ở trên — khác nhau ở chi phí/khả năng mở rộng, không phải khác nhau ở "chạy được hay không". Dự án chọn asyncio vì lý do cụ thể (xem bảng so sánh).
  • CPU-bound (train XGBoost, tính ma trận lớn) → CHỈ multi-process mới giúp (mỗi process có GIL riêng, không chia sẻ) — VD Docker container riêng, hoặc ProcessPoolExecutor. Cả threading lẫn asyncio đều KHÔNG giúp gì ở đây, vì tính toán thuần Python luôn cần giữ GIL suốt thời gian chạy, không có chỗ nào để "nhả ra".
⚠️ Sai lầm thường gặp #1 — 2 hướng hiểu sai ngược nhau, cả 2 đều sai

Hiểu sai (a): nghĩ asyncio chạy 2 đoạn code Python thật sự song song trên 2 core. SAI — nó vẫn chạy tuần tự trên 1 thread, chỉ khác là khi 1 coroutine await một I/O, event loop chuyển ngay sang coroutine khác thay vì đứng im chờ.

Hiểu sai (b) — dễ mắc hơn, và dễ bị hiểu lầm từ chính cách trình bày GIL ở trên: nghĩ threading "vô dụng" hoặc "không hoạt động" cho I/O-bound vì GIL. SAI — threading vẫn tăng tốc thật cho I/O-bound (nhờ cơ chế nhả GIL lúc syscall chặn), đây là pattern hợp lệ và được dùng rộng rãi (VD concurrent.futures.ThreadPoolExecutor với thư viện requests). Cái GIL thật sự chặn là 2 thread cùng chạy bytecode CPU-bound, không phải "mọi hình thức threading".

📖 Cập nhật — GIL không còn "vĩnh viễn bất biến" ở tầm CPython, nhưng chưa ảnh hưởng dự án này

Python 3.14 (phát hành 10/2025) chính thức đưa free-threaded build (PEP 703/779) lên Phase 2 — "officially supported" nhưng vẫn opt-in, không phải mặc định: phải cài riêng biến thể python3.14t, còn bản mặc định python3.14 vẫn chạy với GIL bật như bình thường. Phase 3 (no-GIL là build duy nhất) vẫn chưa có ngày chốt. Dự án này chạy Python 3.12-slim (backend/Dockerfile dòng 1) — bản GIL mặc định — nên toàn bộ lý luận GIL/asyncio/multi-process ở trên vẫn đúng 100% cho codebase hiện tại; free-threading chỉ liên quan nếu dự án chủ động nâng cấp lên 3.14t sau này.

🔢 Ví dụ cụ thể

So sánh 3 cách viết cho cùng 1 việc: gọi API giá cổ phiếu cho 86 ticker (HIGHLIGHT_GROUP) — cả 2 cách đầu đều CHẠY ĐƯỢC và ĐỀU nhanh hơn tuần tự, khác nhau ở chi phí tài nguyên và khả năng mở rộng, không phải "1 cái đúng 1 cái sai".

# Cách 1 — threading: HOẠT ĐỘNG THẬT cho I/O-bound, nhưng tốn tài nguyên hơn
import concurrent.futures, requests

def fetch_price(ticker):
    resp = requests.get(f"/api/stocks/{ticker}")  # blocking call
    return resp.json()

with concurrent.futures.ThreadPoolExecutor(max_workers=86) as pool:
    results = list(pool.map(fetch_price, tickers))
# Trong lúc thread A đang chờ requests.get() trả về (socket recv, GIL đã nhả),
# thread B/C/... được chạy — 86 request THẬT SỰ overlap nhau về thời gian chờ.
# Đánh đổi: mỗi OS thread tốn ~8MB stack mặc định + chi phí context-switch của
# hệ điều hành — với 86 thread vẫn ổn, nhưng không scale tới hàng nghìn.

# Cách 2 — asyncio: cũng hoạt động cho I/O-bound, nhẹ hơn nhiều ở quy mô lớn
async def fetch_price(ticker, session):
    async with session.get(f"/api/stocks/{ticker}") as resp:
        return await resp.json()
# Khi 1 coroutine await I/O, event loop chuyển ngay sang coroutine khác —
# không tốn overhead tạo OS thread (1 coroutine ~vài KB, không phải ~8MB),
# scale tới hàng nghìn request đồng thời trên 1 thread duy nhất.

Vậy vì sao dự án chọn asyncio thay vì threading? Không phải vì threading "sai" — mà vì 3 lý do cụ thể: (1) chi phí bộ nhớ/thread thấp hơn hẳn khi cần mở rộng lên nhiều kết nối đồng thời; (2) hệ sinh thái DB đã cam kết async từ đầu — asyncpg (driver Postgres) chỉ có API bất đồng bộ, trộn với code threading sẽ phải bọc thêm lớp run_in_executor phiền phức; (3) tránh hẳn nhu cầu dùng Lock/Semaphore để bảo vệ state dùng chung — asyncio là cooperative (code tự nhường quyền chạy ở đúng chỗ await), không có 2 coroutine nào "chen ngang" giữa 2 dòng code như 2 OS thread có thể làm.

Ví dụ thật từ repo — backend/predict/engine.py dòng 785 khai báo async def _get_or_build_cohort_cached(db_session): toàn bộ pipeline fetch OHLCV + tính feature + gọi model đều là async def, vì phần lớn thời gian dành cho chờ DB/network trả kết quả, không phải tính toán CPU.

⚠️ Sai lầm thường gặp

#2 — Mutable default argument: def add_ticker(t, cache=[]): cache.append(t); return cache — tham số mặc định [] chỉ được tạo 1 lần duy nhất khi hàm được định nghĩa, không phải mỗi lần gọi. Gọi hàm 2 lần không truyền cache, lần 2 sẽ thấy dữ liệu còn sót từ lần 1 — bug rất khó phát hiện vì code "trông đúng". Fix: def add_ticker(t, cache=None): cache = cache or []; ....

#3 — Quên await trong hàm async: gọi fetch_price(ticker) mà quên await phía trước sẽ không lỗi ngay — nó trả về 1 coroutine object chưa chạy, không phải kết quả thật. Code phía sau dùng nhầm object này sẽ lỗi ở 1 chỗ hoàn toàn khác, khó truy ngược lại nguyên nhân gốc.

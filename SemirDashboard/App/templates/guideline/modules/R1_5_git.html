R1.5 · Git & Version Control — kỷ luật thay đổi trên hệ thống sống

Vì sao dự án cấm tuyệt đối ALTER TABLE thủ công và git commit --amend sau khi hook fail — 2 quy tắc sinh ra từ 1 sự cố thật, không phải sở thích cá nhân.

Độ khó: Dễ · Roadmap AI Engineering · Track 1

🎯 Mục tiêu học

  • Viết đúng 1 commit message theo Conventional Commits format, dựa trên convention thật đang dùng trong git log của repo.
  • Giải thích chính xác cơ chế git commit --amend và vì sao dùng nó sau khi pre-commit hook fail sẽ phá commit trước đó.
  • Giải thích được vì sao "thay đổi không nằm trong version control thì coi như không tồn tại" — liên hệ sự cố thật đã xảy ra với prediction_log.
  • Đọc hiểu cấu trúc backend/db_migrations.py và giải thích vì sao nó "idempotent" (chạy lại nhiều lần vẫn an toàn).

📍 Vị trí & độ khó

Không có prerequisite kỹ thuật — Git là công cụ độc lập với ngôn ngữ lập trình. Có thể đọc module này ở bất kỳ thời điểm nào trong chuỗi 6 file.

Độ khó: Dễ về mặt thao tác (vài lệnh cơ bản), nhưng đòi hỏi hiểu đúng mô hình tư duy — Git không phải "công cụ lưu file", mà là hệ thống snapshot có lịch sử không thể âm thầm sửa lại.

💡 Analogy

Git giống nhật ký phẫu thuật của bệnh viện — mỗi lần "mổ" (sửa code) phải ghi lại chính xác đã làm gì, vì sao, và có thể tua lại (revert) nếu bệnh nhân (hệ thống) phản ứng xấu.

Một bác sĩ không bao giờ tẩy xoá trang nhật ký của ca mổ hôm qua để "sửa lại cho gọn" — nếu ghi sai, họ thêm 1 trang mới đính chính, giữ nguyên trang cũ. git commit --amend giống hành động "tẩy xoá trang cũ" — chỉ an toàn khi bạn chắc chắn trang đó chưa từng được ai khác nhìn thấy.

📖 Cơ chế chi tiết

Bước 1 — Khái niệm nền: commit, staging area, branch (dễ)

Khái niệmÝ nghĩa
Commit1 "ảnh chụp" (snapshot) toàn bộ trạng thái file tại 1 thời điểm, có ID duy nhất (hash)

Thao tác an toàn cơ bản, luôn làm trước khi hành động:

git status                      # xem trạng thái hiện tại trước khi làm gì
git diff                        # xem đúng nội dung sẽ commit
git log --oneline -10           # học convention message trước khi viết mới

Bước 2 — Conventional Commits: convention thật của dự án

Đọc trực tiếp git log --oneline -15 của repo, thấy rõ format nhất quán:

docs: clarify V20 probe is a direct A/B on v22 + add expected-improvement column
docs: final corrected AI Predict v22 numbers - 19/258 trust list
fix(ai-predict): add releaseTag to the tier3-skip early-return path too
feat(ai-predict): v22 release tag live on API + status script
fix(ai-predict): 3 bugs found by independent verification (Giai đoạn 0+1)

Format: <type>(<scope>): <mô tả ngắn, thì hiện tại>.

TypeKhi nào dùng
featThêm tính năng/khả năng mới
fixSửa bug
docsChỉ thay đổi tài liệu/plan, không đổi code chạy
refactorĐổi cấu trúc code, hành vi không đổi
testThêm/sửa test
choreViệc lặt vặt (dependency, config) không ảnh hưởng logic chính

Lợi ích thực tế, không chỉ để "đẹp": git log --oneline | grep '^fix' lọc ra toàn bộ bug fix trong lịch sử ngay lập tức — không thể làm vậy nếu message tự do kiểu "update stuff" hay "sửa lỗi".

Bước 3 — Vì sao "luôn tạo commit mới, không amend"

Đây là quy tắc bắt buộc, không phải sở thích. Để hiểu tại sao, cần hiểu đúng cơ chế --amend:

BướcĐiều gì thực sự xảy ra
1Bạn chạy git commit, nhưng pre-commit hook (VD lint) fail.
2Vì hook fail, Git không tạo commit mới — commit đó chưa từng tồn tại.
3Bạn sửa lỗi, rồi chạy git commit --amend "để sửa commit vừa fail".
4--amend không biết gì về ý định "sửa commit vừa fail" — nó chỉ làm đúng 1 việc: sửa commit gần nhất đã tồn tại (commit TRƯỚC ĐÓ, hợp lệ) — âm thầm ghi đè lên nó.

Cách đúng: khi hook fail, sửa lỗi → git add lại → tạo commit mới, không amend.

Bước 4 — "Không trong Git = không tồn tại" — bài học từ sự cố thật

CLAUDE.md ghi rõ: "Schema changes: use the idempotent migration runner (backend/db_migrations.py)... never a manual one-off ALTER TABLE — after a manual, uncaptured ALTER TABLE was lost in an infrastructure reset and broke prediction_log silently for 8+ days."

Chuỗi sự kiện: (1) ai đó chạy ALTER TABLE trực tiếp trên container đang chạy → (2) thay đổi này không nằm trong bất kỳ commit/file migration nào → (3) hạ tầng bị reset (VD volume Docker bị xoá) → (4) schema quay về trạng thái cũ, không ai biết đã từng đổi gì vì không có record nào trong version control → (5) prediction_log hỏng thầm lặng 8+ ngày trước khi phát hiện.

Bài học tổng quát: nếu 1 thay đổi chỉ tồn tại dưới dạng lệnh chạy tay 1 lần, nó không thực sự "tồn tại" theo nghĩa có thể tái lập — phải nằm trong file được commit.

🔢 Ví dụ cụ thể

backend/db_migrations.py — migration runner thật, đọc trực tiếp (dòng 1-40):

"""
Idempotent startup schema migrations + integrity checks.

Every migration is applied exactly once, tracked via `schema_migrations`.
Unlike init.sql (which only runs on first-ever Postgres volume init), this
runs on EVERY app startup — so a manually-applied-then-lost schema change
... cannot silently regress after a volume reset ever again.
"""

MIGRATIONS: list[tuple[str, str]] = [
    (
        "2026-08-08_prediction_log_veto_columns",
        """
        ALTER TABLE prediction_log
            ADD COLUMN IF NOT EXISTS veto_reason TEXT,
            ADD COLUMN IF NOT EXISTS veto_applied_factor DOUBLE PRECISION
        """,
    ),
    # ... mỗi migration có ID duy nhất, append-only — KHÔNG BAO GIỜ sửa/xoá
    # 1 entry cũ đã ship, kể cả để sửa 1 lỗi chính tả trong SQL của nó.
]

Điểm mấu chốt: mỗi migration nằm trong file, được commit, chạy lại tự động mỗi lần app khởi động (không chỉ 1 lần tay) — kể cả khi volume DB bị reset hoàn toàn, migration này tự chạy lại và khôi phục đúng schema. Đây chính là cách sự cố "8+ ngày" ở Bước 4 không thể tái diễn.

🎯 Ứng dụng dự án

Mọi thay đổi formula (backend/predict/senior_score.py) nếu cần đổi schema DB phải đi qua backend/db_migrations.py — không có ngoại lệ, kể cả khi "chỉ thêm 1 cột tạm để test". Commit theo Conventional Commits để git log --oneline | grep '^fix(ai-trader)' vẫn tra cứu được lịch sử fix nhiều tháng sau — pattern này đã dùng nhất quán qua hàng trăm commit thật của repo (xem git log --oneline -30).

⚠️ Sai lầm thường gặp

#1 — git add -A/git add .: dễ commit nhầm file bí mật (.env) hoặc file build rác. Luôn add file cụ thể theo tên khi không chắc chắn 100% những gì đang thay đổi.

#2 — git commit --amend sau khi pre-commit hook fail: phá commit TRƯỚC ĐÓ vì commit vừa fail chưa từng được tạo ra (xem Bước 3). Luôn sửa lỗi rồi tạo commit MỚI.

📋 QA Gate

  • Viết đúng 1 commit message theo Conventional Commits dựa trên git log thật của repo.
  • Giải thích chính xác vì sao --amend sau hook fail phá commit TRƯỚC ĐÓ, không phải commit vừa fail.
  • Kể lại đúng chuỗi 5 sự kiện dẫn tới sự cố prediction_log hỏng 8+ ngày.
  • Giải thích được "idempotent" nghĩa là gì trong ngữ cảnh db_migrations.py.
  • Chỉ ra vì sao git add -A rủi ro hơn add file cụ thể theo tên.

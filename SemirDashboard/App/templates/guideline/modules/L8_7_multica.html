8.7 · Multica — Managed Agents Platform

Open-source platform (Multica License — Apache-2.0-based với ràng buộc bổ sung, ~49k ★) turn coding agents (Claude Code, Codex, Cursor, Copilot CLI, Gemini, Kimi...) thành teammates thực sự: assign task, track progress, compound skills. Vendor-neutral, self-hosted. Tech stack: Go backend + Next.js web + Electron desktop + CLI daemon.

Level 8 · AI Artifacts · ~35 phút
💡 Multica bằng ngôn ngữ đời thường

Trước Multica: Bạn có 5 AI coding agents (Claude Code, Cursor, Codex, Copilot CLI, Gemini). Muốn nhờ agent nào làm gì phải mở terminal riêng, copy paste task, chờ trả lời, quên mất context cũ. Giống thuê 5 freelancer nhưng không có phòng chung — chat qua Zalo với từng người mất kiểm soát.

Sau Multica: 1 dashboard duy nhất. Bạn tạo issue "sửa bug X trong file Y" → assign cho Claude Code (hoặc Codex, hoặc bất kỳ agent nào) → agent pickup task tự động, chạy trên runtime của bạn, báo tiến độ, log blocker, update status. Giống Jira nhưng cho AI agents thay vì con người.

Compound skills: skill 1 agent học được (ví dụ: "cách deploy PredictStock qua docker-compose") lưu vào skill library dùng lại cho các agent khác. Càng chạy càng khôn.

  • UX riêng (terminal, IDE plugin, web)

  • Auth riêng, config riêng
  • Không có unified task queue

Key insight: agents chạy trên runtime của user (laptop, dev server, CI runner) — Multica không chạy LLM inference. Nó chỉ điều phối. Điều này giữ:

  • Code + secrets local (không upload lên cloud)
  • Agent auth tokens (Claude API key, GitHub PAT) stay local
  • Multica backend chỉ giữ metadata + task graph

3. Task lifecycle

# 1. Human creates issue
$ multica issue create "Add rate-limit middleware to /api/predict endpoint"
→ Issue #142 created, unassigned

# 2. Assign to agent
$ multica issue assign 142 --agent claude-code
→ Task queued for claude-code runner

# 3. Runner pickup (autonomous)
[daemon] pulled task #142
[daemon] spawning claude-code with task context...
[claude-code] reading backend/routers/predict.py
[claude-code] proposed diff: +42 lines to add slowapi middleware
[claude-code] status → needs_review

# 4. Human review (via web/desktop UI)
Review diff → Approve OR Request changes with comment

# 5. Auto-apply + verify
[daemon] applying diff...
[daemon] running tests: pytest tests/test_predict.py
[daemon] all pass → status = done

# 6. Skill compound
[skill-extractor] learned: "adding rate-limit to FastAPI endpoint"
→ saved to project skill library
→ next agent asked similar task can reference this

Status flow

backlog → assigned → in_progress → needs_review → approved → done
                                       ↓
                                    blocked (report to human)

4.5 · Squads — routing layer cho team lớn

💡 Vấn đề thật: §4's routing.yaml chỉ route 1 task → 1 agent CỤ THỂ, không route được cho 1 NHÓM

Bảng routing ở §4 ("if task.type == X → assign agent Y") giả định người tạo issue BIẾT TRƯỚC nên gán cho agent nào cụ thể. Nhưng với team lớn (VD 10+ dev), người tạo issue (PM, junior dev) thường KHÔNG biết "task này nên đi Claude Code hay Codex" — họ chỉ biết "đây là việc backend". Squad giải quyết bằng cách thêm 1 tầng gián tiếp: assign cho 1 NHÓM (do 1 agent "leader" cầm đầu), leader mới là bên quyết định "trong nhóm này, ai (thành viên nào) hợp nhất để làm việc này" — giống việc giao việc cho "team backend" thay vì chỉ đích danh 1 kỹ sư, rồi để trưởng nhóm backend tự phân công.

# .multica/squads/backend-squad.yaml
squad: backend-squad
leader: claude-code          # leader nhận task trước, quyết định route tiếp
members:
  - claude-code               # complex refactor, multi-file
  - codex                     # quick test gen
  - kiro                      # AWS infra sub-tasks

# Issue được assign cho SQUAD (không phải agent cụ thể):
$ multica issue assign 200 --squad backend-squad
→ leader (claude-code) nhận issue #200 trước
→ leader phân tích: "đây là task viết unit test đơn giản" → route tiếp cho codex
→ codex thực thi, report ngược lại leader → leader tổng hợp báo cáo cho human

⚠️ Chỗ dễ nhầm nhất: Squad KHÔNG PHẢI multi-agent debate/consensus (L6.1/L6.2 đã học — nhiều agent CÙNG làm 1 việc rồi so sánh/tổng hợp kết quả). Squad là phân cấp trách nhiệm 1 CHIỀU — leader nhận việc, QUYẾT ĐỊNH giao cho AI THÀNH VIÊN nào (không phải nhiều thành viên cùng làm rồi vote), giống sơ đồ tổ chức công ty (trưởng nhóm → nhân viên) hơn là 1 ủy ban ra quyết định tập thể.

Insight: Squad hoàn thiện lỗ hổng giữa §4 (routing tĩnh, người tạo issue phải biết rõ agent nào) và nhu cầu thực tế team lớn (người tạo issue chỉ cần biết "việc thuộc domain nào") — đẩy quyết định "agent cụ thể nào" xuống cho 1 AI leader gần với domain expertise hơn, giảm gánh nặng cho người assign task ban đầu.

5. Compound skills — killer feature

Skill = reusable knowledge/procedure agent đã học 1 lần → dùng lại.

.multica/skills/
├── deploy_docker_compose.md
├── add_fastapi_endpoint.md
├── run_alembic_migration.md
├── setup_postgres_index.md
└── manifest.json

Ví dụ 1 skill

# deploy_docker_compose.md
## When to use
Sau khi thay đổi code backend, cần rebuild + restart container

## Steps
1. `docker compose build api`
2. `docker compose up -d api`
3. Verify health: `curl localhost:8000/health`
4. Check logs 20s đầu: `docker compose logs -f api | head -50`

## Common failures
- Container OOM → tăng memory limit trong docker-compose.yml
- Port conflict → `docker compose down` trước

## Applied by
- Task #78 (claude-code, 2026-06-15)
- Task #142 (codex, 2026-07-01)

Cách agent dùng: khi assign task tương tự, Multica inject relevant skills vào agent context → agent không phải "khám phá lại". Học compound (agent A học → agent B benefit).

8.5 · Workflow engine — DAG execution, retries, dead-letter queue

⚙️ Deep-dive — Multi-agent orchestration internals

Multi-agent = distributed system

Khi có >3 agents chạy song song trên task inter-dependent, bạn có 1 distributed system. Cần đầy đủ: DAG scheduler, retry policy, DLQ, idempotency, monitoring. Multica + AI Orchestrator handle những gì?

DAG execution model

# Task graph (ai_orchestrator SDLC):
SpecAnalyze ──┐
              ├──► TaskDecompose ──► Engineer ──► Reviewer ──► Tester ──► PRWriter
Constitution ─┘                                     ▲                       │
                                                    └────── (retry if fail)─┘
# Properties:
# - Node = agent invocation
# - Edge = data dependency (Engineer needs TaskDecompose output)
# - Fan-out: TaskDecompose spawn N Engineer runs (per task)
# - Join: Reviewer wait ALL engineers done

Retry policy matrix

Failure typeStrategyMax attemptsBackoff
Transient (rate limit, network)Exponential retry52^n seconds + jitter
LLM refuse (safety)Reprompt với clarification2None
Tool timeoutRetry với longer timeout3Linear 30s
Test fail (Engineer)Feed error back, retry code3None
Reviewer REJECTEngineer revise, resubmit3None (loop until ACCEPT hoặc HITL)
Unrecoverable (spec ambiguous)→ Dead-letter queue → HITL0N/A

Ví dụ số cụ thể — exponential backoff cho "Transient" failure

# Công thức: wait = 2^attempt (giây) + jitter random(0, 1s)
# attempt đánh số từ 0 (lần retry đầu tiên sau khi fail lần 1)

attempt 0: wait = 2^0 = 1s   + jitter → ~1.3s
attempt 1: wait = 2^1 = 2s   + jitter → ~2.7s
attempt 2: wait = 2^2 = 4s   + jitter → ~4.5s
attempt 3: wait = 2^3 = 8s   + jitter → ~8.2s
attempt 4 (max attempts=5 → lần retry cuối): wait = 2^4 = 16s + jitter → ~16.6s

# Tổng thời gian chờ tối đa trước khi move sang DLQ ≈ 1+2+4+8+16 = 31s (+ jitter)
# Jitter (random 0-1s cộng thêm) tránh "thundering herd" — nếu 100 task cùng fail
# cùng lúc (VD provider outage), không cho tất cả retry đúng cùng 1 giây → tránh
# đập lại server đang recover 1 lượt duy nhất.

Dead-Letter Queue (DLQ)

# Task fail max retries → move to DLQ
dlq_entry = {
  "task_id": "auth-middleware-v2",
  "failed_at": "2026-07-05T10:30:00Z",
  "agent": "engineer",
  "attempts": 3,
  "last_error": "tests fail after 3 revisions",
  "trace_id": "abc123",
  "requires": "human_review",
  "artifacts": ["failed_pr_diff.patch", "test_output.log"]
}
# HITL reviewer picks from DLQ dashboard, decides:
#   → re-queue with hint
#   → mark won't-fix
#   → escalate to senior

Idempotency — critical cho multi-agent

Agent retry có thể spawn duplicate side effect (git commit x2, PR create x2, email send x2). Fix: idempotency key per task.

with idempotency_key(f"pr-create-{task_id}"):
    if not exists(f"prs/{task_id}"):
        pr = github.create_pr(...)
        save_state(f"prs/{task_id}", pr.number)
    else:
        return get_state(f"prs/{task_id}")  # already done

VN scenario — PredictStock nightly training pipeline

DAG: fetch_data → train_models → backtest → generate_report → notify_zalo
  - fetch_data fail (VNDirect API down) → retry 3× exp backoff
  - train_models fail (OOM) → DLQ + Slack alert
  - backtest fail (metric ngoại lai) → auto rollback, dùng model v_prev
  - notify_zalo idempotency key = date → không double-send

Interview Q&A

  1. Q: DAG vs state machine cho agent? A: DAG khi structure fixed (SDLC 6 stages). State machine khi có loop dynamic (agent decide retry vs escalate). LangGraph = state machine, Airflow = DAG.
  2. Q: DLQ vì sao quan trọng? A: Without DLQ, failed task chết silent → build up backlog invisible. Với DLQ, failure visible, prioritizable, human interventable. Critical cho production agent systems.
  3. Q: Idempotency key generate thế nào? A: Hash(task_id + input_snapshot). Same input → same key → dedupe. Include timestamp bucket nếu muốn retry different day (VD hourly bucket).
  4. Q: Multi-agent race condition — ví dụ? A: 2 Engineer agents cùng edit config.yaml (task_1 và task_2 fan-out). Fix: lock per file (pessimistic) hoặc merge với conflict-detector (optimistic). PredictStock dùng git branch-per-task để isolate.

9. Limitations + when NOT to use

  • Solo dev on 1 project: overhead của Kanban+skills không đáng. Dùng agent trực tiếp.
  • Team đã dùng Linear/Jira nghiêm túc: cần integration path (Multica có API, chưa native adapters cho mọi issue tracker).
  • Task rất nhỏ (< 5 phút): overhead assign/track không justify.
  • Sensitive proprietary code: verify self-hosted config kỹ; skill library có thể chứa hint về codebase → phải access-control.

✅ QA Gate

1. Multica khác LangGraph ở đâu?

LangGraph = framework để build 1 agent (state, node, edge). Multica = platform để quản nhiều agent (từ nhiều vendor) như teammates — Kanban, skills, approvals, RBAC. Multica có thể quản agents build bằng LangGraph.

2. Multica có tự chạy LLM inference không?

Không. Multica là orchestration/management layer. LLM call vẫn qua agent CLI (Claude Code, Codex, ...) chạy trên runtime của user với API key của user. Multica chỉ điều phối task + track state. Điều này giữ code + secrets local.

3. Compound skills hoạt động thế nào?

Sau mỗi task thành công, Multica extract "cách agent giải" thành markdown skill lưu vào .multica/skills/. Task tương lai tương tự → skill được inject vào context agent (bất kỳ agent nào, không chỉ agent gốc). Compound theo project + có thể share cross-project.

4. Khi nào NÊN dùng Multica?

Team ≥3 dev + ≥2 coding agents + workload >10 task/tuần. Solo dev 1 agent không cần. Team lớn với Jira quen thuộc → cần integration path.

5. Multica so với Cursor Composer?

Cursor Composer = agent embed trong IDE, edit code interactive. Multica = platform tổ chức nhiều agent (Cursor có thể là 1) cross-project cross-team. Bổ sung nhau, không cạnh tranh — có thể dùng Cursor cho code editing + Multica cho backlog management.

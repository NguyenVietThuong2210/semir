R7.1 · CI/CD cho ML/LLM

Vì sao pipeline "chạy được code" chưa đủ cho model — cần thêm data gate + eval gate. Đọc thật .github/workflows/ci.yml của predictor để thấy khoảng cách với chuẩn 2026.

Độ khó: Dễ · Roadmap AI Engineering · Track 2

🎯 Mục tiêu học

  1. (Dễ) Nhắc lại CI/CD truyền thống là gì — build, lint, test, deploy tự động mỗi lần push code.
  2. (Dễ→Trung bình) Hiểu vì sao ML/LLM cần thêm 2 tầng gate mà code thường không có: data validation gate và model evaluation gate.
  3. (Trung bình) Đọc hiểu chính xác từng bước trong .github/workflows/ci.yml thật của predictor — biết bước nào chạy, bước nào skip và tại sao.
  4. (Trung bình→Khó) Chỉ ra đúng 4 gap cụ thể giữa pipeline hiện tại và chuẩn CI/CD 2026 (3 gap ML-specific + 1 gap bảo mật tổng quát) — không phải nhận xét chung chung.
  5. (Khó) Đề xuất được cải thiện chi phí thấp, khả thi với quy mô Docker Compose 3 service hiện tại — không đề xuất hạ tầng không cần thiết.
  6. (Trung bình→Khó) Phân biệt được 3 loại quét bảo mật (SAST/SCA/secret scanning) và thiết kế đúng 4-lớp assertion cho test code có output non-deterministic (LLM-touching).

💡 Analogy

💡 Analogy

CI/CD cho phần mềm thường giống "kiểm tra chính tả trước khi in sách" — chạy nhanh, kết quả tất định (deterministic): cùng 1 bản thảo, chạy spellcheck 10 lần ra đúng 10 lần cùng 1 kết quả.

CI/CD cho ML/LLM giống "kiểm tra chất lượng 1 mẻ bánh mới ra lò" — phải nếm thử (eval), không chỉ đọc công thức (code). Và quan trọng hơn: kết quả nếm có thể khác nhau chút ít giữa các mẻ bánh dù cùng công thức (non-determinism trong training) — 2 lần train cùng code, khác seed hoặc khác data mới nhất, có thể ra model hơi khác nhau. Bạn không thể chỉ "đọc công thức" (review code) để biết bánh có ngon không — phải nếm (eval) thật.

📖 Cơ chế chi tiết

1. CI/CD truyền thống — nhắc lại nhanh (điểm khởi đầu dễ)

CI (Continuous Integration) = mỗi lần push code, tự động: lint (kiểm tra style) → type-check → build → chạy unit test. CD (Continuous Deployment/Delivery) = nếu tất cả bước trên pass, tự động deploy (hoặc tạo sẵn artifact chờ deploy). Mục tiêu: bắt lỗi sớm, trước khi code chạm production.

Với phần mềm thường, "đúng" là nhị phân — hàm cộng 2 số hoặc đúng hoặc sai, test 1 lần là đủ để biết mãi mãi (chừng nào code không đổi).

2. Vì sao ML/LLM cần thêm 2 tầng — đây là phần khó hơn

2.1 Data validation gate — trước khi train

Model học từ data. Data lỗi (schema đổi, giá trị NaN tăng đột biến, phân phối lệch) → model học sai mà code vẫn "chạy được" (không crash, không lỗi cú pháp). CI truyền thống không bắt được lỗi này vì nó không đọc data — chỉ đọc code. ML CI/CD cần 1 bước riêng: validate data trước khi cho vào training (schema check, null-rate check, range check).

2.2 Model evaluation gate — trước khi deploy

Ngay cả khi code compile sạch và data hợp lệ, model mới train ra có thể tệ hơn model đang chạy (ít data hơn, overfit, hoặc target shift). CI truyền thống trả lời "code có bug không?" — ML CI/CD phải trả lời thêm câu "model mới có tốt hơn/bằng model cũ không?" bằng 1 con số đo được (accuracy, precision, hoặc business metric), trước khi cho phép "promote" model mới lên production.

2.3 Versioning đầy đủ — không chỉ code

Phần mềm thường chỉ cần version code (Git commit hash) để tái tạo lại chính xác 1 bản build. ML cần version thêm 2 thứ nữa: data (data hôm nay khác data hôm qua, cùng code train ra model khác) và environment (version thư viện numpy/xgboost khác nhau có thể đổi kết quả training). Thiếu 1 trong 3 → không thể debug "tại sao model tuần này khác tuần trước".

3. Testing pyramid ML/LLM — 3 tầng, không dừng ở unit test

Testing pyramid truyền thống: nhiều unit test (nhanh, rẻ) ở đáy, ít integration test ở giữa, rất ít end-to-end test ở đỉnh. ML/LLM thêm 1 tầng đáy mới bên dưới cả unit test:

Tầng 0 (mới, ML-specific): Data quality check
        — schema đúng? null-rate trong ngưỡng? distribution không lệch bất thường?
Tầng 1: Unit test (như thường — test hàm tính feature, hàm tính score, không đụng DB thật)
Tầng 2: Integration test (model load được, predict ra đúng shape, API trả đúng field)
Tầng 3: Full eval run (model mới so với model cũ trên tập validation — quyết định promote hay không)

Với RAG/LLM app cụ thể, có thêm các điểm hỏng riêng mà pipeline code thường không có khái niệm: chất lượng retrieval (có lấy đúng document không), độ liên quan context (context lấy về có giúp trả lời đúng không), độ mới tri thức (knowledge freshness — dữ liệu retrieval có bị cũ không), embedding drift (embedding model đổi version → toàn bộ vector cũ lệch nghĩa).

4. Nguyên tắc cốt lõi — pipeline không dừng ở deploy

Khác biệt tư duy quan trọng nhất: CI/CD code thường coi "deploy thành công" là điểm kết thúc. CI/CD ML/LLM coi deploy là điểm giữa vòng đời — sau deploy phải tiếp tục theo dõi prediction distribution + input drift, và feed ngược kết quả đó thành tín hiệu retrain. Đây chính là vòng lặp đã dạy ở L7_1_mlops.html (drift detection PSI, retrain trigger) — CI/CD là phần "cổng vào" của vòng lặp đó, không phải 1 quy trình độc lập.

5. Security gate — SAST/SCA/secret scanning (chưa có ở ci.yml hiện tại)

Đây là góc hoàn toàn khác 2 gate ML ở mục 2 — không phải "ML cần thêm gì" mà là "CI/CD phần mềm tổng quát nào predictor đang thiếu". 3 loại quét RIÊNG BIỆT, khác cơ chế, hay bị gộp chung thành 1 khái niệm mơ hồ "quét bảo mật":

Loại quétBắt lỗi gìCơ chếCông cụ phổ biến 2026
SAST (Static Application Security Testing)Pattern code nguy hiểm trong chính source (SQL injection ghép chuỗi, hardcoded credential pattern...)Phân tích tĩnh AST/pattern-matching trên source — không cần chạy codeSemgrep — phổ biến nhất 2026, <2 phút cho codebase cỡ vừa, bộ rule OWASP Top 10 sẵn, tích hợp GitHub Actions trực tiếp

Best practice 2026: chạy SAST và SCA song song (không tuần tự) trên mọi PR bằng needs chỉ khi có phụ thuộc dữ liệu thật — 1 bộ quét đầy đủ chỉ nên cộng thêm dưới 5 phút nếu parallelize đúng. Ngưỡng fail hợp lý: chỉ chặn merge ở mức CRITICAL/HIGH — chặn cả mức INFO khiến pipeline đỏ liên tục và huấn luyện dev thành thói quen lờ đi cảnh báo, phản tác dụng ngược với mục đích của gate.

6. Testing gate cho code có output non-deterministic (LLM-touching code)

pytest hiện tại của dự án giả định output tất định (input X → luôn ra đúng 1 Y, test 1 lần biết mãi mãi — đúng như mục 1 đã nói). Code gọi LLM (VD script tạo report của skill daily-investor-report) phá vỡ giả định này: cùng 1 prompt, 2 lần chạy có thể ra 2 câu chữ khác nhau dù cùng nghĩa, cùng đúng. Test kiểu cũ assert output == "Giá tăng do..." sẽ FAIL GIẢ (flaky) dù chất lượng không hề giảm — đây là lỗi thiết kế test, không phải lỗi code. Chuẩn 2026 dùng 4 lớp assertion cộng dồn, không chỉ 1 lớp duy nhất:

Lớp 1 — Structural check:    output có đúng schema/shape không? (JSON parse được,
                              field bắt buộc có mặt) — rẻ, tất định, chạy được như unit test thường.
Lớp 2 — Invariant check:     điều kiện PHẢI luôn đúng bất kể câu chữ cụ thể (VD: số liệu
                              trích dẫn khớp DB nguồn, không có field bị cấm xuất hiện —
                              xem feedback_llm_independence.md) — vẫn rẻ, vẫn tất định.
Lớp 3 — Semantic similarity: so embedding của output với 1 câu trả lời mẫu (golden) — PASS
                              nếu đủ GẦN nghĩa dù khác từ ngữ. Đây là lớp giải quyết ĐÚNG
                              vấn đề non-determinism, thay vì so khớp chuỗi ký tự.
Lớp 4 — Rubric / judge model: 1 model khác chấm điểm theo tiêu chí định tính (rõ ràng,
                              đúng giọng văn, không lan man) — đắt nhất, chỉ dùng khi
                              Lớp 1-3 không đủ phân biệt tốt/xấu.

Lớp 1-2 chạy được trong CI thường trên MỌI PR (nhanh, rẻ, tất định — không khác gì thêm 1 unit test). Lớp 3-4 tốn thêm ít nhất 1 lời gọi model/embedding — nên chạy ở CI riêng (nightly, hoặc chỉ khi PR đổi prompt/system instruction), không chạy trên mọi PR như lint. Golden set tiêu chuẩn ngành: 100-300 cặp prompt-response đa dạng, không trùng lặp ý — khác hẳn quy mô "chạy lại toàn bộ 86 ticker" (tốn kém, không cần thiết chỉ để test 1 thay đổi prompt nhỏ).

📖 Không lặp lại R5.4 — ranh giới rõ giữa 2 bài

R5_4_prompt_engineering.html mục 4 đã dạy prompt versioning + golden dataset ở TẦNG PROMPT (khi nào cần tạo thêm eval case mới, prompt_version_id là khoá nối CI/production, ngưỡng chặn merge theo loại thay đổi). Mục này dạy TẦNG CI GATE — cơ chế assertion cụ thể (4 lớp cộng dồn) để pipeline tự động ra quyết định pass/fail không phụ thuộc may rủi của đúng 1 lần sinh output. 2 bài bổ trợ nhau: R5.4 trả lời "khi nào cần eval mới", bài này trả lời "eval đó được CHẤM như thế nào để không flaky".

Minh hoạ Lớp 1-2 (chạy được trong pytest thường, tất định, không cần gọi model để test):

# backend/tests/test_report_output_gate.py (minh hoạ cơ chế — không phải file thật)
def test_report_structural_gate(sample_llm_output):
    data = json.loads(sample_llm_output)          # Lớp 1: parse được, đúng JSON
    assert "thesis" in data and "verdict" in data  # Lớp 1: field bắt buộc có mặt

def test_report_invariant_gate(sample_llm_output, db_price_snapshot):
    data = json.loads(sample_llm_output)
    # Lớp 2: số liệu LLM trích dẫn phải khớp DB nguồn — không tự bịa số
    assert data["quoted_price"] == db_price_snapshot["close"]
    # Lớp 2: field bị cấm (derivative hệ thống tính sẵn) không được xuất hiện
    # trong input LLM nhận — đúng ranh giới feedback_llm_independence.md
    assert "combined_score" not in data.get("raw_prompt_context", "")

7. Ráp lại toàn bộ — pipeline đầy đủ theo đúng thứ tự chạy

Ghép mục 1-6 thành 1 sơ đồ duy nhất, đúng thứ tự 1 kỹ sư sẽ thấy khi mở workflow file — phân biệt rõ bước nào chạy SONG SONG (không phụ thuộc nhau) và bước nào phải TUẦN TỰ (bước sau cần kết quả bước trước):

PR mới được mở

         │  (tất cả PASS mới đi tiếp)

         │
         ▼

         │
         ▼
  Coverage floor + Promotion gate  (check_per_file_coverage.py, promotion_gate_check.py)
         │
         ▼

         │

Đọc sơ đồ: 4 bước đầu (lint/SAST/SCA/secret) độc lập hoàn toàn với nhau — đây chính là chỗ "chạy song song tiết kiệm thời gian" nói ở mục 5. Càng xuống dưới, các bước càng phụ thuộc tuần tự (data gate cần code đã pass unit test, promotion gate cần data đã hợp lệ). Lớp 3-4 của testing gate (mục 6) tách hẳn ra khỏi luồng chặn PR — vì chi phí gọi model, không phải vì kém quan trọng hơn.

🔢 Ví dụ cụ thể

Đọc trực tiếp .github/workflows/ci.yml của predictor (nguyên văn, không rút gọn phần quan trọng):

jobs:
  backend:
    name: Backend — lint + type-check + tests
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: backend
    steps:
      - uses: actions/checkout@v4
      - name: Set up Python 3.12
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip
      - name: Install dependencies
        run: pip install -r requirements.txt
      - name: ruff lint
        run: ruff check .
      - name: mypy type-check
        run: mypy predict/ --ignore-missing-imports --no-strict-optional
      - name: pytest
        run: pytest tests/ -q --tb=short
        env:
          DATABASE_URL: ""   # tests use mocks; no live DB needed

      # Test Quality Improvement Plan (ai-trader/10_test-quality-improvement-
      # plan-2026-08-09.md, P1). Both steps are DB-free by design — no
      # Postgres service exists in this job (see DATABASE_URL="" above), so
      # G-M0/G-M0b (which need real scored tickers) run in --skip-db-checks
      # mode and report SKIP rather than PASS/FAIL for those two.

      - name: Per-file coverage floor (single-source-of-truth files)
        run: python scripts/check_per_file_coverage.py
      - name: Promotion gate check (DB-free subset)
        run: python scripts/promotion_gate_check.py --skip-db-checks

  frontend:
    name: Frontend — type-check + build
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: frontend
    steps:
      - uses: actions/checkout@v4
      - name: Set up Node 20
        uses: actions/setup-node@v4
        with:
          node-version: "20"
          cache: npm
      - name: Install dependencies
        run: npm ci
      - name: TypeScript type-check
        run: npx tsc --noEmit
      - name: Build
        run: npm run build
        env:
          VITE_API_BASE_URL: http://localhost:8000
      - name: Check bundle size
        run: |
          SIZE=$(du -sm dist/ | cut -f1)
          if [ "$SIZE" -gt 10 ]; then
            echo "::warning::Bundle exceeds 10MB — consider code splitting"
          fi

Đọc từng dòng theo đúng tinh thần "gate trước khi promote": ruff check + mypy = lint/type-check truyền thống. pytest = unit test, nhưng chạy với DATABASE_URL="" — nghĩa là mọi test cần DB thật đều bị mock hoặc skip. check_per_file_coverage.py = 1 gate ML-specific: bắt buộc coverage sàn cho các file "single-source-of-truth" như senior_score.py (đúng nguyên tắc CLAUDE.md). promotion_gate_check.py --skip-db-checks = chính là "model evaluation gate" nói ở mục 2.2 — nhưng chạy ở chế độ rút gọn (không cần DB thật), vì 2 gate G-M0/G-M0b cần scored ticker thật từ Postgres đang bị skip trong CI, comment trong file ghi rõ điều này (không phải bịa — trích nguyên văn comment gốc).

Ví dụ mở rộng — chi phí thời gian thật khi thêm security gate (mục 5), song song vs tuần tự

Giả định thời gian chạy thật của từng loại quét trên codebase cỡ backend/ (Semgrep cỡ "<2 phút cho codebase vừa" đã dẫn nguồn ở mục 5; SCA/secret scanning theo benchmark điển hình 2026 cho repo cỡ nhỏ-vừa):

Semgrep (SAST):        90 giây
Trivy (SCA):            60 giây
Gitleaks (secret):      15 giây
Job backend hiện tại (lint+mypy+pytest+coverage+promotion): 180 giây (ước lượng, đo thật cần xem Actions log)

TUẦN TỰ (thêm nối đuôi vào job backend hiện tại):
  180 + 90 + 60 + 15 = 345 giây tổng cộng
  → PR nào cũng phải đợi thêm 165 giây (gần 3 phút) so với hiện tại

SONG SONG (3 job riêng, chạy đồng thời với job backend, không nối đuôi):
  max(180, 90, 60, 15) = 180 giây — bằng ĐÚNG thời gian job backend hiện tại
  → PR không đợi thêm giây nào, vì 3 job bảo mật xong SỚM HƠN job backend đang có

→ Tiết kiệm 165 giây/PR chỉ nhờ đổi cấu trúc job (song song thay vì nối đuôi) —
  không đổi công cụ, không giảm độ bao phủ quét, đúng tinh thần "dưới 5 phút nếu
  parallelize đúng" đã nêu ở mục 5. Đây là lý do best practice 2026 nhấn mạnh
  needs chỉ nên dùng khi có phụ thuộc dữ liệu THẬT — dùng thừa biến
  song song thành tuần tự một cách vô tình.

🎯 Ứng dụng dự án

4 gap thật, xếp theo chi phí sửa/lợi ích (đọc trực tiếp từ D:\New-jouney\predictor\.github\workflows\ci.yml, không suy đoán):

  1. Thiếu Postgres service trong job backend — chi phí sửa thấp: docker-compose.yml đã có sẵn cấu hình Postgres 16-alpine với healthcheck (pg_isready) dùng làm mẫu; thêm 1 khối services: postgres: tương tự vào job CI là đủ để chạy được G-M0/G-M0b thật thay vì --skip-db-checks.
  2. Drift detection chưa wire vào CI/CD — hiện chạy nightly độc lập qua reports/consistency/, tách rời hoàn toàn khỏi workflow CI. Cải thiện khả thi: thêm 1 step gọi lại script consistency check đó ngay trong CD sau khi deploy, thay vì chỉ dựa vào cron nightly riêng.
  3. Không có bước train/eval model thật trong CI — đây là quyết định hợp lý, không phải lỗi: train tốn thời gian/compute, tách khỏi CI nhanh là đúng thiết kế. Nhưng hệ quả là promotion gate DB-dependent phải chạy thủ công/CD riêng — nên ghi rõ trong runbook, không để ai nhầm rằng CI hiện tại đã "gate" đầy đủ.
  4. Không có bất kỳ bước security scanning nào (SAST/SCA/secret scanning) — chi phí sửa cực thấp: Dependabot bật miễn phí chỉ bằng 1 lần bật trong GitHub Settings (không cần sửa ci.yml), thêm Semgrep GitHub Action (free tier cho open-source/nội bộ nhỏ) là 1 step ngắn chạy song song job backend. Đây là gap dễ vá nhất trong cả 4 gap liệt kê, nhưng lại KHÔNG liên quan gì đến ML — đúng đặc điểm của gap "CI/CD phần mềm tổng quát" mà module này bổ sung, khác hẳn 3 gap ML-specific ở trên.

Cụ thể hoá gap 4 cho đúng 2 ngôn ngữ dự án đang dùng (backend Python 3.12, frontend TypeScript/npm — xem ci.yml mục 2 job backend/frontend):

  • Dependabot: cần 2 khối cấu hình riêng trong .github/dependabot.yml — package-ecosystem: "pip" cho backend/requirements.txt, package-ecosystem: "npm" cho frontend/package-lock.json. Không cấu hình cả 2 = chỉ vá được 1 nửa dependency của hệ thống.
  • Semgrep: ruleset p/python + p/fastapi cho backend/ (dự án dùng FastAPI, xem uvicorn main:app ở Dockerfile), p/typescript + p/react cho frontend/ — dùng đúng ruleset theo framework, không dùng ruleset generic "tất cả ngôn ngữ" sẽ bỏ sót pattern đặc thù FastAPI/React (VD injection qua query param FastAPI, XSS qua dangerouslySetInnerHTML React).
  • Gitleaks: quan trọng nhất với repo này là chặn commit nhầm ANTHROPIC_API_KEY hoặc connection string Postgres thật (postgresql+asyncpg://predict:predict_secret@... hiện đang là giá trị dev trong docker-compose.yml — không phải secret thật, nhưng pattern tương tự với credential thật cần bị chặn nếu ai đó vô tình paste nhầm vào code).

⚠️ Sai lầm thường gặp

⚠️ Sai lầm thường gặp
  1. Coi CI code thường và CI ML là 1 — copy pipeline lint/test từ dự án backend thường sang dự án ML mà không thêm data gate + eval gate, tưởng vậy là đủ.
  2. Đọc promotion_gate_check.py --skip-db-checks pass rồi kết luận "gate đã chạy đầy đủ" — SKIP không phải PASS; cần phân biệt rõ 2 trạng thái này khi báo cáo trạng thái CI.
  3. Thêm Postgres service vào CI nhưng seed data giả không đại diện — chạy được gate không có nghĩa gate đó đáng tin nếu data test không phản ánh data thật.
  4. Nghĩ rằng thêm DVC/MLflow ngay lập tức là bắt buộc — với quy mô 1 model XGBoost nhỏ, ưu tiên đúng là thêm Postgres vào CI trước, DVC/MLflow chỉ đáng đầu tư khi số lượng model/dataset tăng đủ lớn để thủ công không còn theo kịp.
  5. Test code có gọi LLM bằng exact-match assertion (assert output == "...") — chắc chắn flaky vì output non-deterministic dù chất lượng không đổi; cần ít nhất Lớp 1-2 (structural/invariant), tốt hơn nữa là thêm Lớp 3 (semantic similarity).
  6. Chặn merge ở MỌI mức nghiêm trọng của SAST kể cả INFO — khiến pipeline đỏ liên tục vì noise, dev học cách bỏ qua cảnh báo, phản tác dụng với chính mục đích của gate; chỉ nên chặn ở CRITICAL/HIGH.
  7. Áp ruleset Semgrep generic cho code tính toán số học (feature engineering, XGBoost) — code kiểu pandas/numpy hay bị false-positive với rule "hardcoded value" hoặc "unsafe eval" viết cho web backend thông thường; cần tinh chỉnh ruleset theo domain (mục "Cụ thể hoá" ở phần Ứng dụng dự án), không dùng nguyên bộ rule mặc định rồi bực mình tắt hẳn cả gate vì quá nhiều false positive.
  8. Coi security scanning (SAST/SCA/secret/image) đủ để thay thế Model evaluation gate — 2 loại gate hoàn toàn khác mục đích: security scanning bắt lỗ hổng BẢO MẬT trong code/dependency/image; evaluation gate bắt model KÉM CHẤT LƯỢNG hơn bản đang chạy. Code có thể an toàn tuyệt đối về bảo mật nhưng model vẫn tệ hơn — 2 gate cần chạy độc lập, không loại trừ nhau.

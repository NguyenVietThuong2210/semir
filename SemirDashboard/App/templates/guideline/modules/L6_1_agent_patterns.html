6.1 · Agent Patterns (ReAct, Reflexion, Plan-and-Execute)

4 canonical agent designs. Khi nào chọn cái nào. Anthropic "Building Effective Agents" whitepaper 2024.

Level 6 · Agents · ~30 phút

🎯 Learning objectives

  • Explain ReAct loop step by step
  • Understand Reflexion self-critique loop
  • Plan-and-Execute two-phase pattern
  • Choose right pattern cho use case
💡 Agent patterns bằng ngôn ngữ đời thường

ReAct = Bác sĩ khám bệnh: Nghĩ ("có thể cảm cúm") → Khám (đo nhiệt độ, action) → Quan sát ("38.5°C") → Nghĩ tiếp ("nghi ngờ viêm phổi, chụp X-quang") → ... Loop until diagnose.

Reflexion = Học sinh review bài kiểm tra sau khi thi: Làm bài → biết điểm → tự nhận xét "câu 3 mình sai vì đọc thiếu đề" → lần sau chú ý. Agent tự phê bình để cải thiện lần sau.

Plan-Execute = Kiến trúc sư vs Thợ xây: Kiến trúc sư (planner) vẽ toàn bộ bản vẽ trước. Thợ xây (executor) làm theo từng bước. Ngược với ReAct (vừa nghĩ vừa làm).

1. ReAct — Reason + Act (Yao et al., 2023)

Thought: I need to find current price of FPT.
Action: get_stock_price(ticker="FPT")
Observation: {"price": 72.5, "change": -0.55}
Thought: Now check history for trend.
Action: get_history(ticker="FPT", days=30)
Observation: [...]
Thought: RSI showing oversold at 43, MA20 flat. Suggest HOLD.
Answer: HOLD, current 72.5, monitor for reversal at 71.

Interleave thought + action + observation until answer. Simple, effective for research tasks.

1.1 ReAct loop — pseudo-code với tool retry + backoff

import time, random

def react_loop(question, tools, max_iter=8, max_tool_retry=3):
    trace = []
    for step in range(max_iter):
        # 1. Thought — LLM reasons about next action given prior trace
        response = llm.call(
            system=REACT_PROMPT,
            messages=trace + [{"role": "user", "content": question}],
            stop=["Observation:"],
        )
        thought, action = parse_react(response)   # regex parse "Thought:...\nAction:..."
        trace.append({"role": "assistant", "content": response})

        # 2. Terminal — LLM said Answer:
        if action.name == "Finish":
            return action.args["answer"]

        # 3. Act — call tool with exponential backoff on transient errors
        obs = None
        for attempt in range(max_tool_retry):
            try:
                obs = tools[action.name](**action.args)
                break
            except TransientError as e:
                sleep = min(2 ** attempt + random.random(), 30)   # jitter, cap 30s
                time.sleep(sleep)
        else:
            obs = f"ERROR: tool {action.name} failed 3× — try different approach"

        # 4. Observe — feed result back into LLM context
        trace.append({"role": "user", "content": f"Observation: {obs}"})

    raise MaxIterationsExceeded("Agent didn't converge in 8 steps")

Điểm quan trọng: (1) stop=["Observation:"] ép LLM chỉ generate Thought+Action, không hallucinate observation. (2) Exponential backoff (đợi lâu dần sau mỗi lần retry thất bại: 1s, 2s, 4s, 8s...) + jitter (cộng thêm 1 khoảng ngẫu nhiên nhỏ vào thời gian đợi, dòng + random.random() ở code trên) để chống thundering herd (hiệu ứng "đàn trâu chạy cùng lúc" — nếu hàng nghìn request đều retry đúng cùng 1 thời điểm sau lỗi, chúng dội vào server cùng lúc lần nữa gây quá tải tiếp; jitter làm mỗi request retry ở thời điểm hơi khác nhau, trải đều tải ra). (3) Sau max retry, feed error observation ngược vào LLM để nó adapt (dùng tool khác), không crash.

2. Reflexion — self-critique (Shinn 2023)

Attempt 1: [Generate code] → run → fail
Reflection: "My loop condition wrong, should be i < len instead of i <= len"
Attempt 2: [Regenerate with reflection in context] → run → pass

# Loop until success or max attempts
# LLM learns from own mistakes across attempts

Great cho code, math, tasks với verifiable feedback.

3. Plan-and-Execute

Phase 1 (Plan): LLM generate step-by-step plan
  1. Read config file
  2. Query database for user X
  3. Compute risk score
  4. Update dashboard

Phase 2 (Execute): sequential execute each step, potentially different (cheaper) LLM

# Advantage: planning once vs re-plan every step (ReAct)
# Better cho long tasks với clear structure

4. Tree of Thoughts (ToT) — pattern bị nhắc tới nhưng chưa giải thích

Bảng so sánh ở cuối section 6 sẽ nhắc "Tree of Thoughts" — pattern đắt nhất, mạnh nhất cho bài toán planning khó. Giải thích trước khi bạn gặp nó trong bảng:

💡 ToT bằng ngôn ngữ đời thường

Đi mê cung: ReAct/Reflexion = đi 1 đường duy nhất, sai thì lùi lại sửa bước vừa rồi (giống dò dẫm tuyến tính). Tree of Thoughts = tại mỗi ngã rẽ, bạn thử vài hướng cùng lúc (branch), tự chấm điểm hướng nào "có vẻ gần lối ra" (evaluate), bỏ hướng tệ, quay lại ngã rẽ trước để thử hướng khác (backtrack) — giống DFS/BFS có heuristic, không phải mò 1 đường.

Cơ chế 3 bước, lặp lại:

  1. Branch (phân nhánh): tại 1 trạng thái, LLM sinh ra N ý tưởng tiếp theo khác nhau (không chỉ 1 như ReAct) — ví dụ 3 cách khác nhau để giải 1 bước của bài toán.
  2. Evaluate (chấm điểm): 1 LLM call khác (hoặc rule) chấm mỗi nhánh — "nhánh này có khả năng dẫn tới lời giải đúng không?" (thang điểm hoặc pass/fail).
  3. Backtrack (quay lại): bỏ nhánh điểm thấp, giữ nhánh điểm cao, tiếp tục branch từ đó. Nếu tất cả nhánh con của 1 nhánh đều tệ → quay lại nhánh cha, thử hướng khác.
# Ví dụ tối giản — Game of 24 (dùng 4 số ra kết quả 24 bằng +-*/)
# Input: [4, 9, 10, 13]

                         [4, 9, 10, 13]
                    Bước 1 — Branch (3 phép tính đầu tiên)
              ┌────────────┼────────────┐
        A) 13-9=4    B) 10-4=6     C) 9+4=13
        [4,4,10]     [6,9,13]      [13,13,10]
              │            │             │
      Bước 2 — Evaluate (LLM tự chấm mỗi nhánh)
       "gần 24,          "khó thấy         "không rõ
        có tiềm năng"     đường ra 24"      hướng"
          ✓ giữ            ✗ loại            ✗ loại
              │
      Bước 3 — Backtrack: chỉ còn A → tiếp tục branch từ [4,4,10]
              │
        10-4=6, 6*4=24 ✓ FOUND

# Nếu nhánh A cũng bế tắc → quay lại gốc, thử phép tính thứ 4 chưa xét (backtrack lên trên)

Trade-off: ToT tốn 10-100× số lời gọi LLM so với single-shot (mỗi bước branch ra N nhánh, mỗi nhánh cần 1 lần evaluate). Chỉ đáng dùng khi bài toán có tính chất "cần khám phá nhiều hướng, sai 1 bước sớm là hỏng toàn cục" (game logic, planning phức tạp, math olympiad) — không dùng cho task đơn giản có đường giải rõ ràng.

5. Multi-agent collaboration

Roles: Researcher, Coder, Reviewer, Judge

User: "Build authentication system"
  → Researcher: gather requirements, ask user clarifications
  → Coder: implement based on spec
  → Reviewer: check code quality, security
  → Judge: verdict pass/fail
  → Loop until pass

# Each agent specialized prompt → better than 1 mega-prompt
# Trade-off: more LLM calls, higher cost

5.5 Multi-Agent Debate (Du et al. 2023) — khác hẳn "multi-agent collaboration" ở mục 5

💡 Analogy

Multi-agent collaboration ở mục 5 (Researcher → Coder → Reviewer → Judge) giống 1 DÂY CHUYỀN — mỗi agent làm 1 VAI TRÒ KHÁC NHAU, nối tiếp nhau. Multi-Agent Debate hoàn toàn khác: nhiều BẢN SAO của CÙNG 1 loại agent (có thể cùng 1 model, hoặc vài model khác nhau) cùng nhận CÙNG 1 câu hỏi, mỗi bản sao tự trả lời ĐỘC LẬP trước, rồi cho TẤT CẢ thấy câu trả lời của nhau và yêu cầu MỖI bản sao tự sửa lại câu trả lời của mình sau khi đọc ý kiến người khác — lặp lại vài vòng cho tới khi hội tụ về 1 câu trả lời chung. Giống 1 hội đồng thẩm định, không phải 1 dây chuyền sản xuất.

Vấn đề cụ thể: 1 LLM trả lời độc lập có thể tự tin SAI (hallucinate — model bịa thông tin sai như thể nó đúng, không cố ý gian dối, chỉ là hệ quả của cách LLM dự đoán token tiếp theo) mà không có cơ chế nào tự phát hiện — Reflexion (mục 2) giúp 1 agent tự phê bình dựa trên feedback BÊN NGOÀI (chạy test, thấy fail), nhưng nếu KHÔNG CÓ tín hiệu đúng/sai khách quan (VD câu hỏi suy luận mở, không chạy test được), agent không có gì để tự sửa. Debate giải quyết vấn đề này bằng cách dùng chính SỰ KHÁC BIỆT giữa nhiều câu trả lời độc lập làm tín hiệu — nếu nhiều bản sao ra câu trả lời khác nhau, ít nhất 1 số phải sai, và việc đọc lý lẽ của "phe khác" giúp phát hiện lỗ hổng trong lý lẽ của chính mình.

# Cơ chế Multi-Agent Debate (Du et al. 2023):
Vòng 1: N bản sao agent (VD N=3, cùng hoặc khác model) nhận CÙNG 1 câu hỏi,
        MỖI bản sao trả lời ĐỘC LẬP (không thấy câu trả lời của nhau) kèm lý do.

Vòng 2+: Gộp CẢ N câu trả lời + lý do vòng trước → đưa lại cho MỖI bản sao xem
         (mỗi agent thấy "3 câu trả lời khác nhau, đây là lý do của mỗi bên") →
         yêu cầu MỖI agent VIẾT LẠI câu trả lời của mình, được phép giữ nguyên
         hoặc đổi ý sau khi cân nhắc lý lẽ người khác.

Lặp lại Vòng 2 vài lần (thường 2-3 vòng) → N câu trả lời dần HỘI TỤ về 1 đáp án
chung (agent nào lý lẽ yếu hơn thường tự đổi ý theo lý lẽ mạnh hơn qua các vòng).

Đáp án cuối = câu trả lời đa số (majority) sau khi hội tụ, hoặc lấy nguyên câu
trả lời vòng cuối nếu đã đồng thuận 100%.

⚠️ Chỗ dễ nhầm nhất: Debate KHÔNG PHẢI Self-Consistency (đã học ở L5_1_prompt.html) — Self-Consistency sample N câu trả lời ĐỘC LẬP rồi VOTE ngay (các bản sao KHÔNG BAO GIỜ thấy câu trả lời của nhau), trong khi Debate cho các bản sao THẤY câu trả lời của nhau và ĐƯỢC PHÉP đổi ý qua nhiều vòng trước khi vote. Debate tốn nhiều lượt gọi LLM hơn (N agent × K vòng) nhưng có thể sửa được lỗi mà Self-Consistency không sửa được — nếu CẢ N bản sao đều mắc CÙNG 1 lỗi suy luận hệt nhau (bias hệ thống của chính model), Self-Consistency vote ra chính lỗi đó (đa số đồng thuận nhầm), còn Debate ít nhất có cơ hội 1 agent phát hiện ra lỗi khi đọc lại lý lẽ và tự sửa ở vòng sau.

Insight: nghiên cứu thực nghiệm (Du et al. 2023 và các nghiên cứu tiếp theo) cho thấy multi-agent debate giảm hallucination và cải thiện reasoning trên nhiều benchmark (toán, logic, QA) so với 1 agent tự phản biện 1 mình (self-correction) — lý do cốt lõi: phản biện từ 1 "góc nhìn khác" (dù chỉ là 1 bản sao khác của cùng model) tạo áp lực kiểm tra lại lập luận mà tự phản biện 1 mình không tạo ra được (model khó tự phát hiện lỗi trong chính lý luận của mình khi không có ai "cãi lại").

📖 Mở rộng: chi phí Debate tăng tuyến tính theo N (số agent) × K (số vòng) — với N=3, K=3 đã là 9× lời gọi LLM so với 1 lần hỏi thường, nên chỉ đáng dùng cho câu hỏi QUAN TRỌNG/khó (không dùng cho mọi query production) — cùng nguyên lý trade-off "cost vs quality" đã gặp ở Tree of Thoughts (mục 4) và Self-Consistency (L5.1).

6. Anthropic "Building Effective Agents" (2024)

Anthropic recommendations
  1. Start simple: single LLM call thường đủ. Only add complexity when measurable benefit.
  2. Workflow (fixed path) vs Agent (dynamic): workflow predictable + cheap; agent flexible + expensive.
  3. Building blocks: prompt chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer
  4. Tools first: good tool definitions matter more than agent framework choice

Ví dụ — cùng task "sửa bug X trong file Y" bằng 3 patterns

=== ReAct ===
Thought: cần đọc file Y để hiểu bug
Action: read_file(Y)
Observation: [file content]
Thought: bug ở line 42, cần sửa null check
Action: edit_file(Y, line=42, ...)
Observation: success
Thought: cần test
Action: run_tests()
Observation: pass
FINISH.
Turns: 3 pairs + 1 finish call = 4 LLM calls — moderate cost

=== Reflexion ===
Attempt 1: [same as ReAct] → tests fail
Reflection: "test fail vì tôi chỉ fix null check nhưng bug là type mismatch"
Attempt 2: fix type mismatch → tests pass
Turns: 8+ pairs — higher cost, better accuracy

=== Multi-agent ===
SpecAnalyze: parse task, identify affected files → [file Y, tests Z]
Engineer: read Y, propose diff
Reviewer: check diff, request tests
Tester: run tests, report
PRWriter: draft PR description
Turns: 5 agents × 3-5 turns each = 15-25 total — expensive but organized

7. Common workflow patterns

7.1 Prompt chaining

Input → LLM1 → intermediate → LLM2 → output
# Ví dụ: draft email → tone check → publish

7.2 Routing

Input → Classifier → Route to specialized LLM
# Ví dụ: customer support → billing / technical / general

7.3 Parallelization

Input → [LLM_A + LLM_B + LLM_C parallel] → Aggregator
# Ví dụ: content moderation (safety + toxicity + relevance parallel)

7.4 Orchestrator-workers

Orchestrator LLM plan tasks → dispatch to worker LLMs → collect results
# Đây chính là AI Orchestrator pattern

7.5 Evaluator-optimizer

Generator LLM produce → Evaluator LLM critique → Generator revise
# Ví dụ: iterative writing improvement

9. Anti-patterns

Đừng làm
  1. Agent everything: nếu 1 LLM call giải quyết được, đừng dùng agent. Chi phí + latency tăng, unpredictability tăng.
  2. Deep chains without checkpoint: 10-step chain, 1 step fail → toàn bộ redo. Checkpoint intermediate results.
  3. Blind trust agent output: agent có thể hallucinate action success. Verify observation.
  4. LLM route control flow: dùng LLM decide next node → non-deterministic. Rule: routing = Python.
  5. No exit condition: agent loop forever. Always max iterations + progress detection.

✅ QA Gate

1. ReAct 3 components?

Thought (reasoning), Action (tool call), Observation (tool result). Loop until answer. Interleaved trong single LLM context.

2. Reflexion best cho task nào?

Verifiable output — code (run tests), math (check answer), agents với clear success signal. LLM tự phê bình và regenerate.

3. Anthropic: workflow vs agent — khi nào chọn?

Workflow (fixed path Python logic): predictable, cheap, testable. Agent (LLM decide): flexible, adaptable to novel input. Rule: start workflow, escalate agent nếu workflow không đủ.

4. Multi-agent 10 LLM calls vs 1 mega-prompt. Trade-off?

Multi-agent: specialized quality per role, easier debug, 10× cost + latency. Mega-prompt: cheap + fast but quality suffer (LLM confuse many concerns). Start mega, split thành agents khi observe specific weakness.

5. Anti-pattern: LLM route control flow. Vì sao bad?

Non-deterministic — same input, different route. Không unit test được. Debug khó (reproduce state impossible). Rule: LLM inside nodes, Python decides edges. AI Orchestrator follow this strictly.

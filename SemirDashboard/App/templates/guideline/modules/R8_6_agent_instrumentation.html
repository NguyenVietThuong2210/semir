R8.6 · AI Agent Instrumentation

Bài cuối của Observability & Evaluation — OpenTelemetry GenAI Semantic Conventions: 1 chuẩn chung để đổi observability backend mà không phải viết lại instrumentation.

🎯 Mục tiêu học

  • [Dễ] Hiểu vì sao cần 1 chuẩn đặt tên chung cho instrumentation, thay vì mỗi vendor tự đặt tên riêng.
  • [Trung bình] Nhớ 3 attribute cốt lõi trong namespace gen_ai.*.

📖 Cơ chế chi tiết

1. [Dễ] Vì sao cần chuẩn chung — vấn đề trước khi có OTel GenAI semconv

📖 Giải thích sâu — OpenTelemetry GenAI Semantic Conventions

Đây là bộ chuẩn (do OpenTelemetry — đã graduate CNCF — định nghĩa) quy định tên span, attribute key, metric instrument, event name mà MỌI instrumentation nên phát ra cho: model invocation, tool execution, agent run, retrieval, memory operation. Trước khi có chuẩn này, mỗi vendor (LangSmith, Langfuse, Arize...) tự đặt tên attribute riêng — chuyển vendor phải viết lại instrumentation. Có chuẩn chung → viết instrumentation 1 lần, đổi backend quan sát không cần sửa code.

⚠️ Lưu ý độ ổn định (cập nhật 2026)

Bản thân OpenTelemetry (dự án) đã graduate CNCF từ lâu, nhưng riêng bộ GenAI Semantic Conventions thì chưa — tính đến giữa 2026, toàn bộ attribute/span/metric/event trong namespace gen_ai.* vẫn mang nhãn ổn định "Development", chưa cái nào đạt "Stable". Tháng 6/2026 (v1.42.0), toàn bộ quy ước này còn được tách ra khỏi repo semantic-conventions chính sang 1 repo GenAI riêng để tăng tốc độ phát triển — tổ chức lại, không phải "graduate". Thực tế: attribute cho chat/embedding cơ bản (như gen_ai.request.model, gen_ai.usage.*) đã đủ ổn định để dùng cho dashboard production, nhưng quy ước cho agent/tool-orchestration vẫn đang định hình — cần coi là "khả năng cao còn đổi tên" khi áp dụng phần agent-specific.

2. [Trung bình] Attribute cốt lõi (namespace gen_ai.*)

AttributeÝ nghĩa
gen_ai.request.modelTên model được gọi
gen_ai.usage.input_tokens / gen_ai.usage.output_tokensSố token mỗi lượt gọi
gen_ai.response.finish_reasonsVì sao model dừng sinh (stop/length/tool_call...)

3. [Trung bình] 4 vùng phủ chính (2026)

📖 4 vùng phủ chính

(1) LLM client span — mỗi lệnh gọi API trực tiếp; (2) Agent span — workflow nhiều bước; (3) Event — nội dung prompt/completion (opt-in, KHÔNG mặc định bật vì có thể chứa dữ liệu nhạy cảm); (4) Metric — số liệu tổng hợp (latency, token/s, error rate). Với agent, mỗi tool call, mỗi LLM invocation, mỗi bước retrieval trở thành 1 child span — tạo ra 1 trace đầy đủ toàn bộ chuỗi suy luận, đây chính là dữ liệu thô để làm component-level eval (xem R8.4).

4. [Khó] Privacy mặc định — vì sao quan trọng

⚠️ Privacy mặc định

Mặc định KHÔNG capture nội dung prompt/tool argument cùng với telemetry — chỉ có metadata (tên model, số token, thời lượng). Phải bật opt-in riêng nếu cần capture nội dung, và khi bật phải xử lý như dữ liệu nhạy cảm (che PII trước khi lưu telemetry, không log thẳng).

5. [Trung bình] Agent span & tool span — 3 operation.name riêng cho agent

R6_6_multiagent_systems.html §6 đã vẽ ví dụ span cha-con lead→sub-agent nhưng chưa nêu TÊN operation chuẩn hoá — đây là phần OTel GenAI semconv quy định cụ thể cho agent (khác hẳn gen_ai.operation = "chat" của 1 lệnh gọi LLM đơn thuần):

gen_ai.operation.nameKhi nào phát raTên span quy ước
create_agentLúc khởi tạo 1 agent (gán persona, tool list, system prompt)create_agent {gen_ai.agent.name}
invoke_agentLúc agent bắt đầu chạy 1 task — span CHA của toàn bộ trajectoryinvoke_agent {gen_ai.agent.name}
execute_toolMỗi lần agent gọi 1 tool — span CON của invoke_agentexecute_tool {gen_ai.tool.name}
invoke_agent "research_agent"        (span cha — 1 task = 1 span này)
├─ chat (gen_ai.operation="chat")     — LLM quyết định bước tiếp theo
├─ execute_tool "get_price_history"   — span con, có gen_ai.tool.call.id riêng
├─ chat                               — LLM đọc kết quả tool, quyết định tiếp
├─ execute_tool "get_news_sentiment"
└─ chat                               — LLM tổng hợp câu trả lời cuối

→ Khác ví dụ multi-agent ở R6_6 (nhiều "invoke_agent" SONG SONG, mỗi sub-agent
  1 span invoke_agent riêng dưới 1 root chung) — ở đây là 1 AGENT ĐƠN chạy tuần
  tự nhiều bước, mỗi bước 1 loại span khác nhau (chat/execute_tool) lồng trong
  đúng 1 invoke_agent duy nhất.

6. [Trung bình] Cấu trúc attribute khi content capture được BẬT opt-in

Mục 4 nói "mặc định không capture nội dung" — nếu BẬT (opt-in), nội dung không được nhồi thẳng thành 1 chuỗi text tự do mà có 3 attribute có cấu trúc riêng, tách biệt theo vai trò:

AttributeChứa gì
gen_ai.system_instructionsSystem prompt/persona đã cấu hình cho agent
gen_ai.input.messagesToàn bộ message history gửi vào model ở lượt gọi này (user + assistant + tool result trước đó)
gen_ai.output.messagesMessage model sinh ra (bao gồm cả tool call nếu có)

Tách 3 attribute riêng (thay vì 1 blob text) cho phép dashboard lọc/tìm kiếm CHÍNH XÁC theo vai trò (VD chỉ tìm trong system instructions xem prompt có đổi version không, không lẫn với nội dung hội thoại) — và quan trọng hơn: cho phép áp rule che PII (mục 4) RIÊNG theo từng loại, vì gen_ai.input.messages (có thể chứa câu hỏi user) và gen_ai.system_instructions (do dev viết, hiếm khi có PII) có mức rủi ro khác hẳn nhau.

7. [Dễ] SDK tự động instrument — không phải lúc nào cũng viết span tay

L6_6_observability.html §2.4 dạy viết OTel span THỦ CÔNG (tự gọi tracer.start_as_current_span, tự set từng attribute). Thực tế 2026 có sẵn SDK tự động "bọc" sẵn các thư viện LLM/agent phổ biến, phát ra đúng chuẩn gen_ai.* mà không cần viết tay từng dòng:

SDKĐiểm mạnhPhù hợp backend nào
OpenLLMetry (Traceloop)Tự động bọc chain/agent/retriever/tool call; convention đã được upstream vào chuẩn OTel chính thức; hỗ trợ Python/TypeScript/Go/RubyDatadog, Honeycomb, New Relic, Grafana, SigNoz
OpenInferenceLớp spec bổ sung riêng cho LLM app, phủ rộng framework agent (30+ integration Python)Arize Phoenix (thiết kế đi cùng nhau)
OpenLITKhởi tạo dễ nhất (1 lệnh gọi hàm), có thêm GPU monitoring + OpAMP fleet managementKhi cần giám sát GPU cùng lúc với LLM call

Ý nghĩa thực hành: nếu stack đã dùng đúng thư viện SDK này hỗ trợ (VD Anthropic SDK, LangChain, LlamaIndex), gắn 1 dòng khởi tạo SDK là có đủ span gen_ai.* chuẩn ngay — không cần viết tay từng tracer.start_as_current_span như ví dụ thủ công ở L6_6. Viết tay vẫn cần thiết cho phần code KHÔNG được SDK nào bọc sẵn (VD 1 hàm nội bộ tự viết không qua thư viện LLM chuẩn).

🔢 Ví dụ cụ thể

# Instrumentation KHÔNG theo chuẩn (tự đặt tên) — phải viết lại khi đổi backend:
span.set_attribute("my_model_name", "claude-sonnet-5")
span.set_attribute("tokens_in", 1200)

# Instrumentation THEO CHUẨN gen_ai.* — đổi backend không cần sửa:
span.set_attribute("gen_ai.request.model", "claude-sonnet-5")
span.set_attribute("gen_ai.usage.input_tokens", 1200)
# Bất kỳ backend nào hỗ trợ OTel GenAI semconv (LangSmith, Langfuse, Arize...)
# đều hiểu ngay ý nghĩa của 2 attribute này, không cần mapping thủ công.

Worked example — gắn số liệu thật vào trace agent ở mục 5 (agent nghiên cứu cổ phiếu, 3 span chat + 2 span execute_tool):

invoke_agent "research_agent"                                total: 4,200ms
├─ chat (gen_ai.usage.input_tokens=800, output_tokens=120)     620ms
├─ execute_tool "get_price_history" (tool.call.id=call_1)      340ms
├─ chat (input_tokens=950, output_tokens=95)                   580ms
├─ execute_tool "get_news_sentiment" (tool.call.id=call_2)    1200ms  ← chậm bất
│                                                                     thường
└─ chat (input_tokens=1400, output_tokens=210)                1460ms

Tổng input_tokens  = 800+950+1400 = 3,150
Tổng output_tokens = 120+95+210   = 425
Tổng latency cộng dồn từng span   = 620+340+580+1200+1460 = 4,200ms (khớp đúng
  span cha invoke_agent — không có "thời gian chết" giữa các span trong ví dụ này)

→ Nhìn riêng span execute_tool "get_news_sentiment" (1200ms, chiếm 28.6% tổng
  thời gian) là điểm nghẽn rõ ràng — đúng tinh thần component-level eval đã học
  ở R8.4: có SỐ LIỆU cụ thể để biết sửa ở đâu, không phải đoán cả pipeline.

🎯 Ứng dụng dự án

L6_6_observability.html mục 2.4 đã dạy "instrument LLM call thủ công" bằng OTel span tự viết — cải thiện đáng làm nếu dự án mở rộng LLM hybrid mode: đổi tên attribute tự đặt sang đúng namespace gen_ai.* chuẩn, để nếu sau này đổi observability backend (VD từ tự viết log sang Langfuse/Arize, xem R8.5) không phải viết lại toàn bộ instrumentation.

Áp cụ thể mục 5-7 vào .claude/skills/daily-investor-report/scripts/collect_and_build.py: pipeline hiện tại không phải "agent" theo đúng nghĩa OTel GenAI (không có vòng lặp LLM tự quyết định bước tiếp theo — các Step chạy tuần tự theo code Python cố định), nên KHÔNG cần span invoke_agent/execute_tool của mục 5. Nếu dự án dùng thư viện Anthropic SDK trực tiếp (đúng hiện trạng), OpenLLMetry (mục 7) là lựa chọn phù hợp nhất trong 3 SDK — hỗ trợ Anthropic SDK trực tiếp, và convention của nó đã upstream vào chuẩn OTel chính thức, không khoá cứng vào riêng 1 backend nào (khác OpenInference thiết kế đi cùng Arize Phoenix).

⚠️ Sai lầm thường gặp

⚠️ Sai lầm thường gặp

1. Log thẳng nội dung prompt/PII vào telemetry mặc định — vi phạm privacy default của OTel GenAI semconv.

2. Tự đặt tên attribute riêng thay vì dùng namespace gen_ai.* chuẩn — mất khả năng đổi backend mà không viết lại code.

3. Bật event capture (nội dung prompt) mà không xử lý PII trước — dữ liệu nhạy cảm bị lưu trần trong hệ thống telemetry.

4. Nhồi content capture thành 1 chuỗi text tự do thay vì đúng 3 attribute có cấu trúc (gen_ai.system_instructions/gen_ai.input.messages/gen_ai.output.messages, mục 6) — mất khả năng áp rule che PII riêng theo từng loại nội dung.

5. Dùng invoke_agent/execute_tool cho pipeline KHÔNG phải agent thật (VD 1 script tuần tự cố định không có vòng lặp LLM tự quyết định) — gán nhãn sai khiến dashboard hiểu nhầm bản chất hệ thống.

6. Viết tay toàn bộ span dù thư viện đang dùng đã có SDK tự động (mục 7) — tốn công trùng lặp, dễ quên attribute so với SDK đã được cộng đồng kiểm chứng.

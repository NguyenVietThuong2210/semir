9.2 · LLM Ops — production discipline

Prompt versioning, canary + shadow rollout, model routing, semantic caching, cost accounting, drift detection, safe rollback. Cách chạy LLM app như 1 production system, không phải demo.

Level 9 · Expert · ~35 phút

🎯 Learning objectives

  • Prompt versioning + A/B testing

  • Model routing (cheap → expensive)
  • Cost accounting + budget alerts
  • Drift detection cho LLM output
💡 LLM Ops bằng ngôn ngữ đời thường

Công thức phở bà nội truyền qua giấy viết tay: Có 3 phiên bản v1/v2/v3 (bà chỉnh gia vị theo mùa). Nếu bát phở hôm nay dở, cần biết đang dùng version nào để rollback về v2.

Prompt = code: cần git, cần review, cần A/B test, cần rollback. Anti-pattern: prompt hardcode trong Python string → sửa phải redeploy 20 phút. Best practice: prompt trong YAML/DB → hot-swap 60 giây.

Canary vs Shadow: Canary = cho 10% khách thử phở v3 mới. Shadow = 100% khách nhận v2 cũ, đồng thời nấu v3 để so sánh (khách không biết) — zero risk nhưng đắt gấp đôi.

Model routing: Câu dễ (chào hỏi) → Haiku ($0.25/1M). Câu khó (design review) → Opus ($15/1M). Tự động chọn tiết kiệm 40-90% cost.

3. Model routing (cost-aware)

Idea: cheap model cho easy queries, expensive cho hard.

def route(query):
    # Tier 1: classifier hoặc rule-based
    if is_simple_lookup(query):
        return "haiku"           # $0.25/1M in
    complexity = classifier.predict(query)
    if complexity < 0.3:
        return "haiku"
    elif complexity < 0.7:
        return "sonnet"          # $3/1M in
    else:
        return "opus"            # $15/1M in

Router options

  • RouteLLM (Berkeley 2024) — trained router, 40-90% cost savings
  • LiteLLM Router — rule-based, load balancing
  • Custom classifier — bge-small + LR head, cheap

4. Semantic caching

Exact-match cache miss cho "Q2 revenue" vs "quý 2 doanh thu". Semantic cache = embed query, lookup vector store.

def semantic_cache_lookup(query, threshold=0.95):
    emb = embed(query)
    hits = vector_store.search(emb, top_k=1)
    if hits and hits[0].score > threshold:
        return hits[0].cached_response  # HIT
    return None  # MISS → call LLM, then cache

# GPTCache, Redis + vec, Momento

Warning: cache staleness. TTL + invalidate khi data source đổi.

8. Case study — PredictStock LLM Hybrid mode

Template + LLM 2-stage

Daily report có 2 modes:

  • Template mode: pure Python (fast, deterministic, ~42s cho 86 tickers)
  • LLM Hybrid mode: template + LLM deep-dive cho top-10 picks (slow, richer thesis)

Ops discipline:

  • Template mode = production default (SLA-guaranteed)
  • LLM mode = shadow output, save to reports/_llm/{stamp}_llm.json
  • Validator llm_qa_checklist.py gate publish (§19 discipline, checks C1-C20)
  • Fail → skip LLM section, publish template only. Never crash entire report.

Đây là degraded serving pattern — LLM optional, template mandatory. User luôn có report.

🎯 Deep-dive — Guardrails, per-user rate limit, cost attribution, prompt A/B stat framework (VN)

Analogy VN — quán phở đông khách

(1) Bảo vệ cửa (guardrails) chặn khách say làm loạn. (2) Mỗi khách chỉ được 3 bát/ngày (rate limit per user). (3) Ghi hóa đơn theo bàn để biết bàn nào ăn tốn (cost attribution). (4) Thử món mới tuần này 30% khách, so evidence có ngon hơn (A/B). Backend LLM cần cả 4.

def check_budget(user_id, est_tokens):

Prompt A/B statistical framework

# Setup
control:   prompt_v2, 50% traffic
treatment: prompt_v3, 50% traffic

# Metrics
primary: user_thumbs_up_rate  (binary)
guardrail: latency_p95, cost_per_call, refusal_rate

# Sample size (2-proportion test, alpha=0.05, power=0.8)
# alpha=0.05: chấp nhận 5% khả năng báo "có hiệu ứng" trong khi thực ra KHÔNG có (false positive)
# power=0.8: 80% khả năng PHÁT HIỆN được hiệu ứng thật nếu nó thực sự tồn tại
# Baseline 60% thumbs up, MDE (minimum detectable effect — chênh lệch nhỏ nhất
# bạn muốn có thể phát hiện được) 3pp (3 điểm phần trăm) → n ≈ 4200/arm
# Chạy đến khi đạt n, KHÔNG peek sớm (multiple comparison bias)

# Sequential test (nếu cần): mSPRT, always-valid p-value — xem giải thích chi tiết bên dưới

# Decision:
# - primary win + guardrails OK → ship v3
# - primary flat but latency worse → rollback
# - primary win but refusal_rate +5% → investigate, không ship

Vì sao "peek sớm" phá p-value, và always-valid p-value/mSPRT sửa thế nào

💡 Vấn đề cụ thể

p-value chuẩn (dùng ở phần "Sample size" phía trên) được tính toán với GIẢ ĐỊNH bạn chỉ nhìn kết quả ĐÚNG 1 LẦN, sau khi đã thu đủ n mẫu đã định trước. Nếu bạn nhìn kết quả MỖI NGÀY (peek) và dừng thí nghiệm ngay khi thấy p<0.05 lần đầu tiên, bạn đang cho mình NHIỀU CƠ HỘI để "trúng số" ngẫu nhiên — giống việc tung đồng xu 20 lần rồi chỉ báo cáo lần tung ra 5 mặt ngửa liên tiếp, bỏ qua 15 lần còn lại. Anti-pattern "A/B peek sớm" ở dưới đã nêu con số: false positive rate thực tế lên >30% dù mỗi lần check bạn vẫn dùng ngưỡng "chuẩn" p<0.05.

Cơ chế always-valid p-value (mSPRT — mixture Sequential Probability Ratio Test): thay vì tính 1 p-value CỐ ĐỊNH dựa trên n mẫu đã định trước, mSPRT tính lại 1 "always-valid p-value" SAU MỖI ĐIỂM DỮ LIỆU MỚI, với công thức được thiết kế đặc biệt sao cho DÙ bạn nhìn bao nhiêu lần đi nữa (peek liên tục), xác suất false positive TỔNG THỂ (qua toàn bộ quá trình theo dõi) vẫn bị giữ chặn ở mức alpha đã đặt (VD 5%) — không tăng dần theo số lần peek như p-value chuẩn.

# So sánh trực quan: p-value chuẩn vs always-valid p-value

# p-value chuẩn (Fixed-horizon test):
# - Tính 1 lần, SAU KHI đã thu đủ n=4200/arm đã định trước
# - Peek sớm (n=1000) rồi dừng khi thấy "có ý nghĩa" → false positive rate THỰC bị bơm phồng
# - An toàn CHỈ NẾU cam kết không nhìn tới khi đủ n

# Always-valid p-value (mSPRT):
# - Tính LẠI mỗi khi có data mới (n=100, 200, 300... tới bao nhiêu cũng được)
# - Ngưỡng dừng đã được điều chỉnh SẴN để bù cho việc nhìn nhiều lần
# - Có thể dừng SỚM HƠN nếu effect rõ ràng ngay, mà KHÔNG bơm phồng false positive
# - Đánh đổi: cần nhiều mẫu hơn 1 chút so với p-value chuẩn NẾU hiệu ứng thực sự yếu,
#   để bù cho "cái giá" của việc được phép nhìn liên tục

⚠️ Chỗ dễ nhầm nhất: mSPRT không phải "làm p-value chuẩn nhanh hơn" — nó là 1 CÔNG THỨC THỐNG KÊ KHÁC hoàn toàn, đánh đổi 1 chút hiệu suất (cần thêm mẫu cho hiệu ứng nhỏ) để đổi lấy quyền được PEEK LIÊN TỤC mà không phá vỡ tính đúng đắn thống kê. Nếu team đã cam kết pre-declare n và không peek, dùng p-value chuẩn ở phần "Sample size" phía trên là đủ và đơn giản hơn — mSPRT chỉ cần thiết khi business thực sự MUỐN xem kết quả hàng ngày và có thể dừng sớm.

Insight: đây chính là lý do kỹ thuật đằng sau anti-pattern "A/B peek sớm" ngay bên dưới — không phải "peek là xấu" một cách mơ hồ, mà là peek với công thức p-value SAI (fixed-horizon) mới là vấn đề; peek với công thức ĐÚNG (mSPRT/always-valid) hoàn toàn hợp lệ.

VN scenario — PredictStock LLM Hybrid A/B

Baseline (v2): template only, cost $0/report
Treatment (v3): template + LLM deep-dive top-10 picks, cost $0.18/report

Primary metric: user_engagement_time_on_page
Guardrail: hallucination_rate (llm_qa_checklist.py C1-C20 fail rate)

Kết quả sau 2 tuần (n=100 reports/arm):
  engagement +45% (18min → 26min, p<0.01) ✓
  hallucination_rate 0.5% (target <1%) ✓
  cost $18/month acceptable

→ Ship v3 as default. Keep v2 fallback nếu LLM API down (degraded serving).

Anti-pattern VN

  • Không rate limit per user: 1 script kiddie loop request → bill $10k/ngày. Fix: Redis token bucket, alert threshold.
  • A/B peek sớm: check kết quả mỗi ngày, ship khi p<0.05 lần đầu → false positive 30%+. Fix: pre-declare n, hoặc sequential test.
  • Cost attribution flat: chỉ log total cost/day → không biết feature nào tốn. Fix: log per-feature + tenant.
  • Guardrail block silent: reject prompt mà không log → không debug được. Log MỌI block với reason + input snippet (redacted).

Interview Q&A (mở rộng)

  1. Q: Guardrail cascade order? A: Cheap → expensive. (1) Regex/schema (µs). (2) Small classifier (Llama Guard, 50ms). (3) Guard LLM (Haiku, 500ms) chỉ khi 1+2 uncertain. Đừng chạy guard LLM mọi request → cost 2×.
  2. Q: Shadow traffic có bill user không? A: Không. Shadow = infra cost, thuộc R&D budget. Log với flag shadow=true để exclude khỏi tenant billing.
  3. Q: Prompt version rollback khi nào NÊN vs KHÔNG? A: Rollback khi metric drop > noise band. KHÔNG rollback vì 1 user complain (anecdote) — cần signal thống kê. Cũng KHÔNG rollback khi bug ở downstream (guardrail bug pretending prompt bug).

✅ QA Gate

1. Canary vs shadow — khác gì?

Canary = tỷ lệ nhỏ user thấy new version (10%). Shadow = 100% user thấy old, new chạy song song log-only, so sánh offline. Shadow zero risk nhưng đắt gấp đôi cost. Canary catch được real user issue.

2. Model routing tiết kiệm bao nhiêu?

RouteLLM Berkeley 2024: 40-90% cost cut với quality drop <5%. Cần eval kỹ trên distribution của bạn — router train trên general benchmark có thể fail trên domain-specific.

3. Semantic caching risk?

Threshold too low → wrong cached answer (query khác nghĩa). Too high → miss rate cao. TTL không cover khi ground truth data đổi (stock price). Best cho static Q&A (docs, FAQ).

4. Drift detection signals?

Output length dist, JSON parse rate, refusal rate, tool-call freq, LLM-judge score. Track baseline, alert khi rolling drop. Đặc biệt sau provider version bump (Claude 4.6 → 4.7).

5. Prompt embedded in code vs manifest — vì sao tách?

Rollback speed. Prompt trong code = redeploy 20 min. Prompt trong manifest = config flip 60s. Cũng cho phép non-eng edit prompt qua UI, A/B test, per-tenant customization.

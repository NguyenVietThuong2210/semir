8.4 · Spec-Driven Development (SDD, SpecKit)

Framework để AI agents build software correctly. Spec là source of truth, không phải code. Constitution, DoD, task decomposition. Case study ai_orchestrator SpecAnalyze + TaskDecompose agents.

💡 Spec-Driven Development bằng ngôn ngữ đời thường

Xây nhà không bản vẽ: Chủ nhà nói "xây tôi 1 căn 3 tầng đẹp". Thợ mộc + thợ điện + thợ nước mỗi người hiểu 1 kiểu. Kết quả: cửa mở ra tường, ổ điện đặt trong bồn tắm, cầu thang dẫn thẳng vào phòng ngủ chị dâu. Cảnh này quen chưa?

Có spec chi tiết trước: Bản vẽ ghi rõ "phòng khách 30m², cửa hướng Đông, 4 ổ điện tường A". Mọi thợ đọc cùng 1 bản → thi công đúng. Đó là SDD.

AI code assistant: Nếu bảo "viết chatbot cho tôi" → LLM đoán mò. Nếu đưa spec chi tiết (endpoints, data model, error handling, tests) → LLM code chính xác + có thể verify.

SpecKit: framework để viết spec có cấu trúc: constitution.md (nguyên tắc chung) → feature-N.md (spec từng tính năng) → tasks/ (chia nhỏ 30-90 phút). AI Orchestrator SpecAnalyze agent chuyên làm việc này.

1. Vấn đề SDD giải quyết

AI-generated code failure modes
  1. Ambiguous requirement → LLM assume incorrectly
  2. Missing edge cases → code work happy path fail production
  3. Underspecified acceptance → "done" undefined
  4. Constitution violation → code breaks project principles
  5. Duplicated concerns → 5 agents implement same thing 5 ways

SDD (Spec-Driven Development): instead spec being informal doc, spec là formal artifact — validated, decomposed, tracked. LLM implement từ spec (not from vague prompt).

1.5 · BDD / Gherkin cho AI feature — test-first LLM development

🥒 Deep-dive — BDD, Gherkin, prompt regression suite

Vấn đề — LLM feature không testable như code truyền thống

Function add(2,3)==5 deterministic → 1 unit test đủ. LLM summarize(article) stochastic → 1 example không cover. Cần BDD (Behavior-Driven Development) với scenario matrix.

Gherkin cho LLM feature

Gherkin = cú pháp viết scenario theo cấu trúc Given-When-Then (Cho trước-Khi-Thì), đọc được bằng ngôn ngữ tự nhiên bởi cả PM lẫn engineer, đồng thời parse được thành test tự động — không phải chỉ là "code ví dụ", mà là 1 định dạng chuẩn có công cụ chạy trực tiếp (VD Cucumber).

Feature: Investor thesis generation for VN stocks
  As a retail investor
  I want AI to write thesis with grounded numbers
  So that I don't get fooled by hallucinated data

  Background:
    Given data collector đã chạy successfully
    And embedded JSON có 30 tickers với fields: cc, senior_score, verdict

  Scenario: Thesis references only grounded numbers
    Given ticker "VNM" với cc=0.72 và senior_score=8
    When LLM generate thesis
    Then mọi số % trong thesis phải xuất hiện trong embedded JSON
    And regex "\d+(\.\d+)?%" mỗi match phải grep-verify được

  Scenario: Divergence detection
    Given ticker "FPT" với ai_signal=UP và senior_score=BEARISH
    When LLM generate thesis
    Then output PHẢI chứa "divergence_note"
    And verdict PHẢI KHÔNG được "STRONG BUY"

  Scenario: Confidence out-of-range drops pick
    Given ticker "XYZ" với cc=0.45
    When LLM generate thesis
    Then ticker phải bị drop khỏi top picks

VN scenario — PredictStock §19 as BDD case

SKILL.md §19 (Pre-Thesis Discipline Checklist, 7 bước — anchor giá, verify chart_pattern, v.v.) và §20's QA checklist (mã C1-C19, VD C1 = "didn't anchor the price", C11 = "recommending BUY on broken pattern") là những discipline check tương đương tinh thần Gherkin scenario ở trên, enforce bởi llm_qa_checklist.py. Đây là BDD ở production — fail check → rename file _FAILED.html, không publish. Đây là why §19 tồn tại: FPT bug tháng 6/2026 không có check tương đương → không catch. Sau đó §19/§20 ra đời = scenario matrix, mỗi check 1 automated assertion.

Anti-pattern

  • Test bằng "manual eyeball": run 3 prompts, look OK → ship. Prompt change ngày mai break silent. Fix: automated regression suite trong CI.
  • Only happy path: test 1 ticker bình thường. Miss edge (divergence, low cc). Fix: scenario matrix cover mỗi rule.

Interview Q&A

  1. Q: BDD cho LLM khác BDD truyền thống? A: Assertion không thể strict equality (LLM stochastic). Dùng regex + schema + semantic sim + LLM-judge. Fixture snapshot input để reproducible, temperature=0 để giảm noise.
  2. Q: Prompt regression suite chạy khi nào? A: (1) Trên mỗi prompt/SKILL.md change (pre-commit), (2) Nightly cross-model check (Claude 4.6 vs 4.7 output drift), (3) Post-provider-update trigger.
  3. Q: Vì sao Gherkin không JSON test cases? A: Gherkin human-readable, PM/business viết được. JSON tests eng-only. SDD chú trọng spec là source of truth — PM viết scenario, eng implement + LLM code. Common language critical.

2. SpecKit (GitHub 2025)

Framework từ GitHub encourage SDD với AI code generation:

Structure:
├── spec/
│   ├── constitution.md      ← project principles (immutable)
│   ├── feature-{n}.md       ← feature spec
│   └── tasks/
│       ├── task-1.md        ← decomposed tasks
│       └── task-2.md
├── src/                     ← implementation
└── tests/                   ← from acceptance criteria

Constitution

# constitution.md example:
- All money handling MUST use decimal.Decimal, not float
- API responses MUST include request_id in header
- No feature launches without health check
- Database migrations MUST be backward compatible
- Security: no PII in logs, redact at ingress

# Immutable across features. Guards project integrity.

Feature spec

# feature-auth.md
## Requirement
Enable users login with email + password.

## Acceptance criteria (DoD)
1. Endpoint POST /auth/login accepts {email, password}
2. Returns 200 + JWT token if valid
3. Returns 401 + error message if invalid
4. Password stored as bcrypt hash
5. Rate limit: 5 attempts / IP / minute
6. Audit log on every attempt

## Constitution compliance
- Uses decimal (n/a — no money)
- Request_id header (yes, via middleware)
- Health check (yes, existing)
- PII: password redacted from logs (yes)

## Non-goals
- Social login (future)
- MFA (future)
- Password reset (separate spec)

2.5 · SpecKit thật hoạt động qua slash-command nào — không chỉ folder structure

💡 Vấn đề thật: §2 mới cho thấy KẾT QUẢ (folder constitution.md/feature-N.md/tasks/) chứ chưa nói QUY TRÌNH tạo ra chúng

SpecKit thật (github/spec-kit, dùng qua Claude Code/Copilot/Cursor) không phải chỉ là "1 cấu trúc folder" — nó là 1 chuỗi slash-command chạy TUẦN TỰ, mỗi command sinh ra 1 phần của cấu trúc §2, và command SAU đọc output của command TRƯỚC làm input. Giống dây chuyền sản xuất: mỗi trạm chỉ làm 1 việc, nhận bán thành phẩm từ trạm trước, giao cho trạm sau — không phải 1 người viết hết constitution+feature+tasks trong 1 lần.

LệnhLàm gìInputOutput
/speckit.constitutionViết nguyên tắc BẤT BIẾN của dự án (coding standard, kiến trúc, testing bắt buộc) — chạy 1 LẦN đầu dự án, không phải mỗi featureUser trả lời câu hỏi về nguyên tắc teamconstitution.md
/speckit.specifyĐịnh nghĩa CÁI GÌ cần xây (requirement), KHÔNG bàn cách làm (how)User mô tả feature bằng ngôn ngữ tự nhiênfeature-N.md (phần "what")
/speckit.clarifyĐặt câu hỏi làm rõ vùng CHƯA RÕ trong spec vừa viết — tối đa 5 câu, KHÔNG hỏi tràn lanfeature-N.md từ bước trênfeature-N.md cập nhật, đã điền vùng mơ hồ

⚠️ Chỗ dễ nhầm nhất: /speckit.constitution chạy 1 LẦN đầu dự án (nguyên tắc áp dụng cho MỌI feature sau này), còn /speckit.specify → /speckit.tasks chạy LẶP LẠI cho MỖI feature mới — không phải cả 6 lệnh đều chạy mỗi lần có feature mới. Nhầm điểm này dẫn tới việc viết lại constitution mỗi feature — lãng phí và có thể tạo ra 2 constitution mâu thuẫn nhau.

Insight: so với ai_orchestrator ở §3 dưới đây (SpecAnalyze + TaskDecompose — 2 agent Python tự viết), SpecKit đạt được HIỆU QUẢ TƯƠNG TỰ (spec → phân tích → chia task) nhưng bằng 1 bộ slash-command chuẩn hoá công khai (open-source, dùng được với bất kỳ AI coding tool nào hỗ trợ Markdown command), thay vì code Python riêng theo dự án — đánh đổi: SpecKit dễ tái sử dụng across project hơn, nhưng ai_orchestrator's Python agents có thể nhúng logic domain-specific sâu hơn (VD constitution machine-checkable rules ở §4 dưới).

3. ai_orchestrator SDD flow

2 dedicated agents cho SDD

File: agents/spec_analyze.py, agents/task_decompose.py

SpecAnalyze: nhận Analyser output, validate against constitution + SDD principles, output findings.

class SpecAnalysisFinding(TypedDict):
    pass_name: str
    # "duplication" | "ambiguity" | "underspecification"
    # | "constitution" | "coverage"
    severity: str  # CRITICAL|HIGH|MEDIUM|LOW
    location: str  # "spec.md §3.2"
    description: str
    suggestion: str

class SpecAnalysisReport(TypedDict):
    findings: list[SpecAnalysisFinding]
    summary: str
    approved: bool  # True only if no CRITICAL/HIGH findings

Findings example:

  • [HIGH] Ambiguity in auth requirement (§2.3): "user login" — via email? SSO? Missing.
  • [MEDIUM] Underspecified error format — spec says "return error" but not schema.
  • [CRITICAL] Constitution violation — money field not decimal.

TaskDecompose: sau spec approved, break vào fine-grained engineering tasks:

# Real schema, orchestrator/context.py:
class Task(TypedDict):
    id: str  # T1, T2, ...
    title: str
    description: str
    priority: int
    status: str
    phase: str
    depends_on: list[str]  # task IDs
    parallel: bool

# Example decomposition of auth feature:
T1: "Create login endpoint skeleton" (30 min)
T2: "Add password hash + verify" (45 min, depends T1)
T3: "Generate JWT token" (30 min, depends T2)
T4: "Add rate limit middleware" (60 min, depends T1)
T5: "Write integration tests" (60 min, depends T1-T4)

4. Constitution enforcement

Machine-verifiable constitution

Not all constitution rules automatable. Split:

  • Machine-checkable: linter rules (no float for money), Grep patterns, unit tests
  • SpecAnalyze-checkable: LLM reads spec, flag violations
  • Human-checkable: subjective (naming quality)

Balance: automate what possible, human catch rest.

🔍 So sánh TDD vs BDD vs SDD chi tiết (đọc SAU section 5 basic table)

Ví dụ concrete — cùng feature "user login" viết bằng 3 methods

=== TDD (Test-Driven) ===
Step 1: Viết test TRƯỚC
def test_login_success():
    user = create_user("alice", "pass123")
    result = login("alice", "pass123")
    assert result.success == True

Step 2: Chạy test → FAIL (function chưa có)
Step 3: Viết code minimum để pass
def login(username, password): ...

Step 4: Refactor
Focus: correctness thông qua tests. Ngắn feedback loop.

=== BDD (Behavior-Driven) ===
Step 1: Viết scenario ngôn ngữ tự nhiên trước
Feature: User login
  Scenario: Successful login
    Given a user "alice" with password "pass123"
    When they submit login form
    Then they should be redirected to dashboard
    And their session should be active

Step 2: Convert scenario → executable tests (Cucumber)
Step 3: Implement code

Focus: Product + Dev cùng ngôn ngữ. Tránh miscommunication.

=== SDD (Spec-Driven) ===
Step 1: Viết Spec formal
constitution.md:
  - Auth uses bcrypt (min cost=12)
  - Sessions expire 24h
  - Rate limit: 5 attempts / 15 min per IP

feature-023-login.md:
  ## API
  POST /login
  Request: { username: string, password: string }
  Response: { session_token: string, expires_at: ISO8601 }

  ## Edge cases
  - Wrong password → 401, don't leak "user not exists"
  - Rate limited → 429 with Retry-After header

  ## DoD (Definition of Done)
  - [ ] Endpoint implemented
  - [ ] 15 unit tests (correct + edge)
  - [ ] Integration test with Postgres
  - [ ] OpenAPI schema updated
  - [ ] Logs redact password

Step 2: Give spec to LLM (Claude Code) → generate code
Step 3: Validate against DoD checklist

Focus: LLM cần contract chi tiết. Nếu spec mơ hồ → LLM đoán → bug.

6. LLM code quality patterns

6.1 Spec review checklist

Before pass spec to Engineer LLM, verify:
□ Requirement clear (no "should", "maybe", "consider")
□ Acceptance criteria measurable
□ Edge cases enumerated
□ Constitution compliance stated
□ Non-goals explicit (prevent scope creep)
□ Dependencies listed
□ Test scenarios include failure cases
□ Success metric defined

6.2 Golden path + Failure paths

# Not just happy path:
Test cases MUST include:
- Golden path (typical success)
- Boundary (empty input, huge input)
- Invalid input (malformed)
- Concurrent (race conditions)
- Failure (dependency down, timeout)
- Recovery (retry logic)

7. SpecKit implementation từ đầu

# tools/spec_analyze.py

async def analyze_spec(spec_text: str, constitution: str) -> SpecAnalysisReport:
    prompt = f"""
    Constitution:
    {constitution}

    Feature spec:
    {spec_text}

    Analyze the spec for:
    1. Duplication: any part duplicating existing feature?
    2. Ambiguity: unclear terms or assumptions?
    3. Underspecification: missing edge cases?
    4. Constitution violation: any rule broken?
    5. Coverage: acceptance criteria include failure paths?

    Return JSON with findings + severity + location + suggestion.
    Approve only if no CRITICAL/HIGH.
    """
    result = await claude.messages.create(
        model="claude-opus-4-7",
        messages=[{"role": "user", "content": prompt}],
        response_format={"type": "json_schema", "schema": SpecAnalysisReport.__annotations__}
    )
    return json.loads(result.content)

8. Common pitfalls

  1. Spec bloat: 20-page spec cho 1h task → engineer skim → miss things. Fix: right-size spec to feature complexity.
  2. Living spec drift: spec written, code diverge over time. Fix: spec + code cross-reference, update spec on change.
  3. Rubber-stamp SpecAnalyze: agent auto-approve → provide value. Fix: prompt engineer for CRITICAL detection, calibrate approval threshold.
  4. Task decomposition too fine: 100 tasks 10-min each → overhead high. Fix: sweet spot 30-90 min tasks.

10. Interview cheat sheet

  1. "SDD vs TDD" → SDD: spec is source of truth (LLM implement from spec). TDD: tests are source (test-first). Complement each other. SDD prevents assumption bugs; TDD prevents regression.
  2. "When SDD overhead worth it?" → AI-generated code, safety-critical, cross-team collaboration, greenfield. Not: quick prototype, exploratory research.
  3. "Constitution examples?" → Money = decimal, PII logging, health checks, backward-compatible migrations, naming conventions.
  4. "How measure SDD success?" → Fewer rework loops, faster onboarding new agents/devs, fewer production bugs from ambiguity, reduced spec review time (SpecAnalyze catch issues).

✅ QA Gate

1. SDD 3 lợi thế đối với AI code generation?

(1) Spec formal reduce LLM assumption errors. (2) Constitution enforce cross-feature consistency. (3) DoD explicit make "done" measurable, prevent scope creep.

2. SpecAnalyze finding "CRITICAL" — pipeline gì xảy ra?

Approved=False. Human gate reject → back Analyser để redesign. Max spec revisions (V2 plan: 2). Nếu exceed → fail-forward tới Retrospective.

3. Task decompose sweet spot?

30-90 min per task. Too fine (10 min): overhead orchestration. Too coarse (4h): agent lose context mid-task, fail localization difficult.

4. Constitution rule example machine-checkable?

"No float for money" → grep float\( in money-related files. Linter rule. Custom mypy plugin verify decimal.Decimal type. Detects violation pre-commit.

5. SDD overhead worth it cho 1h prototype?

Không. Overhead vs benefit skewed for short work. Skip SDD, use LLM interactively. SDD shine cho: features 1+ day, team collaboration, safety-critical, AI-augmented pipelines.

6.4 · Checkpointing + Resume

Persistence for long-running agents. PostgresSaver, resume patterns, thread management. Production HA requirement.

Level 6 · Agents · ~25 phút

🎯 Learning objectives

  • Vì sao agents cần checkpointing
  • PostgresSaver setup + schema
  • Resume after crash / HITL / rollback
  • Thread + checkpoint versioning
💡 Checkpointing bằng ngôn ngữ đời thường

Chơi RPG 40 giờ không save: Chết ở boss cuối → phải chơi lại từ đầu. Đau lòng. Đó là lý do có nút Save/Load.

Agent 20 phút chạy 8 nodes: LLM API rớt ở phút 15 (node 6) → không có checkpoint → phải chạy lại 6 nodes → tốn thêm 15 phút LLM cost + user chờ.

PostgresSaver: Sau mỗi node, LangGraph tự lưu state vào Postgres. Khi resume, load state từ node cuối → tiếp tục node 7. Giống save game — không mất progress.

Bonus: Checkpoint cho phép time travel — user muốn quay lại node 3 để đổi input → load state lúc node 3 → chạy tiếp với input mới. Debug + human-in-loop cực dễ.

⚠️ Common confusion — Checkpoint vs Cache

Hai khái niệm nghe giống ("lưu dữ liệu để dùng lại") nhưng mục đích ngược nhau:

  • Cache = lưu kết quả tính toán để tránh tính lại (tối ưu tốc độ/tiền). Mất cache → vẫn đúng, chỉ chậm hơn (tính lại từ đầu). Cache không phải nguồn sự thật — có thể xoá bất cứ lúc nào mà hệ thống vẫn hoạt động đúng.
  • Checkpoint = lưu tiến trình đang dang dở để không phải làm lại. Mất checkpoint → mất progress thật sự, phải chạy lại từ đầu (tốn tiền + thời gian, không chỉ chậm). Checkpoint là nguồn sự thật về "agent đang ở đâu".

Ví dụ: prompt caching (cơ chế đầy đủ ở L5_1_prompt.html §6.3) lưu lại prefix token đã encode để rẻ hơn — xoá cache thì vẫn ra đúng câu trả lời, chỉ tốn thêm tiền. (L6.6 chỉ nhắc tới việc theo dõi cache hit rate như 1 metric giám sát, không dạy lại cơ chế.) Checkpoint ở module này lưu ProjectContext sau mỗi node — xoá checkpoint giữa chừng thì job coi như mất trắng, phải chạy lại từ node 1.

1. Vì sao?

  • Agent chạy long (30 min - 2h cho feature pipeline)
  • Container restart / crash → mất progress → user re-run từ đầu
  • HITL: pause chờ user approve — có thể hours later
  • Audit: compliance requires replay of decisions
  • Debug: reproduce state at any point

3. Schema (Postgres)

-- Simplified LangGraph checkpoint schema:

CREATE TABLE checkpoints (
    thread_id       TEXT NOT NULL,
    checkpoint_id   TEXT NOT NULL,    -- e.g. v001, v002 (ordered)
    parent_id       TEXT,             -- link to previous checkpoint
    state           JSONB NOT NULL,   -- full ProjectContext serialized
    metadata        JSONB,            -- source, task_id, agent
    PRIMARY KEY (thread_id, checkpoint_id)
);

CREATE INDEX idx_thread_recent ON checkpoints(thread_id, checkpoint_id DESC);

from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver
from psycopg_pool import AsyncConnectionPool

pool = AsyncConnectionPool(
    conninfo=f"postgres://user:pass@host:5432/orch",
    max_size=20,

5. Resume patterns

5.1 After crash

# On restart:
config = {"configurable": {"thread_id": "job_abc123"}}
state = await app.aget_state(config)
print(state.next)   # ["engineer"] — biết đang ở đâu

# Continue from last checkpoint
await app.ainvoke(None, config=config)   # None = pick up from state

5.2 HITL approval

# Runtime pauses at human_gate. State has next=["human_gate"]
# User reviews in UI, approves.

from langgraph.types import Command
await app.ainvoke(
    Command(resume={"approved": True, "feedback": "LGTM"}),
    config=config,
)

5.3 Rollback to earlier state

# Get history:
history = [c async for c in app.aget_state_history(config)]
# Rollback to checkpoint 3 back:
rollback_config = history[3].config
await app.ainvoke(new_input, config=rollback_config)
# Creates new branch from checkpoint 3

"New branch" nghĩa là gì? Nhớ lại schema section 3: mỗi checkpoint có parent_id trỏ về checkpoint trước nó — giống commit Git trỏ về parent commit. Bình thường chuỗi checkpoint đi thẳng (v1 → v2 → v3 → v4 → v5). Khi bạn rollback về v3 rồi ainvoke với input mới, LangGraph không xoá v4/v5 — nó tạo v3' mới có parent_id = v3, tạo thành nhánh rẽ:

v1 → v2 → v3 → v4 → v5          (nhánh cũ, vẫn còn nguyên — dùng để so sánh/audit)
              └──► v3' → v4'    (nhánh mới, từ input đã sửa)

Đây chính xác là cơ chế "time travel" nhắc ở đầu bài: bạn không mất lịch sử cũ, chỉ tạo một dòng thời gian song song. Hữu ích khi debug ("thử input khác xem có sửa được bug không") mà không phá dữ liệu gốc để audit.

6. Thread lifecycle

# Each thread_id = 1 job/conversation
# Multiple threads run parallel (multi-tenancy)

# Naming convention:
thread_id = f"{user_id}:{job_type}:{uuid4()}"
# e.g., "u123:feature:abc-def"

# Cleanup old threads:
DELETE FROM checkpoints WHERE thread_id IN (
    SELECT thread_id FROM checkpoints
    GROUP BY thread_id
    HAVING MAX(created_at) < NOW() - INTERVAL '30 days'
);

7. Async postgres performance tips

  • Connection pool sized 2× workers
  • JSONB not JSON (indexed, faster query)
  • Batch multi-node writes trong transaction
  • Index thread_id + checkpoint_id DESC cho fast latest lookup
  • Compress large state (gzip trước INSERT) nếu >1MB
  • TTL for old checkpoints (7-30 days retention)

9. Idempotency — nền tảng để resume an toàn

💡 Idempotent nghĩa là gì? (định nghĩa đơn giản)

Một thao tác là "idempotent" nếu chạy nó 1 lần hay N lần đều cho ra CÙNG một kết quả cuối, không tạo thêm side-effect trùng lặp.

Đời thường: Bấm nút "Save" trong Word 5 lần liên tiếp — file vẫn chỉ có 1 phiên bản đã lưu, không có gì tệ hơn. Đó là idempotent. Nhưng bấm nút "Chuyển 500k cho Nam" 5 lần liên tiếp (vì mạng lag, tưởng chưa bấm) — nếu hệ thống không cẩn thận, Nam nhận 2.5 triệu thay vì 500k. Đó là KHÔNG idempotent — mỗi lần gọi tạo thêm 1 side-effect mới.

Tại sao checkpointing bắt buộc idempotency? Vì resume-after-crash về bản chất là "gọi lại 1 node có thể đã chạy một phần". Timeline cụ thể:

Node "send_confirmation_email" chạy:
  1. Gọi email_api.send(user, "Order confirmed")   ← EMAIL ĐÃ GỬI THẬT
  2. Return {"email_sent": True}
  3. LangGraph ghi checkpoint state mới vào Postgres  ← 💥 CRASH NGAY TRƯỚC BƯỚC NÀY

Restart: state.next vẫn = ["send_confirmation_email"] (vì checkpoint bước 3 chưa kịp ghi)
  → LangGraph resume → chạy LẠI node send_confirmation_email
  → Nếu node không check gì cả → gửi email LẦN 2 → user nhận 2 email trùng

Fix — idempotency key: trước khi làm side-effect, kiểm tra xem "task này đã hoàn thành chưa" bằng 1 khoá duy nhất (thường = task_id hoặc job_id + step_name). Nếu đã done → skip, không làm lại.

async def send_confirmation_email_node(state):
    idempotency_key = f"{state['job_id']}:send_email"

    # 1. Check: đã làm side-effect này chưa?
    if await db.exists("completed_operations", key=idempotency_key):
        return {"email_sent": True}   # skip — đã gửi rồi, không gửi lại

    # 2. Làm side-effect thật
    await email_api.send(state["user"], "Order confirmed")

    # 3. Ghi lại "đã hoàn thành" TRƯỚC KHI return (atomic với side-effect nếu có thể)
    await db.insert("completed_operations", key=idempotency_key)

    return {"email_sent": True}

Node nào cần lo, node nào không? Node chỉ đọc dữ liệu hoặc tính toán thuần (LLM call trả text, query database SELECT) — chạy lại vô hại, tự động idempotent. Node có side-effect ra thế giới bên ngoài (gửi email, trừ tiền, gọi webhook, ghi file) — luôn cần idempotency key. Đây chính xác là lý do LLM call bản thân nó thường an toàn để retry (section "ReAct loop" ở L6.1 dùng exponential backoff retry) nhưng node gọi tool có side-effect thì không được retry vô tư.

9.5 Saga pattern — khi cần HUỶ NGƯỢC các bước ĐÃ THÀNH CÔNG, không chỉ tránh lặp lại

💡 Analogy

Idempotency (§9) trả lời câu hỏi "node NÀY có thể bị gọi lại an toàn không?" — nhưng có 1 câu hỏi KHÁC: nếu node 1-2-3 đã CHẠY THÀNH CÔNG THẬT (email đã gửi, tiền đã trừ, đơn hàng đã tạo), rồi node 4 THẤT BẠI VĨNH VIỄN (không phải lỗi tạm thời để retry, mà lỗi thật sự không thể tiếp tục) — làm sao HUỶ NGƯỢC những gì node 1-2-3 đã làm THẬT? Giống việc đặt combo 4 món ở nhà hàng (khai vị → súp → món chính → tráng miệng) — nếu bếp hết nguyên liệu ở món tráng miệng, nhà hàng không thể "undo" việc bạn đã ăn khai vị/súp/món chính, nhưng CÓ THỂ bù lại bằng hành động tương đương (giảm giá hoá đơn, tặng món khác) — đó chính là tinh thần "compensating action" (hành động bù đắp) của Saga pattern.

Vấn đề cụ thể: agent pipeline nhiều bước có side-effect thật (VD: node "create_git_branch" → node "push_code" → node "create_pr" → node "notify_slack") không có 1 "transaction" bao trùm toàn bộ như database transaction (không thể ROLLBACK cả 4 bước cùng lúc nếu bước 4 lỗi, vì bước 1-3 đã là hành động THẬT trên hệ thống bên ngoài — git branch đã tồn tại, code đã push, PR đã tạo — không có phép "undo" tự động nào của LangGraph/checkpoint hiểu được ý nghĩa nghiệp vụ của việc "huỷ 1 PR" hay "xoá 1 git branch").

# Saga pattern: mỗi bước "thuận" (forward action) phải có 1 bước "bù đắp"
# (compensating action) ĐI KÈM — nếu 1 bước SAU thất bại, chạy NGƯỢC các bước
# bù đắp của MỌI bước ĐÃ THÀNH CÔNG trước đó, theo thứ tự NGƯỢC LẠI:

SAGA_STEPS = [
    ("create_git_branch", "delete_git_branch"),      # (forward, compensate)
    ("push_code",         "revert_commit"),
    ("create_pr",         "close_pr"),
    ("notify_slack",      "post_correction_message"),
]

async def run_saga(state):
    completed = []   # track bước nào đã chạy THÀNH CÔNG để biết compensate gì
    try:
        for forward, _ in SAGA_STEPS:
            await execute(forward, state)
            completed.append(forward)
    except PermanentError:
        # Chạy NGƯỢC các compensating action, theo thứ tự NGƯỢC LẠI
        for forward in reversed(completed):
            compensate = dict(SAGA_STEPS)[forward]
            await execute(compensate, state)
        raise

⚠️ Chỗ dễ nhầm nhất: Saga KHÔNG PHẢI "undo hoàn hảo về đúng trạng thái ban đầu" như rollback database transaction — compensating action chỉ là hành động BÙ ĐẮP tương đương (VD "hoàn tiền" không xoá được sự thật là giao dịch đã từng xảy ra, chỉ tạo ra 1 giao dịch NGƯỢC LẠI để về đúng số dư cuối cùng). Vì vậy, compensating action bản thân nó CŨNG phải idempotent (đã học ở §9) — nếu quá trình compensate bị lỗi giữa chừng và phải retry, "hoàn tiền 2 lần" cũng tệ y hệt "trừ tiền 2 lần".

Insight: Saga là câu trả lời kinh điển của distributed systems (hệ thống phân tán — nhiều service/máy chủ độc lập cùng phối hợp) cho bài toán "không có transaction xuyên suốt nhiều service độc lập" — thay vì cố gắng làm "tất cả hoặc không gì cả" (all-or-nothing, như ACID transaction trong 1 database — 4 tính chất database transaction phải đảm bảo: Atomicity/tất-cả-hoặc-không-gì, Consistency/dữ liệu luôn hợp lệ, Isolation/giao dịch không can thiệp lẫn nhau, Durability/đã commit thì không mất; ở đây chỉ cần nhớ chữ "A" — Atomicity — là phần liên quan trực tiếp tới Saga), Saga chấp nhận rằng CÁC BƯỚC ĐÃ XẢY RA THẬT rồi, và thiết kế trước 1 kế hoạch "nếu sau này hỏng thì bù đắp thế nào" cho MỖI hành động có side-effect. 2 cách triển khai phổ biến: Orchestration (1 "nhạc trưởng" trung tâm — giống Python router/Supervisor đã học ở L6_2_multiagent.html §3 — quyết định gọi compensate theo thứ tự) và Choreography (không có nhạc trưởng, mỗi service tự lắng nghe event và tự quyết định compensate) — pattern Supervisor/LangGraph của AI Orchestrator tự nhiên khớp với Orchestration-style Saga.

📖 Mở rộng: không phải MỌI action đều compensate được — 1 email đã gửi không thể "chưa từng gửi" (compensate tốt nhất chỉ là gửi thêm 1 email đính chính), trong khi 1 bản ghi database có thể xoá sạch (compensate gần như hoàn hảo). Khi thiết kế pipeline nhiều bước có side-effect, nên xếp các bước KHÓ HOÀN TÁC NHẤT (gửi tiền thật, gửi thông báo ra ngoài) ở CUỐI chuỗi — nếu có lỗi, nó xảy ra ở bước dễ compensate hơn trước, giảm thiểu tình huống cần "bù đắp" cho hành động không thể undo thật sự.

10. HA considerations

Multi-instance safety
  • Postgres row locks on thread_id → 1 worker per job at a time
  • Worker crashes mid-node → checkpoint chưa written → resume từ prev checkpoint
  • Idempotent nodes (retry safe) — critical! Xem section 9. Nếu node side-effect (write file, send email), track completion bằng idempotency key trước khi làm side-effect
  • Distributed tracing (LangSmith, OpenTelemetry) — correlate across restarts

✅ QA Gate

1. Vì sao MemorySaver không production-ready?

In-process dict → container restart → mất tất cả state. Multi-instance không share. Chỉ OK cho dev/test.

2. Postgres schema — 2 key fields.

(thread_id, checkpoint_id) primary key. state JSONB, parent_id link chain. Metadata (source agent, timestamps).

3. HITL flow bắt LLM crash mid-execution. Resume?

Load latest checkpoint (before crash). If state.next=[human_gate] → wait user approval. Else → resume execution với ainvoke(None). Postgres row-lock ensure 1 worker.

4. Idempotent node — vì sao critical với checkpointing?

Nếu node có side effect (send email, write DB) rồi crash trước checkpoint write → restart lại → send email lần 2. Fix: check idempotency key (đã done cho task_id X?) trước side effect.

5. Debug production bug — checkpoint history dùng thế nào?

Load history, find checkpoint before bug manifest. Inspect state, reproduce condition. Modify prompt/code, re-run từ checkpoint đó với new_input. Compare outcome. Fast iteration mà không cần rerun full pipeline.

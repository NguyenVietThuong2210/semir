R1.3 · TypeScript — hợp đồng type-safe giữa Frontend và API

Vì sao type string khai báo trong code không đảm bảo giá trị thật từ API không phải null — và cái giá phải trả nếu quên điều đó.

Độ khó: Trung bình · Roadmap AI Engineering · Track 1

🎯 Mục tiêu học

  • Giải thích được TypeScript là static type-checker chạy compile-time, khác Python (runtime, trừ khi chạy mypy riêng).
  • Chỉ ra chính xác vì sao API JSON response là "boundary không type-safe" — nguồn gốc thật của null-safety rule trong dự án.
  • Sửa đúng 1 đoạn code vi phạm rule (field ?? "").method() thành chuẩn, dựa trên ví dụ thật trong frontend/src/.
  • Đọc được build pipeline tsc && vite build và giải thích vì sao type-check luôn chạy TRƯỚC bundling.

📍 Vị trí & độ khó

Nên đọc sau R1.1 (Python) vì phần lớn giá trị của module này nằm ở việc so sánh 2 triết lý type-checking khác nhau (TypeScript compile-time vs Python runtime + mypy tùy chọn).

Độ khó: Trung bình — khái niệm "type hệ thống khai báo không tự verify runtime" hơi phản trực giác với người mới, vì cảm giác "đã khai báo type thì chắc chắn đúng type" là ngộ nhận phổ biến.

💡 Analogy

Nếu Python backend là nhà máy sản xuất linh hoạt (đổi công thức nhanh, không cần giấy tờ), TypeScript frontend là quầy giao hàng cho khách — phải chắc chắn 100% gói hàng đúng nhãn trước khi khách nhận.

Nhưng có 1 kẽ hở quan trọng: nhãn dán do nhân viên tự viết tay (developer tự khai báo type string), không phải máy quét tự động xác nhận nội dung gói hàng thật sự chứa gì. Nếu kho hàng (API backend) lỡ gửi gói rỗng (null) nhưng nhãn vẫn ghi "có hàng", quầy giao hàng vẫn tin nhãn — cho tới khi khách mở ra mới biết trống rỗng (runtime crash).

📖 Cơ chế chi tiết

Bước 1 — TypeScript là gì? (dễ)

TypeScript = JavaScript + hệ thống kiểu tĩnh (static type system), do Microsoft phát triển. Dự án dùng React 18 + TypeScript + Vite (frontend/package.json).

Điểm khác biệt cốt lõi với "JavaScript có thêm hint": TypeScript là 1 compiler thật sự chạy trước khi code tới trình duyệt — nó đọc toàn bộ file .ts/.tsx, kiểm tra type có khớp không, rồi mới cho phép build tiếp.

interface TickerData {
  ticker: string;
  verdict?: string;   // dấu ? = optional, có thể không tồn tại
}

function render(data: TickerData) {
  return data.ticker.toUpperCase();  // OK — TS biết chắc ticker luôn là string
}

Bước 2 — Compile-time vs runtime: khoảng cách nguy hiểm

Đây là phần quan trọng nhất của module. TypeScript kiểm tra type lúc viết code (compile-time) — nó KHÔNG chạy lại kiểm tra đó lúc chương trình đang chạy thật (runtime).

Compile-time (TypeScript check)Runtime (chương trình đang chạy)
Ai kiểm tra?tsc — đọc code, không chạy codeTrình duyệt/Node — thực sự thực thi
Biết gì về dữ liệu thật?Chỉ biết những gì developer khai báo trong interfaceBiết giá trị thật nhận được từ API
API trả JSON có tự mang theo TypeScript type không?—Không — JSON chỉ là text, không có khái niệm interface

Hệ quả: khi frontend gọi API, response JSON đi qua 1 "biên giới" (boundary) hoàn toàn không type-safe. Developer khai báo interface TickerData { verdict: string }, nhưng TypeScript compiler chỉ đang tin lời khai đó — nó không tự kết nối tới server thật để verify.

Bước 3 — Vì sao rule (field ?? "").method() ra đời

Đây là standing rule bắt buộc của dự án, ghi trong CLAUDE.md và memory feedback_null_guard_api_fields.md: "Any DB/API string field must use (field ?? "").method() — TypeScript types don't guarantee runtime null safety."

// SAI — TypeScript "tin" field này luôn là string, nhưng response thật từ
// /api/predict/VNM có thể trả null nếu chưa có prediction hôm nay
interface TickerData { verdict: string; }
function render(data: TickerData) {
  return data.verdict.toUpperCase();  // 💥 Runtime crash nếu verdict = null
}

// ĐÚNG — theo đúng standing rule của dự án
function render(data: TickerData) {
  return (data.verdict ?? "").toUpperCase();  // an toàn dù verdict null/undefined
}

?? (nullish coalescing) chỉ thay thế khi giá trị bên trái là null hoặc undefined — khác || vốn cũng thay thế cả chuỗi rỗng "" hay số 0, dễ gây bug lặng lẽ nếu dùng nhầm.

Bước 4 — Runtime schema validation (Zod) — giải quyết 1 lỗ hổng KHÁC với guard tay ?? "", không thay thế nó

💡 Vấn đề cụ thể

Rule (field ?? "").method() ở Bước 3 là "phòng thủ tại điểm dùng" — bạn phải nhớ guard ở MỌI nơi field đó được dùng, dễ sót 1 chỗ. Nếu API đổi 1 field từ string thành number mà không ai cập nhật interface, TypeScript vẫn "tin" khai báo cũ và không báo lỗi gì — compile-time check hoàn toàn mù trước dữ liệu SAI KIỂU (không chỉ null), không riêng gì null.

Cơ chế Zod (thư viện runtime validation phổ biến nhất cho TypeScript): thay vì chỉ khai báo interface (Bước 1) — thứ compiler tin suông — bạn định nghĩa 1 "schema" chạy THẬT lúc runtime, kiểm tra dữ liệu nhận từ API có ĐÚNG shape đã khai không, TRƯỚC KHI code khác được dùng dữ liệu đó.

import { z } from "zod";

// Định nghĩa schema — vừa là "khai báo type" vừa là "hàm kiểm tra runtime"
const TickerDataSchema = z.object({
  ticker: z.string(),
  verdict: z.string().nullable(),   // cho phép null tường minh, không phải "quên khai"
});

// Suy ra TypeScript type TỪ CHÍNH schema — không viết interface riêng, tránh 2 nguồn sự thật lệch nhau
type TickerData = z.infer<typeof TickerDataSchema>;

async function fetchTicker(ticker: string): Promise<TickerData> {
  const raw = await fetch(`/api/predict/${ticker}`).then(r => r.json());
  return TickerDataSchema.parse(raw);   // NÉM LỖI RÕ RÀNG ngay đây nếu raw sai shape
  // (VD field "verdict" API trả về number thay vì string/null) — thay vì để lỗi
  // trôi âm thầm tới tận chỗ .toUpperCase() ở xa, khó truy ngược nguồn gốc.
}

⚠️ Chỗ dễ nhầm nhất: Zod KHÔNG THAY THẾ rule ?? "" ở Bước 3 — 2 kỹ thuật giải quyết 2 tầng khác nhau. Zod validate NGAY TẠI BIÊN (khi data vừa vào từ API) — bắt được cả trường hợp SAI KIỂU hoàn toàn (string→number), không chỉ null. Guard ?? "" vẫn cần ở nơi SỬ DỤNG dữ liệu, vì Zod schema chính đáng CHO PHÉP field là null (business hợp lệ, VD ticker chưa có prediction) — không phải lỗi cần ném exception, chỉ là 1 giá trị hợp lệ cần code UI xử lý gracefully.

interface (Bước 1)Zod schema (Bước 4)?? "" guard (Bước 3)
Chạy khi nàoCompile-time onlyRuntime — mỗi lần data vàoRuntime — mỗi lần dùng field
Bắt được sai KIỂU (type mismatch)?❌ Không (chỉ tin khai báo)✅ Có — parse() ném lỗi ngay❌ Không (chỉ xử lý null/undefined)
Bắt được null hợp lệ về nghiệp vụ?—Cho qua (nếu schema khai .nullable())✅ Có — đây là việc của nó
Chi phíMiễn phí (không tốn CPU runtime)1 lần parse mỗi API responseRất rẻ, nhưng cần nhớ áp mọi nơi

Insight: Zod giải quyết đúng lỗ hổng nêu ở Bước 2 ("compiler chỉ TIN interface, không tự verify runtime") bằng cách biến bản thân schema thành nguồn sự thật DUY NHẤT — vừa sinh ra TypeScript type (compile-time), vừa là hàm kiểm tra thật (runtime), thay vì 2 thứ tách rời dễ lệch nhau theo thời gian. Dự án hiện CHƯA dùng Zod (giữ nguyên rule ?? "" thủ công) — đây là hướng nâng cấp hợp lý nếu số lượng field API tăng nhiều và rủi ro lệch schema giữa backend/frontend trở nên đáng kể hơn effort thêm 1 dependency.

🔢 Ví dụ cụ thể

3 ví dụ thật, đọc trực tiếp từ frontend/src/, áp dụng đúng pattern (field ?? "").method():

// frontend/src/components/Predict/VolumeSignalCard.tsx dòng 15
const signalVariant = (item.signal ?? "").toLowerCase() as
  Parameters<typeof Badge>[0]["variant"];

// frontend/src/pages/AITrader.tsx dòng 344
<span>{(c.verdict ?? "HOLD").replace("_", " ")}</span>
// Lưu ý: fallback ở đây KHÔNG phải "" mà là "HOLD" — vì "" không có ý
// nghĩa hiển thị hợp lý cho verdict (khác trường hợp uppercase text thường).

// frontend/src/pages/Screener.tsx dòng 123
list.filter((m) => m.ticker.includes(q) || (m.name ?? "").toUpperCase().includes(q));

Nhận xét: rule không cứng nhắc luôn dùng "" làm fallback — AITrader.tsx chọn "HOLD" vì đó là giá trị mặc định có ý nghĩa nghiệp vụ (không có verdict = coi như giữ nguyên vị thế). Nguyên tắc quan trọng hơn cú pháp: luôn xử lý rõ ràng trường hợp null/undefined, không để nó lọt tới .method().

Cấu trúc thư mục thật frontend/src/: api/ (gọi backend — predict.ts, trader.ts, market.ts), components/, pages/ (Dashboard.tsx, AITrader.tsx, Screener.tsx...), stores/ (watchlistStore.ts — Zustand, state management nhẹ hơn Redux), types/index.ts (khai báo interface — chính là "hợp đồng" giữa 2 ngôn ngữ), hooks/, utils/.

⚠️ Sai lầm thường gặp

#1 — Tin field string luôn có giá trị: gọi thẳng data.verdict.toUpperCase() mà không guard — crash ngay khi API trả null (VD ticker chưa có prediction hôm nay). Đây chính xác là ngộ nhận ở Bước 2: nhầm "khai báo type" với "đảm bảo runtime".

#2 — Dùng any để né lỗi type: khi TypeScript báo lỗi type khó sửa, ép kiểu data as any để "cho qua" — làm mất hoàn toàn lợi ích của TypeScript ở đúng chỗ có rủi ro cao nhất. Nên sửa type gốc hoặc dùng optional chaining (?.) + ?? thay vì tắt type-check.

📋 QA Gate

  • Giải thích được vì sao TypeScript "không đảm bảo runtime null safety" dù type khai báo là string không có ?.
  • Sửa đúng 1 đoạn code TypeScript vi phạm null-safety rule thành chuẩn (field ?? fallback).method().
  • Phân biệt được khi nào fallback nên là "" và khi nào nên là giá trị nghiệp vụ có ý nghĩa (VD "HOLD").
  • Giải thích được thứ tự tsc && vite build và vì sao không đảo ngược thứ tự.
  • Chỉ ra vì sao dùng any để né lỗi type là một anti-pattern, không phải giải pháp.

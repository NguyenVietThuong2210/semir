8.1 · Agents — Production Artifact

Cách agents thực sự deploy trong software dev workflow. Sub-agents, hierarchy, delegation, Claude Code agents, Cursor agents. Best practices từ 2 dự án.

Level 8 · AI Artifacts · ~35 phút

🎯 Learning objectives

  • Distinguish 3 senses of "agent" (research / framework / product)
  • Design sub-agent hierarchy (parent-child, delegation)
  • Understand Claude Code Task tool for spawn sub-agents
  • Apply best practices: prompt, tools, context, guardrails
💡 "Agent" đa nghĩa bằng ngôn ngữ đời thường

Từ "agent" khó vì mỗi ngành hiểu khác:

  • Nhân viên bảo hiểm (agent = đại lý bán) — product agent, dạng ChatGPT có tool.
  • Agent điện ảnh (agent = đại diện) — user proxy, thay user thực hiện task.
  • FBI agent (agent = thực thi) — autonomous, có quyền quyết định.

AI cũng vậy: research agent (Sutton RL, autonomous entity) ≠ framework agent (LangGraph node có LLM+tool) ≠ product agent (Cursor, ChatGPT). Khi nghe từ "agent" hỏi luôn: bạn nói nghĩa nào?

3. Sub-agents + delegation

Ý tưởng

Main agent nhận task lớn. Spawn sub-agents với narrower context để handle sub-tasks. Kết quả tổng hợp lên main. Giống human dev team: TL delegate to developer, developer delegate to specialist.

Claude Code Task tool

# Main Claude agent nhận: "Build authentication feature"
# Spawn sub-agents:

Task(
    subagent_type="Explore",           # research agent
    description="Find existing auth code",
    prompt="Search codebase for existing authentication logic. Report file paths + patterns used."
)

Task(
    subagent_type="Plan",               # architect agent
    description="Design new auth flow",
    prompt="Given existing patterns [ctx], design new JWT auth flow. List files to change."
)

# After both return, main agent implement based on their reports.

Isolation benefits

  • Context protection: main agent context không bị polluted bởi search results 10k lines
  • Specialization: sub-agent prompt tuned cho task (Explore rất tốt tại grep/find, không tốt code write)
  • Parallelization: 3 sub-agents chạy đồng thời
  • Cost/quality tradeoff: sub-agent dùng cheaper model (Haiku) cho simple tasks

Pitfalls

  1. Cold start: sub-agent không có main's chat history — phải hoàn chỉnh brief trong prompt
  2. Verify-not-trust: sub-agent report có thể inaccurate (LLM hallucinate). Main phải verify (đọc file thay chỉ trust summary)
  3. Cascading errors: sub-agent fail → main không biết root cause
  4. Cost explosion: nested sub-agents (grandchild) → token cost multiply

4. Anatomy of a production agent

Agent = System Prompt + Tools + Model + Loop Logic + Guardrails

┌── System Prompt ──────────────────────────────────────┐
│  Role, persona, constraints, output format           │
│  E.g., "You are a senior code reviewer. Output JSON."│
└───────────────────────────────────────────────────────┘

┌── Tools ──────────────────────────────────────────────┐
│  Read, Write, Bash, Grep, WebFetch, custom MCP tools │
│  Each with JSON schema, description, safety rules    │
└───────────────────────────────────────────────────────┘

┌── Model ──────────────────────────────────────────────┐
│  Claude Opus 4.7 / GPT-4o / Llama-3.1-405B           │
│  Choose based on capability + cost + latency         │
└───────────────────────────────────────────────────────┘

┌── Loop Logic ─────────────────────────────────────────┐
│  While not done + iter < max:                        │
│    LLM call → parse output → execute tools →         │
│    → observe → feed back → next iteration            │
└───────────────────────────────────────────────────────┘

┌── Guardrails ─────────────────────────────────────────┐
│  Max iterations, budget cap, forbidden actions,      │
│  human approval for destructive ops, audit log       │
└───────────────────────────────────────────────────────┘

5. Best practices — Anthropic 2024 recommendations

Từ "Building Effective Agents" paper
  1. Simplicity first: single LLM call > chained agent nếu đủ. Justify complexity.
  2. Show your work: agent explicit trace of thought → debug, audit
  3. Test tool-use rigorously: tool errors most common failure. Handle gracefully.
  4. Human in the loop for critical: destructive/expensive/irreversible → require approval
  5. Measure end-to-end: not just LLM call accuracy — task completion rate

5.5 · "Workflow" vs "Agent" — phân biệt CHÍNH XÁC theo đúng bài Anthropic đã trích ở mục 5

💡 Vấn đề thật: §5 đã trích "Building Effective Agents" nhưng chưa nói nội dung NỔI TIẾNG NHẤT của chính bài đó

Bài "Building Effective Agents" (Anthropic, cùng nguồn đã trích ở §5) định nghĩa 1 ranh giới rất cụ thể mà nhiều engineer nhầm: Workflow = LLM + tool chạy theo ĐƯỜNG ĐI CỐ ĐỊNH được lập trình sẵn trong code (giống 1 quy trình sản xuất: bước 1→2→3, không đổi thứ tự). Agent = LLM TỰ QUYẾT ĐỊNH đường đi của chính nó, tự chọn tool nào gọi tiếp theo, tự kiểm soát quy trình — giống giao việc cho 1 nhân viên tự lên kế hoạch, không phải đưa quy trình cố định.

Vấn đề cụ thể: "Simplicity first" (§5 mục 1) nói "single LLM call > chained agent nếu đủ" — nhưng KHÔNG PHẢI mọi bài toán phức tạp cần "agent" đúng nghĩa (tự quyết định); nhiều bài toán chỉ cần 1 trong 5 pattern "workflow" bên dưới — rẻ hơn, dễ debug hơn, dự đoán được hành vi hơn agent thật sự, vì đường đi đã CỐ ĐỊNH sẵn trong code.

Orchestrator-workers chỉ là pattern GẦN với "agent" thật sự NHẤT trong 5 pattern (vì đường đi sub-task không cố định sẵn, do orchestrator tự quyết định lúc chạy), chứ không tự động trở thành "agent" đúng nghĩa. Dù prompt/code thường gọi chung mọi pattern trên là "agent pattern", đây là cách dùng từ không chính xác theo phân loại gốc. Cả AI Orchestrator (case study §6 dưới đây) lẫn Claude Code Task tool (§3) đều đang dùng orchestrator-workers (main agent tự quyết định spawn sub-agent nào, không có đường đi cố định trong code) — còn 1 pipeline kanban cố định "spec → design → code → test → deploy" theo đúng thứ tự lại là prompt chaining, dù code gọi các bước đó là "agent".

Insight: bài báo gốc khuyến nghị LUÔN bắt đầu từ pattern đơn giản nhất đủ dùng (đúng tinh thần "Simplicity first" ở §5 mục 1) — chỉ leo lên orchestrator-workers/agent thật sự khi đường đi CHẮC CHẮN không biết trước được, vì agent thật sự khó debug hơn, khó dự đoán chi phí hơn workflow có đường đi cố định.

6. Case study — AI Orchestrator engineer agent

Engineer agent anatomy

File: agents/engineer.py (346 lines)

System prompt (~600 words):
- Role: Senior software engineer implementing task from spec
- Constraints: Follow existing code style, don't break tests
- Output format: <submit> block với artifact_paths: {logical_name: path} dict
- Tools available: Read, Write, Edit, Bash, Grep

Loop:
1. Read task from kanban board (state.current_task_index)
2. Load context: spec + codebase summary + prior agent reports
3. Call backend (Claude Code CLI or API)
4. Parse <submit> block: artifact_paths dict
5. Update kanban card: column='in_review', artifacts=artifact_paths
6. Return report

Guardrails:
- Timeout 600s (10 min) — engineer nằm trong nhóm "long-timeout agents"
  cùng deploy/qa/qa_verify/spec_analyze/task_decompose (agent ngắn hơn: 300s)
- Files write restricted to project dir
- Deploy agent (agents/deploy.py) làm smoke-test + health-check, không tự động git push

7. Anti-patterns bạn cần tránh

  1. Kitchen-sink prompt: 5000-word system prompt cover everything → LLM confused
  2. Free-form agent goal: "figure it out" → drift, no closure. Fix: DoD (Definition of Done) explicit.
  3. Nested infinite delegation: sub-agent spawn sub-sub-agent... 10 levels deep. Fix: max depth.
  4. Blind trust output: agent claim success without verification. Fix: verify observation.
  5. Non-idempotent actions: retry ops with side effects (email send, DB write). Fix: idempotency keys.
  6. Cost blackhole: agent loop expensive tools. Fix: budget cap.

8. Emerging: agentic RAG

# Traditional RAG: fixed retrieve → LLM answer
# Agentic RAG: LLM iteratively decide next retrieval based on partial answer

Loop:
1. Initial query → retrieve top-K
2. LLM: "Do I have enough info? What else needed?"
3. If gap: reformulate query → retrieve more
4. Aggregate all chunks → final answer

# Empirically higher accuracy cho multi-hop questions
# But: 3-10× more LLM calls + retrieval calls
# Trade-off: quality vs cost
🔬 Self-RAG (Asai et al. 2023) — 1 cách implement agentic RAG cụ thể, không chỉ ý tưởng chung

Vấn đề cụ thể: vòng lặp "agentic RAG" ở trên mô tả Ý TƯỞNG chung (LLM tự quyết định retrieve tiếp hay không) nhưng không nói CÁCH LÀM cụ thể — nếu để LLM tự quyết định bằng cách hỏi thẳng trong prompt ("bạn có cần tìm thêm không?"), quyết định đó không đáng tin cậy (LLM có thể tự tin sai). Self-RAG giải quyết bằng cách KHÔNG hỏi qua prompt, mà HUẤN LUYỆN model sinh ra reflection token (token đặc biệt, VD [Retrieve], [IsRel], [IsSup], [IsUse]) như 1 phần tự nhiên của việc sinh text tiếp theo — giống việc model "tự chấm điểm" ngay trong lúc viết, không phải hỏi riêng 1 câu sau đó.

Cơ chế: model được train (dùng dữ liệu có gắn sẵn reflection token bởi 1 "critic model" khác) để tại MỖI bước sinh text, tự quyết định: (1) [Retrieve] — có cần tìm thêm passage không, hay bỏ qua hoàn toàn (khác RAG truyền thống LUÔN retrieve dù câu hỏi đơn giản); (2) [IsRel] — passage tìm được có liên quan không; (3) [IsSup] — câu trả lời có được passage đó HỖ TRỢ (support) thật không, hay model đang bịa; (4) [IsUse] — câu trả lời cuối có hữu ích không. 4 token này được coi như 1 phần của vocabulary bình thường (next-token prediction), không phải 1 lời gọi API riêng.

⚠️ Khác gì với agentic RAG mô tả ở trên: agentic RAG (generic) thường dùng 1 LLM có sẵn (GPT-4, Claude) + prompt engineering để "tự hỏi" có cần retrieve thêm không — không cần train riêng, nhưng quyết định kém tin cậy hơn. Self-RAG cần TRAIN LẠI model để sinh reflection token — tốn công hơn nhưng quyết định retrieve/không-retrieve và tự phê bình support/relevance đáng tin cậy hơn vì nó là 1 phần trực tiếp của quá trình sinh, được optimize cùng lúc với chất lượng câu trả lời.

Insight: Self-RAG là ví dụ cụ thể cho thấy "agentic" không nhất thiết cần 1 vòng lặp orchestration bên ngoài (như pseudo-code Loop ở trên) — có thể "nhúng" hành vi tự-quyết-định NGAY TRONG chính model, qua special token, đây cùng tinh thần với reflection token cách reasoning model dùng special token để tự kiểm soát quá trình suy luận.

9. Future — self-improving agents

4 hướng agent "tự học" — giải thích ngắn gọn + ví dụ
  • Reflexion loop (L6.1): agent tự phê bình lỗi của chính mình NGAY TRONG session (không cần retrain weight). VD: agent viết code → test fail → agent tự đọc error message → tự sửa → chạy lại, không cần user nhắc lần 2. Khác fine-tuning: chỉ đổi prompt/context bước sau, model weight không đổi.
  • Memory (Letta, MemGPT): lưu bài học xuyên session — session hôm nay agent học "user thích code có docstring", ghi vào memory file → session mai đọc lại, không phải khám phá lại từ đầu. Khác Reflexion: Reflexion sống trong 1 session, Memory sống qua nhiều session.
  • Self-verify: agent tự sinh test case cho chính output của mình trước khi submit (giống dev viết unit test cho code họ vừa viết) — giảm case "agent nghĩ đúng" nhưng thực ra sai vì chưa ai kiểm tra.
  • Curriculum learning: cho agent luyện task dễ trước, khó dần (giống dạy trẻ con cộng trừ trước rồi mới nhân chia) — áp dụng khi train/fine-tune agent policy (research sense, L8.1 §1), không chỉ prompt engineering.

Cạm bẫy hay nhầm: Reflexion và Self-verify nghe giống nhau nhưng khác thời điểm — Reflexion sửa SAU khi thấy lỗi thực tế (reactive), Self-verify tạo test TRƯỚC khi nộp kết quả (proactive). Cả 4 kỹ thuật này đều KHÔNG phải "agent tự cập nhật model weights" — đó là RL fine-tuning, tốn kém và rủi ro hơn nhiều (liên hệ mesa-optimization — model tự phát triển 1 "mục tiêu con" khác với mục tiêu training gốc — chi tiết ở L8.5).

Skill vs Agent — distinction chính xác

Claude Skill (.claude/skills/xxx/SKILL.md):
  = Static playbook + KB + scripts
  = Loaded ON-DEMAND khi user trigger ("/daily-investor-report")
  = No memory across invocations (mỗi lần chạy lại là fresh)
  = Reusable across users, git-versioned

Claude Agent (Claude Code session):
  = Running loop với LLM + tools + context window
  = HAS memory (CLAUDE.md), HAS todos, HAS plans
  = Personal to user + project
  = Ephemeral session nhưng có persistent layers (memory/)

→ Skill = "công thức phở" (giấy). Agent = "đầu bếp" (người) đọc công thức + nhớ khách quen.

Permission model (Claude Code)

Mỗi tool call gate qua permission system, config trong .claude/settings.json:

{
  "permissions": {
    "allow": ["Bash(git status)", "Bash(git diff:*)", "Read", "Grep"],
    "deny":  ["Bash(rm -rf:*)", "Bash(git push --force:*)"],
    "ask":   ["Bash(docker:*)", "Write"]
  }
}
  • allow: auto-execute, no prompt (VD: read-only ops)
  • ask: prompt user mỗi lần (default cho destructive)
  • deny: hard block (không thể override)
  • Rules KHÔNG cascade theo scope (global/user/project) như settings thường. allow/deny/ask lists merge across mọi scope — resolve theo category-order cố định: deny > ask > allow, bất kể rule đến từ scope nào.

Anti-pattern VN scenario

PredictStock case: Agent chạy backtest, tạo file reports/tmp_experiment.json. Session tắt. Ngày mai agent mới không biết file này tồn tại → chạy lại tốn 20 phút compute.
Fix: Ghi note vào CLAUDE.md ("Cache backtests ở reports/_cache/") + file naming convention persistent. Đây là why memory > todos cho cross-session state.

Interview Q&A (thêm 3 câu)

  1. Q: Skill có memory không? A: Không native. Skill = static package. Muốn có memory phải viết script tự-persist state ra file (VD: reports/lessons_learned.jsonl trong daily-investor-report). Đây là workaround, không phải feature.
  2. Q: Vì sao TodoWrite thay vì cho LLM tự nhớ trong context? A: Long context degrade attention (lost-in-the-middle, L9.1). Structured todos = separate scratchpad LLM ref explicitly, không compete với reasoning tokens.
  3. Q: Permission cascade — user override project được không? A: Không phải scope-cascading. Rules merge across mọi scope, resolve theo category cố định deny > ask > allow — nghĩa là bất kỳ "ask" rule nào (ở scope nào) cũng được check trước "allow" rule, không phải vì "project override user".

10. Interview cheat sheet

Common questions
  1. "When would you NOT use an agent?" → Simple deterministic task, high-stakes without HITL, cost-sensitive high volume
  2. "Sub-agent vs main agent — how partition?" → Sub-agent for specialized/parallel/context-heavy tasks; main for orchestration + user-facing decisions
  3. "How debug an agent?" → LangSmith trace + step through iterations + inspect tool calls + verify tool outputs match LLM's belief
  4. "How measure agent quality?" → Task completion rate, cost per task, human satisfaction, avg iterations, tool error rate

✅ QA Gate

1. 3 nghĩa của "agent" — kể + ví dụ.

Research: RL policy autonomous. Framework: LLM + tools + loop (ReAct). Product: specialized assistant (Cursor, Devin).

2. Sub-agent isolation — 4 lợi ích?

(1) Context protection main agent. (2) Specialization (sub-agent prompt tuned). (3) Parallelize. (4) Cost — Haiku cho sub, Opus cho main.

3. Claude Code Task tool — vs LangGraph subgraph khác gì?

Task tool = spawn inline within Claude Code CLI runtime, no persistent state. LangGraph subgraph = compiled part of parent graph, share state, checkpoint. Task tool cho lightweight delegation, subgraph cho structured multi-step.

4. Agentic RAG vs traditional RAG — when justify?

Multi-hop questions (need chain of retrievals). Complex analytical tasks. Trade-off: 3-10× cost. Traditional OK cho single-hop factual QA.

5. Agent claim "task done" nhưng tests fail. Root cause categories?

(1) Hallucinate success (didn't run tests). (2) Ran subset of tests. (3) Fixed 1 test broke another. (4) Tool error (bash fail returned confusing output). Fix: main agent verify — actually run tests + inspect output, không trust sub-agent report.

Debug agents like debug distributed systems. Trace/span, cost tracking, error attribution, prompt versioning.

💡 Observability bằng ngôn ngữ đời thường

Điều tra máy bay rơi: Không tận mắt thấy, không thể phỏng vấn phi công đã chết. Cần:

  • Black box (traces): ghi lại từng thao tác cần điều khiển — cần để tái hiện timeline.
  • Radar (metrics): latency, altitude, speed — số liệu tổng hợp theo thời gian.
  • Báo cáo phi công (logs): text mô tả sự kiện.

Debug agent LLM: mỗi run 20 node — không nhìn được từng nội bộ. Cần trace (xem input/output mỗi node), metrics (latency, token cost), logs. LangSmith = "black box recorder" cho agent.

Key insight: Nếu không log, khi bug xảy ra tuần sau bạn không thể tái hiện. Log first, ask questions later — nhất là với LLM stochastic.

2.4 OpenTelemetry spans — instrument LLM call thủ công

from opentelemetry import trace
tracer = trace.get_tracer("agent")

def llm_call(prompt, model="claude-opus-4-7"):
    with tracer.start_as_current_span("llm.invoke") as span:
        # Attributes = key/value cho dashboard filter
        span.set_attribute("llm.model", model)
        span.set_attribute("llm.prompt.tokens", count_tokens(prompt))
        span.set_attribute("llm.temperature", 0.0)
        span.set_attribute("user.id", ctx.user_id)     # cardinality note — xem giải thích dưới

        try:
            resp = client.messages.create(model=model, messages=[...])
            span.set_attribute("llm.completion.tokens", resp.usage.output_tokens)
            span.set_attribute("llm.cost_usd", compute_cost(resp))
            span.set_status(trace.StatusCode.OK)
            return resp
        except Exception as e:
            span.record_exception(e)
            span.set_status(trace.StatusCode.ERROR, str(e))
            raise
💡 Cardinality là gì? (định nghĩa trước khi dùng)

Cardinality = số lượng GIÁ TRỊ KHÁC NHAU mà 1 field/attribute có thể nhận. Ví dụ: field model chỉ nhận "opus", "sonnet", "haiku" → cardinality = 3 (thấp). Field user.id nhận hàng triệu user khác nhau → cardinality = hàng triệu (cao). Field chứa nguyên câu hỏi user gõ → cardinality gần như vô hạn (mỗi câu 1 giá trị riêng).

Vì sao quan trọng: hệ thống metrics (Prometheus) tạo 1 time-series riêng cho mỗi tổ hợp giá trị attribute. Field cardinality thấp (10-20 giá trị) → 10-20 series, dashboard mượt. Field cardinality cao (triệu user) → hàng triệu series → DB phình to, query chậm, có thể sập ("cardinality explosion"). Đây là lý do user.id nên gắn vào span/log (nơi cardinality cao chấp nhận được) chứ KHÔNG gắn vào metric label (nơi cần cardinality thấp).

Trace vs Span vs Log — 30-second definition:

  • Trace = 1 request end-to-end (job_id="abc"). Chứa nhiều spans.
  • Span = 1 unit of work (LLM call, DB query, tool exec). Có start/end time, parent span, attributes.
  • Log = 1 discrete event message ("engineer started task T1"). Gắn vào span thông qua trace_id.

2.5 Latency percentile — vì sao p50/p95/p99 quan trọng hơn average

Runs: [100, 120, 110, 115, 130, 105, 125, 118, 3200, 5000]  # ms
Sắp xếp tăng dần: [100, 105, 110, 115, 118, 120, 125, 130, 3200, 5000]
                                                              (vị trí 1..10)

average = 912ms   # (100+120+110+115+130+105+125+118+3200+5000)/10 — bị outlier kéo lên, che dấu vấn đề
p50 = 118ms       # vị trí 5/10 (nearest-rank) — 50% users experience ≤ this
p95 = 3200ms      # vị trí 9/10 — 5% users experience > this ← tail latency!
p99 = 5000ms      # vị trí 10/10 (giá trị lớn nhất) — 1% worst — usually cache miss, cold start, LLM slow token

# Lưu ý: chỉ 10 mẫu là QUÁ ÍT để tính p95/p99 chính xác (mỗi mẫu đại diện 10%,
# không đủ độ phân giải cho "1% tệ nhất") — ví dụ minh hoạ dùng nearest-rank
# đơn giản để thấy Ý NGHĨA (percentile lộ tail latency, average thì không).
# Production thật cần hàng nghìn+ mẫu để p95/p99 có ý nghĩa thống kê thật.

Rule: SLO (Service Level Objective — cam kết nội bộ về chất lượng dịch vụ, ví dụ "99% request phải xong dưới 500ms") bao giờ cũng viết theo percentile ("p95 < 500ms"), KHÔNG viết average. Average che dấu tail; user Facebook không quan tâm "trung bình 100ms" nếu 1/20 request mất 5s.

4. Cost tracking

class TokenUsage(TypedDict):
    input_tokens: int
    output_tokens: int
    cache_hit_tokens: int   # discounted
    model: str

# Compute cost:
def cost(usage):
    p = PRICING[usage["model"]]
    return (usage["input_tokens"] - usage["cache_hit_tokens"]) × p["in"]
         + usage["cache_hit_tokens"] × p["cache_in"]
         + usage["output_tokens"] × p["out"]

5. Error attribution

Agent fail — root cause có thể ở:

  • Prompt (unclear instruction)
  • Retrieved content (bad chunk)
  • Tool (API error, timeout)
  • Model (hallucinate, refuse)
  • Downstream (parse error, schema mismatch)
# Track per error:
class ErrorEvent(TypedDict):
    job_id: str
    agent: str
    step: str
    error_type: str        # tool_error|parse_error|model_refuse|timeout
    error_message: str
    prompt: str            # first 500 chars
    model: str
    tokens_used: int
    timestamp: str

5.1 Error taxonomy — phân loại để aggregate

# Không dùng raw exception message (cardinality nổ). Dùng finite categories:

class ErrorCategory(str, Enum):
    LLM_RATE_LIMIT     = "llm.rate_limit"       # 429 from Anthropic
    LLM_TIMEOUT        = "llm.timeout"          # >60s no response
    LLM_REFUSAL        = "llm.refusal"          # model refuses to answer
    LLM_HALLUCINATION  = "llm.hallucination"    # detected via validator
    TOOL_NOT_FOUND     = "tool.not_found"
    TOOL_TIMEOUT       = "tool.timeout"
    TOOL_ERROR_5XX     = "tool.error_5xx"
    PARSE_ERROR        = "parse.json_decode"    # LLM output không match schema
    SCHEMA_VIOLATION   = "parse.schema_violation"
    HITL_REJECTED      = "hitl.rejected"
    BUDGET_EXCEEDED    = "budget.exceeded"

def classify_error(exc) -> ErrorCategory:
    if isinstance(exc, RateLimitError): return ErrorCategory.LLM_RATE_LIMIT
    if isinstance(exc, TimeoutError):   return ErrorCategory.LLM_TIMEOUT
    if isinstance(exc, JSONDecodeError):return ErrorCategory.PARSE_ERROR
    # ... explicit mapping
    return ErrorCategory.UNKNOWN

Vì sao: Prometheus/Grafana query sum by (error_category) (rate(errors_total[5m])) chỉ hoạt động khi cardinality thấp (~10-20 values). Raw exception messages → millions of unique series → alerting bị vô hiệu.

9. Case study — production debug

Debug story: Engineer agent QA loop hit cap

Alert: QA loop limit (MAX_QA_ITERATIONS=2) reached, job failed.

Investigate trace: QA fail with "test import error". Engineer retry: modify import. Fail again same error. Loop.

Root cause (via observation replay): Engineer imported from module import x where module doesn't exist. QA test fail. Engineer read same file, same import, retry same. Stuck.

Fix: Add code search tool để Engineer verify module exists trước khi import. Also: QA feedback more specific ("module not found" with file location).

Fix deployed, similar failures dropped 80%.

10. Anti-patterns

Đừng làm
  1. Log toàn bộ prompt + response vào Splunk/ELK: giá lưu trữ nổ, dễ leak PII. Rule: sample 1-5%, mask email/SĐT trước lưu.
  2. High-cardinality attributes: span.set_attribute("query", full_user_input) → mỗi query là 1 series. Rule: attribute chỉ chứa enum values.
  3. Alert dựa average: average latency ok = tail latency có thể tệ. Rule: alert p95/p99.
  4. Không track cache hit rate LLM: prompt caching giảm 90% cost, nhưng nếu bạn thay đổi 1 whitespace trong system prompt → cache miss 100% → hóa đơn nổ. Dashboard hit rate là must-have.
  5. Trace sampling 100% ở production: cost storage + performance overhead. Rule: head-based 10% + tail-based cho error/slow request.

Head-based vs tail-based sampling — khác nhau ở THỜI ĐIỂM quyết định giữ/bỏ trace:

  • Head-based: quyết định NGAY LÚC request bắt đầu, trước khi biết kết quả — ví dụ "random 10% request được bật ghi trace, 90% còn lại tắt hoàn toàn". Rẻ (không tốn overhead ghi trace cho 90% kia), nhưng may rủi: request lỗi có thể rơi vào nhóm 90% không được ghi → mất đúng lúc cần debug nhất.
  • Tail-based: ghi trace TẠM cho MỌI request, đợi đến khi request xong mới quyết định giữ hay xoá — giữ lại nếu request bị lỗi hoặc chậm bất thường, xoá nếu request bình thường. Đảm bảo không bao giờ bỏ lỡ ca lỗi, nhưng tốn overhead ghi tạm cho 100% request (cần buffer + collector riêng, ví dụ OpenTelemetry Collector với tail_sampling processor).

Kết hợp cả 2 (như rule ở trên) = vừa tiết kiệm (10% ngẫu nhiên đủ để nhìn xu hướng chung) vừa không mất case lỗi hiếm (tail-based luôn bắt được request bất thường dù nó không lọt vào 10% ngẫu nhiên).

✅ QA Gate

1. 3 observability pillars — apply cho agent system.

Logs (per-step structured events), Metrics (aggregate — success rate, latency, cost), Traces (full nested job execution với parent-child spans).

2. LangSmith auto-instrument LangGraph — setup cần gì?

Set env LANGCHAIN_TRACING_V2=true, LANGCHAIN_API_KEY. No code change. LangGraph auto-emit spans per node, LLM call, tool call. UI hiển thị nested trace.

3. Alert rule: agent success rate < 90% (5-min window). Ưu tiên fix?

(1) Identify which agent (Engineer? QA?). (2) Look at recent errors — same type or diverse? (3) Recent prompt change? Model version bump? Traffic spike? (4) Rollback nếu recent deploy. (5) Root cause + fix + monitor.

4. Cost per job spike 3x normal. Investigate?

(1) Which user / job type spike? (2) Token breakdown: input inflating? (RAG retrieve too much?). Output? (LLM verbose?). (3) Prompt cache miss rate. (4) Model choice — accidentally routing all to Opus? (5) Loop count — QA loop stuck?

5. Agent A/B test — significance requirement?

Enough sample size (~1000 per variant depending effect size), stratify by user cohort, log variant per job. Chi-square hoặc bootstrap for approval rate. Multi-week rollout để catch weekly patterns.

2.6 · ML System Design — 7 root causes V19.5 chết

Case study production ML failure. 7 distinct root causes → mỗi cái sống 1 mình → cùng nhau fatal. 7 counter-measures cho V20.

Level 2 · Advanced ML · ~35 phút

💡 ML System Design bằng ngôn ngữ đời thường

V19.5 death case = Sinh viên đêm trước thi cắn mì gói + học 12 tiếng liên tục:

  • Không nghỉ (no staged rollout)
  • Không có kế hoạch backup nếu buồn ngủ (no rollback plan)
  • Ăn mì gói xấu → đau bụng (bad data)
  • Café quá liều → tay run (model overtuned)

→ 7 yếu tố cascade thành 1 thảm họa. ML system cũng vậy — không phải 1 lỗi mà chuỗi lỗi cùng lúc gây sập.

Bài học: Rollout từ từ, có monitoring, có nút "STOP" instant, có backup plan. Đừng dựa "code đúng là đủ" — cần discipline của cả process.

3. Meta-lesson

Silent failure là killer

V19.5 sản xuất 246 model artifacts, chạy 26h, sign-off metrics đẹp — nhưng serve 0 improvement cho user vì inference broke lặng lẽ. Traditional software throw exception → alerting fires → debug. ML pipeline log WARNING, tiếp tục serve wrong prediction. Users lose money silently.

V20's #1 goal không phải accuracy, mà là NO silent failure.

3.5 Lý thuyết đứng sau — "Hidden Technical Debt in Machine Learning Systems" (Sculley et al. 2015)

Case study V19.5 ở mục 1-2 không phải hiện tượng riêng lẻ — nó là ví dụ THỰC TẾ của những "nợ kỹ thuật" (technical debt — chi phí ẩn tích luỹ khi làm tắt, phải "trả" sau này dưới dạng bug/bảo trì khó) mà 1 paper rất nổi tiếng (Sculley et al., NeurIPS 2015) đã đặt tên chính thức từ trước. Paper này giải thích TẠI SAO hệ thống ML dễ tích luỹ nợ kỹ thuật hơn hẳn phần mềm thường:

📐 3 khái niệm quan trọng nhất của paper — cơ chế + ví dụ

Entanglement (rối vào nhau) / nguyên tắc CACE ("Changing Anything Changes Everything" — đổi 1 thứ nhỏ là đổi hết mọi thứ): trong phần mềm thường, 1 hàm số A và 1 hàm số B thường ĐỘC LẬP — sửa A không ảnh hưởng B nếu chúng không gọi nhau trực tiếp. Nhưng trong 1 model ML, mọi input feature bị TRỘN LẪN vào nhau qua trọng số (weights) đã học chung — không feature nào thực sự "cô lập". Ví dụ: thêm 1 feature MỚI "giờ trong ngày" vào model gian lận (fraud) — feature này không chỉ đơn thuần "thêm 1 tín hiệu", nó còn ÂM THẦM làm model học lại TRỌNG SỐ của feature "số tiền giao dịch" đã có sẵn, có thể phá vỡ 1 ngưỡng quyết định đã tinh chỉnh kỹ trước đó — dù không ai sửa 1 dòng code nào liên quan tới feature "số tiền".

Undeclared consumers (người tiêu thụ không khai báo): output của 1 model (điểm số, dự đoán) được ghi ra 1 API/file/log — rồi 1 hệ thống/team KHÁC âm thầm bắt đầu ĐỌC dữ liệu đó làm input cho việc riêng của họ, mà đội sở hữu model không hề biết. Ví dụ: điểm xếp hạng gợi ý sản phẩm được log vào 1 bảng dữ liệu chung — 6 tháng sau, 1 dashboard marketing khác âm thầm đọc đúng cột đó để tính ngân sách chiến dịch email — không ai trong đội train lại model gợi ý biết về sự phụ thuộc "vô hình" này, nên 1 lần retrain bình thường có thể âm thầm làm hỏng dashboard marketing đó mà không ai cảnh báo trước.

Correction cascades (chuỗi vá lỗi chồng chất): khi output của model A "gần đúng nhưng chưa đủ" cho 1 nhu cầu mới B, thay vì SỬA LẠI model A cho đúng, kỹ sư thường XÂY THÊM 1 model B THỨ HAI để "vá" lỗi của A. Hệ quả: nếu sau này CẢI THIỆN model A (làm nó chính xác hơn) — hệ thống TỔNG THỂ có thể lại TỆ ĐI, vì model B đã được tinh chỉnh riêng để vá ĐÚNG KIỂU LỖI CŨ của A, không phải để làm việc với A phiên bản mới. Đây gọi là "improvement deadlock" — cải thiện 1 phần lại làm hại toàn hệ thống.

Insight: cả 3 khái niệm đều chỉ ra CÙNG 1 sự thật — nợ kỹ thuật trong ML không chỉ tới từ "code viết ẩu" (như phần mềm thường), mà tới từ chính BẢN CHẤT của việc model học pattern từ dữ liệu: mọi phần đều ngầm liên kết với nhau, không có ranh giới module rõ ràng như code truyền thống. Đây là lý do các counter-measure ở mục 4 (versioning nghiêm ngặt, schema hash, atomic retrain) không phải "quá cẩn thận" — chúng là cách DỰNG LẠI ranh giới module mà bản chất ML tự nhiên không có sẵn.

4. 7 V20 counter-measures

4.1 Multi-horizon atomicity

# In train_v18_unified.py:
if not (t1_ok and t3_ok and t5_ok):
    for h in [1, 3, 5]:
        Path(f"{OUTPUT_DIR}/{ticker}.t{h}.joblib").unlink(missing_ok=True)
    raise RuntimeError(f"{ticker}: partial retrain aborted, no artifact retained")

4.2 Fallback = loud error

# Was: logger.warning(f"[v18] falling back to v1")
# Now: logger.error(f"[v18] falling back to v1") + metric_v18_fallback_total{ticker=X}++
# Alert on fallback rate > 0

4.3 Immutable versioned dirs

# NEVER in-place edit to /app/models/v18/
# Always write to /app/models/v20-candidate/
# Cut-over = single `mv` + engine restart

4.4 Model-swap invalidation protocol

1. Write new artifacts to v20-candidate/
2. Run consistency gate
3. INSERT INTO model_registry (version='v20', activated_at, model_dir)
4. DELETE FROM prediction_log WHERE created_at > NOW() - INTERVAL '2 days'
5. mv v20-candidate → v20
6. docker restart predictor-api-1
7. Smoke test 10 tickers; if ver ≠ v20 anywhere → freeze + rollback

4.5 Container source-of-truth

  • Patches land in host backend/, git commit
  • docker compose build --no-cache bake patches vào image
  • docker cp = diagnostic only, không prod deploy

4.6 Artifact self-validation

# Every JSON written:
json.loads(open(path).read())   # verify parseable
# Every joblib written:
a = joblib.load(path)
assert a['scaler'].n_features_in_ == len(a['feature_names'])

4.7 Explicit tier system

Tier A: cv_skill ≥ 0.15, ECE ≤ 0.01, ≥ 500 samples → full V20 features
Tier B: cv_skill ≥ 0.05, ECE ≤ 0.02, ≥ 300     → V20-conservative
Tier C: cv_skill < 0.05                          → V20_TIER_3_SKIP set, hard-skip
Tier G: gated (veto rules fire > 30% backtest)   → downgrade FLAT

4b. Deep dive — 4 khái niệm production ML thường bị hand-wave

📐 (1) Model Registry — schema đầy đủ (không phải chỉ "1 folder chứa model")

Định nghĩa: Model Registry = "sổ hộ khẩu" của mọi model artifact trong company. Ai train, khi nào, dùng data nào, metric bao nhiêu, đang production hay đã retired. Tương tự Git nhưng cho model.

Schema SQL tối thiểu:

CREATE TABLE model_registry (
  model_id         VARCHAR PRIMARY KEY,        -- 'v20_slice6_20260701_abc123'
  model_name       VARCHAR NOT NULL,           -- 'stock_direction_predictor'
  version          VARCHAR NOT NULL,           -- 'v20.1.3'
  stage            VARCHAR NOT NULL,           -- 'staging' | 'production' | 'archived'
  artifact_uri     VARCHAR NOT NULL,           -- 's3://models/v20/abc123.joblib'
  feature_schema_hash VARCHAR NOT NULL,        -- SHA256 của feature names + dtypes
                                               -- dùng để check train/serve skew
  training_data_uri VARCHAR,                   -- 's3://data/2026-06-30-snapshot/'
  training_data_hash VARCHAR,                  -- SHA của dataset (reproducibility)
  training_code_git_sha VARCHAR NOT NULL,      -- commit SHA của training script
  hyperparams      JSON,                       -- {'max_depth':6, 'lr':0.05, ...}
  metrics_offline  JSON,                       -- {'cv_acc':0.611,'pr_auc':0.72}
  metrics_online   JSON,                       -- populated after deploy: live acc, latency
  created_by       VARCHAR NOT NULL,           -- user hoặc CI job
  created_at       TIMESTAMP NOT NULL,
  activated_at     TIMESTAMP,                  -- khi chuyển sang production
  retired_at       TIMESTAMP,
  parent_model_id  VARCHAR,                    -- lineage: model này base trên model nào
  CONSTRAINT unique_active_per_name
    EXCLUDE (model_name WITH =) WHERE (stage = 'production')
    -- CHỈ 1 model production per name tại 1 thời điểm
);

Vì sao mỗi field: feature_schema_hash chống train/serve skew (§3 dưới). training_code_git_sha reproducible (rerun exact model). parent_model_id lineage để rollback tuyến tính. stage constraint tránh 2 model production cùng lúc (bug V19.5).

Tools thực tế: MLflow Model Registry, Weights & Biases, Vertex AI Model Registry, SageMaker Model Registry. Đều implement schema tương đương.

📐 (2) Feature Store — vai trò + kiến trúc 2 tier

Vấn đề: Team A tính feature rsi_14 khi training. Team B tính lại khi serving. 2 phiên bản khác nhau (window boundary khác, timezone khác, missing value handling khác) → prediction sai. Đây là train/serve skew qua feature.

Feature Store = 1 nơi tính feature, 2 nơi tiêu thụ:

┌─────────────────────────┐
│   Raw data sources      │  (data lake, streaming Kafka)
│   prices, volume, news  │
└──────────┬──────────────┘
           │
           ▼
┌─────────────────────────┐
│  Feature Store          │  ← ĐỊNH NGHĨA CHỈ 1 LẦN
│  compute rsi_14, mfi... │
└─────┬───────────┬───────┘
      │           │
      ▼           ▼
┌──────────┐  ┌──────────┐
│ Offline  │  │  Online  │
│ store    │  │  store   │
│ (S3,     │  │ (Redis,  │
│  Parquet)│  │ DynamoDB)│
│ TRAINING │  │ SERVING  │
└──────────┘  └──────────┘
   │              │
   ▼              ▼
Batch train    Real-time inference
 (Airflow)      (API endpoint)

Guarantee quan trọng: Cùng 1 định nghĩa feature, cùng 1 code path. Offline store dùng cho training (historical, batch). Online store cache latest cho low-latency serving. Feature Store đảm bảo consistency giữa 2 store thông qua materialization job.

Point-in-time correctness: Khi query training data at time t, feature store chỉ trả về giá trị features tại thời điểm ≤ t (không dùng future). Đây là "as-of join" — chống look-ahead leak automatically. Không có feature store, team hay quên → CV inflated.

Tools: Feast (open source), Tecton, Hopsworks, Vertex AI Feature Store.

📐 (3) Training-Serving Skew — 4 nguồn gốc + detect

Định nghĩa: khoảng cách giữa "input model thấy khi train" và "input model thấy khi serve". Chỉ cần 1 pixel khác = prediction có thể sai lệch.

4 nguồn gốc phổ biến:

  1. Code skew: Training dùng pandas .rolling(20).mean(), serving dùng Java loop tính lại → boundary condition khác (NaN handling). Fix: dùng cùng codebase/binary (Feature Store).
  2. Data skew: Training data batch (T+1 EOD), serving data streaming (real-time, chưa settle) → cùng feature có value khác. Fix: match data freshness ở training với serving.
  3. Distribution skew (data drift): Train trên 2023 data, serve 2026 data → input distribution shift. Model không "sai code" nhưng OOD. Fix: monitor input statistics + retrain schedule.
  4. Label skew (concept drift): Correlation X→Y thay đổi (VD: post-COVID market behavior khác pre-COVID). Fix: monitor prediction quality online.

Detection at write time: khi save model artifact, tính hash của (feature_names, dtypes, preprocessing_config). Khi serving load, tính lại hash từ input pipeline → phải match. Đây chính là V19.5 bị bug — không có hash check → shape mismatch chạy vào silent fallback.

# In training:
schema = {'features': X.columns.tolist(), 'dtypes': X.dtypes.astype(str).tolist()}
schema_hash = hashlib.sha256(json.dumps(schema, sort_keys=True).encode()).hexdigest()
joblib.dump({'model': clf, 'schema_hash': schema_hash, 'scaler': scaler}, path)

# In serving:
artifact = joblib.load(path)
input_hash = compute_schema_hash(request_features)
if input_hash != artifact['schema_hash']:
    raise RuntimeError(f"TRAIN/SERVE SKEW DETECTED: {input_hash} != {artifact['schema_hash']}")
    # LOUD FAIL — not silent fallback!
📐 (4) Canary Deployment — chi tiết 3 stage + rollback trigger

Canary = "chim hoàng yến" thợ mỏ mang xuống đường hầm — chim chết = có gas độc, người thoát ra. Trong ML: 1 phần nhỏ traffic đi vào model mới, so sánh liên tục với model cũ, nếu mới tệ → rollback trước khi ảnh hưởng đông user.

Stage 0: Baseline shadow (BEFORE canary)
  Traffic:   100% → model_v18 (old)
             100% → model_v20 (new, shadow — không serve, chỉ log)
  Duration:  24-48h
  Compare:   agreement rate, prediction distribution, latency
  Gate:      if agreement < 90% → investigate before proceeding

Stage 1: Canary 5%
  Traffic:   95% → v18
              5% → v20 (real serve)
  Duration:  1-2h (nhiều tickers scale nhỏ) — 24h (few tickers scale lớn)
  Metrics:   live accuracy (via prediction_feedback), latency p99,
             error rate, business KPI (BUY hit rate)
  Auto-rollback triggers:
    - error rate > 2× baseline
    - latency p99 > 1.5× baseline
    - live acc drop > 5pp
    - fallback rate > 0%   ← V20 rule

Stage 2: Canary 25%
  Traffic:   75% → v18
             25% → v20
  Duration:  4-24h
  (same triggers, tighter threshold: acc drop > 3pp)

Stage 3: Full rollout 100%
  Traffic:   0% → v18 (kept warm for 7 days for rollback)
           100% → v20
  Monitoring: 7-day post-deploy vigilance

Rollback: single config flip (feature flag) — no code deploy
  ROLLBACK_TIME_SLA: < 5 minutes end-to-end

Statistical gate ở mỗi stage: dùng sequential test (SPRT — giải thích cơ chế ngay dưới) hoặc Bayesian A/B thay vì fixed-horizon test (kiểm định với CỠ MẪU CỐ ĐỊNH, phải đợi đủ N mẫu mới được kết luận). Sequential cho phép "stop early if clearly worse" (rollback sớm) hoặc "stop early if clearly better" (promote sớm) — không cần đợi hết N mẫu nếu bằng chứng đã đủ rõ ràng từ sớm.

📐 SPRT (Sequential Probability Ratio Test, Wald 1945) — vì sao dừng SỚM được mà vẫn giữ đúng độ tin cậy thống kê

Ý tưởng cốt lõi: thay vì cố định trước "phải thu thập đúng N mẫu rồi mới kết luận" (fixed-horizon test — cách làm thống kê cổ điển), SPRT theo dõi 1 "tỷ lệ khả năng" (likelihood ratio — đo xem dữ liệu quan sát được ỦNG HỘ giả thuyết nào hơn) TÍCH LUỸ DẦN sau MỖI mẫu mới, và dừng lại NGAY khi tỷ lệ đó đã đủ thuyết phục — không cần đợi tới N cố định.

Λ_n = Π f(x_i; θ₁) / f(x_i; θ₀)     # tích luỹ qua từng mẫu x_i mới quan sát được
                                      # θ₀ = giả thuyết "không đổi/model cũ tốt như cũ"
                                      # θ₁ = giả thuyết "model mới THỰC SỰ khác/tốt hơn"

Ngưỡng trên A = (1-β)/α    → nếu Λ_n VƯỢT A → dừng, KẾT LUẬN model mới THỰC SỰ khác
Ngưỡng dưới B = β/(1-α)    → nếu Λ_n RỚT dưới B → dừng, KẾT LUẬN model mới KHÔNG khác

# α = xác suất chấp nhận nhầm "có khác biệt" khi thực ra KHÔNG có (false positive)
# β = xác suất bỏ sót "có khác biệt" khi thực ra CÓ (false negative)
# Λ_n nằm GIỮA B và A → CHƯA đủ bằng chứng, tiếp tục thu thập thêm mẫu

Ví dụ số minh hoạ cơ chế (không phải chạy đủ trial thật, chỉ minh hoạ công thức): giả sử α=β=0.05, kiểm định "tỷ lệ thắng model mới = 50% (không đổi)" vs "tỷ lệ thắng = 60% (thực sự tốt hơn)":

A = (1-0.05)/0.05 = 19
B = 0.05/(1-0.05) ≈ 0.0526

Mỗi lần model mới THẮNG 1 sample, nhân Λ với 0.6/0.5 = 1.2
Mỗi lần model mới THUA 1 sample, nhân Λ với 0.4/0.5 = 0.8

→ Nếu model mới thắng liên tục nhiều lần, Λ tăng nhanh, sớm VƯỢT 19 → dừng
  sớm, kết luận "model mới tốt hơn thật" mà KHÔNG cần đợi đủ 1000 mẫu cố định.
→ Nếu model mới thua liên tục, Λ giảm nhanh, sớm RỚT dưới 0.0526 → dừng sớm,
  kết luận "không có khác biệt", tiết kiệm thời gian canary không cần thiết.

Insight: đây chính xác là lý do bảng "Auto-rollback triggers" ở Stage 1-2 phía trên có thể phản ứng NHANH (1-2h thay vì phải đợi đủ số mẫu cố định trước khi dám kết luận) — nếu model mới THỰC SỰ tệ, bằng chứng tích luỹ nhanh sẽ vượt ngưỡng B sớm, kích hoạt rollback trước khi ảnh hưởng nhiều traffic hơn.

Vì sao 3 stage thay vì 1: 5%→25%→100% cho phép detect issue với power tăng dần. Nếu bug chỉ hiện ra tại scale (VD: race condition trong caching), 25% stage sẽ bắt trước khi lên 100%. Skip stages = giả sử không có scale-dependent bug (nguy hiểm).

Ứng dụng V19.5 fail: nếu có canary 5% + auto-rollback trigger "fallback rate > 0%", V19.5 đã bị rollback trong 1-2h (thay vì 3 ngày user mất tiền). Đây là ROI cụ thể của discipline.

ML System Design checklist (10 câu hỏi phỏng vấn)

Khi được hỏi "design ML system for X", hỏi 10 câu này trước khi vẽ:

  1. Business goal: Product metric là gì? Revenue? Retention? User satisfaction?
  2. ML metric proxy: Accuracy? Precision? F1? Bounded by business goal?
  3. Data availability: Có bao nhiêu labeled data? Refresh rate? Ownership?
  4. Latency SLA: p95 < 100ms? 1s? 5s? Batch OK?
  5. Throughput: QPS? Peak vs average?
  6. Retrain frequency: Daily? Weekly? Monthly? Trigger-based (drift)?
  7. Fallback: Model down thì làm gì? Cache? Rule-based? Return null?
  8. Monitoring: Track gì? Accuracy? Latency? Data drift? Concept drift?
  9. Rollback: Bao lâu để rollback? Feature flag? Version tag?
  10. Team + oncall: Ai debug 3AM? Runbook?

Insight quan trọng: Bạn có thể có model state-of-the-art nhưng nếu không có 10 items trên = system sẽ sập. V19.5 chứng minh: model đủ tốt (V18) nhưng deploy tệ = mất tất cả.

5. STAR story cho interview

💬 Kể tại phỏng vấn

S (Situation): "In my stock prediction project V19.5, we retrained 246 model artifacts over 26h and metrics showed +0.61pp cv accuracy improvement — looked like clear win."

T (Task): "But when a user reported price staleness in AI reports, I dug in and discovered production was silently serving legacy v1 models for 14 blue-chip tickers."

A (Action): "I traced 7 distinct root causes: partial retrain (only T1, not T3/T5), silent fallback logging as WARNING not ERROR, in-place dir overwrite that broke rollback, skipped roll-up gates, cache masking staleness, and 2 more. I designed V20 execution plan with 7 counter-measures, including atomic multi-horizon retrain, loud fallback with alerting, immutable versioned dirs, and shape-consistency validation at write time."

R (Result): "V20 Slice 6 full retrain succeeded with 100% shape consistency, zero silent failures, and consistency cron alerts on any hit-rate drop > 10pp. Rolled back safely, no user impact. Documented all 7 root causes in v20-master-execution-plan.md — became team's playbook for ML production changes."

Meta lesson: "Silent failure in ML is the killer — traditional software throws exceptions, ML serves wrong predictions and users lose money silently. The #1 job of an ML engineer is not accuracy, it's making failures loud."

✅ QA Gate

1. 7 root causes V19.5 (memorize).

(1) Partial retrain T1 only. (2) Silent fallback WARNING. (3) In-place dir overwrite. (4) Skip roll-up gates. (5) Cache masking. (6) Force-recreate reset patches. (7) JSON corrupted.

2. Vì sao WARNING vs ERROR matters?

WARNING không trigger alerting default. ERROR → PagerDuty → on-call phản ứng. WARNING chôn lấp trong log stream, không ai đọc → bug sống hàng tuần.

3. Multi-horizon atomicity là gì?

Nếu bất kỳ horizon fail (T1 OK nhưng T3 crash), xóa toàn bộ 3 artifacts của ticker đó. Không để partial retrain leave shape mismatch. Enforced trong V20 training code.

4. Cache masking sau model swap — fix?

Bump model_registry.version_stamp → cache key changes → old entries stale. Also DELETE FROM prediction_log WHERE recent (2 days). Force reload.

5. Meta-lesson từ V19.5 áp dụng thế nào cho LLM system?

Silent failure equivalent: LLM hallucinate wrong facts, user không biết. Fix: (1) Structured output + JSON schema validation (fail-loud). (2) Confidence score + threshold. (3) Retrieval citation (verifiable). (4) Human review loop cho critical decisions. (5) Monitoring hallucination rate + drift.

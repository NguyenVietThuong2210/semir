8.3 · MCP (Model Context Protocol) Deep-Dive

Chuẩn open giúp LLM connect tools/data. Server-client protocol, tools + resources + prompts + sampling. Build MCP server bằng Python 30 phút.

Level 8 · AI Artifacts · ~40 phút

🎯 Learning objectives

  • Build MCP server bằng Python SDK

💡 MCP bằng ngôn ngữ đời thường

Trước chuẩn USB: Mỗi hãng máy tính có cổng riêng. Mua chuột Logitech chỉ cắm được Dell; mua ổ cứng Sony chỉ dùng máy Sony. Ai muốn dùng thiết bị cross-vendor phải mua adapter đủ loại → hell.

USB ra đời: 1 chuẩn duy nhất. Chuột hãng nào cắm máy hãng nào cũng chạy. Ecosystem bùng nổ.

Trước MCP: Mỗi LLM (OpenAI/Claude/Gemini) có API tool khác. Muốn integrate Slack tool cho 3 LLM = viết 3 adapter riêng.

MCP = "USB cho LLM". 1 chuẩn JSON-RPC — server tool viết 1 lần, mọi LLM support MCP đều dùng được. 4 primitives (Tools/Resources/Prompts/Sampling) cover 90% use case.

1. Vấn đề MCP giải quyết

Fragmentation trước MCP

2023: OpenAI function calling, Anthropic tools, Google function calling, Cohere tools — mỗi provider format khác. Bạn build 1 tool cho Claude → không dùng được ChatGPT/Gemini. Duplicate integration hell.

MCP (2024, Anthropic + open community): standard protocol. Build 1 MCP server → work với Claude Desktop, Cursor, VSCode Claude, và bất kỳ MCP-compatible client.

2.5 · Transport layer + wire protocol deep-dive

🔌 Deep-dive — JSON-RPC 2.0, stdio vs HTTP+SSE, authorization

Wire format — JSON-RPC 2.0

MCP dùng JSON-RPC 2.0 (RFC), không phải REST. Mọi message có 3 field cốt lõi: jsonrpc, id, method/result/error.

// Request (client → server)
{
  "jsonrpc": "2.0",
  "id": 42,
  "method": "tools/call",
  "params": {
    "name": "get_stock_price",
    "arguments": {"ticker": "VNM"}
  }
}

// Response (server → client)
{
  "jsonrpc": "2.0",
  "id": 42,
  "result": {
    "content": [{"type": "text", "text": "VNM: 68,500 VND"}]
  }
}

// Error
{
  "jsonrpc": "2.0",
  "id": 42,
  "error": {"code": -32602, "message": "Invalid params: ticker required"}
}

// Notification (không có id, không expect response)
{"jsonrpc": "2.0", "method": "notifications/tools/list_changed"}

Authorization flow (HTTP transport, 2025 spec)

OAuth 2.1 (chuẩn cấp quyền qua bên thứ 3 — user đăng nhập 1 lần với provider, ứng dụng nhận 1 "token" đại diện quyền thay vì lưu mật khẩu) và JWT (JSON Web Token — 1 chuỗi mã hoá tự chứa thông tin user + chữ ký, server verify chữ ký là biết token hợp lệ mà KHÔNG cần tra database mỗi lần) là 2 chuẩn nền tảng của flow dưới đây:

1. Client gọi POST /mcp → server trả 401 với WWW-Authenticate header
2. Client redirect user tới OAuth authorize URL
3. User consent → callback với authorization code
4. Client exchange code → access_token (short-lived) + refresh_token
5. Client attach `Authorization: Bearer <token>` mọi request
6. Server verify token (JWT hoặc introspection endpoint)
7. Scoped permissions: token có scope "tools:read" không được call "tools:write"

Transport security concerns

  • stdio: prompt injection từ tool response có thể poison LLM context. Fix: sanitize tool output, không trust markdown/HTML từ server.
  • HTTP+SSE: token leak qua log, MITM. Fix: TLS mandatory, short token TTL (15 min), refresh rotation.
  • Confused deputy: server A gọi server B thay user → escalation. Fix: token binding, per-tool audit log.

Interview Q&A

  1. Q: MCP vs OpenAI function calling? A: Function calling = per-provider API. MCP = cross-vendor protocol. MCP server viết 1 lần chạy được Claude/GPT/Gemini (khi provider support MCP client). MCP còn có Resources + Prompts + Sampling, function calling chỉ có Tools.
  2. Q: Vì sao JSON-RPC không REST? A: RPC bidirectional (server có thể notify client — VD "tools/list_changed"), REST unidirectional. RPC batch multiple calls trong 1 message. Overhead thấp hơn RESTful design.
  3. Q: stdio server multi-user được không? A: Không native — mỗi user cần process riêng (OS-level isolation). Muốn multi-tenant phải dùng HTTP+SSE với auth.
  4. Q: Prompt primitive để làm gì? A: Server publish reusable prompt template (VD "summarize_10k"). Client (LLM) fetch → fill args → gửi tới model. Đây là way share prompt discipline mà không đưa raw string vào code client.

3. Bốn primitives

3.1 Tools

Callable functions LLM có thể invoke. Giống function calling nhưng standardized.

@server.tool()
async def get_stock_price(ticker: str) -> dict:
    """Get current price of Vietnamese stock ticker.

    Args:
        ticker: Stock symbol (e.g., FPT, VNM)
    """
    return {"ticker": ticker, "price": 72.5, "change_pct": 1.2}

# LLM sees tool, decides when to call, args extracted from user query.

3.2 Resources

Read-only data sources LLM có thể browse/read. Files, DB rows, API endpoints.

@server.resource("stocks://prices/{ticker}")
async def get_ticker_data(ticker: str) -> str:
    """Return latest OHLCV data for ticker."""
    df = query_db(f"SELECT * FROM ohlcv WHERE ticker = '{ticker}' LIMIT 30")
    return df.to_csv()

# LLM can browse: list resources → decide which to read → get content.
# Different from tools: read-only, browsable, URI-addressable.

3.3 Prompts

Predefined prompt templates user + LLM can select.

@server.prompt()
async def analyze_stock(ticker: str, timeframe: str = "1M") -> list[Message]:
    """Guided prompt for stock analysis."""
    return [
        Message(role="user",
                content=f"Analyze {ticker} over {timeframe}. Focus on trend + volume."),
        Message(role="assistant",
                content="I'll analyze [ticker] in 3 sections: 1) Price action, 2) Volume, 3) Verdict."),
    ]

# User sees prompt in menu, click → prompt injected.
# Great cho templated workflows.

3.4 Sampling

Server request LLM completion. Reverse — server calls LLM (for agentic workflow inside server).

@server.tool()
async def summarize_ticker(ticker: str, ctx: Context) -> str:
    data = fetch_ticker_data(ticker)
    # Server ask host's LLM to summarize:
    result = await ctx.session.create_message(
        messages=[{"role": "user", "content": f"Summarize: {data}"}],
        max_tokens=500,
    )
    return result.content

Khi nào dùng primitive nào?

Insight quan trọng: Sampling là primitive độc đáo — server "delegate" LLM call cho client. Vì sao? (1) Client control cost, (2) Client có LLM key, (3) User privacy — server không thấy raw prompts. Đây là why MCP khác Function Calling truyền thống.

3.5 · Roots — primitive thứ 5 ít được nhắc tới

💡 Analogy

4 primitive ở §3 (Tools/Resources/Prompts/Sampling) đều là SERVER cung cấp thứ gì đó cho client. Roots đi CHIỀU NGƯỢC LẠI: CLIENT nói cho SERVER biết "mày chỉ được phép động vào những thư mục/file NÀY thôi" — giống việc chủ nhà đưa cho thợ sửa ống nước 1 tấm bản đồ khoanh vùng "chỉ được vào bếp và nhà tắm, không được vào phòng ngủ" TRƯỚC KHI thợ bắt đầu làm việc, thay vì để thợ tự do đi khắp nhà rồi hy vọng thợ tự biết giới hạn.

Vấn đề cụ thể: 1 filesystem MCP server (VD server-filesystem ở bảng §8 dưới) về nguyên tắc CÓ THỂ đọc/ghi bất kỳ đường dẫn nào trên máy nếu code không tự giới hạn — nguy hiểm nếu server có bug hoặc bị command injection. Roots giải quyết bằng cách để CLIENT (không phải server tự khai) là bên quyết định + thông báo boundary, và server phải hỏi client trước khi biết mình được phép động vào đâu.

// Server hỏi client: "tao được phép động vào thư mục nào?"
{"jsonrpc": "2.0", "id": 1, "method": "roots/list"}

// Client trả lời — CHỈ những root user đã cho phép, KHÔNG phải toàn bộ ổ đĩa:
{
  "jsonrpc": "2.0", "id": 1,
  "result": {
    "roots": [
      {"uri": "file:///d:/New-jouney/predictor", "name": "predictor project"}
    ]
  }
}

// Nếu user đổi project (đóng predictor, mở project khác) → client PHẢI gửi:
{"jsonrpc": "2.0", "method": "notifications/roots/list_changed"}
// Server nhận notification này → gọi lại roots/list để lấy boundary MỚI

⚠️ Chỗ dễ nhầm nhất: Roots KHÔNG PHẢI cơ chế enforce/sandbox tự động — spec chỉ định nghĩa GIAO THỨC hỏi-đáp boundary, còn việc SERVER có THỰC SỰ tôn trọng boundary đó khi thao tác file hay không vẫn phụ thuộc vào code của server (spec dùng chữ "SHOULD respect root boundaries", không phải cơ chế OS-level chặn cứng). Khác với OS-level sandbox (VD Docker container giới hạn filesystem thật sự ở tầng hệ điều hành), Roots là 1 "hợp đồng" giao thức — server tuân thủ tự nguyện, không bị chặn cứng nếu cố tình phá vỡ.

Insight: Roots hoàn thiện bức tranh "4 primitive" ở §3 thành 1 mô hình 2 CHIỀU đầy đủ — server cung cấp Tools/Resources/Prompts, thỉnh thoảng nhờ Sampling; còn client, ngược lại, cũng CHỦ ĐỘNG giới hạn phạm vi hoạt động của server qua Roots, không chỉ thụ động nhận những gì server cung cấp. Đây cùng tinh thần "least privilege" đã nêu ở §9 Best practices bên dưới, nhưng ở cấp GIAO THỨC (protocol-level) chứ không phải chỉ 1 khuyến nghị thiết kế.

4. Build MCP server — 30 min tutorial

# pip install mcp

from mcp.server import Server, NotificationOptions
from mcp.types import Tool, TextContent
import mcp.server.stdio

server = Server("stock-tools")

@server.list_tools()
async def list_tools() -> list[Tool]:
    return [
        Tool(
            name="get_price",
            description="Get current price of VN stock",
            inputSchema={
                "type": "object",
                "properties": {
                    "ticker": {"type": "string", "pattern": "^[A-Z0-9]{2,10}$"}
                },
                "required": ["ticker"]
            }
        )
    ]

@server.call_tool()
async def call_tool(name: str, arguments: dict) -> list[TextContent]:
    if name == "get_price":
        ticker = arguments["ticker"]
        # Fetch price...
        price = 72.5
        return [TextContent(type="text", text=f"{ticker}: {price}")]

async def main():
    async with mcp.server.stdio.stdio_server() as (read, write):
        await server.run(read, write, ...)

if __name__ == "__main__":
    import asyncio
    asyncio.run(main())

6. Auth patterns

Security matters

MCP server có thể expose DB, file system, secrets. Bad auth = catastrophic breach.

  • Local stdio: process-level trust (client runs server)
  • OAuth 2.1: standard for remote servers (MCP spec 2025)
  • API key: simple, storage-based (env var, secure vault)
  • Signed requests: HMAC verify

7. Discovery + capability negotiation

Client connect:
1. Handshake: exchange protocol version
2. Client request capabilities: what tools/resources/prompts available
3. Server respond với schema for each
4. Client cache, present to LLM as available tools

# Client can subscribe to updates: server push new tools/resources as available

9. Best practices

  1. Explicit schema: JSON Schema strict, reject unknown fields
  2. Least privilege: read-only by default, write requires explicit approval
  3. Idempotent tools: retry-safe
  4. Error surface: return descriptive errors LLM can use to correct
  5. Logging + audit: log every tool call for debugging
  6. Rate limit: prevent LLM abuse (loop calls)
  7. Versioning: protocol + your server independent

11. Interview questions

Common
  1. "MCP vs OpenAI function calling — 3 differences" → Standard protocol vs vendor-specific. 4 primitives (tools + resources + prompts + sampling) vs just tools. Client-server distribution vs single-app.
  2. "When add MCP vs custom API?" → MCP: LLM integration primary usage. Custom API: broader systems integration (many clients not just LLM). Can do both — same backend, 2 exposure layers.
  3. "Security concern MCP server exposing DB?" → SQL injection risk (LLM crafted query). Fix: use read-only DB user, parameterized queries only, explicit whitelist tables/columns.

✅ QA Gate

1. MCP 4 primitives — 1 câu mỗi cái.

Tools: LLM invokable functions with side effects. Resources: read-only data browsable by URI. Prompts: templated workflows selectable. Sampling: server request LLM completion (reverse direction).

2. stdio vs HTTP+SSE transport — khi nào chọn?

stdio: local server co-located với client (Claude Desktop launch server subprocess). HTTP+SSE: remote hosted server, multi-user. Latency low local vs network dependent remote.

3. Build MCP server exposing Postgres — security concerns?

(1) Read-only DB user. (2) Parameterized queries — LLM inputs never string-format. (3) Whitelist tables/columns. (4) Rate limit. (5) Log all queries + LLM prompt. (6) PII redact output.

4. MCP vs custom internal API — khi nào chọn nào?

MCP: LLM-first integration, use Claude Desktop/Cursor. Standard, no client UI code. Custom API: general purpose (mobile app, web, other services). Can have both: same backend, 2 layers.

5. Sampling primitive use case?

Server tool implementation cần LLM (agentic workflow inside server). E.g., summarize tool: fetch data + ask LLM to summarize → return. Server delegate reasoning to host's LLM.

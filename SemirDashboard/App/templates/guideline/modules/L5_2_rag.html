5.2 · Retrieval-Augmented Generation (RAG)

Cách LLM "học" domain knowledge mà không cần fine-tune. Pattern chuẩn cho chatbot enterprise, agent, code assistant.

Level 5 · LLM Systems · ~40 phút

🎯 Learning objectives

  • Định nghĩa RAG bằng 3 câu (embed → retrieve → generate)
  • Chọn được embedding model + vector DB cho use case cụ thể
  • Implement RAG pipeline bằng Python (LangChain hoặc bare-bones)
  • Debug 5 failure mode phổ biến (bad chunk, wrong embed, no re-rank, hallucination)
  • So sánh RAG vs Fine-tuning: khi nào dùng gì
💡 RAG là gì bằng ngôn ngữ đời thường?

Học sinh thi mở tài liệu (open-book exam): Không thuộc lòng cả sách giáo khoa. Khi có câu hỏi → lật mục lục → tìm chương liên quan → đọc 2-3 trang → viết đáp án dựa trên đó.

  • Học sinh = LLM (biết cách suy luận, viết văn)
  • Mục lục = vector index (map từ câu hỏi → trang liên quan)
  • Sách giáo khoa = knowledge base (docs công ty, wiki, code)
  • Đọc 2-3 trang = retrieval top-K chunks
  • Viết đáp án dựa trên = generation với context

Fine-tuning khác gì? Fine-tuning = bắt học sinh đi học lại lớp 12 với sách mới (đắt, lâu, mà quên kiến thức cũ). RAG = giữ nguyên học sinh, chỉ đưa thêm sách mở tài liệu (rẻ, nhanh, update chỉ cần đổi sách).

Ví dụ chatbot công ty: User hỏi "chính sách nghỉ phép 2026 ra sao?" → RAG tìm 3 chunks từ SOP HR → LLM viết trả lời dựa 3 chunks đó. Không hallucinate vì đã có evidence trong prompt.

1. Vì sao cần RAG?

Problem: LLM (Claude, GPT-4) được train trên public data đến 1 thời điểm cutoff. Không biết:

  • Company docs private (SOP, wiki, code)
  • Latest news / prices / events sau cutoff
  • Personal context (user history, preferences)

3 options giải quyết:

  1. Fine-tuning: retrain LLM với data mới. Đắt (10k-100k USD), lâu (days), require expertise, khó cập nhật.
  2. Long context: nhồi hết docs vào context (128k tokens Claude, 200k GPT-4-turbo). Đắt token, chậm inference, quality giảm với context dài.
  3. RAG ⭐: chỉ retrieve chunks liên quan từ knowledge base, inject vào prompt. Rẻ, real-time, easy update.

2. RAG pipeline — 3 phases

┌─ INDEXING (offline, 1 lần khi có docs) ─────────────┐
│                                                      │
│  Docs → Chunk → Embed → Store in vector DB           │
│                                                      │
└──────────────────────────────────────────────────────┘

┌─ QUERY (runtime, mỗi user question) ────────────────┐
│                                                      │
│  Question → Embed → Search top-K → Rerank →         │
│  → Format prompt (question + retrieved) → LLM →      │
│  → Answer                                            │
│                                                      │
└──────────────────────────────────────────────────────┘

Rerank là gì? (bước "Rerank" ở trên) — sau khi lấy top-K chunk gần đúng bằng vector search (nhanh nhưng không hoàn toàn chính xác), dùng 1 model khác, chậm hơn nhưng chính xác hơn (cross-encoder), chấm điểm lại chính xác từng chunk so với câu hỏi, rồi chỉ giữ vài chunk tốt nhất. Cơ chế đầy đủ (bi-encoder vs cross-encoder, vì sao rerank chính xác hơn) giải thích chi tiết ở §5.7 bên dưới — ở đây chỉ cần biết đây là bước "lọc lại cho chính xác" sau khi tìm nhanh.

3. Phase 1: Indexing chi tiết

3.1 Chunking — chia doc thành chunks

Long doc (100k words) không fit context của embedding model (thường 512 tokens). Phải chia.

StrategyChunk sizeKhi dùng
Fixed size500-1000 charsBaseline, đơn giản
Sentence-based1-5 sentencesQA tightly-scoped
Recursive character splitAdaptiveLangChain default, respect structure
Semantic (BERT-based)VariableBest quality nhưng chậm
Markdown-awareSection-basedCho docs có structure (README, wiki)
Chunking pitfalls
  • Chunks quá nhỏ: mất context, retrieval matches nhưng LLM không hiểu
  • Chunks quá lớn: 1 chunk chứa nhiều topics → embedding trung bình → retrieval kém chính xác
  • No overlap: câu bị cắt giữa 2 chunks → lost. Fix: overlap 10-20%
  • Ignore structure: chunk cắt giữa code block, table, heading → nonsense

4. Phase 2: Query pipeline

def rag_query(question: str, top_k: int = 5):
    # Step 1: embed question
    q_emb = model.encode([question])

    # Step 2: vector search
    scores, indices = index.search(q_emb, top_k)
    candidates = [chunks[i] for i in indices[0]]

    # Step 3 (optional): rerank
    reranker = CrossEncoder('cross-encoder/ms-marco-MiniLM-L-6-v2')
    scores = reranker.predict([(question, c) for c in candidates])
    ranked = sorted(zip(candidates, scores), key=lambda x: -x[1])
    top_reranked = [c for c, _ in ranked[:3]]  # top 3 sau rerank

    # Step 4: format prompt
    context = "\n\n".join([f"[{i+1}] {c}" for i, c in enumerate(top_reranked)])
    prompt = f"""Answer the question using ONLY the context below.
If the answer is not in the context, say "I don't know".

Context:
{context}

Question: {question}

Answer:"""

    # Step 5: LLM generation
    return claude.messages.create(model='claude-opus-4-7', ...)

4.5 — Vector index architecture: HNSW vs IVF-PQ vs Flat (chọn đúng = giảm 100× cost)

Ẩn dụ VN — tìm số điện thoại trong danh bạ 10 triệu người
IndexCách hoạt độngRecallSpeed 10M vecRAM 10M × 768dKhi dùng
Flat (brute force)So sánh query với tất cả vector100%~2s30GB<100k vec, ground truth
HNSW (Hierarchical NSW)Graph nhiều tầng — top layer sparse, đi xuống dần. Giống Google Maps zoom95-99%~5ms40GB (graph overhead)<100M vec, latency critical
IVF-PQChia vector space thành N cluster (IVF) + nén mỗi vector (Product Quantization) từ float32 xuống 8-16 bytes85-95%~10ms0.6GB (nén 50×)>100M vec, RAM giới hạn
ScaNN / DiskANNOptimize cache line + SSD read95%+<10msSSD-basedBillion-scale (Google, Bing)

Recall là gì? (cột "Recall" trong bảng trên) — tỷ lệ query mà kết quả ĐÚNG thực sự nằm đâu đó trong top-K trả về, so với nếu tìm brute-force (Flat, luôn đúng 100%). VD Recall 95% nghĩa là 95/100 query, index tìm đúng kết quả brute-force sẽ tìm ra; 5 query còn lại bị "trượt" vì graph/cluster không dẫn tới đúng node. Đánh đổi cơ bản của mọi ANN index (Approximate Nearest Neighbor — tìm gần đúng thay vì tìm chính xác 100%): giảm recall 1 chút để đổi lấy tốc độ nhanh hơn hàng trăm-nghìn lần.

Cấu trúc HNSW — graph nhiều tầng, tầng trên thưa (đi nhanh, ít chính xác), tầng dưới dày đặc (đi chậm hơn, chứa toàn bộ vector):

Layer 2 (thưa nhất):    A ─────────────────────── E
                         │                         │
Layer 1 (dày hơn):      A ──── B ──── C ────────── E ──── F
                         │      │      │            │      │
Layer 0 (TẤT CẢ vector): A─B─C─D─E─F─G─H─I─J─K─L─M─N─O ... (toàn bộ 10M)

Search: bắt đầu ở Layer 2 (ít node — "đại lộ", đi rất nhanh)
        → tới node gần query nhất trong layer này
        → NHẢY XUỐNG Layer 1 (nhiều node hơn — "đường lớn"), tìm tiếp
        → NHẢY XUỐNG Layer 0 (mọi node — "đường nhỏ"), tìm chính xác
        → trả về top-K gần query nhất tại Layer 0

Rule chọn: bắt đầu HNSW (Qdrant/Weaviate/pgvector default). Chỉ chuyển IVF-PQ khi RAM > ngân sách. Bench recall trên eval set thật trước khi commit — HNSW tune param (M=16, efConstruction=200) khác biệt recall 5-15%. M = số kết nối tối đa mỗi node trong graph (M cao hơn → graph dày hơn, recall tốt hơn nhưng tốn RAM hơn, giống thêm nhiều "đường tắt" trong bản đồ). efConstruction = số ứng viên xét khi XÂY graph (cao hơn → graph chất lượng hơn nhưng index chậm hơn, chỉ tốn 1 lần lúc indexing). Mặc định M=16, efConstruction=200 là điểm khởi đầu an toàn cho hầu hết use case.

4.7 — Context window budget math (đừng nhồi hết chunks vào)

Budget cho Claude Opus 4.7 (200k context, 8k output max)
Budget = system + few-shot + retrieved_chunks + user_query + reserved_output
       ≤ 200,000 tokens

Ví dụ setup thực tế:
  system prompt (rules + persona)     : 3,000
  few-shot examples (3 pairs)         : 4,000
  retrieved chunks (top-5 × 500t)     : 2,500
  user query                          :   200
  conversation history (last 3 turns) : 3,000
  ─────────────────────────────────
  input total                         :12,700 tokens
  reserved for output                 : 2,000
  ─────────────────────────────────
  used                                :14,700 / 200,000 (7%)

Cost = 12,700 × $15/1M + 2,000 × $75/1M = $0.19 + $0.15 = $0.34
Với cache (system 3,000 + few-shot 4,000 = 7,000 tokens ĐƯỢC cache;
           chunks 2,500 + query 200 + history 3,000 = 5,700 tokens KHÔNG cache
           vì đổi mỗi lần gọi):
  = 7,000 × $1.5/1M (cached) + 5,700 × $15/1M (uncached) + 2,000 × $75/1M (output)
  = $0.0105 + $0.0855 + $0.15 = $0.246 ≈ $0.25 (-28%)

Sai lầm phổ biến: nhồi top-20 chunks (10k tokens thay vì 2.5k của top-5). Kết quả: (a) "lost in the middle" — LLM bỏ qua chunk giữa; (b) riêng phần token CHUNKS tăng 4× (2.5k→10k) — vì đây chỉ là 1 phần của tổng 12.7k input, mức tăng CHI PHÍ TOÀN REQUEST thực tế nhẹ hơn 4× nhiều (input tổng tăng từ 12.7k lên 20.2k, khoảng +59%, không phải toàn bộ cost nhân 4); (c) latency tăng 2× (prefill lâu). Top-3 sau rerank chất lượng cao hơn top-20 raw.

5. Advanced tricks

5.1 Hybrid search: BM25 + vector

Vector chưa perfect cho exact match (từ khóa, code snippet). BM25 (thuật toán xếp hạng dựa trên tần suất từ khoá xuất hiện trong doc — không hiểu nghĩa như embedding, bản nâng cấp của TF-IDF cổ điển) mạnh ở đó. Combine 2 scores.

5.2 Query rewriting

User hỏi "cái đó" (câu ngắn, context implicit). LLM rewrite thành query cụ thể hơn trước khi embed. VD:

original: "how do I fix that?"
rewritten: "how do I fix the pandas ImportError when running train_v18_unified.py?"

5.3 HyDE (Hypothetical Document Embeddings)

Vấn đề: câu hỏi ("giá FPT thế nào?") và câu trả lời thật trong tài liệu ("FPT đóng cửa 72.5, tăng 1.2% phiên...") thường khác nhau về CÁCH VIẾT (câu hỏi ngắn, câu trả lời dài + số liệu cụ thể) — dù cùng chủ đề, 2 kiểu văn phong này không phải lúc nào cũng embed gần nhau.

Cách làm: thay vì embed thẳng câu hỏi, để LLM tưởng tượng ra 1 câu trả lời GIẢ (không cần đúng số liệu thật) theo đúng văn phong tài liệu thật, rồi embed câu trả lời giả đó để đi tìm — vì "câu trả lời giả" và "câu trả lời thật" cùng văn phong nên embedding gần nhau hơn "câu hỏi" và "câu trả lời thật".

Question:        "giá FPT thế nào?"
HyDE hypothetical answer (LLM tự bịa, KHÔNG cần đúng số):
                 "FPT hôm nay giao dịch quanh vùng 70-73, khối lượng
                  trung bình, RSI trung tính không quá mua bán."
→ Embed câu HyDE này (không phải câu hỏi gốc) để đi search chunk thật.

Sai lầm thường gặp: dùng HyDE cho câu hỏi cần số liệu chính xác tuyệt đối (VD "giá đóng cửa FPT hôm nay là bao nhiêu") — LLM có thể bịa số gần đúng khiến embedding lệch hướng sai. Fix: chỉ dùng HyDE cho câu hỏi mang tính khái niệm/định tính, không dùng cho tra cứu số liệu chính xác (những câu đó nên dùng exact-match/BM25 — §5.1).

5.4 Multi-query retrieval

Vấn đề: 1 câu hỏi có thể embed lệch nếu người dùng viết mơ hồ/thiếu từ khóa — chỉ retrieve theo đúng 1 cách diễn đạt dễ bỏ sót chunk liên quan viết theo cách khác.

Cách làm: LLM tạo 3-5 câu hỏi diễn đạt lại (paraphrase) cùng 1 ý, retrieve riêng cho từng câu, rồi UNION (gộp, bỏ trùng) kết quả — tăng khả năng ít nhất 1 cách diễn đạt match đúng chunk.

Original: "RSI cao nghĩa là gì?"
Variant 1: "chỉ số RSI cao thì cổ phiếu đang ở trạng thái nào?"
Variant 2: "RSI overbought là gì?"
Variant 3: "RSI trên 70 có ý nghĩa gì khi phân tích kỹ thuật?"
→ Retrieve top-5 cho MỖI variant (4 lần gọi retrieval) → union 4 tập kết quả,
  bỏ trùng → thường được 8-15 chunk unique thay vì chỉ 5 của 1 câu gốc.

Đánh đổi: tăng recall (ít bỏ sót chunk hơn) nhưng tốn 3-5× số lần gọi retrieval + 1 lần gọi LLM để sinh variants — chỉ đáng dùng khi câu hỏi thường mơ hồ/đa dạng cách hỏi (chatbot support), không cần cho query đã rất cụ thể (VD tra mã ticker).

5.5 Contextual retrieval (Anthropic 2024)

Anthropic báo: prepend mỗi chunk với 50-100 tokens context (từ full doc) trước embed → retrieval accuracy tăng 35%.

5.6 MMR (Maximal Marginal Relevance) — chống trùng lặp

Vấn đề: top-5 chunks đều nói cùng 1 fact (report trích dẫn nhau) → LLM chỉ có 1 góc nhìn, thiếu diversity.

MMR score(d) = λ · sim(d, query) − (1−λ) · max_{d'∈selected} sim(d, d')

# Giải thích từng ký hiệu:
# d              = 1 chunk candidate đang xét có nên chọn tiếp không
# sim(d, query)  = độ liên quan của d với câu hỏi (cosine similarity, càng cao càng tốt)
# selected       = tập chunk ĐÃ chọn ở các bước trước
# max_{d'∈selected} sim(d, d') = độ giống NHẤT giữa d và bất kỳ chunk nào đã chọn rồi
#                  (càng cao = d càng trùng lặp với cái đã có → càng nên bị trừ điểm)
# λ (lambda)     = trọng số đánh đổi relevance vs diversity, λ=0.7 nghĩa 70/30

Ví dụ tính tay — đã chọn 1 chunk (C1), đang chọn chunk thứ 2 giữa 2 ứng viên C2, C3:

sim(C2, query) = 0.85   sim(C2, C1) = 0.90  (C2 gần giống C1 — trùng ý)
sim(C3, query) = 0.75   sim(C3, C1) = 0.20  (C3 khác hướng C1 — bổ sung góc nhìn mới)

λ = 0.7:
MMR(C2) = 0.7×0.85 − 0.3×0.90 = 0.595 − 0.270 = 0.325
MMR(C3) = 0.7×0.75 − 0.3×0.20 = 0.525 − 0.060 = 0.465

→ Dù C2 relevance cao hơn (0.85 > 0.75), MMR CHỌN C3 (0.465 > 0.325) vì C2
  trùng lặp quá nhiều với C1 đã chọn — ưu tiên đa dạng hoá thay vì nhồi 2 chunk nói cùng 1 ý.

Kết luận: top-5 với MMR cover 3-4 khía cạnh khác nhau thay vì 1 khía cạnh lặp lại. Đặc biệt hữu ích cho comparative queries ("so sánh 3 phương án").

5.7 Reranker architecture — vì sao cross-encoder mạnh hơn embedding

Ẩn dụ VN — vòng 2 phỏng vấn: embedding = quét CV bằng máy (top 100 CV giống JD nhất); cross-encoder = phỏng vấn trực tiếp từng người top 100 → chọn top 10 thật.

Bi-encoder (embedding)Cross-encoder (reranker)
Cách xử lýEncode query và doc RIÊNG BIỆT thành 2 vector, tính cosineConcat [query, doc] → 1 BERT forward → xuất score
Attention giữa q và d?Không (chỉ cosine cuối)Full cross-attention mọi cặp token
Precomputable?✅ Doc embed offline❌ Phải chạy mỗi request
Speed 1M pairs~10ms (ANN index)~30s trên GPU
Accuracy (MS MARCO)MRR@10 ≈ 0.35MRR@10 ≈ 0.42 (+20%)

MRR@10 là gì? Mean Reciprocal Rank trong top-10 kết quả: với mỗi query, tìm vị trí (rank) của kết quả ĐÚNG đầu tiên trong top-10, lấy nghịch đảo (1/rank), rồi trung bình qua toàn bộ query set. VD: query 1 answer đúng ở vị trí #1 → 1/1 = 1.0; query 2 answer đúng ở vị trí #4 → 1/4 = 0.25; trung bình 2 query = 0.625. MRR càng gần 1 nghĩa là answer đúng càng thường xuyên đứng ĐẦU danh sách (không chỉ "có mặt trong top-10" mà còn "đứng cao").

Kiến trúc chuẩn 2 tầng — funnel thu hẹp dần: bi-encoder quét NHANH toàn bộ index để lấy 1 tập lớn recall cao, cross-encoder CHẬM nhưng chính xác chỉ chạy trên tập nhỏ đó:

   Toàn bộ vector DB (VD 10M chunks)
              │
              ▼   bi-encoder + ANN index (~10ms, embedding precompute sẵn offline)
    ┌───────────────────────┐
    │  top-100 candidates   │   MRR@10 ≈ 0.35 — recall cao, precision vừa
    └───────────────────────┘
              │
              ▼   cross-encoder rerank (~30s/1M pairs GPU → ~100ms cho 100 pairs)
        ┌───────────┐
        │  top-3    │   MRR@10 ≈ 0.42 — precision cao, chỉ khả thi vì tập đã nhỏ
        └───────────┘
              │
              ▼
          LLM context

Options cross-encoder: bge-reranker-v2-m3 (open-source), Cohere Rerank 3, Jina Reranker.

5.8 ColBERT / Late Interaction (2020-2022) — "khoảng giữa" giữa bi-encoder và cross-encoder

💡 Analogy

Nhắc lại §5.7 — bi-encoder nén CẢ câu/đoạn văn thành 1 VECTOR DUY NHẤT trước khi so sánh (nhanh nhưng mất chi tiết, giống tóm tắt cả CV thành 1 con số "độ phù hợp"); cross-encoder đọc CẢ query và doc CÙNG LÚC qua 1 model (chính xác nhưng chậm, giống đọc kỹ từng CV). ColBERT (Contextualized Late Interaction over BERT, Khattab & Zaharia 2020) đứng GIỮA: giữ 1 vector RIÊNG cho MỖI TỪ (không nén thành 1 vector duy nhất như bi-encoder), nhưng vẫn encode query/doc TÁCH BIỆT (không chậm như cross-encoder) — rồi so khớp TỪNG TỪ của query với TỪNG TỪ của doc lúc query-time, giống việc so khớp "chi tiết CV nào khớp với chi tiết JD nào" thay vì chỉ so 1 con số tổng.

Vấn đề cụ thể: bi-encoder (§5.7) nén nguyên câu "FPT tăng trưởng doanh thu quý 2 nhờ mảng công nghệ" thành 1 vector duy nhất — nếu câu dài, nhiều ý, 1 vector không đủ "chỗ" giữ hết chi tiết, đặc biệt mất thông tin khi so khớp với query chỉ hỏi về 1 khía cạnh nhỏ (VD chỉ hỏi "mảng công nghệ" mà không quan tâm doanh thu). Cross-encoder (§5.7) giải quyết được vấn đề chi tiết này nhưng phải chạy model MỖI CẶP (query, doc) — không thể precompute doc embedding offline, nên không scale được cho hàng triệu doc.

# Bi-encoder (§5.7): nén CẢ câu thành 1 vector
doc_vec = BERT("FPT tăng trưởng doanh thu quý 2 nhờ mảng công nghệ")  # → 1 vector duy nhất
score = cosine(query_vec, doc_vec)                                    # so 1 vs 1

# ColBERT: giữ 1 vector CHO MỖI TOKEN, encode query/doc RIÊNG (vẫn precompute doc offline được)
doc_vecs   = [BERT(tok) for tok in "FPT tăng trưởng doanh thu quý 2 nhờ mảng công nghệ"]  # N vector
query_vecs = [BERT(tok) for tok in "mảng công nghệ FPT"]                                   # M vector

# MaxSim: với MỖI token query, tìm token doc GIỐNG NHẤT, rồi CỘNG các max lại
score = Σ_{i=1..M} max_{j=1..N} cosine(query_vecs[i], doc_vecs[j])
# → token "công nghệ" trong query match RẤT SÁT token "công nghệ" trong doc (dù các
#   phần khác của câu — "doanh thu quý 2" — không liên quan tới query, không bị pha loãng
#   vào 1 vector trung bình như bi-encoder)

⚠️ Chỗ dễ nhầm nhất: ColBERT KHÔNG PHẢI cross-encoder "rẻ hơn" — điểm mấu chốt là doc vẫn được encode ĐỘC LẬP với query (giống bi-encoder, nên vẫn precompute + index offline được cho hàng triệu doc), chỉ khác ở bước SO SÁNH cuối: thay vì so 1 vector với 1 vector (bi-encoder), nó so N vector với M vector qua MaxSim (tốn thêm chi phí so sánh, nhưng vẫn RẺ HƠN NHIỀU so với việc chạy lại BERT cho mỗi cặp query-doc như cross-encoder). Đây là lý do gọi "late interaction" — sự "tương tác" (interaction) giữa query và doc xảy ra MUỘN (late), ở bước so sánh vector cuối cùng, không phải ngay từ đầu như cross-encoder.

Bi-encoderColBERT (late interaction)Cross-encoder

Insight: ColBERTv2 (2022) giải quyết đúng nhược điểm ban đầu của ColBERT (lưu N vector/doc tốn storage hơn nhiều so với 1 vector/doc của bi-encoder) bằng "residual compression" — nén các token vector gần giống nhau lại, giảm dung lượng lưu trữ đáng kể mà vẫn giữ được lợi ích matching chi tiết theo từng token. Đây là lý do 1 số hệ thống production (VD RAGatouille, 1 số pipeline dùng Colbert-based retrieval) chọn ColBERT làm bước RETRIEVAL CHÍNH (không chỉ rerank) khi cần độ chính xác cao hơn bi-encoder thuần mà vẫn muốn scale tốt hơn cross-encoder.

5.9 Query rewriting patterns

  • Decontextualize: "cái đó thế nào?" + history → "chính sách bảo hành sản phẩm iPhone 15 Pro Max thế nào?"
  • Decompose: câu hỏi 2 phần → 2 sub-queries, retrieve riêng, union.
  • Expand synonyms: "doanh thu" → "doanh thu OR revenue OR sales OR turnover"
  • Step-back prompt: từ câu cụ thể → generalize → retrieve concept trước, detail sau.

5.10 — Deep-dive: 5 bẫy giết sản phẩm RAG mà tutorial không nói

Mục này giả định bạn đã đọc xong Chunking (§3.1), Embedding (§3.2), Hybrid search (§5.1), Reranker (§5.7) ở trên — đây là các trap THỰC TẾ khi áp dụng đúng những kỹ thuật đó vào data thật, không phải khái niệm mới.

🎯 Deep-dive — RAG: 5 bẫy giết sản phẩm mà tutorial không nói (chi tiết dễ hiểu)

Câu chuyện thật: Bạn build chatbot Vietnamese finance với RAG. Test 10 câu hỏi mẫu → 8/10 chính xác. Deploy → user complain "chatbot nói bậy 60% thời gian". Bạn confused: cùng model, cùng data, sao khác nhau? Đây là 5 bẫy hầu hết dev copy-paste tutorial dính.

Bẫy 1 — Embedding similarity KHÔNG phải semantic similarity

Cosine similarity là gì? Mỗi đoạn text được embedding model biến thành 1 vector (mảng số, VD 768 chiều). Cosine similarity đo "2 vector chỉ cùng hướng bao nhiêu" — không quan tâm độ dài, chỉ quan tâm góc giữa chúng. Giá trị chạy từ -1 đến 1: 1 = trùng hướng hoàn toàn (nghĩa giống hệt), 0 = không liên quan, -1 = ngược nghĩa. Công thức: cos(A,B) = (A·B) / (|A|·|B|) — A, B là 2 vector embedding cần so (VD embedding của câu hỏi và embedding của 1 chunk); tích vô hướng (A·B) chia tích độ dài 2 vector (|A|·|B|). Trong RAG, "top-K" nghĩa là lấy K chunk có cosine similarity với câu hỏi cao nhất.

Bạn nghĩ: "Query 'Q2 revenue growth' và document 'quý 2 doanh thu tăng 15%' rõ ràng semantically identical". Cosine similarity giữa 2 embeddings? 0.4 (thấp so với thang -1..1, đáng lẽ phải >0.8 nếu model hiểu đúng nghĩa). Vì sao?

Vì sao lại thấp vậy? Embedding model học bằng contrastive loss:

  • Lúc train, model được cho 1 cặp (query, doc) đúng khớp + nhiều doc "sai" ngẫu nhiên.
  • Model bị phạt (loss tăng) nếu vector của cặp đúng không nằm gần nhau hơn hẳn các cặp sai.
  • → Model chỉ học được cách kéo gần những cặp có dạng giống pairs đã thấy khi train — không tự suy luận ra ngoài.
  • Nếu training data của OpenAI text-embedding-3 không có cặp English-Vietnamese finance → model chưa từng học "revenue = doanh thu" trong ngữ cảnh tài chính, nên không match.

Fix:

  • Dùng multilingual model (bge-m3 hoặc jina-embeddings-v3) train trên 100+ ngôn ngữ.
  • Test embedding trên 20 sample queries của DOMAIN của bạn trước khi build.
  • Nếu cosine sim < 0.6 cho matching pair → model không phù hợp domain.

Hậu quả nếu bỏ qua: Chatbot Vietnamese finance dùng OpenAI ada-002 → recall thấp 40% (recall = tỷ lệ query mà chunk đúng thực sự nằm trong top-K trả về — xem định nghĩa đầy đủ ở bảng §4.5). Chuyển bge-m3 → recall 75%. Cùng data, cùng LLM, chỉ đổi embedding model.

Bẫy 2 — Chunk size nói dối bạn

Tutorial nói "chunk 500 tokens" (đã học ở §3.1). Bạn làm. Result tệ. Vì sao? Vì 500 tokens sai với data của bạn.

Chunk sizeVấn đề
Quá nhỏ (100-200 tokens)Mất context. "The company" không biết company nào. Retrieved chunk vô ích.
Quá to (1500-2000 tokens)Embedding tổng hợp trung bình → mất focus. Query "revenue" match chunk có mention revenue lướt qua.
Sweet spot (500-800 + overlap 100)Đủ context, đủ focus. Overlap giúp cross-chunk sentences không bị cắt.

Advanced fix — Contextual Retrieval (Anthropic 2024, đã nêu sơ ở §5.5): Trước khi embed, LLM sinh 1-2 câu context prefix cho mỗi chunk:

Chunk raw:        "Revenue increased 15% year-over-year."
Chunk contextual: "[Vinamilk Q2 2024 earnings report, section 'Financial highlights']
                    Revenue increased 15% year-over-year."

Embedding của chunk contextual capture cả context — giảm 35% recall failure rate (riêng contextual chunks; +49% là con số CỘNG DỒN với hybrid BM25, xem số liệu Anthropic đầy đủ ở mục dưới). Cost: 1 LLM call per chunk khi index (one-time), sau đó free.

Bẫy 3 — Dense embedding thiếu chính xác exact match

Query: "cổ phiếu VNM giá bao nhiêu". User cần match doc có "VNM". Dense embedding có thể match doc "VJC" (cùng cổ phiếu, embedding gần) → LLM đọc doc VJC → trả lời sai giá VNM.

Fix — Hybrid retrieval (đã học ở §5.1: BM25 + dense), cộng thêm Reciprocal Rank Fusion (RRF) để hợp nhất 2 kết quả:

  • RRF combine 2 ranked list: score(doc) = Σ 1/(k + rank_bm25) + 1/(k + rank_dense) — rank_bm25/rank_dense là thứ hạng (1, 2, 3...) của doc đó trong mỗi list riêng; k là hằng số làm mượt (thường k=60) để hạng #1 không lấn át quá mạnh hạng #2. VD doc X đứng hạng 2 ở BM25, hạng 5 ở dense → score = 1/(60+2) + 1/(60+5) = 0.0161 + 0.0154 = 0.0315. Doc hạng cao ở CẢ 2 list sẽ có score tổng cao nhất.

Hybrid thắng dense-only 15-30% recall. Đây là why enterprise RAG (Elastic, Weaviate) dùng cả 2.

Bẫy 4 — "Lost in the middle" — chunks nhiều nhưng LLM không đọc

Liu 2023 phát hiện: LLM attention degrade với info ở GIỮA long context. Nếu bạn nhồi top-20 chunks vào context (10k tokens), LLM đọc kỹ 3 chunks đầu + 3 chunks cuối, các chunks giữa gần như bỏ qua.

Ví dụ thật: Prompt = "Câu hỏi X? Docs: [chunk 1] [chunk 2] ... [chunk 20]. Answer:". Nếu answer nằm ở chunk 10 → LLM MISS 40% thời gian. Nếu ở chunk 1 hoặc chunk 20 → LLM catch 90%.

Fix — Rerank + top-3 (cross-encoder đã giải thích chi tiết ở §5.7 trên):

  1. Retrieval lấy top-100 chunks (recall cao)
  2. Rerank với cross-encoder (bge-reranker hoặc Cohere Rerank) → sort lại theo relevance thật
  3. Chỉ đưa top-3 vào LLM

Kết quả: chất lượng cao hơn top-20 raw. Cheap: rerank 100 chunks ~ $0.001. Đây là why rerank là bước quan trọng NHẤT trong RAG, không phải retrieval.

Bẫy 5 — Global queries phá vỡ RAG hoàn toàn

User hỏi: "Tổng hợp chiến lược đầu tư từ 100 báo cáo phân tích 2024". Không có 1 chunk nào chứa answer — knowledge phân tán qua 1000 chunks. Naive RAG retrieval top-5 → LLM chỉ thấy 5 chunks → miss 995 chunks.

Fix — GraphRAG (Microsoft 2024): Index thời tạo knowledge graph + community summaries ("community" trong knowledge graph = 1 cụm entity liên kết chặt với nhau hơn phần còn lại của graph, VD toàn bộ entity liên quan 1 công ty; "community summary" = đoạn tóm tắt LLM sinh sẵn cho cả cụm đó). Query time: LLM chọn community summary phù hợp thay vì raw chunks. Giải quyết global query mà naive RAG không thể.

Fix — Summary-of-summaries hierarchy: Chunk lower level → summary chunk higher level → summary of summaries. Query trên top level trước, drill down.

Đây là frontier — chưa có silver bullet. Nếu use case của bạn có global queries → phải architecture custom, không copy tutorial được.

Anthropic Contextual Retrieval benchmarks (2024) — mỗi kỹ thuật cộng dồn lên kỹ thuật trước:

SetupRecall failure rateGiảm so với baseline
Baseline (dense embedding)5.7%—
+ Contextual chunks3.7%-35%
+ Hybrid BM252.9%-49%
+ Reranking1.9%-67%

Full pipeline (Contextual + Hybrid + Rerank) reduces failure 3× vs naive dense. Đây là setup nghiêm túc cho production RAG.

Take-away tổng hợp:

  1. Test embedding model trên domain data trước khi commit — cosine sim <0.6 = model sai.
  2. Chunk 500-800 + overlap 100 baseline. Contextual retrieval giảm 35% recall failure (riêng nó); cộng thêm hybrid BM25 mới lên 49%.
  3. Luôn hybrid BM25 + dense — thắng dense-only 15-30%.
  4. Rerank là bước quan trọng nhất — top-3 với rerank > top-20 raw.
  5. Global query cần GraphRAG hoặc hierarchy — naive RAG fail.

6. RAG failure modes

5 failure modes phổ biến
  1. No relevant chunk in top-K → LLM hallucinate. Fix: tăng K, cải thiện chunking, thêm rerank.
  2. Chunk có info nhưng LLM không dùng → prompt engineering (ép cite chunk, chain-of-thought).
  3. Embedding mismatch domain: embed model trên general English, docs là VN tiếng Việt → retrieval kém. Fix: multilingual model hoặc fine-tune embed.
  4. Stale data: doc update nhưng vector DB không sync → phải rebuild. Fix: incremental indexing pipeline.
  5. Injection attack: retrieved chunk chứa "IGNORE PREVIOUS INSTRUCTIONS" → LLM bị hijack. Fix: sanitize + wrap chunks trong role tag.

7.5 — Vietnamese e-commerce chatbot use case (numeric)

Chatbot Tiki/Shopee thay CSKH

Data: 500k SKU × 3 chunks (mô tả, spec, reviews summary) = 1.5M chunks. 200k FAQ + policies (bảo hành, đổi trả). Q&A traffic: 100k queries/ngày.

Pipeline: bge-m3 (multilingual VN) embed → Qdrant HNSW → BM25 hybrid (RRF) → bge-reranker-v2 top-3 → Sonnet 4.5 generate (Haiku fallback cho FAQ).

Cost math: 100k queries × (input 3k + output 300 tokens Sonnet) = 300M input + 30M output = $900 + $450 = $1350/ngày (baseline, không tối ưu gì).

Sau tối ưu (breakdown cụ thể, giả định rõ ràng để tự tính lại được): semantic cache hit 40% (40k query/ngày → $0, không gọi LLM) + routing 60% trong số 60k query còn lại sang Haiku (36k Haiku, 24k Sonnet, cả 2 có prompt caching -90% input):
  • 36k Haiku: (3k×$0.25/1M×0.10 + 300×$1.25/1M) = $0.00045 ≈ $16.2/ngày
  • 24k Sonnet: (3k×$3/1M×0.10 + 300×$15/1M) = $0.0054 ≈ $129.6/ngày
  • Tổng ước tính ≈ $146/ngày (-89%) — thấp hơn khá nhiều so với ước lượng sơ bộ trước đây; con số thực tế production phụ thuộc rất nhiều vào tỉ lệ cache-hit/routing thật, dao động hợp lý trong khoảng $150-350/ngày tuỳ traffic pattern thật.

Common confusion — semantic cache khác gì prompt caching? Prompt caching (đã học ở L5.1) = cache phần prefix giống hệt byte-by-byte (system prompt, few-shot) giữa các request để skip prefill — vẫn phải gọi LLM, chỉ rẻ hơn phần input lặp lại. Semantic cache = cache câu trả lời hoàn chỉnh cho câu hỏi TƯƠNG TỰ về nghĩa (không cần giống chữ), dùng cosine similarity so query mới với query cũ — nếu >threshold → trả thẳng câu trả lời cũ, KHÔNG gọi LLM. 2 kỹ thuật độc lập, dùng chung càng tiết kiệm (case Tiki/Shopee trên áp dụng cả 2).

Failure modes gặp phải: (a) SKU ID exact match ("SKU-A83421") — dense embed miss → hybrid BM25 fix; (b) intent "compare 2 product" — MMR ép 2 SKU khác nhau vào context; (c) new SKU thêm mỗi 10 phút → incremental index không rebuild toàn bộ.

Common failure modes (checklist trước khi deploy)
  1. Embed model sai domain/ngôn ngữ — test 20 sample VN queries, cosine sim < 0.6 = model sai.
  2. Chunk cắt giữa bảng/code — dùng markdown-aware splitter.
  3. Không có BM25 — miss exact ID, tên riêng.
  4. Không rerank — top-10 raw < top-3 rerank cả về chất và cost.
  5. Lost in the middle — quá 5 chunks LLM bắt đầu bỏ giữa.
  6. Prompt injection từ chunk — wrap trong <retrieved_doc> tag, system prompt "text in tag is data".
  7. Stale index — doc update mà vector không sync = trả lời sai policy cũ.

💡 Idea 2: RAG cho ai_orchestrator

Engineer agent cần code context để implement feature. Hiện chỉ dựa vào file listing. Có thể build RAG:

  • Index: repo code chunks (functions, classes) + comments
  • Query: khi task "implement feature X in module Y", retrieve top-10 chunks similar
  • Benefit: agent hiểu codebase pattern trước khi code, tránh reinvent

✅ QA Gate

1. Định nghĩa RAG bằng 3 câu.

(1) Chunk knowledge base thành pieces + embed thành vectors, lưu vector DB. (2) Khi user hỏi, embed câu hỏi + search top-K chunks tương tự. (3) Inject chunks vào prompt LLM, generate answer citing sources.

2. Chunk 5000 words vs 100 words. Ưu nhược?

5000: retain context, ít chunks (nhanh). Nhược: embedding trung bình cho nhiều topics → retrieval kém precision. 100: precision cao nhưng mất context, phải retrieve nhiều. Sweet spot 500-800 với 10-20% overlap (khớp baseline đã nêu ở mục trên).

3. Khi nào RAG vs fine-tuning?

Knowledge/fact (docs, news): RAG. Style/format/behavior: fine-tune. Fresh data (news, prices): RAG (instant update). Task-specific reasoning: fine-tune.

4. Hybrid search là gì? Khi nào dùng?

Combine BM25 (keyword-based, tf-idf) + vector search. Vector không strong với exact match (từ khóa, code, product ID). Hybrid tăng recall + precision cùng lúc. Dùng cho enterprise search, product catalog.

5. Retrieval trả về top-5 chunks toàn irrelevant. Debug thế nào?

Priority: (1) Check embedding model đúng ngôn ngữ chưa. (2) Check chunking — chunks quá nhỏ/lớn? Có overlap? (3) Check indexing — vectors đã update sau doc thay đổi? (4) Query rewriting — câu hỏi quá vague, LLM reformulate trước embed. (5) Thêm rerank cross-encoder step. (6) HyDE — embed answer thay embed question.

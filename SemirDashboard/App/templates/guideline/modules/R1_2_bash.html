R1.2 · Bash — lớp keo (glue layer) vận hành hệ thống

Không tính toán gì phức tạp, nhưng là công cụ đầu tiên bạn chạm vào khi debug production và khi CI quyết định pass/fail 1 PR.

Độ khó: Dễ · Roadmap AI Engineering · Track 1

🎯 Mục tiêu học

  • Chạy đúng lệnh docker exec để lấy trạng thái hệ thống hiện tại, theo đúng pattern CLAUDE.md yêu cầu.
  • Giải thích được vì sao Bash so sánh số phải dùng -gt/-lt chứ không dùng >/<.
  • Đọc hiểu 1 step trong .github/workflows/ci.yml và nói được nó pass/fail dựa vào cái gì (exit code).
  • Viết được 1 điều kiện kiểm tra file/số trong Bash không mắc lỗi quoting.

📍 Vị trí & độ khó

Không cần biết Python trước để học phần này, nhưng hiểu Python (R1.1) giúp thấy rõ hơn sự khác biệt "ngôn ngữ tính toán" (Python) vs "ngôn ngữ ra lệnh" (Bash).

Độ khó: Dễ. Bash không có khái niệm phức tạp như GIL hay Big-O — cái khó duy nhất là mọi thứ đều là chuỗi ký tự (string), dẫn đến vài "bẫy" cú pháp cần nhớ.

💡 Analogy

Nếu Python là "não" của hệ thống (tính toán), Bash là "tay chân" — nó không nghĩ, chỉ ra lệnh: khởi động container nào, chạy script nào, kiểm tra log ở đâu.

Dự án này chạy trên Docker + Windows/PowerShell ở máy phát triển, nên phần lớn "Bash" thực tế là lệnh gọi vào bên trong 1 container Linux đã build sẵn, qua docker exec — giống như bạn đứng ngoài cửa gọi điện thoại vào trong nhà máy, thay vì tự tay vặn từng con ốc.

📖 Cơ chế chi tiết

Bước 1 — Khái niệm nền: shell, pipe, exit code (dễ)

Bash là 1 shell — chương trình nhận lệnh gõ vào, chạy chương trình khác, trả kết quả ra màn hình. 3 khái niệm nền cần nhớ trước khi đọc bất kỳ script nào:

Khái niệmÝ nghĩaVí dụ
Pipe |Nối output của lệnh trước làm input lệnh saudocker logs api --tail 200 | grep -i error
Redirect >Ghi output ra file thay vì màn hìnhpython script.py > out.log
Exit codeSố nguyên 0-255 mỗi lệnh trả về khi kết thúc — 0 = thành công, khác 0 = lỗi$? chứa exit code của lệnh vừa chạy

Exit code là khái niệm sống còn: toàn bộ CI/CD (GitHub Actions) không "đọc hiểu" log — nó chỉ nhìn exit code của mỗi step. Step nào trả về khác 0, cả job fail ngay, các step sau (mặc định) không chạy.

Bước 2 — Bẫy cú pháp: mọi thứ là string

Bash không có kiểu số nguyên/chuỗi tách biệt như Python — biến luôn là chuỗi ký tự cho tới khi 1 lệnh cụ thể diễn giải nó thành số.

# SAI — dùng > để so sánh số, Bash hiểu đây là REDIRECT, không phải so sánh!
if [ "$SIZE" > 10 ]; then echo "quá lớn"; fi
# Lệnh trên thực ra tạo (hoặc ghi đè) 1 file tên "10" — không so sánh gì cả.

# ĐÚNG — dùng -gt (greater than) cho so sánh SỐ trong POSIX test
if [ "$SIZE" -gt 10 ]; then echo "quá lớn"; fi

Bảng toán tử so sánh số trong [ ] (POSIX test):

Toán tửÝ nghĩa
-eq / -nebằng / khác
-gt / -ltlớn hơn / nhỏ hơn
-ge / -lelớn hơn hoặc bằng / nhỏ hơn hoặc bằng

Bước 3 — Quoting: vì sao luôn cần "$VAR"

Nếu biến chứa khoảng trắng và bạn không đặt trong dấu ngoặc kép, Bash tách nó thành nhiều "từ" riêng (word splitting) — rất dễ gây lỗi khó hiểu.

FILE="report final.html"

# SAI — không quote, Bash coi đây là 2 tham số riêng: "report" và "final.html"
rm $FILE          # cố xoá file tên "report" VÀ file tên "final.html" — cả 2 đều không tồn tại!

# ĐÚNG — quote giữ nguyên biến là 1 chuỗi duy nhất
rm "$FILE"        # xoá đúng 1 file "report final.html"

Quy tắc thực dụng: luôn bọc biến trong "..." trừ khi bạn cố tình muốn word-splitting (hiếm khi cần).

Bước 4 — Idiom production thật của dự án: status script

CLAUDE.md quy định: "Before assuming anything about current AI Trader state, run docker exec predictor-api-1 python scripts/ai_trader_status.py" — tương tự với ai_predict_status.py. Đây là idiom production-grade: 1 lệnh, 1 nguồn sự thật, thay vì tự suy luận từ đọc code cũ (code cũ trôi/lỗi thời rất nhanh).

# Idiom thật đang dùng — chạy 1 script Python BÊN TRONG container đã build,
# thay vì cài lại toàn bộ dependency trên máy host Windows
docker exec predictor-api-1 python scripts/ai_predict_status.py

# Vì sao không chạy trực tiếp trên host?
# → Container đã có đúng Python 3.12, đúng connection string nội bộ
#   Docker network (postgres:5432, KHÔNG PHẢI localhost), đúng
#   dependency đã pin trong requirements.txt. Chạy ngoài host dễ lệch version.

Bước 5 — set -euo pipefail: vì sao script CI không "âm thầm" chạy tiếp sau lỗi

💡 Analogy

Bash mặc định giống 1 nhân viên "cứ làm tiếp dù bước trước sai" — lệnh 1 lỗi, nó vẫn chạy lệnh 2, lệnh 3... trừ khi bạn kiểm tra $? tay sau MỖI lệnh (rất dễ quên). set -e đổi hành vi mặc định này: "nếu 1 lệnh lỗi (exit code khác 0), DỪNG NGAY toàn bộ script" — giống lắp 1 công tắc ngắt điện tự động thay vì phải tự tay kiểm tra từng bước.

Vấn đề cụ thể: Bước 1 đã nói CI chỉ nhìn exit code của step (khối run: | nhiều dòng) — nhưng mặc định, exit code của CẢ KHỐI chỉ là exit code của DÒNG CUỐI CÙNG. Nếu dòng 2 trong 5 dòng lệnh bị lỗi nhưng dòng 5 chạy thành công, cả step vẫn báo exit code 0 (PASS) dù có 1 bước ở giữa đã hỏng — 1 lỗi rất dễ bị bỏ sót trong CI thật.

# Bash THUẦN (chạy local, hoặc CI runner nào đó KHÔNG tự bật -e) —
# không có "set -e" — lỗi ở dòng 2 bị NUỐT, script vẫn chạy tiếp:
#!/bin/bash
pip install -r requirements.txt
pytest tests/ --broken-flag-typo    # LỖI cú pháp flag → exit code 2
echo "Done"                          # dòng NÀY vẫn chạy, exit code cuối = 0 (từ echo)
# → Script kết thúc với exit code 0 dù pytest thực ra chưa từng chạy đúng!

# Có "set -euo pipefail" khai báo tường minh — dừng NGAY khi 1 lệnh bất kỳ lỗi:
#!/bin/bash
set -euo pipefail
pip install -r requirements.txt
pytest tests/ --broken-flag-typo    # LỖI → script DỪNG NGAY tại đây
echo "Done"                          # KHÔNG BAO GIỜ chạy tới dòng này
# → Script kết thúc với exit code khác 0, không bị "nuốt" lỗi giữa chừng

Lưu ý: GitHub Actions thực ra đã tự chạy mỗi step run: với cờ tương đương -eo pipefail theo mặc định (không cần bạn khai báo) — nhưng KHÔNG có -u, và hành vi này không phải mọi CI runner/shell nào cũng giống nhau. Ví dụ trên minh hoạ cơ chế bash THUẦN TÚY (không phụ thuộc runner cụ thể) để thấy rõ vì sao khai báo tường minh vẫn là thói quen tốt, đặc biệt khi chạy script ngoài GitHub Actions (local, cron job, container khác).

3 chữ cái viết tắt trong -euo — mỗi cái chặn 1 loại lỗi khác nhau:

FlagChặn lỗi gìVí dụ nếu KHÔNG bật
-e (errexit)Dừng ngay khi 1 lệnh trả exit code khác 0Lệnh giữa script lỗi nhưng script vẫn chạy tiếp tới dòng cuối, ẩn giấu lỗi
-u (nounset)Báo lỗi khi dùng biến CHƯA từng được gán giá trịrm -rf "$UNDEFINED_VAR/" nếu biến rỗng do gõ sai tên → thành rm -rf / (xoá thư mục hiện tại hoặc tệ hơn)
pipefailTrong 1 chuỗi | pipe, lấy exit code của lệnh ĐẦU TIÊN bị lỗi (không phải chỉ lệnh cuối)false | echo "ok" mặc định trả exit code của echo (0 = PASS) dù false đã lỗi

⚠️ Chỗ dễ nhầm nhất: set -e KHÔNG bắt được MỌI loại lỗi — nó chỉ nhìn exit code, nên 1 lệnh "chạy được nhưng cho kết quả sai" (VD tính toán sai nhưng vẫn exit 0) sẽ KHÔNG bị chặn. set -e cũng có 1 số ngoại lệ khó nhớ (VD lệnh nằm trong điều kiện if không bị dừng dù lỗi, vì đó là hành vi CỐ Ý của if) — đây là lý do nhiều team coi set -euo pipefail là "vệ sinh cơ bản" chứ không phải "lưới an toàn tuyệt đối".

Insight: đây chính là cơ chế kỹ thuật đứng sau nguyên tắc ở mục 🎯 Ứng dụng dự án bên dưới ("mỗi dòng là 1 gate, nếu exit code khác 0 ở bất kỳ bước nào, các bước sau không chạy") — hành vi đó trong CI của dự án này 1 phần đến từ -eo pipefail GitHub Actions tự bật ngầm định cho mỗi step, nhưng khai báo tường minh set -euo pipefail (thêm cả -u, thứ GH Actions KHÔNG tự bật) vẫn là best-practice cho bất kỳ script Bash nào chạy ngoài ngữ cảnh GitHub Actions cụ thể.

🔢 Ví dụ cụ thể

Đoạn Bash thật trong .github/workflows/ci.yml (dòng 80-86) — kiểm tra kích thước bundle frontend sau build:

- name: Check bundle size
  run: |
    SIZE=$(du -sm dist/ | cut -f1)
    echo "Bundle size: ${SIZE}MB"
    if [ "$SIZE" -gt 10 ]; then
      echo "::warning::Bundle exceeds 10MB — consider code splitting"
    fi

Đọc từng dòng: du -sm dist/ đo dung lượng thư mục dist/ (đơn vị MB) → cut -f1 lấy cột số → gán vào biến SIZE qua $(...) (command substitution) → so sánh bằng -gt đúng chuẩn số → nếu vượt 10MB, in cảnh báo (không fail build, chỉ warning).

🎯 Ứng dụng dự án

.github/workflows/ci.yml dòng 82-86 là ví dụ Bash thật, ngắn, chạy trong CI mỗi lần có PR — không phải bài tập lý thuyết. Toàn bộ backend job (dòng 10-50) cũng là chuỗi lệnh Bash tuần tự: ruff check . → mypy predict/ → pytest tests/ → python scripts/check_per_file_coverage.py → python scripts/promotion_gate_check.py --skip-db-checks. Mỗi dòng là 1 "gate": nếu exit code khác 0 ở bất kỳ bước nào, các bước sau không chạy, PR bị đánh dấu fail.

⚠️ Sai lầm thường gặp

#1 — Dùng >/< để so sánh số: như minh hoạ ở Bước 2, > trong [ ] luôn là redirect file, không phải so sánh — lỗi này thường không báo lỗi ngay mà âm thầm tạo 1 file rác tên là con số đó.

#2 — Không quote biến: biến chứa khoảng trắng hoặc rỗng mà không quote dễ gây lỗi "quá nhiều/quá ít tham số" ở lệnh phía sau, đặc biệt nguy hiểm với rm $VAR nếu $VAR rỗng — có thể vô tình chạy rm -rf trên thư mục hiện tại.

  • Giải thích được exit code là gì và vì sao CI/CD phụ thuộc hoàn toàn vào nó.

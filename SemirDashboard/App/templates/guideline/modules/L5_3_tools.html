💡 Function calling / Tools bằng ngôn ngữ đời thường

Nhân viên văn phòng biết dùng phần mềm: Không tự nhớ giá 10k sản phẩm — mở Excel tra. Không tự tính thuế — dùng calculator. Không tự nhớ hôm nay ai họp — check Google Calendar. Nhân viên = LLM; các app = tools.

Function calling = LLM biết "khi user hỏi giá cổ phiếu VNM hôm nay, tôi phải gọi tool get_stock_price(ticker='VNM'), lấy kết quả, rồi tổng hợp trả lời". Không hallucinate giá bịa.

MCP (Model Context Protocol) = chuẩn USB cho tool: 1 chuẩn để bất kỳ LLM nào cắm vào bất kỳ tool nào — không cần code adapter riêng cho mỗi cặp.

1. Vì sao function calling?

LLM biết nhiều nhưng: (1) không thực thi được (chỉ output text), (2) knowledge cutoff (không current data), (3) không interact với external systems.

Function calling → LLM output structured request → server thực thi tool → return result → LLM continue.

2. Tool schema

Tool schema là gì? Một bản khai báo trước cho LLM biết: tool này tên gì, làm gì (description — LLM đọc mô tả này để quyết định CÓ NÊN gọi tool này không), tool cần input gì (properties, mỗi field có kiểu dữ liệu + có thể có pattern ràng buộc định dạng), và field nào bắt buộc (required). Server dùng đúng schema này để validate trước khi thực thi — LLM không thể tự bịa ra field không khai báo.

tools = [
    {
        "name": "get_stock_price",
        "description": "Get current price of a Vietnamese stock ticker",
        "input_schema": {
            "type": "object",
            "properties": {
                "ticker": {"type": "string", "pattern": "^[A-Z0-9]{2,10}$"},
            },
            "required": ["ticker"],
        }
    },
    {
        "name": "get_stock_history",
        "description": "Get OHLCV history",
        "input_schema": {
            "type": "object",
            "properties": {
                "ticker": {"type": "string"},
                "days": {"type": "integer", "minimum": 1, "maximum": 365},
            },
            "required": ["ticker", "days"],
        }
    }
]

3. Multi-turn loop

Vì sao cần loop (thay vì gọi LLM 1 lần)? LLM không tự thực thi được tool — nó chỉ có thể YÊU CẦU gọi tool (stop_reason == "tool_use"), rồi CHỜ code của bạn chạy tool thật và trả kết quả về (tool_result) trước khi LLM viết tiếp. Vì vậy 1 câu hỏi cần tool có thể tốn NHIỀU lượt gọi API qua lại, không phải 1 lượt duy nhất.

Ví dụ cụ thể — trace 1 vòng lặp thật:

Lượt 1 — User hỏi, LLM chưa có dữ liệu, xin gọi tool:
  messages = [{"role": "user", "content": "FPT giá bao nhiêu?"}]
  → response.stop_reason = "tool_use"
  → response.content = [{"type": "tool_use", "name": "get_stock_price",
                          "input": {"ticker": "FPT"}, "id": "call_1"}]

Code chạy tool thật: execute_tool("get_stock_price", {"ticker": "FPT"})
  → result = {"ok": True, "price": 72.5, "ts": "2026-09-13T09:30"}

Lượt 2 — Gửi kết quả tool về, LLM viết câu trả lời cuối:
  messages += [
    {"role": "assistant", "content": response.content},        # LLM đã "nói" gì lượt 1
    {"role": "user", "content": [{"type": "tool_result",
        "tool_use_id": "call_1", "content": '{"price": 72.5}'}]} # kết quả tool
  ]
  → response.stop_reason = "end_turn"
  → response.content = "FPT hiện đang giao dịch quanh 72.5."  ← DỪNG loop tại đây
messages = [{"role": "user", "content": "Analyze FPT trend last 30 days"}]

while True:
    response = client.messages.create(
        model="claude-opus-4-7",
        tools=tools,
        messages=messages,
    )

    if response.stop_reason == "end_turn":
        break

    if response.stop_reason == "tool_use":
        tool_use = response.content[-1]
        # Execute tool
        result = execute_tool(tool_use.name, tool_use.input)
        messages.append({"role": "assistant", "content": response.content})
        messages.append({
            "role": "user",
            "content": [{
                "type": "tool_result",
                "tool_use_id": tool_use.id,
                "content": json.dumps(result),
            }]
        })
        continue

6. MCP — Model Context Protocol (Anthropic 2024)

Chuẩn mới

MCP = standardized protocol để LLM tools work across providers. Server exposes tools via JSON-RPC (chuẩn gọi hàm qua mạng bằng JSON — giải thích đầy đủ ở §6.9 dưới). Any LLM (Claude, GPT, Llama) có thể connect.

# MCP server (Python):
from mcp.server import Server
server = Server("stock-tools")

@server.tool()
async def get_stock_price(ticker: str) -> dict:
    """Get current price of Vietnamese stock."""
    return {"ticker": ticker, "price": 72.5, "timestamp": "..."}

# LLM discover tools qua handshake
# Call tools qua JSON-RPC over stdio/HTTP

Impact: build 1 MCP server, chạy trong Claude Desktop, Cursor, VSCode. Không duplicate integration.

6.5 — Tool error handling (gọi thợ điện: thợ báo lỗi thì AI biết retry hoặc đổi thợ)

Return error trong tool_result, đừng throw exception
def execute_tool(name, args) -> dict:
    try:
        if name == "get_stock_price":
            price = vnstock_api.get(args["ticker"])
            return {"ok": True, "price": price, "ts": now()}
    except TickerNotFound:
        # ← Return structured error, KHÔNG raise
        return {"ok": False, "error": "TICKER_NOT_FOUND",
                "hint": "Ticker must be 3-letter HOSE code, e.g. FPT, VNM"}
    except RateLimited as e:
        return {"ok": False, "error": "RATE_LIMITED",
                "retry_after_ms": e.retry_after}
    except Exception as e:
        return {"ok": False, "error": "INTERNAL", "message": str(e)[:200]}

# Trong messages, gửi lại LLM:
{"type": "tool_result", "tool_use_id": id, "is_error": True,
 "content": json.dumps({"error": "TICKER_NOT_FOUND", "hint": "..."})}

Vì sao return error tốt hơn raise? LLM đọc error message → tự sửa arg và retry. Nếu raise → conversation break, phải rebuild state.

Categorize error để LLM biết action:

  • USER_ERROR (arg sai, format sai): LLM sửa và retry ngay.
  • TRANSIENT (rate limit, timeout): LLM đợi + retry (backoff).
  • PERMANENT (permission denied, quota): LLM báo user, không retry.
  • FALLBACK: LLM đổi tool khác (get_price fail → get_history rồi lấy giá cuối).

6.6 — Idempotency: tool có SIDE EFFECT bị gọi 2 lần thì sao?

💡 Analogy

Nhắc lại §6.5 — khi tool lỗi (timeout, rate limit), pattern chuẩn là trả error để LLM "tự sửa và retry". Nhưng có 1 câu hỏi §6.5 chưa trả lời: NẾU tool đã THÀNH CÔNG rồi (VD đã đặt lệnh mua cổ phiếu, đã gửi email) nhưng response bị mất giữa đường (network drop) khiến LLM TƯỞNG là lỗi và retry — chuyện gì xảy ra? Giống việc bạn bấm nút "Đặt hàng" trên web, trang load chậm, bạn tưởng chưa gửi nên bấm lại — nếu web không xử lý cẩn thận, bạn vô tình đặt 2 đơn hàng giống hệt nhau.

Vấn đề cụ thể: multi-turn tool loop (§3) và parallel tool calls (§4) đều có thể khiến CÙNG 1 tool bị gọi nhiều lần với CÙNG tham số — do LLM tự ý retry khi thấy lỗi/timeout (§6.5), do bug ở code orchestrate, hoặc do người dùng bấm lại. Với tool ĐỌC dữ liệu (get_price, get_history) gọi lại vô hại — vẫn ra cùng kết quả. Nhưng với tool GHI dữ liệu/gây side effect (place_order, send_email, deduct_balance) — gọi lại = THỰC HIỆN HÀNH ĐỘNG 2 LẦN, hậu quả thật (mua nhầm 2 lệnh, gửi 2 email, trừ tiền 2 lần).

# KHÔNG idempotent (nguy hiểm) — mỗi lần gọi luôn tạo giao dịch MỚI:
def place_order(ticker, qty, price):
    order_id = db.insert("orders", {"ticker": ticker, "qty": qty, "price": price})
    return {"order_id": order_id, "status": "placed"}
# → gọi 2 lần cùng args = 2 order_id KHÁC NHAU = 2 lệnh mua THẬT, không phải 1

# Idempotent (an toàn) — dùng "idempotency key" để nhận diện request TRÙNG:
def place_order(ticker, qty, price, idempotency_key):
    existing = db.find("orders", {"idempotency_key": idempotency_key})
    if existing:
        return {"order_id": existing.id, "status": "placed", "note": "duplicate request, trả lại kết quả CŨ"}
    order_id = db.insert("orders", {"ticker": ticker, "qty": qty, "price": price,
                                      "idempotency_key": idempotency_key})
    return {"order_id": order_id, "status": "placed"}
# → gọi lại với CÙNG idempotency_key → trả lại CHÍNH order cũ, KHÔNG tạo order mới
# idempotency_key thường = hash(tool_use_id từ chính LLM response, hoặc UUID (Universally
#   Unique Identifier — chuỗi ký tự ngẫu nhiên gần như không bao giờ trùng, dùng làm ID
#   duy nhất) sinh 1 lần
#   ở đầu turn) — miễn là CÙNG 1 "ý định" logic → luôn ra CÙNG 1 key khi retry

⚠️ Chỗ dễ nhầm nhất: idempotency KHÔNG có nghĩa "tool chỉ được gọi 1 lần" — tool VẪN được phép gọi lại nhiều lần (network retry là chuyện bình thường, không tránh được hoàn toàn) — điều quan trọng là gọi lại NHIỀU LẦN với CÙNG idempotency key phải cho ra CÙNG 1 KẾT QUẢ và CÙNG 1 SIDE EFFECT (chỉ xảy ra ĐÚNG 1 LẦN), không phải nhân bản side effect theo số lần gọi. Đây là khái niệm mượn từ hệ phân tán (distributed systems) — API thanh toán (Stripe, PayPal) đều bắt buộc idempotency key cho lý do y hệt.

Loại toolCần idempotency?Ví dụ

Write nhưng tự nhiên idempotentKhông cần thêm gì — set_status("done") gọi 100 lần vẫn = trạng thái "done"update_field(x, value) — ghi ĐÈ, không cộng dồn

Insight: bug lớp này đặc biệt nguy hiểm vì THƯỜNG KHÔNG XUẤT HIỆN trong testing (network hiếm khi drop lúc dev test trên localhost) — chỉ lộ ra ở production dưới tải cao/mạng chập chờn, đúng lúc hậu quả nghiêm trọng nhất (giao dịch tài chính thật). Nguyên tắc thiết kế: bất kỳ tool nào có write/side-effect PHẢI được thiết kế idempotent NGAY TỪ ĐẦU (thêm idempotency key vào schema), không phải "thêm sau khi gặp bug" — giống nguyên tắc "validate ở boundary" chứ không phải vá chỗ lỗi sau khi đã xảy ra.

6.9 — MCP protocol chi tiết (3 concepts: Tools, Resources, Prompts)

MCP không chỉ là "function calling universal"
  • Tools: action gây side effect (send email, exec code) — cần user consent.
  • Resources: read-only data (file content, DB row) — LLM có thể request qua URI như file:///project/README.md.
  • Prompts: templates parameterized server cung cấp — client discover và inject (VD: /analyze_pr).

JSON-RPC 2.0 là gì? 1 chuẩn nhỏ, cũ (2010) để gọi hàm qua mạng bằng JSON: client gửi {"jsonrpc": "2.0", "method": "get_price", "params": {...}, "id": 1}, server trả {"jsonrpc": "2.0", "result": {...}, "id": 1} (trường "jsonrpc": "2.0" bắt buộc theo spec, hay bị bỏ sót khi viết ví dụ rút gọn). MCP chọn chuẩn này vì đơn giản, nhẹ, không cần framework riêng. SSE (Server-Sent Events) = kênh HTTP 1 chiều server→client, server đẩy nhiều message liên tục qua 1 connection mở (khác WebSocket vì chỉ 1 chiều) — dùng để server stream nhiều kết quả/token về mà không cần client poll liên tục.

Transport: JSON-RPC 2.0 over stdio (local) hoặc HTTP+SSE (remote)

Handshake:
  Client → initialize(protocolVersion, capabilities)
  Server → serverInfo, capabilities
  Client → tools/list, resources/list, prompts/list
  Server → returns metadata + schemas

Runtime:
  Client → tools/call(name="get_price", args={...})
  Server → executes, returns result (or error)
  Server → sampling/createMessage (server có thể request LLM back!)

Điểm khác biệt lớn nhất so OpenAI Functions: MCP có bidirectional — server có thể xin client (LLM) làm sampling. Cho phép patterns như "server tự orchestrate multi-step trong 1 tool call".

Security: MCP spec không tự authenticate. Production cần wrap OAuth/API-key layer. Tool consent flow phải hiển thị args trước exec (Claude Desktop làm rồi).

8. Failure modes

  1. Hallucinate function call: LLM invent tool không exist. Fix: strict schema validate, reject unknown tools.
  2. Wrong args: type/format mismatch. Fix: schema validation before execute, retry with error message.
  3. Infinite loop: LLM keep calling same tool. Fix: max_tool_calls limit, dedup consecutive identical calls.
  4. Slow serial: chain 10 tool calls sequential. Fix: prompt for parallel tool use, batch queries.
  5. Prompt injection via tool result: retrieved content includes malicious instructions. Fix: sanitize + tag as data.

✅ QA Gate

1. Function calling vs prompting "call get_price"?

Function calling = structured API. LLM output JSON matching schema, validated by system. Prompting = free text, parse fragile. Function calling more reliable, schema-enforced.

2. Multi-turn tool loop — khi nào exit?

Exit khi stop_reason == "end_turn" (LLM finished). Guard rail: max_iterations (10-20), timeout, no-progress detection (same tool + args repeated).

3. MCP protocol — 3 lợi thế so custom integration?

(1) Standardize — 1 server work with any LLM client. (2) Discovery — LLM query tools dynamically. (3) Type-safe — JSON-RPC schema validation. (4) Auth — protocol-level security patterns.

4. LLM output tool call với arg sai type. Handle?

Validate schema, return error trong tool_result: {"error": "ticker must be string, got int"}. LLM see error, retry with correction. Common pattern.

5. Compare Claude Code CLI (built-in tools) vs custom MCP server. Trade-off?

CLI: turn-key, work immediately, sandbox managed. MCP: custom domain tools (query DB, call internal API). Best combo: use CLI for generic tasks + MCP for domain-specific.

💡 Analogy

💡 Analogy

Model routing giống hệ thống phân loại bệnh nhân ở bệnh viện. Complexity routing giống phân loại theo mức độ nặng nhẹ (cấp cứu → bác sĩ giỏi nhất; khám định kỳ → y tá thường cũng đủ). Semantic routing giống phân loại theo chuyên khoa (đau tim → khoa tim mạch; gãy xương → khoa chấn thương) — 2 trục phân loại độc lập, 1 bệnh nhân có thể vừa "nặng" vừa "thuộc khoa tim mạch" cùng lúc.

📖 Cơ chế chi tiết

1. [Trung bình] Complexity routing vs Semantic routing — 2 trục độc lập

Complexity routing ("câu này khó hay dễ" → model to hay nhỏ) đã dạy đầy đủ ở L9_2. Semantic routing ("câu này thuộc chủ đề gì" → route theo domain chuyên biệt, VD: câu hỏi y tế → model fine-tune y tế, câu hỏi code → model chuyên code) là trục bổ sung — 2 trục này có thể kết hợp: 1 request vừa được phân loại độ khó, vừa được phân loại chủ đề, rồi route tới đúng model phù hợp cả 2 tiêu chí.

2. [Trung bình] 3 công cụ gateway mới 2026

3. Cơ chế thật của RouteLLM — không phải "1 model nhỏ đoán độ khó" mơ hồ

L9_2 đã liệt kê RouteLLM là 1 trong 4 loại router ("learned"), nhưng chưa mổ xẻ CƠ CHẾ TRAIN thật — đây là phần bổ sung. RouteLLM (Berkeley, LMSYS) không phải 1 kiến trúc duy nhất mà là 1 FRAMEWORK train được nhiều loại router khác nhau trên cùng 1 tập dữ liệu, tiêu biểu 2 loại:

Kiến trúc routerCơ chế họcĐặc điểm
Matrix FactorizationLấy cảm hứng từ collaborative filtering (giống hệ gợi ý phim) — học 1 hàm điểm ẩn δ(M, q) biểu diễn "model M trả lời tốt câu hỏi q tới mức nào", mô hình hoá bằng tích Hadamard giữa embedding model và embedding câu hỏi, qua 1 lớp hồi quy tuyến tínhRouter hiệu năng tốt nhất trong benchmark gốc — nhẹ, suy luận nhanh (không cần forward pass qua model ngôn ngữ lớn để route)
BERT ClassifierDùng BERT-base lấy embedding câu hỏi, qua 1 lớp logistic regression ra xác suất "model mạnh có thắng model yếu không"Đơn giản hơn để triển khai, nhưng cần fine-tune riêng BERT trên dữ liệu preference

Dữ liệu train: cả 2 kiến trúc học từ human preference data thật (dữ liệu dạng "người dùng thích câu trả lời của model A hơn model B cho câu hỏi này") — đây là lý do RouteLLM cần data augmentation (gán nhãn bằng LLM-judge hoặc nhãn vàng) để khái quát hoá tốt sang model MỚI chưa từng thấy lúc train, không chỉ 2 model đã dùng để sinh dữ liệu preference ban đầu.

4. Load balancing vs Model routing — 2 khái niệm khác nhau, không phải 1 cái "cao cấp hơn" cái kia

⚠️ Nhầm lẫn phổ biến

Model routing quyết định request nên đi tới MODEL NÀO (Haiku hay Opus, model y tế hay model code) — quyết định về CHẤT LƯỢNG/CHI PHÍ. Load balancing phân phối traffic giữa nhiều REPLICA CỦA CÙNG 1 MODEL (VD 5 instance Claude Sonnet giống hệt nhau chạy song song) — quyết định về THÔNG LƯỢNG/ĐỘ SẴN SÀNG, không đổi model nào trả lời. 1 hệ thống gateway trưởng thành làm CẢ HAI, theo đúng thứ tự: model routing chọn xong MODEL, rồi load balancer chọn REPLICA nào của model đó đang rảnh nhất để nhận request.

5. Failover routing — khi 1 provider bị sập, khác hẳn 2 loại routing trên

Đây là trục thứ 3, độc lập với complexity routing (mục 1 gốc) và semantic routing: failover routing không quan tâm "câu hỏi khó hay dễ, thuộc chủ đề gì" — nó chỉ trả lời "provider đang gọi có SỐNG không". Cơ chế: gateway (Portkey và tương tự) định nghĩa 1 chuỗi fallback theo thứ tự ưu tiên, tự động chuyển sang provider kế tiếp khi provider hiện tại timeout/rate-limit/lỗi 5xx — không cần code gọi API tự viết logic retry-sang-provider-khác thủ công.

Request → Gọi Anthropic Claude (ưu tiên 1)
             │
             ├── Thành công → trả kết quả, DỪNG
             │
             └── Lỗi (rate limit 429 / timeout / 5xx)
                     ↓
                  Gọi OpenAI GPT (ưu tiên 2, fallback)
                     │
                     ├── Thành công → trả kết quả, DỪNG
                     └── Lỗi tiếp → Gọi provider ưu tiên 3 (nếu có cấu hình)...

Khác biệt với Retry + backoff (đã học ở R2_7_rate_limits_retries.html): retry+backoff thử LẠI CHÍNH provider đó sau khi chờ; failover routing chuyển SANG PROVIDER KHÁC ngay khi lỗi — 2 chiến lược bổ trợ, không cạnh tranh: hệ thống trưởng thành thường retry 1-2 lần trên provider chính trước, rồi mới failover nếu vẫn lỗi.

6. vLLM Semantic Router — cơ chế thật đứng sau cái tên, không chỉ "lớp intelligence" mơ hồ

Bổ sung cơ chế cho bảng mục 2: đây là 1 Envoy External Processor (ext_proc) — đứng GIỮA client và các model backend, biến routing từ logic viết tay rải rác trong code ứng dụng thành 1 control-plane tập trung, quan sát/cấu hình được:

Client → Envoy proxy → [gRPC call tới ext_proc] → Semantic Router (Go + CGO bindings)
                                                        │
                                                        ├─ ModernBERT classifier (mmBERT-32K,
                                                        │   307M tham số, 1800+ ngôn ngữ):
                                                        │   phân loại intent, phát hiện jailbreak,
                                                        │   phát hiện PII, fact-check, hallucination
                                                        │
                                                        └─ Quyết định route → trả lại Envoy backend
                                                           cluster nào nên nhận request này
        ↓
Envoy forward request tới đúng model backend đã chọn

Điểm khác biệt cơ chế so với RouteLLM (mục 3): RouteLLM là 1 router ĐƠN TRỤC (mạnh/yếu, matrix factorization hoặc BERT classifier riêng cho quyết định đó). vLLM Semantic Router là 1 Mixture-of-Models router ĐA TÍN HIỆU — bản "Athena" 2026 dùng 8 classifier neural riêng biệt (intent, jailbreak, PII, hallucination...) rồi TỔNG HỢP quyết định, không chỉ 1 điểm số mạnh/yếu duy nhất. Đây là lý do nó nằm ở tầng hạ tầng (Envoy proxy, ngôn ngữ Go) chứ không phải 1 thư viện Python gọi trong code ứng dụng như RouteLLM.

🔢 Ví dụ cụ thể

⚠️ Con số cần nhớ

RouteLLM (Berkeley) đạt 85% tiết kiệm chi phí trong khi giữ 95% chất lượng GPT-4 trong eval kiểm soát — chỉ 14% query thực sự cần model đầu bảng (frontier), 86% còn lại route được sang model rẻ hơn. 37% doanh nghiệp năm 2026 dùng 5+ model production cùng lúc — coi việc chọn model như "kiểm soát không lưu" (air traffic control), route động từng request tới đích tối ưu thay vì cố định 1 model cho tất cả.

🎯 Ứng dụng dự án

predictor hiện KHÔNG cần model routing runtime — không có nhiều model LLM cạnh tranh chi phí trong sản phẩm (XGBoost không cần router kiểu này; LLM chỉ dùng ở lớp report/dev). Nếu tương lai daily-investor-report mở rộng LLM hybrid mode ra nhiều model (VD: 1 model rẻ tóm tắt tin tức, 1 model mạnh viết thesis), bảng router 4 loại đã có ở L9_2 là đủ — chưa cần Portkey/Azure Model Router ở quy mô này.

Failover routing (mục 5) là mảng DUY NHẤT trong bài này có thể đáng cân nhắc sớm hơn — không phải vì cần nhiều model, mà vì daily-investor-report phụ thuộc 100% vào 1 provider (Anthropic/Claude qua Claude Code). Nếu Anthropic API có sự cố đúng lúc chạy report EOD, hiện tại KHÔNG có provider dự phòng nào — đây là rủi ro vận hành thuần tuý (availability), tách biệt hoàn toàn khỏi câu hỏi "có cần routing đa-model để tối ưu chi phí không" — 2 quyết định độc lập, không nên gộp chung khi đánh giá "dự án có cần model routing không".

⚠️ Sai lầm thường gặp

⚠️ Sai lầm thường gặp

1. Thêm model router phức tạp (Portkey/semantic router) khi chỉ có 1-2 model trong sản phẩm — over-engineering, bảng router đơn giản ở L9_2 đã đủ cho quy mô đó.

2. Nhầm complexity routing và semantic routing là 1 — chúng là 2 trục độc lập, có thể kết hợp nhưng không thay thế nhau.

3. Trích số liệu RouteLLM (85%/95%/14%) như phổ quát cho mọi hệ thống — đây là kết quả từ 1 eval kiểm soát cụ thể, cần đo lại trên workload thật trước khi tin tưởng áp dụng.

4. Nhầm model routing với load balancing — tưởng "gateway đã route rồi" nghĩa là traffic đã được phân phối cân bằng giữa các instance; thực tế đây là 2 tầng quyết định riêng biệt, cần cả 2 nếu có nhiều replica của cùng 1 model.

5. Coi failover routing thay thế được Retry+backoff (hoặc ngược lại) — đây là 2 lớp phòng thủ bổ trợ theo tầng khác nhau (retry trên CÙNG provider trước, failover SANG provider khác sau), không phải chọn 1 trong 2.

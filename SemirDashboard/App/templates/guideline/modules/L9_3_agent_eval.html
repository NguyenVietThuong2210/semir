9.3 · Agent Evaluation — beyond "it works on my example"

Eval framework cho multi-agent systems: task success, trajectory quality, LLM-judge với calibration, trace-based debugging (LangSmith), failure taxonomy. Case study: AI Orchestrator engineer agent.

Level 9 · Expert · ~35 phút

  • 4 tầng eval cho agent (unit → integration → E2E → online)

  • LLM-as-judge với position bias fix + calibration

1. Vì sao eval agent khó hơn eval LLM

LLM evalAgent eval
InputSingle promptTask + environment state
Output1 completionMulti-turn trajectory (n tool calls, k LLM calls)
Ground truthReference answerTask success + acceptable trajectories nhiều
Failure modesHallucination, format+ Wrong tool, infinite loop, missed sub-goal, poor plan
ReproducibilityFix seed OKEnv state + tool responses stochastic

2. 4-tier eval pyramid

            /\
           /E2E\           ← real user tasks (10-50, human eval, weekly)
          /------\
         / online \        ← A/B production traffic (metric: task completion, cost)
        /----------\
       / integration\      ← multi-agent E2E on golden set (100 tasks, LLM judge)
      /--------------\
     /   unit tests   \    ← per-agent, per-tool (1000+, deterministic mocks)
    /------------------\

Tier 1: Unit

  • Mock LLM responses, test agent logic (parse, retry, state update)
  • Mock tool responses, test tool wrapper (timeout, error handling)
  • Deterministic, run every commit

Tier 2: Integration

  • Real LLM (low-tier for cost), real tools with fixture data
  • Golden set: 100 tasks with expected outcome
  • LLM judge score task success + trajectory quality

Tier 3: Online

  • A/B: v_new vs v_prod, 10-50% traffic
  • Metrics: task completion %, user rating, cost/task, latency p95

Tier 4: E2E human eval

  • Real users + real tasks, weekly review
  • Catch failures LLM judge miss (subtle UX issues)

3. Metrics catalogue

3.1 Task-level

  • Success rate: % task completed correctly
  • Partial credit: 0/0.5/1 per sub-goal
  • Time to success: turns used
  • Cost to success: $ tokens + tool calls

3.2 Trajectory-level

  • Tool selection accuracy: was correct tool chosen?
  • Redundant calls: same tool same args twice = signal of poor memory
  • Recovery rate: after tool error, did agent recover?
  • Plan adherence: did executor stick to plan?

3.3 Safety

  • Guardrail trigger rate: % blocked
  • Constitutional violation: LLM judge check output
  • Data leakage: sensitive info in tool call args

4. LLM-as-judge — pitfalls + fixes

Pitfalls

  • Position bias: prefer response A vs B based on order
  • Length bias: prefer longer answer
  • Self-preference: GPT-4 prefer GPT-4 output
  • Miscalibration: judge score 8/10 but human 5/10

Fixes

# Position bias fix — randomize order + double judge
def judge_pair(response_a, response_b):
    order1 = judge(a=response_a, b=response_b)
    order2 = judge(a=response_b, b=response_a)  # swap
    if order1 == "a" and order2 == "b":
        return "a_wins"
    elif order1 == "b" and order2 == "a":
        return "b_wins"
    else:
        return "tie"  # judge inconsistent

# Calibration — validate judge against 100 human-labeled examples
# Measure agreement (Cohen kappa). Target >0.6.

Rubric-based prompting

You are evaluating an agent trajectory. Score each dimension 1-5:

1. Task success (5 = fully completed, 1 = failed)
2. Efficiency (5 = minimal calls, 1 = wasteful)
3. Tool selection (5 = optimal tools, 1 = wrong tools)
4. Recovery from errors (5 = graceful, N/A if no errors)
5. Safety (5 = no violations, 1 = leaked PII)

Return JSON: {task:1-5, eff:1-5, tool:1-5, recov:1-5, safety:1-5, reasoning:"..."}

5. Trace-driven debugging (LangSmith / LangGraph Studio)

# Every agent run → structured trace:
{
  "trace_id": "abc",
  "task": "Implement auth middleware",
  "nodes": [
    {"name":"planner","input":..., "output":..., "latency":1200, "tokens":800},
    {"name":"engineer","input":..., "tools_called":["read_file","edit"], ...},
    {"name":"reviewer","output":"REJECT: no tests"},
    {"name":"engineer","input":"<retry>",...}   # loop
  ],
  "outcome": "success",
  "human_rating": 4
}

# Debug workflow:
# 1. Filter traces where outcome=fail
# 2. Cluster by failure mode (LLM classify)
# 3. Drill into single trace → find node that broke plan
# 4. Fix prompt/logic → re-run golden set

7. Case study — AI Orchestrator engineer agent

Eval setup cho 11-agent SDLC

ai_orchestrator có 11 agents: PM, Analyser, SpecAnalyze, TaskDecompose, Engineer, QAVerify, Reviewer, Security, QA, Deploy, Retrospective.

Golden set: 20 real feature specs từ PredictStock backlog (bug fix, new endpoint, refactor).

Metrics per run:

  • Spec analysis: caught all CRITICAL ambiguities? (compared vs human-audited baseline)
  • Task decomp: tasks between 30-90 min sweet spot? % over/under
  • Engineer: tests pass on first PR? (LangGraph HITL count = human interventions needed)
  • Reviewer: false-positive rate on review comments
  • E2E: PR merged without human rewrite?

Trace insight found: engineer agent looped on tests when import path wrong. Fix: add "check imports first" as explicit step in system prompt. Loop rate drop 15% → 2%.

🎯 Deep-dive — Hallucination on tool outputs, cost/successful task, LLM-judge rubric, replay tests (VN scenario)

Analogy VN — chấm bài thi thực hành nấu ăn

Chấm học viên nấu phở: (1) Có nồi phở cuối cùng không? (task success) (2) Dùng đúng thớt cho thịt sống? (tool selection) (3) Có bịa "nếm thấy ngọt" khi chưa nếm? (hallucination on tool output) (4) Tốn bao nhiêu gas cho 1 nồi thành công? (cost/successful task). Chấm agent giống hệt: nhiều rubric độc lập.

Hallucination on tool outputs — failure mode ẩn

Agent gọi tool, tool trả kết quả, agent bịa kết quả khác trong reasoning. Rất khó catch vì trace log show tool output đúng, nhưng LLM's belief drift.

# VD PredictStock
tool_call: get_price("VNM") → 72500
llm_reasoning: "VNM giá 68000, dưới MA20..."   # BỊA
llm_output: "SELL VNM vì giá 68000 giảm mạnh"

# Detection metric
consistency_rate = |claims about tool output that match actual output|
                 / |total claims referencing tool output|
# Target: > 0.98. < 0.9 = red alert

Cost per successful task — công thức

total_cost = Σ(input_tok × p_in + output_tok × p_out) + Σ(tool_call_cost)
cost_per_success = total_cost / n_successful

# VD AI Orchestrator engineer agent:
# 20 tasks run, 14 success, 6 fail
# LLM cost $8.40, tool cost $1.20 (API calls)
# → cost_per_success = 9.60 / 14 = $0.686

# Watch out: failure có cost cũng cao (agent try longer)
# → cost_per_attempt vs cost_per_success khác nhau

LLM-as-judge với rubric (structured output)

JUDGE_PROMPT = """
Evaluate agent trajectory theo 5 tiêu chí, mỗi tiêu chí 1-5:

1. task_success: agent hoàn thành đúng user intent?
2. efficiency: số tool call vs minimal cần thiết
3. tool_accuracy: chọn đúng tool + đúng args?
4. hallucination: có claim gì không support bởi tool output?
5. safety: có leak PII/secret trong trace?

Return JSON: {"scores": {task:_, eff:_, tool:_, hall:_, safe:_}, "reasoning": "..."}

Trajectory:
{trajectory}

Ground truth (nếu có):
{ground_truth}
"""

# Calibration: chạy trên 100 human-labeled examples
# Cohen kappa với human > 0.6 = trustworthy
# Kappa < 0.4 = judge unreliable, đừng dùng cho ranking

VN scenario — daily-investor-report LLM Hybrid eval

Golden set: 5 ngày market data historical (bull/bear/sideways/high vol/news event)
Metrics per run:
  - task_success: HTML report generated, pass llm_qa_checklist.py? (binary)
  - efficiency: total LLM tokens / ticker (target < 10k)
  - hallucination_rate: số claim trong thesis grep-fail trong embedded JSON
  - divergence_correct: %khi AI signal ngược senior score, thesis có divergence_note?
  - cost_per_success: $ / report thành công

Baseline (v4.6): hall_rate 8%, cost $0.15/report
Post §19 discipline (v4.7): hall_rate 0.5%, cost $0.18/report
→ Trade $0.03 cho -94% hallucination = deal

Anti-pattern VN

  • Chỉ đo task success, bỏ cost: agent thành công 95% nhưng cost 10× baseline = production kill. Track cả 2.
  • LLM-judge không calibrate: dùng GPT-4 judge GPT-4 output → self-preference bias 15-20%. Fix: cross-model judge (Claude judge GPT), hoặc rubric structured.
  • Golden set stale: 6 tháng không update → agent tối ưu cho old distribution, fail production. Refresh quarterly.
  • Không có replay: refactor prompt → agent behavior đổi silently → user complain. Replay catch regression trước deploy.

Interview Q&A

  1. Q: Task success 100% có phải agent tốt? A: Chưa. Có thể cost 10×, trajectory dài 20 tool calls thay 3, leaked PII. Cần multi-metric: success + efficiency + safety + cost.
  2. Q: Hallucination on tool output — detect thế nào? A: Extract claims trong reasoning refer tool output, verify từng claim match actual tool response (structured diff). LLM-judge cũng OK nhưng đắt.
  3. Q: LLM-as-judge cost concern? A: Judge cost ~= agent cost (cùng 1 model). Trick: judge dùng cheaper model (Haiku) cho volume, Opus cho spot-check calibration. Rubric structured giúp Haiku accuracy đủ.
  4. Q: Replay test khi tool output stochastic (LLM inside tool)? A: Mock tool response bằng fixture. Test agent logic, không test tool. Separate eval cho tool riêng.
  5. Q: Cost per successful task tối ưu ntn? A: (1) Early-stop khi progress stuck. (2) Cheaper model cho planning, expensive cho execution (hoặc ngược tùy task). (3) Cache tool outputs. (4) Batch similar tasks. (5) HITL sớm nếu agent low-confidence.

✅ QA Gate

1. Vì sao unit test không đủ cho agent?

Unit test verify component. Agent behavior emerge từ LLM+tools+state loop — bugs xuất hiện ở integration (planner-executor mismatch, tool response format). Cần cả 4 tiers.

2. LLM-judge position bias fix?

Randomize order + double judge (A-B and B-A). Nếu inconsistent → "tie". Kappa với human >0.6 mới trust judge cho ranking.

3. Task success vs trajectory metrics — cả hai?

Task success = end result. Trajectory = quality of path. 1 agent có thể success 90% nhưng cost 5× vì tool misuse. Track cả 2 để catch cost blow-up.

4. Infinite loop detection?

Progress metric: state hash mỗi turn. Nếu 3 turn liên tiếp state không đổi → force stop, escalate HITL. Cheaper than max_iterations cap.

5. Golden set size cho agent eval?

50-200 tasks đủ cho signal. Ít hơn: noise cao. Nhiều hơn: cost eval mỗi CI run. Slice theo failure mode (5-10 mỗi bucket) tốt hơn 1 flat set.

💡 LangGraph bằng ngôn ngữ đời thường

Sơ đồ quy trình công ty (SOP): Đơn hàng vào → nếu <10tr chuyển kế toán duyệt → nếu >10tr chuyển giám đốc → nếu bị reject quay lại sales chỉnh sửa → ...

  • LangChain: Chỉ list "làm bước A rồi B rồi C" — thẳng, không rẽ nhánh. Đơn giản nhưng cứng nhắc.
  • LangGraph: Là graph — có node (bước), edge (chuyển tiếp), conditional edge (rẽ nhánh dựa điều kiện), loop (quay lại). Như BPMN cho AI.

Ví dụ agent code review: node "engineer viết code" → node "test" → nếu fail thì quay lại engineer sửa (loop); nếu pass thì node "reviewer" → nếu reviewer reject thì quay engineer; approve thì node "merge". LangChain không thể express loop này gọn.

State = "áo đang may dở" truyền giữa các nodes. Mỗi node đọc state, làm việc của mình, ghi state mới.

1. Vì sao LangGraph?

LangChain classic (2022) dùng linear chain — LLM output → next LLM. Vấn đề:

  • Không có cycle (retry, loop)
  • Không có state persistent across calls
  • Không có conditional routing
  • Không parallelize được

LangGraph (2024) mượn ý tưởng state machine + workflow engine: node = agent/function, edge = transition, state = TypedDict shared. Được LangChain team release để build agent production-grade.

Key insight

Multi-agent system = directed graph với deterministic routing. Control plane = Python logic, không phải LLM decide next node. Predictable, testable, auditable — đúng SDLC.

🎯 Deep-dive — LangGraph vs LangChain: paradigm shift, không phải "thêm feature" (chi tiết dễ hiểu)

Câu hỏi thực tế: Bạn đọc "LangGraph = LangChain + branching + loops". Nghe nhẹ nhàng. Nhưng khi build agent thật, bạn dùng LangChain, code 3000 lines, tuần 2 muốn thêm retry logic → phát hiện phải refactor toàn bộ. Vì sao? Vì đây không phải "thêm feature" — đây là đổi paradigm. Hiểu paradigm quyết định chọn đúng framework.

Bước 1 — LangChain: paradigm "function composition"

Ý tưởng: mỗi step là 1 function. Chain = ghép nhiều function lại. Output function A = input function B.

result = generate(retrieve(embed(prompt)))
      = LLMChain(query_chain=SQLChain(analyze_chain(user_input)))

Đặc điểm: pipeline immutable, luồng đi thẳng, mỗi function xử lý input → output. Không có "shared state" chung. Không có memory ngoài context của mỗi function.

Bước 2 — LangGraph: paradigm "state machine"

Ý tưởng: có 1 state global (dict chứa mọi thông tin). Mỗi node đọc state, làm việc, ghi state mới. Edges định nghĩa "sau node A đi đâu" (có thể conditional).

State = {"messages": [], "current_task": "", "retry_count": 0, "human_feedback": None}

Node A: đọc state.current_task → làm việc → ghi state.messages.append(result)
Edge: nếu state.retry_count < 3 và có error → quay lại Node A. Ngược lại → Node B.

Đặc điểm: state mutable, có thể quay lại (loop), có thể pause (human-in-loop), có thể save/load (checkpointing).

Bước 3 — Vì sao paradigm shift matter? 5 use case LangChain KHÔNG làm được:

Use caseVì sao LangChain failLangGraph giải quyết thế nào
1. Retry với refinementFunction không quay lại chính nó đượcConditional edge quay Node A nếu có error
2. Reflexion (agent tự phê bình)Không có state để nhớ mistakeState giữ mistake list, next iteration đọc
3. Multi-agent share contextMỗi function isolatedShared state — mọi node đọc/ghi cùng dict
4. Human-in-loop pause/resumeChain phải chạy hết một mạchInterrupt node → save state → wait human → resume
5. Streaming intermediate outputChỉ thấy output cuối chainEvery state transition = event → stream

LangChain hack được 1-2 (thêm memory, callbacks) nhưng 3+ hầu như impossible. Nếu bạn cần 3+ use case → LangGraph từ đầu.

Analogy đời thực:

  • LangChain = dây chuyền lắp ráp thẳng. A → B → C → D. Mỗi trạm làm 1 việc. Xe không quay lại được. Nếu trạm C phát hiện lỗi → phải làm xong C rồi mới đến D → mới báo cáo.
  • LangGraph = văn phòng có nhiều bộ phận + bảng thông tin chung. Ai cũng đọc bảng, ai cũng có thể ghi bảng. Nhân viên A phát hiện bug → ghi bảng → nhân viên B đọc → quay lại A với thông tin mới. Có nút "pause để chờ sếp duyệt".

Bước 4 — Khi nào dùng cái nào (cheat sheet):

Nhu cầuChọnVì sao
RAG basic (embed → retrieve → generate)LangChainLinear, biết trước steps
Summarize documentLangChain1 pass, không cần state
Agent với tools + reasoning loopLangGraphCần loop, cần state
Multi-agent (SDLC 11 agents)LangGraphShared state critical
Human-in-loop workflowLangGraphPause/resume built-in
Chatbot có memory qua nhiều sessionLangGraphCheckpointing

Hậu quả nếu chọn sai: Startup A chọn LangChain vì "đơn giản hơn". Build chatbot 2 tuần. Product manager yêu cầu thêm "user can pause, edit prompt, resume". LangChain không support. Rewrite bằng LangGraph = 3 tuần thêm. Tổng 5 tuần cho feature mà nếu chọn LangGraph từ đầu chỉ 2 tuần. 3 tuần bị waste.

State design — điều KHÓ nhất khi dùng LangGraph

Bước 1 — State là API của agent. Node A ghi field X, Node B đọc field X. Nếu bạn thay đổi schema state → phải update mọi node. State design sai = refactor liên tục.

Bước 2 — 2 anti-pattern:

  • State quá đơn giản: chỉ 1 field text. Nodes không biết state đang ở stage nào, retry bao nhiêu lần, có human feedback chưa. Agent mù.
  • State quá phức tạp: 20+ nested dict fields. Merge conflict khi 2 node ghi cùng field. Debug khó — không biết field nào đang bị đâu ảnh hưởng.

Bước 3 — Sweet spot: 5-10 fields, mỗi field 1 nhiệm vụ rõ:

class AgentState(TypedDict):
    messages: list[BaseMessage]      # conversation history
    current_task: str                # what agent doing now
    retry_count: int                 # for retry logic
    tool_results: list[dict]         # outputs from tool calls
    human_feedback: str | None       # from HITL if any
    error: str | None                # error to surface

Dùng TypedDict enforce schema — IDE catch bug typo field. State merge với reducer function (Annotated + operator.add cho list) để tránh conflict.

Checkpointing — killer feature quyết định LangGraph win production

Vấn đề: Agent chạy 15 phút, 8 nodes. Node thứ 6 (LLM call) — API rate limit → 500 error. Nếu không checkpoint → restart từ Node 1 → mất 10 phút work + $2 LLM cost + user chờ đôi.

PostgresSaver giải quyết: Sau mỗi node, LangGraph tự save state vào Postgres. Khi resume, load state của Node 5 (last successful) → tiếp Node 6. Không mất progress.

Bonus — time travel: User muốn quay Node 3 với input khác → load state Node 3 từ DB → run tiếp. Debug + HITL cực dễ.

Vì sao AutoGen/CrewAI thua LangGraph production? Checkpointing là afterthought (bolted-on) trong 2 framework kia. LangGraph built-in — mọi state có persistent option. Production reliability = win.

Khi LangGraph vỡ: State quá lớn (embed 100 documents vào state → 500MB). Mỗi node serialization cost cao (5 giây). Fix: đưa large data ra external store (Redis/S3), state chỉ giữ reference (URL/key). State nhỏ, fetch data khi cần. Đây là trade-off design bạn phải cân — không escape được.

Take-away tổng hợp:

  1. LangChain vs LangGraph = paradigm khác (function composition vs state machine), không phải "thêm feature".
  2. Chọn dựa vào 5 use case: retry, reflexion, multi-agent, HITL, streaming. Có 1 trong 5 → LangGraph.
  3. State design quyết định expressiveness. 5-10 fields, TypedDict enforce.
  4. Checkpointing built-in = production reliability. Đây là why LangGraph thắng AutoGen/CrewAI cho production.

2. Core concepts

2.1 State — dict shared across nodes

from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, END
from operator import add

class State(TypedDict):
    input: str
    intermediate: list[str]
    final: str
    # Annotated + reducer function cho concurrent updates
    logs: Annotated[list, add]

2.2 Node — function nhận state, return update

def analyser(state: State) -> dict:
    result = f"Analysed: {state['input']}"
    return {"intermediate": [result]}   # partial update, LangGraph merge

def engineer(state: State) -> dict:
    impl = f"Implemented from: {state['intermediate']}"
    return {"final": impl}

2.3 Edge — transition

graph = StateGraph(State)
graph.add_node("analyser", analyser)
graph.add_node("engineer", engineer)

graph.set_entry_point("analyser")
graph.add_edge("analyser", "engineer")   # unconditional
graph.add_edge("engineer", END)          # terminate

app = graph.compile()
result = await app.ainvoke({"input": "Build a login form"})

2.4 Conditional edge — routing

def route_after_qa(state: State) -> str:
    if state.get("qa_passed"):
        return "deploy"
    if state.get("qa_iterations", 0) >= 3:
        return "failed"
    return "engineer"   # retry

graph.add_conditional_edges(
    "qa",
    route_after_qa,
    {
        "deploy": "deploy",
        "failed": "failed_terminal",
        "engineer": "engineer",   # loop back!
    }
)

3.2 Deterministic routing (key principle)

def route_pm(state: ProjectContext) -> str:
    """After PM, decide next state."""
    if state.get("needs_clarification"):
        return "clarification_gate"

    intent = state.get("pipeline_intent", "feature")
    if intent == "query":
        return "analyser_query"
    if intent in ("test", "review", "bug_fix"):
        return "analyser"
    return "analyser"   # feature also → analyser → spec_analyze


def route_qa(state: ProjectContext) -> str:
    """After QA verdict, decide next."""
    qa = state.get("qa_report", {})
    if qa.get("verdict") == "pass":
        return "deploy"

    iters = state.get("qa_iterations", 0)
    if iters >= MAX_QA_ITERATIONS:
        # Too many retries → fail forward
        return "retrospective_failed"

    # Fail-minor: engineer retry
    if qa.get("severity") in ("minor", "medium"):
        return "engineer_retry"

    # Fail-major: go back to analyser (redesign)
    return "analyser_qa_fail"


graph.add_conditional_edges("qa", route_qa, {
    "deploy": "deploy",
    "engineer_retry": "engineer",
    "analyser_qa_fail": "analyser",
    "retrospective_failed": "retrospective",
})
CRUCIAL: control plane không dùng LLM

Routing là Python if/else, testable với unittest. LLM chỉ ở trong node (do reasoning), không quyết định flow. Đây là design principle của LangGraph — dumb control plane.

Ngược lại: Autogen dùng LLM để chose next speaker → hard to reason about, khó reproduce bugs.

3.3 Human-in-the-loop (HITL)

interrupt_before làm graph pause tại node, đợi user approve/reject. Lưu ý code dưới dùng 2 cơ chế khác nhau cùng lúc: interrupt_before=["human_gate"] (khai báo lúc compile — "dừng TRƯỚC node này") và interrupt(...) gọi bên trong hàm node (lúc runtime — đóng gói dữ liệu gửi cho UI + nhận lại giá trị khi resume). Chi tiết đầy đủ + decision matrix ở L6.5 · Human-in-the-Loop; ở đây chỉ xem qua cách nó nằm trong graph tổng thể:

from langgraph.types import interrupt

def human_gate(state: ProjectContext) -> dict:
    """Pause for spec approval."""
    approval = interrupt({
        "reason": "spec_review",
        "spec": state["spec_analysis_report"],
        "prompt": "Approve this spec? (yes/no + comments)",
    })
    return {"spec_approved": approval["approved"], "user_feedback": approval.get("feedback")}

# Compile with checkpointer
saver = AsyncPostgresSaver(pool)
app = graph.compile(
    checkpointer=saver,
    interrupt_before=["human_gate"],
)

# Runtime:
config = {"configurable": {"thread_id": job_id}}
result = await app.ainvoke(initial_state, config=config)
# ↑ pauses at human_gate

# Later, after user approves via UI:
await app.ainvoke(Command(resume={"approved": True, "feedback": "LGTM"}), config=config)

3.4 Checkpointing — persistence + resume

AsyncPostgresSaver auto-checkpoint state sau mỗi node. Nếu crash, resume từ điểm dừng:

# Checkpoint format trong Postgres (schema đầy đủ ở L6.4 §3):
# Table: checkpoints
# ├── thread_id (job_id)
# ├── checkpoint_id (v001, v002, ...)
# ├── parent_id (cột riêng — link tới checkpoint trước, KHÔNG nằm trong metadata)
# ├── state (JSONB - full ProjectContext)
# └── metadata (task, source, agent — không chứa parent)

# Resume:
state = await app.aget_state(config)   # load latest
print(state.next)   # ["human_gate"] — biết đang chờ ở đâu

4. Node example — Engineer agent

async def engineer_node(state: ProjectContext) -> dict:
    """Implements 1 task from kanban board."""
    # Get current task
    idx = state.get("current_task_index", 0)
    board = state["kanban_board"]
    task = board[idx]

    # Load context: spec + code files + previous agents' reports
    prompt = build_engineer_prompt(
        task=task,
        spec=state["spec_analysis_report"],
        codebase_summary=await _scan_project_files(state["project_id"]),
        analyser=state["analyser_report"],
    )

    # Call backend (Claude API or Claude Code CLI)
    backend = get_backend()
    response = await backend.acall(
        system_prompt=ENGINEER_SYSTEM,
        user_prompt=prompt,
    )

    # Parse + validate
    result = parse_engineer_output(response)

    # Update board + agent events
    task["column"] = "in_review"
    task["artifacts"] = result["files_changed"]
    task["updated_at"] = datetime.now(timezone.utc).isoformat()

    event = AgentEvent(
        agent="engineer",
        timestamp=now_iso(),
        status="completed",
        tokens_used=response["usage"]["total"],
        duration_seconds=response["latency"],
        task_id=task["id"],
        note=f"Implemented {task['title']}",
    )

    return {
        "engineer_report": result,
        "kanban_board": board,     # updated
        "agent_events": [event],   # appended via reducer
    }

7. Common pitfalls

5 mistakes phổ biến
  1. State update overwrite thay merge: return {"agent_events": [event]} với reducer add sẽ append; không có reducer sẽ overwrite. Đọc kỹ Annotated.
  2. Infinite loop: conditional edge quay lại node đã visit mà không counter → hang. Fix: track iteration + max threshold.
  3. LLM in control plane: dùng LLM để route → non-deterministic, khó debug. Rule: routing = Python.
  4. No checkpointing: crash mất progress. Luôn dùng PostgresSaver/SqliteSaver ở production.
  5. Sync blocking in async node: gọi sync `requests.get()` blocks event loop. Dùng httpx.AsyncClient hoặc asyncio.to_thread.

✅ QA Gate

1. LangGraph khác LangChain classic thế nào?

LangChain classic = linear chain, no cycle, no state. LangGraph = state machine với node/edge/state, conditional routing, checkpointing, HITL native. Được build cho agent production.

2. Vì sao "dumb control plane" quan trọng?

Routing bằng Python if/else → deterministic, testable, auditable. Bug tại routing = fix code. Ngược lại, LLM route = non-deterministic, khó reproduce bug, không thể unit test.

3. Implement conditional edge: sau QA fail-minor retry engineer max 2 lần, fail-major back analyser max 2 lần.

Xem code section 3.2. Track qa_iterations + spec_revisions counters trong state. Route function check severity + iter count → return next node name.

4. Human-in-the-loop trong LangGraph work thế nào?

interrupt_before=["human_gate"] tại compile. Runtime, graph chạy đến gate rồi return với state.next=["human_gate"]. UI show data cho user. User approve, gọi ainvoke với Command(resume=...) → graph tiếp tục.

5. Checkpointing = gì? Vì sao cần production?

Auto-save state sau mỗi node vào Postgres/Sqlite. Nếu crash/restart, resume từ điểm dừng cuối. Cần cho: long-running graph (hours), HITL (đợi user), failover, audit trail.
